## 一、全局约定（九条，逐条都要守）

| # | 约定 | 理由 |
|---|---|---|
| 1 | **不用外键约束** | 单体高并发下外键影响写入性能，且阻碍将来分库分表；关联关系由应用层保证，靠索引提速 |
| 2 | 逻辑删除字段 `deleted` 用 `bigint`，0 表示未删，删除时写入**毫秒级**删除时间戳 | 需要保留墓碑的表（见第 9 条 A 类）在同一业务键上可能被反复删除，常量 1 只有一种取值会让第二次删除撞唯一索引；时间戳每次不同，可反复增删，且顺带记录删除时间。单位统一**毫秒**（`System.currentTimeMillis()`）：秒级撞 2038 上界且同秒重复风险高。判断未删除**只能写 `deleted = 0`** |
| 3 | 唯一索引必须**带上 `deleted`**，且 `deleted` 置于**最后一列** | 同上；放尾列是为了保住左侧前缀的匹配能力（`user_id` 单独查也能用上），放最前则前缀失效。注意**未删除不可存 `NULL`**——唯一索引中 NULL 互不相等，会放过重复行 |
| 4 | 主键雪花 ID，`bigint` | 与 `tech/01` 一致；**接口层必须转 String**（JS 精度） |
| 5 | 时间一律 `datetime`，不用时间戳 | 与 `tech/01` 第十章一致；Java 侧 `LocalDateTime` |
| 6 | 金额一律 `decimal(10,2)`，禁止 `float/double` | 避免浮点误差 |
| 7 | 状态字段用 `tinyint` 存 code + Java 枚举承接，注释里写全枚举 | 不用字符串，拼错会静默失效 |
| 8 | 每张业务表必带 `create_time / update_time / deleted`；需要并发保护的加 `version` | 与 `tech/03` W1 工序一致 |
| 9 | **删除分两类实现**，见下方「删除的两类实现」 | 时间戳方案的必要性取决于「重建时是新插一行还是复用旧行」，必须按表分类写死，否则会出现「以为不会撞键、实际撞键」的线上故障 |

字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`（MySQL 8 默认）。表名不加 `t_` 前缀；`user`、`order` 是易冲突词，改用 `app_user`、`trade_order`。

### 删除的两类实现（第 9 条的展开）

软删除一律是 `UPDATE ... SET deleted = <毫秒时间戳>`，行不会消失。区别在于**重建时怎么做**，这决定了时间戳是不是必需的：

| 类 | 适用 | 删除 | 重建 | 表内行数 | 时间戳是否必需 |
|---|---|---|---|---|---|
| **A 类 · 留墓碑** | `app_user`（注销）、字典表、`chat_session`、商品/订单等需要留痕的表 | `UPDATE` 写时间戳 | `INSERT` 新行 | 每次循环 +1 行 | **必需**，否则第二次删除撞唯一键 |
| **B 类 · 复用行** | `favorite` 收藏、关注这类「无审计价值的关联关系」 | `UPDATE` 写时间戳 | `UPDATE` 同一行 `deleted = 0` | 同一业务键恒为 1 行 | 非必需，保留仅用于记录「上次取消时间」 |

**分类判据只有一条：重建出来的是不是同一个实体。** 用户注销后重新注册是一个新账号（新 id、新资料），字典项删掉后重建是一个新字典项（新 id，且旧 id 可能已被历史数据引用）——这两类必须 `INSERT` 新行；收藏取消后再收藏仍是同一段「用户—商品」关系，因此可以复用。

B 类的重建写法：先 `UPDATE ... WHERE user_id = ? AND item_id = ? AND deleted > 0`，影响行数为 0 再 `INSERT`（说明此前无墓碑，属首次建立关系）。这样并发重复点击也是幂等的——A 类同时点两下会有一个 `INSERT` 撞唯一键，需要捕获处理。

选 B 类的理由：收藏关系没有审计价值，不需要知道「曾经收藏过几次」；而 A 类下反复增删会让表持续膨胀，需要额外的归档任务。同一业务键恒为一行的写法没有累积问题，查询也始终只需处理一行。

**B 类为什么仍然写时间戳而不是常量 1**：技术上常量 1 完全够用，同一业务键恒为一行时不存在第二个「已删除」值与之重复。仍然沿用时间戳是为了让 `deleted` 在全库保持一种语义（0 未删 / 非 0 为删除时刻），避免「有的表是布尔、有的表是时间」需要靠人记住哪张表是哪种——一旦有人把「按删除时间归档」的任务用到收藏表上，常量方案下会静默出错。若将来确认收藏表不需要任何时间语义，可改回常量 1，但必须同步修改本节。

## 四、A 档表详细设计

### 4.1 `app_user` 学生用户

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 雪花 |
| openid | varchar(64) | 微信 openid，uk |
| nickname / avatar_url | varchar | 微信昵称头像 |
| phone | varchar(20) | Web 端验证码登录用 |
| real_name | varchar(32) | 认证后写入，**不公开展示** |
| student_no | varchar(32) | 学号，**不公开展示**，uk（含 deleted） |
| college_id / campus_id | bigint | 字典 id |
| auth_status | tinyint | 见枚举，默认 0 |
| credit_score | int | 默认 100，范围 0–120 |
| status | tinyint | 0 正常 / 1 警告 / 2 封禁 |
| ban_until / ban_reason | datetime / varchar | 封禁到期与原因 |

**索引**：`uk(openid)`、`uk(student_no, deleted)`、`idx(college_id)`、`idx(auth_status, credit_score)`（搜索权重与"仅看认证卖家"筛选）

**判据**：学号与姓名只对平台与本人可见，接口出参不得包含（`business/02` F-M5）；信用分只对外输出等级，不输出分数。

### 4.2 `user_auth` 学号认证申请

| 字段 | 类型 | 说明 |
|---|---|---|
| id / user_id | bigint |  |
| real_name / student_no / college_id |  | 申请时填写，可覆盖 `app_user` 快照 |
| credential_url | varchar(255) | 一卡通 / 校园邮箱截图 |
| status | tinyint | 1 审核中 / 2 通过 / 3 未通过 |

**判据**：可重提，所以是一对多不是一对一；一学号多账号要能查出来标异常（`business/03` F-A5）。

### 4.3 `item` 商品

| 字段 | 类型 | 说明 |
|---|---|---|
| id / seller_id | bigint |  |
| title | varchar(100) | 5–50 字 |
| category_id | bigint | 二级分类 |
| grade | char(1) | A / B / C / D |
| price / origin_price | decimal(10,2) | 售价 / 原价 |
| campus_id / meet_point_id | bigint | 校园四项字段之二 |

| reject_reason | varchar(255) | 驳回原因 |
| version | int | **乐观锁**，付款占位用 |

| published_at | datetime | 审核通过时间，排序用 |

**索引（跟着查询模式建，不是跟着字段建）**

| 索引 | 服务哪条查询 |

| `idx_credit(status, published_at)` | 认证/信用权重排序 |
| `ft_title_desc(title, description)` **FULLTEXT, ngram** | 关键词搜索（`tech/01` 7.1） |

**注意**：MySQL 全文索引需在 `my.cnf` 设 `ngram_token_size=2`，建索引时 `WITH PARSER ngram`；全文索引与 `status` 过滤配合时需写成 `MATCH(...) AGAINST(...) AND status = 3`，注意执行计划可能不走全文索引，大数据量下先 `EXPLAIN`。

| 字段 | 类型 | 说明 |
|---|---|---|

## 五、B 档表要点

### 5.1 `item_audit` 商品审核（权重 + SLA 都在这张表）

| 字段 | 说明 |
|---|---|
| priority_score | **基础权重分**（不含等待衰减） |
| enter_queue_at | 进队时间 |
| first_handle_at | 首次处置时间 |
| handler_id | 处置人 |
| handle_cost_ms | 单条处置耗时（前端埋点上报） |
| status / reject_reason | 处置结果与原因 |

**权重分的正确算法**（`tech/01` 9.3）：

```
priority_score = 举报次数×3 + 图片风险×2 + (100−信用分)/10 + 价格异常分
排序时用：priority_score + FLOOR(TIMESTAMPDIFF(HOUR, enter_queue_at, NOW()) / 12)
```

**等待衰减项查询时实时算，不定时回写**——回写会造成写放大，且库里值与展示值不一致时排查困难。

**SLA 两个层级由两个字段撑起**：首审响应 = `first_handle_at − enter_queue_at`；单条处置效率 = `handle_cost_ms`（前端埋点，因为"Drawer 打开"这个动作只有前端知道）。

### 5.2 `report` 举报 / `appeal` 申诉

- `report`：`target_type`（1 商品 / 2 用户）、`target_id`、`reason`、`evidence`(json 图片≤3)、`status`、`result`（1 成立 / 2 不成立）、`handler_id`
- `appeal`：`biz_type`（1 审核 / 2 举报 / 3 订单）、`biz_id`、`reason`、`evidence`、`status`（维持/撤销）、`handler_id`
  - **换人复审**：`handler_id != 原处置人`，写入时校验，单人演示时记录该规则已声明

### 5.3 `admin_user` / `admin_role` / `admin_role_perm`

- 权限点存成 `admin_role_perm(role_id, perm_code)` 行式，不存 JSON——管理端 A9 要按矩阵渲染，行式可直接查
- 16 个权限点：`dashboard.view`、`report.view`、`item.view`、`item.offline`、`item.delete`、`user.view`、`user.verify`、`user.ban`、`review.judge`、`review.forceoff`、`review.appeal`、`order.refund`、`order.arbitrate`、`content.edit`、`settings.edit`、`log.view`
- `admin_user` 含 `fail_count` / `lock_until`（失败 5 次锁 10 分钟）

### 5.4 `sys_operation_log`

模块、操作类型、业务对象 id、描述、**变更前后的值**（`before_value` / `after_value`）、结果（成功/失败）、IP、UA、traceId、耗时。
**只追加，不可删改**；事务提交后异步写入（`tech/01` 5.4）。

### 5.5 `credit_log` 信用分流水

初始 100；完成交易 +1（上限 120）、单方违约 −5、被举报成立 −10、强制下架 −15、封禁清零。
流水表是为了「信用分为什么变了」可追溯——答辩时老师常问。

### 5.6 `user_review` 互评

`uk(order_id, reviewer_id)` 保证一单一评。`rating` 1–5 + `tags`(json) + `comment`。

### 5.7 `carbon_factor` 减碳系数

`category_id / factor_kg / note`，种子值：教材 0.8、数码电子 25、服饰 3、生活用品 5、其他 2。
**论文中必须标注为估算假设**（已拍板），`note` 字段留了写局限说明的位置。

| 学期时间轴 | `item.published_at` + `trade_order.pay_time` | 按周聚合，发布量 / 成交量双线 |
| 学院 × 品类矩阵 | `app_user.college_id` + `item.category_id` + 已完成订单 | 三表 JOIN 后 GROUP BY，可切发布量/成交量/成交率 |
| 面交所热力 | `trade_order.meet_point_id` + `meet_time` | 按面交点 × 时段聚合 |
| 循环率减碳 | `item` 总数 vs 已售出数 + `carbon_factor` | `循环率 = 售出/发布`；减碳 = Σ(售出件数 × 系数) |

一期全部实时聚合，不建中间表——数据量在万级，MySQL 完全够。
