## 一、全局约定（九条，逐条都要守）

| # | 约定 | 理由 |
|---|---|---|
| 1 | **不用外键约束** | 单体高并发下外键影响写入性能，且阻碍将来分库分表；关联关系由应用层保证，靠索引提速 |
| 2 | 逻辑删除字段 `deleted` 用 `bigint`，0 表示未删，删除时写入**毫秒级**删除时间戳 | 需要保留墓碑的表（见第 9 条 A 类）在同一业务键上可能被反复删除，常量 1 只有一种取值会让第二次删除撞唯一索引；时间戳每次不同，可反复增删，且顺带记录删除时间。单位统一**毫秒**（`System.currentTimeMillis()`）：秒级撞 2038 上界且同秒重复风险高。判断未删除**只能写 `deleted = 0`** |
| 3 | 唯一索引必须**带上 `deleted`**，且 `deleted` 置于**最后一列** | 同上；放尾列是为了保住左侧前缀的匹配能力（`user_id` 单独查也能用上），放最前则前缀失效。注意**未删除不可存 `NULL`**——唯一索引中 NULL 互不相等，会放过重复行 |
| 4 | 主键雪花 ID，`bigint` | 与 `tech/01` 一致；**接口层必须转 String**（JS 精度） |
| 5 | 时间一律 `datetime`，不用时间戳 | 与 `tech/01` 第十章一致；Java 侧 `LocalDateTime` |
| 6 | 金额一律 `decimal(10,2)`，禁止 `float/double` | 避免浮点误差 |
| 7 | 状态字段用 `tinyint` 存 code + Java 枚举承接，注释里写全枚举 | 不用字符串，拼错会静默失效 |
| 8 | 每张业务表必带 `create_time / update_time / deleted`；需要并发保护的加 `version` | 与 `tech/03` W1 工序一致 |
| 9 | **删除分两类实现**，见下方「删除的两类实现」 | 时间戳方案的必要性取决于「重建时是新插一行还是复用旧行」，必须按表分类写死，否则会出现「以为不会撞键、实际撞键」的线上故障 |

字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`（MySQL 8 默认）。表名不加 `t_` 前缀；`user`、`order` 是易冲突词，改用 `app_user`、`trade_order`。

### 删除的两类实现（第 9 条的展开）

软删除一律是 `UPDATE ... SET deleted = <毫秒时间戳>`，行不会消失。区别在于**重建时怎么做**，这决定了时间戳是不是必需的：

| 类 | 适用 | 删除 | 重建 | 表内行数 | 时间戳是否必需 |
|---|---|---|---|---|---|
| **A 类 · 留墓碑** | `app_user`（注销）、字典表、`chat_session`、商品/订单等需要留痕的表 | `UPDATE` 写时间戳 | `INSERT` 新行 | 每次循环 +1 行 | **必需**，否则第二次删除撞唯一键 |
| **B 类 · 复用行** | `favorite` 收藏、关注这类「无审计价值的关联关系」 | `UPDATE` 写时间戳 | `UPDATE` 同一行 `deleted = 0` | 同一业务键恒为 1 行 | 非必需，保留仅用于记录「上次取消时间」 |

**分类判据只有一条：重建出来的是不是同一个实体。** 用户注销后重新注册是一个新账号（新 id、新资料），字典项删掉后重建是一个新字典项（新 id，且旧 id 可能已被历史数据引用）——这两类必须 `INSERT` 新行；收藏取消后再收藏仍是同一段「用户—商品」关系，因此可以复用。

B 类的重建写法：先 `UPDATE ... WHERE user_id = ? AND item_id = ? AND deleted > 0`，影响行数为 0 再 `INSERT`（说明此前无墓碑，属首次建立关系）。这样并发重复点击也是幂等的——A 类同时点两下会有一个 `INSERT` 撞唯一键，需要捕获处理。

选 B 类的理由：收藏关系没有审计价值，不需要知道「曾经收藏过几次」；而 A 类下反复增删会让表持续膨胀，需要额外的归档任务。同一业务键恒为一行的写法没有累积问题，查询也始终只需处理一行。

**B 类为什么仍然写时间戳而不是常量 1**：技术上常量 1 完全够用，同一业务键恒为一行时不存在第二个「已删除」值与之重复。仍然沿用时间戳是为了让 `deleted` 在全库保持一种语义（0 未删 / 非 0 为删除时刻），避免「有的表是布尔、有的表是时间」需要靠人记住哪张表是哪种——一旦有人把「按删除时间归档」的任务用到收藏表上，常量方案下会静默出错。若将来确认收藏表不需要任何时间语义，可改回常量 1，但必须同步修改本节。

### 4.4.1 `item_offer` 议价单

一对一私密价：买家对可议价商品出价，卖家同意后买家按该价付款。**议价价只存在这张表与被它成交的那笔订单上，从不写回 `item.price`**，所以议价成功而买家未付款时，其他买家看到的仍是标价。

| 字段 | 类型 | 说明 |
|---|---|---|
| id / item_id / buyer_id | bigint | 一张单据只对一个人、一件商品 |
| seller_id | bigint | 冗余存一份：卖家待办按它建索引，不必回查商品 |
| origin_price | decimal(10,2) | 出价时的标价快照，卖家事后改价不影响已发出的议价 |
| offer_price | decimal(10,2) | 买家出价，须低于标价且不低于标价的 10% |
| status | tinyint | 1 待答复 / 2 已同意 / 3 已拒绝 / 4 已失效 / 5 已下单 |
| expire_time | datetime | 付款截止：同意时写 now+10 分钟，仅 status=2 有意义 |
| handle_time / reject_reason | datetime / varchar(200) | 卖家处理时间与理由 |
| alive | tinyint 生成列 | `status IN (1,2)` 时为 1，其余 NULL |

`alive` 只为一件事存在：**唯一索引 `uk_alive(item_id, buyer_id, alive)` 保证同一买家对同一商品同时只有一条进行中议价**。MySQL 唯一索引允许多个 NULL，所以历史单据（已拒绝、已失效、已下单）不受约束，同一买家可以反复出价。用生成列而不是普通列，是因为普通列要靠业务代码在每次状态变更时维护，漏一处就会永久卡住该买家的出价能力。

### 4.5.1 `user_address` 用户地址

## 五、B 档表要点

### 5.1 `item_audit` 商品审核（权重 + SLA 都在这张表）

| 字段 | 说明 |
|---|---|
| priority_score | 基础权重分（下面四个分量之和）。**冗余快照，队列排序不读它** |
| report_count / image_risk / credit_deduct / price_abnormal | 四个权重分量快照，**排序读的是这四个** |
| enter_queue_at | 进队时间 |
| first_handle_at | 首次处置时间 |
| handler_id | 处置人 |
| handle_cost_ms | **服务端**处理这次处置动作的耗时；不是前端埋点，也不是审核员阅读单据的时长 |
| status / reject_reason | 处置结果与原因 |

**权重分的正确算法**（`tech/01` 9.3；图片风险项按 `business/03` 2026-10-06 勘误）：

```
基础分 = 举报次数×3 + ROUND(图片风险÷10) + (100−信用分)/10 + 价格异常×5
排序键 = 基础分 + FLOOR(TIMESTAMPDIFF(HOUR, enter_queue_at, NOW()) / 12)
```

等待项查询时实时算，不定时回写——回写会造成写放大，且库里值与展示值不一致时排查困难。
它是**补偿**不是衰减，符号为加：每满 12 小时 +1，作用是把积压的老单托上来。

`priority_score` 存的就是上面的基础分，数值上与四个分量之和相等，但**队列排序读分量而不读它**。
原因是 UI 要逐项展示权重构成，总分必须由明细相加而来；读打包好的值会让总分依赖一处可能漂移的存储。
该字段保留给 SQL 层排序与 A8 报表，当前没有读取方（`zz-demo-data.sql` 末尾按同一公式重算了全部行）。

**SLA 两个层级由字段撑起**：首审响应 = `first_handle_at − enter_queue_at`（> 2h 未达标、> 24h 积压红牌）；
单条处置效率的目标值是 30 秒常量，`handle_cost_ms` 记的是服务端处置耗时，
不是"Drawer 打开到提交"的口径——后者只有前端知道，本期未做，准确口径留给 A8 报表。

### 5.2 `report` 举报 / `appeal` 申诉

- `report`：`target_type`（1 商品 / 2 用户）、`target_id`、`reason`、`evidence`(json 图片≤3)、`status`、`result`（1 成立 / 2 不成立）、`handler_id`
- `appeal`：`biz_type`（1 审核 / 2 举报 / 3 订单）、`biz_id`、`reason`、`evidence`、`status`（维持/撤销）、`handler_id`
  - **换人复审**：`handler_id != 原处置人`，写入时校验，单人演示时记录该规则已声明

### 5.3 `admin_user` / `admin_role` / `admin_role_perm`

- 权限点存成 `admin_role_perm(role_id, perm_code)` 行式，不存 JSON——管理端 A9 要按矩阵渲染，行式可直接查
- 17 个权限点：`dashboard.view`、`report.view`、`item.view`、`item.offline`、`item.delete`、`user.view`、`user.verify`、`user.ban`、`review.view`、`review.judge`、`review.forceoff`、`review.appeal`、`order.refund`、`order.arbitrate`、`content.edit`、`settings.edit`、`log.view`
- `admin_user` 含 `fail_count` / `lock_until`（失败 5 次锁 10 分钟）
- `admin_user.username`：登录账号，**唯一索引 `uk_username(username, deleted)`**。注册时由邮箱前缀派生
  （`AdminAccountService.deriveUsername`），派生撞名则补 4 位随机后缀；并发下由唯一索引兜底
  （`register` 捕获 `DuplicateKeyException`，转成 `EMAIL_ALREADY_REGISTERED` 返回）
- `admin_user.email`（2026-09-29 追加）：注册与找回密码用，**唯一索引 `uk_email(email, deleted)`**。
  限 QQ 系（`@qq.com` / `@foxmail.com`）——该限制在**应用层**校验，数据库只保证唯一与格式长度，
  这样以后放开域名不用改表
- `admin_user.status` 三值：`1` 启用 / `0` 停用 / `2` **待分配角色**（注册产生，登录被拦，
  超管分配角色后转 1）。锁定期不占 status，用 `lock_until` 表达
- 邮箱验证码**不落库**：放 Redis（`cm:mail:code:` 前缀），10 分钟过期、一次性。
  不建表是因为验证码是临时凭据，落库只会留下要清理的垃圾行

### 5.4 `sys_operation_log`

模块、操作类型、业务对象 id、描述、**变更前后的值**（`before_value` / `after_value`）、结果（成功/失败）、IP、UA、traceId、耗时。
**只追加，不可删改**；事务提交后异步写入（`tech/01` 5.4）。

### 5.5 `credit_log` 信用分流水

初始 100；完成交易 +1（上限 120）、单方违约 −5、被举报成立 −10、强制下架 −15、管理员人工调整 ±20 以内。
流水表是为了「信用分为什么变了」可追溯——答辩时老师常问。

**封禁不动信用分**（2026-10-30 修正，早期口径写的是「封禁清零」）。信用分记的是交易行为，封禁是账号处置，两者混在一起会让解封出来的用户带着 0 分寸步难行，`credit_log` 里也会留一条无法区分性质的扣分。封禁只写 `app_user.status`、`ban_reason`、`ban_until`。

### 5.6 `user_review` 互评

`uk(order_id, reviewer_id)` 保证一单一评。`rating` 1–5 + `tags`(json) + `comment`。

**四条写入约束**：只有 `status=4`（已完成）的订单可评，其余状态无从评价——交易没走完就评人是没有依据的；收货后 30 天内可评，超窗口不再开放，避免半年前的交易突然被人打一星；`reviewer_id` 必须是该单买家或卖家，`target_id` 就是对方；同一人同一单只能评一次，重复提交返回已有评价而不是覆盖（评价一旦发出就是公开内容，允许改会让「先给好评再改差评」成为报复手段）。

**评价立即可见，不做「双方都评完才互见」**。闲鱼那套双盲设计是为了防止报复性评价，但需要额外的「评价待揭晓」状态与超时自动揭晓任务；毕设规模下，立即可见的收益（页面简单、数据链路短）大于它防的那点风险。代价是「谁先评谁吃亏」，这一点写进已知缺口。

**评分不联动信用分**。信用分在确认收货那一步已经 +1（§5.5），互评再动一次就成了同一件事扣两次分；两者口径必须分开：信用分记行为，评分记主观感受。

### 5.7 社交模块五表（字段唯一来源；业务规则见 notes/22，DDL 见 schema.sql 十）

四块用户端能力，不新增管理端权限点；动态/评论发布即公开，靠 `sys_sensitive_word` 过滤 + `report` 举报后人工，不进预审队列。

| `user_follow` | B 类（复用行） | id / follower_id / followee_id / create_time / deleted；`uk(follower_id,followee_id,deleted)`、`idx_follower(follower_id,deleted,create_time)`、`idx_followee(followee_id,deleted,create_time)` |
| `user_moment` | A 类（留墓碑） | id / user_id / type(1状态 2分享商品,默认1) / content(varchar1000,可空) / images(json,≤9) / item_id(可空) / audit_status(0正常 1敏感词屏蔽 2举报下架,默认0) / create_time / update_time / deleted；`idx_user(user_id,deleted,create_time)`、`idx_square(deleted,audit_status,create_time)` |

### 文件名为什么带 `zz-` 前缀

`db/` 整个目录挂进了 MySQL 的 `/docker-entrypoint-initdb.d/`，首次启动**按文件名顺序**自动执行其中的 `.sql`。ASCII 里数字 < 字母，所以 `01-…`、`99-…` 这类数字前缀都会排在 `schema.sql` 之前——那时表还没建，本文件开头的 `DELETE` 会直接把初始化打挂。

用 `zz-` 才能确保排在 `schema.sql` 之后。**副作用（也是好处）**：删掉数据目录重新初始化时，这份演示数据会自动灌进去，不用手动导入。真想拿到空库，重灌前先把这个文件临时改名。

### 8.3 两条约定

1. **确定性**：所有数值由固定种子的 LCG 生成，不使用 `RAND()`。任何人、任何时间重跑都得到同一份数据，截图与论文数据才对得上。
2. **幂等**：开头先按「明细表 → 主表」顺序 `DELETE` 那 7 张表，可以反复重灌。**只用于演示库。**

「今天」固定为 **2026-09-29**，数据跨度 30 天，目的是让首页 KPI（今日 GMV / 今日成交 / 待审核…）不为 0。已实测的今日口径：GMV 1472.10、成交 4、新增商品 3、待审核 5、待受理举报 3、待复审申诉 2。

### 8.4 与 `/admin/dashboard/*` 的关系
