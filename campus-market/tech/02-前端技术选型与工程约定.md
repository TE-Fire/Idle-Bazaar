# 前端技术选型与工程约定（Vue 3）

> 配套：`design/01-Web用户端-UI设计规范.md`、`design/03-管理端Web-UI设计规范.md`、`business/` 三份业务文档
> 后端契约：`tech/01-后端技术选型与工程约定.md`
> 版本快照：2026-09-26。安装时以官方 `latest` 为准；文档里写的是**当前稳定线**，不是 RC/Alpha。

**选型原则**：前沿但不吃螃蟹。**只用一个 RC 版本 = 给自己埋答辩雷**，所以下面每一个"不用"都比"用"更需要记住。

## 三、工程结构（pnpm workspace）

```
campus-market-web/
├─ apps/
│  ├─ web/          用户 Web 端（黄 #FFD100）—— 对应 design/01
│  ├─ admin/        管理后台（蓝 #1677FF）—— 对应 design/03
│  └─ mini/         小程序（uni-app，橙 #FF6A00）—— 对应 design/02
├─ packages/
│  ├─ tokens/       ★ 设计令牌唯一源头（见第五章）
│  ├─ api/          OpenAPI 生成的 TS 类型 + 请求封装
│  ├─ shared/       权限点常量、状态机枚举、字典类型、格式化工具
│  └─ eslint-config/ 统一规范
├─ pnpm-workspace.yaml
└─ package.json
```

**为什么是 monorepo 而不是两个独立仓库**：三端必须共用三样东西——设计令牌（primitive 层三端一致）、状态机与权限点常量（前后端同名）、接口类型。分成三个仓库后，这三项必然漂移，而它们恰恰是 `design/` 三份规范反复强调的强制对齐项。

**两端是否合并进一个 app**：不合并。用户端与管理端视觉体系、UI 库、目标屏幕（管理端仅 ≥1280，不做移动端适配）都不同，合并只会让样式互相污染。分开部署、分开构建，共享走 `packages/`。

## 四、UI 库选型（分端不统一，是有意为之）

| | 用户 Web 端 | 管理后台 |
|---|---|---|
| UI 库 | **Element Plus** | **Ant Design Vue** |
| 视觉源 | `design/01` 大屏网格电商型（闲鱼网页版 / eBay） | `design/03` 分析台 Light Card（AntD Pro） |
| 主色 | 黄 `#FFD100` + 黑字 | 蓝 `#1677FF` |
| 主要用到的组件 | Upload（拖拽多图）、Form、Select、Dialog、Pagination、Message | Table（筛选/排序/批量）、Form（复杂联动）、Drawer、Descriptions、Tag、Modal |
| 定制诉求 | **高**——商品卡、对比表要自己写，库只提供基础件 | **低**——直接用标准中后台范式 |

理由：

1. **C 端强定制，库越"轻"越好**。用户端真正需要库的只有发布页的拖拽上传与筛选器，其余展示组件（商品卡、对比表）必须自己写才能对上 `design/01` 的网格与悬停规格。Element Plus 体积小（gzip 约 80KB）、CSS 变量换肤直接，正好。
2. **管理端要的是"标准答案"**。审核队列 Drawer 连续审核、报表筛选表格、权限矩阵，AntD 的设计规范本身就覆盖了这些场景，用 Ant Design Vue 等于直接复用 `design/03` 已经画好的样子，不用自己造 Table 的交互。
3. **AntD 的"后台味"用在 C 端是减分项**。把它套到学生逛商品的页面上，会得到"像管理系统的二手平台"。

**代价与对策**：两套库 = 两套心智。对策是——共享层不放任何 UI 组件，只放 Token 与业务常量；两端的按钮/标签等基础件各自封装，但**视觉由 Token 统一**，所以看起来仍是同一产品（这正是 `design/` 的"角色化色彩策略"）。

按需引入用 `unplugin-vue-components` + `unplugin-auto-import`（Vite 8 下注意插件版本兼容，装完先跑一次 `pnpm build` 验证，不通过就退回手动按需 import）。

## 五、样式与设计令牌落地（本项目最关键的一节）

原型（`prototypes/web/web.css`、`prototypes/admin/admin.css`、`prototypes/miniprogram/mini.css`）已经是**完整的 CSS 变量体系**，落地时直接搬，不要重写一遍。

**三端同源，一份 JSON 生成三份产物**

```
packages/tokens/
├─ src/primitive.json       ★ 唯一源：色板 / 字阶 / 间距 / 圆角 / 阴影（三端一致）
├─ src/web.semantic.json    用户端语义层
├─ src/admin.semantic.json  管理端语义层
├─ src/mini.semantic.json   小程序语义层（值 ×2 转 rpx）
└─ scripts/build.mjs        生成 css 变量 / scss 变量 / uni.scss 变量
```

规则（与 `design/` 三份规范一致，不可违反）：

- **业务代码禁止写死色值**，一律 `var(--xxx)`；primitive 层三端共用，semantic 层各端覆盖
- 主色不统一是**角色化色彩策略**，是刻意设计，不是 bug——不要"顺手统一"
- 用户端阴影只在 hover 浮起与对比条两处；管理端卡片默认极浅阴影；**小程序不用阴影**
- 字阶：Web 两端 body 14px；小程序 14pt（`1pt = 2rpx`）；小程序禁用 800 字重

**为什么不上 Tailwind / UnoCSS**：`design/` 已经给出语义化 Token 层，原子化框架会引入第二套命名体系，两边打架时改哪边都不对。且原型里的 class 是语义化的（`.card` / `.tag`），直接迁移成本几乎为零。样式用 Sass 的 `@use`（不要用已废弃的 `@import` 和 node-sass）。

## 六、横切能力约定

### 6.1 请求层（Axios 拦截器）

| 关注点 | 约定 |
|---|---|
| 统一响应 | 后端 `Result{code,msg,data,traceId}`；拦截器内解包，业务层只拿 `data` |
| 错误处理 | `code != 0`（业务成功码是 **0**，不是 200）→ 统一 toast；`1001` → 清会话跳登录；`1002` → 提示无权限（不跳走） |
| traceId | 从响应头取 `X-Trace-Id`，错误提示里带上，联调与后端日志一一对应 |
| 幂等 | 提交类接口带后端下发的防重 token（见 `tech/01` 幂等章节） |
| 取消 | 页面切换用 `AbortController` 取消在途请求，避免瀑布流快速翻页时结果乱序 |

**Long 转 String 已在后端完成**（雪花 ID 一律字符串返回），前端的 `id` 类型必须是 `string`，**不要定义成 `number`**，否则 JS 精度丢失（>2^53 尾数变 00）——这个在订单/商品 ID 上必现。

**null 字段在 JSON 里整个缺省**（后端 `application.yml` 配了 `default-property-inclusion: non_null`，`JacksonConfig` 同步了 `NON_NULL`）：前端拿到的是 `undefined` 而不是 `null`。后果有两条——
① 类型定义里可空的字段要标成**可选**（`parentId?: string | null`）；
② 判空只能用 `!x` 或 `x == null`，**写 `x === null` 永远不成立**。
2026-10-02 字典联调实测踩过：一级分类的 `parentId === null` 筛不出来，分类表整张空白。

### 6.2 路由与权限（管理端）

- 权限点常量从 `packages/shared` 导出，**字符串必须与后端 Sa-Token 注解、原型 `data-perm` 三方同名**（16 个点，如 `review.judge`、`user.ban`）
- 两级控制：路由守卫拦菜单级；`v-perm` 指令拦按钮级（无权限直接不渲染，与原型一致）
- 前端隐藏只是体验层，接口鉴权在后端——这点要在论文里写明，否则会被认为权限是"假的"

### 6.3 状态管理

- Pinia store 按域拆分：`user` / `dict` / `chat` / `order`
- **字典字典只存一份**，启动时拉 `/api/dict/all`，管理端发布后靠版本号失效重拉
- 持久化只存 token 与少量偏好，不存业务列表（缓存列表会导致售出状态不更新）

### 6.4 图表（管理端）

- ECharts 5 + `vue-echarts`，按需引入模块（不要全量引）
- 配色取自 `design/03`（含四张校园图：学期时间轴、学院×品类热力矩阵、面交所热力、循环率减碳）
- 减碳卡片必须显示"估算假设"提示——这是已拍板项，UI 上不能省

### 6.5 上传（用户端发布页）

- 后端返回 MinIO 预签名 URL，前端 **PUT 直传**，不经过应用服务器
- 拖拽排序用 sortablejs；前端只做扩展名与大小初筛，**真实校验在后端（文件魔数）**
- ≤9 张，第一张为主图；发布页右侧实时预览卡复用列表页的商品卡组件

### 6.6 实时通信

- 用户端 Web 与小程序都用原生 WebSocket（后端 Spring WebSocket，非 socket.io）
- 握手带 Sa-Token；心跳 + 指数退避重连自己实现（约 60 行）
- 消息三分区（`PRIVATE / SYSTEM / TRADE`）由前端按 `zone` 字段分流渲染

## 七、与后端的契约对齐清单

| 项 | 约定 | 出处 |
|---|---|---|
| ID 类型 | 一律 `string` | `tech/01` 第五章 |
| 金额 | 后端 BigDecimal 转字符串 / 前端展示 `¥18` 格式，禁用浮点运算 | `design/` 三端规范 |

| 字典 | 分类 / 成色 A–D / 面交点 / 学院 / 校区，走 `/api/dict/all`，三端不得硬编码 | `business/` 三份 |

| 接口类型 | Knife4j（OpenAPI 3）→ `openapi-typescript` 生成到 `packages/api` | `tech/01` 第四章 |
| 校园四项字段 | 成色评级 / 校区 / 面交点 / 学号认证必须在卡片、筛选、详情三处同时可见 | `design/` 三端规范 |

## 八、质量与规范

- TypeScript `strict: true`；`id`、`money`、`status` 三类必须有明确类型别名（`ItemId = string`）
- ESLint 9 flat config（`eslint.config.js`），启用 `eslint-plugin-vue` 的 `<script setup>` 规则
- Prettier 只管格式，不管质量；两者冲突时以 ESLint 为准
- 提交前 `lint-staged` 只查改动文件（全量 lint 在毕设规模下没必要）
- 目录约定：组件 `PascalCase.vue`，组合式函数 `useXxx.ts`，常量 `UPPER_SNAKE`
- 每个页面文件顶部写 10 行以内的注释：对应哪个原型页、对应业务文档哪条流程——**论文的"设计与实现"章节直接从这里摘**
- 开发工序（F0–F6 七道工序、组件规范、CR 清单）见 **`tech/04-前端开发工序与编码规范.md`**

## 九、决策记录

| 决策 | 选择 | 被否掉的选项与原因 |
|---|---|---|
| Vue 版本 | 3.5.x 稳定线 | 3.6 RC：Vapor Mode 不支持 Options API、`getCurrentInstance()` 返回 null，且 alien-signals 响应式重写未稳定，**毕设不押预发布** |
| 构建工具 | Vite 8 | 无悬念选项，唯一注意点是 Node 版本与插件兼容 |
| UI 库 | 分端两个 | 全端统一：要么 C 端有后台味（AntD），要么管理端自己补 Table 交互（EP） |
| 样式方案 | CSS 变量 + Sass | Tailwind / UnoCSS：与既有 Token 体系重复，且原型已是语义化 class |
| 工程形态 | pnpm monorepo | 三仓库：Token / 权限点 / 接口类型必然漂移 |
| SSR | 不做 | 校园内部平台无 SEO 需求；Nuxt 3 已 EOL，Nuxt 5 未稳定 |

### 风险与降级

| 风险 | 降级方案 |
|---|---|
| Vite 8 与按需引入插件不兼容 | 改手动按需 import（多写几行，不影响功能）；或退一个 Vite 大版本 |
| Element Plus 暗色/换肤变量覆盖不全 | 只在 `:root` 覆盖 semantic 层，不碰组件内部变量；极端情况用 `:deep()` 局部覆盖 |
| 两端共享 Token 后视觉仍不一致 | 以 `prototypes/` 三份原型为验收基准，逐页对比截图 |
| ECharts 打包体积偏大 | 按需引入 + 路由级懒加载（A2/A8 单独 chunk） |

## 十、落地顺序建议

1. `packages/tokens` —— 先把三份 Token 从原型 CSS 抽成 JSON 源并生成产物（这步做完，后面写页面几乎不用调样式）
2. `apps/admin` 骨架：登录 → 布局 → 权限指令 → 一个 Table 页（验证权限隔离与字典下发）
3. `apps/admin` A2 看板四张图（论文亮点，且依赖后端接口最少，可先用 mock）
4. `apps/web` 骨架：首页 → 详情 → 发布页（拖拽多图是最难的一页，留到最后）
5. `apps/mini` 复用 `packages/api` 与 Token 源，按 `prototypes/miniprogram/` 逐页搬
