# 后端开发工序与编码规范

> 上游：`business/` 三份业务与流程文档（需求来源）、`prototypes/`（界面依据）
> 平行：`tech/01-后端技术选型与工程约定.md`（技术栈与关键实现）、`tech/02-前端技术选型与工程约定.md`
> 定位：**这份文档是那条流水线**——从"需求"这粒麦子，到"可演示、可答辩"这块面包，中间每一道工序的输入、动作、产出、质检标准。

**用法**：不要把它当"规范读一遍"，而是当**工序卡**。每开始一个新接口/新模块，从 W0 走起，每道工序末尾的 DoD 没打勾就不进下一道。

---

## 零、流水线总览

```
W0 备料  需求确认      business/xx 流程 + prototypes/xx 页面  ──► 需求要点卡
   ↓
W1 成型  领域建模      表结构 + 状态机 + 索引                ──► DDL + 枚举
   ↓
W2 开模  契约先行      XxxReq / XxxVO + Knife4j + 错误码      ──► 接口文档（可给前端）
   ↓
W3 加工  编码实现      Controller → Service → Mapper         ──► 可运行代码
   ↓
W4 质检  校验与自测    边界用例 + 自检清单                    ──► 自测记录
   ↓
W5 包装  提交与评审    分支 + commit + CR 清单                ──► 合并入 develop
   ↓
W6 出厂  联调与交付    mock 数据 + 演示脚本 + 论文素材         ──► 可答辩功能
```

**铁律：W2 不完成，W3 不许开始。** 契约先行的唯一理由是——接口一旦先写代码再补文档，前端就要等你，且文档永远落后于实现。

## 一、W0 备料：需求确认

**输入**：`business/` 中对应流程条目 + `prototypes/` 中对应页面 + `design/` 中对应规范

**标准动作**
1. 在业务文档里找到该需求所属流程，抄下**状态机**与**判据**（例如"改价需重审，改描述免审"）
2. 打开对应原型页，抄下页面出现了哪些字段（校园四项字段是否都在卡片/筛选/详情三处可见）
3. 写出**需求要点卡**（不超过 10 行）：角色、前置状态、操作、后置状态、异常分支、涉及的权限点

**DoD**
- [ ] 知道这个接口的**权限点字符串**（且与前端 `data-perm`、原型一致）
- [ ] 知道涉及的状态流转，且状态值来自 `business/` 已定的枚举，不是自己现编
- [ ] 异常分支已列出（超时、并发冲突、无权限、资源不存在至少四项）
- [ ] 若业务文档里没写清楚 → **先补业务文档，再写代码**，不要靠猜

**常见次品**：跳过这步直接建表 → 表结构和业务流程对不上，返工一次等于写两遍。

## 二、W1 成型：领域建模

**标准动作**
1. 建表：**先画状态字段，再画其余字段**（状态决定这条数据的生命周期）
2. 每张业务表必带六件套：`id`、`create_time`、`update_time`、`create_by`、`update_by`、`deleted`
3. 需要并发保护的表加 `version`（商品、订单）；需要 SLA 计时的加 `enter_queue_at` / `first_handle_at`
4. 索引跟着**查询模式**走，不是跟着字段走：列表页筛选条件 + 排序键组成联合索引
5. 状态字段一律枚举落 code，Java 侧用枚举类承接

**DoD**
- [ ] 每个状态字段都有明确终态，且能画出状态机图
- [ ] 金额字段是 `decimal(10,2)`，不是 `float/double`
- [ ] 时间字段是 `datetime`，不是时间戳
- [ ] 列表查询能命中索引（`EXPLAIN` 看 `type` 不是 `ALL`）
- [ ] 表与字段注释齐全（论文"数据库设计"章节直接摘录）

## 三、W2 开模：契约先行

**标准动作**
1. 写 `XxxReq`（入参）与 `XxxVO`（出参），**禁止 Entity 直接进出 Controller**
2. 给每个字段加校验注解，并按场景分组（发布有"存草稿"与"提交送审"两套校验）
3. 写错误码枚举（分段：商品 10xx、订单 20xx、审核 30xx、用户 40xx、系统 50xx）
4. 加 Knife4j 注解，`@Hidden` 掉内部接口
5. **把接口文档链接发给前端，确认字段能满足页面**——这一步省下的是联调时的来回扯皮

**DoD**
- [ ] 所有 ID 字段类型是 `String`（雪花 ID，防止 JS 精度丢失）
- [ ] 金额字段是 `String` 或 `BigDecimal`，**不是 double**
- [ ] 时间格式统一 `yyyy-MM-dd HH:mm:ss`
- [ ] 分页参数有上限（默认 20，最大 100）
- [ ] 每个非 200 响应都有对应错误码，且前端能据此给出用户可读提示

## 四、W3 加工：编码实现

### 4.1 分层职责（越权即违规）

| 层 | 允许 | 禁止 |
|---|---|---|
| Controller | 参数接收、`@Valid` 校验、调 Service、包装 `Result` | 写业务逻辑、直接调 Mapper、try-catch 吞异常 |
| Service | 业务规则、事务边界、状态流转、发 MQ | 拼 SQL、感知 HTTP（`HttpServletRequest`） |
| Mapper | 单表 CRUD、简单关联 | 写业务判断、写循环 |
| Entity | 与表 1:1 | 出现在 Controller 的返回值里 |

### 4.2 命名

| 对象 | 约定 | 示例 |
|---|---|---|
| 请求体 | `XxxReq` | `ItemPublishReq` |
| 响应体 | `XxxVO` | `ItemDetailVO` |
| 持久对象 | `XxxEntity` | `ItemEntity` |
| 接口/实现 | `XxxService` / `XxxServiceImpl` | 不用 `IItemService` 前缀 |
| 方法 | `get` 单条 / `list` 不分页 / `page` 分页 / `create` / `update` / `remove` | `pageOnSale()` |
| 布尔字段 | DB 用 `is_xxx`，**Java 侧字段名去掉 `is`**，用 `@TableField` 显式映射 | `is_verified` → `verified` |

> 布尔字段那条是真实坑：DB `is_xxx` + Java `isXxx()` 会让 MyBatis-Plus 与 Jackson 各自处理一次前缀，最终序列化出 `xxx` 而不是前端约定的 `isXxx`。统一成 Java 无前缀 + 显式映射。

### 4.3 事务

- 必须写 `@Transactional(rollbackFor = Exception.class)`，**不写 rollbackFor 是错的**（默认只回滚 `RuntimeException`）
- 事务方法要短。事务内**禁止**：发 MQ（除非事务消息）、调外部 HTTP、大批量查询、睡眠
- 同类内部方法互相调用不经过代理，事务与 `@OpLog` 都会失效——需要时拆到另一个 Service

### 4.4 异常与日志

- 错误码契约：全后端只认 `IErrorCode` 接口（`getCode/getMsg`）。**业务模块各自维护错误码枚举**（如 `ItemErrorCode`、`OrderErrorCode`，放各模块 `errcode` 包）并实现该接口；`common` 只维护通用段 `CommonErrorCode`（10xx/50xx）。新模块扩错误码前先在 tech/01 5.5 登记段位
- 业务失败抛 `BizException`，入参优先用错误码枚举，**禁止到处传裸 int code**；快捷写法 `throw ItemErrorCode.ITEM_NOT_FOUND.ex()`
- 条件不满足抛异常的场景**用 `BizAssert` 压成一行**，不写 if 块：`BizAssert.isTrue(order.isOwner(uid), OrderErrorCode.ORDER_NOT_OWNER)`。不用 Hutool 的 `Assert`——它抛 `IllegalArgumentException`，会被兜底成 5000 而丢失业务错误码
- 禁止 `return null` 表示失败；禁止 `catch (Exception e) {}` 空吞；至少 `log.error` 并带 traceId
- 禁止 `System.out` / `e.printStackTrace()`
- 日志脱敏：学号、手机号、身份证、token 不全量打印
- 管理端写操作加 `@OpLog` 注解，异步落 `sys_operation_log`（实现见 `tech/01` §5.4、推导见 `notes/11`）。**注解挂 Controller 不挂 Service**：同一个 Service 方法常被两个入口复用（如 `ItemAdminService#forceOffline` 同时服务商品页与审核队列），挂 Service 会丢掉「从哪个入口来的」；权限点与入口一一对应，挂在入口才配得上。写不出 `bizId` 时留空即可，不要为了凑一个 id 去改方法签名

### 4.5 对象构建与工具类

- **多字段构建**：Entity 一律 `@Accessors(chain = true)` 链式 setter（MyBatis-Plus 兼容）；**Req/VO 用 Lombok `@Builder`**；两者都不用在业务代码里写一长串插入式 `setXxx`
- **判空等基础工具统一用 Hutool**（已引 `hutool-core` 5.8.x）：`StrUtil.isBlank` / `ObjUtil.isNull` / `CollUtil.isEmpty` / `MapUtil.isEmpty` / `NumberUtil`。禁止手写 `s == null || s.isEmpty()`；`String.isBlank()`（JDK 自带）在纯 Java 工具类里可用
- 工具类选型登记在 tech/01 第六章，**不允许同一件事出现两套工具**（如 StrUtil 与 StringUtils 混用）——`spring-core` 的 `StringUtils` 仅用于框架内部扩展点

### 4.6 安全（最容易被忽略、最致命）

- **用户 ID 一律从 Sa-Token 取，禁止从请求参数取**——这是越权漏洞的头号来源
- 所有用户端资源操作必须校验归属（`item.getSellerId().equals(currentUserId)`）
- 管理端接口必须挂权限注解，权限点字符串与前端同名
- 上传文件只信后端的魔数校验，不信前端扩展名

### 4.7 MyBatis-Plus 使用边界

| 能力 | 约定 |
|---|---|
| 逻辑删除 | 全局配置，查询自动带 `deleted = 0` |
| 自动填充 | `create_time` / `update_time` / `create_by` 由 `MetaObjectHandler` 填，不手写 |
| 乐观锁 | 手写条件更新：`.eq(version)` + `setSql("version = version + 1")`，以影响行数判定成败。**不用 `@Version`**——插件只在实体非空时改写 SQL，本项目一律 `update(null, wrapper)`，装了也不生效 |
| 分页 | `Page` 对象，前端传参超上限要截断 |
| Wrapper | 简单条件用；**超过 5 个条件或含子查询就写 XML**，可读性优先 |
| 循环查库 | 禁止。批量用 `in` 或 `批量方法` |

### 4.8 时间与金额

- 时间：`LocalDateTime`，时区 Asia/Shanghai；跨天/超时判断用同一个时钟，不在多处各算各的
- 金额：`BigDecimal`，比较用 `compareTo`，禁止 `==` 与 `double`；展示格式化在 VO 层做

## 五、W4 质检：校验与自测

**每个接口至少跑完这 8 条边界用例**（自测记录要留档，论文"系统测试"章节直接用）

1. 正常流程 ✔
2. 参数缺失 / 非法
3. 无权限（换个账号调）
4. **越权**（A 用户操作 B 用户的资源）
5. 资源不存在
6. 状态不对（对已售出商品下单、对草稿审核）
7. **并发**（同一商品两人同时付款 → 必须只有一个成功）
8. 重复提交（同一请求连发两次 → 幂等）

**DoD**
- [ ] 8 条用例全部跑过，异常路径返回的是业务错误码而不是 500
- [ ] Knife4j 上能调通，响应字段与 W2 契约一致
- [ ] 日志里有 traceId，能根据 traceId 在日志文件里找到完整链路
- [ ] 涉及状态流转的，DB 里实际状态与预期一致（不只看接口返回）

**分支**

```

develop   集成分支
feature/xxx  功能分支，从 develop 切，完成后 PR 回 develop
```

**CR 检查清单**（提 PR 前自己先过一遍）

| # | 检查项 |
|---|---|

## 七、W6 出厂：联调与交付

- **mock 数据脚本**要可重复执行（清空 + 重建），不要手工在库里点
- 演示数据覆盖：各状态商品（含驳回、已售出）、各状态订单、待审核队列不少于 10 条（能体现权重排序）、四张校园图有数据
- 每个演示场景写一张**操作脚本卡**（几步、点哪里、预期看到什么）——答辩时照着走，不会卡壳
- 论文素材同步留档：状态机图、核心接口清单、数据库表清单、关键实现代码片段（`tech/01` 第九章六项）

## 八、反模式清单（见到即打回）

| 反模式 | 为什么是错的 |
|---|---|
| Controller 里写业务 | 无法复用、无法测试、事务边界失控 |
| Entity 直接返回前端 | 暴露内部字段（如 `deleted`、`cost`），且改表即改接口 |
| 用 `Map<String,Object>` 传参 | 没有任何类型保障，联调全靠猜 |
| 把 userId 从请求体取 | 越权漏洞，毕设里最容易被扣分的一类问题 |
| 事务里发 MQ | 事务回滚了消息已发出，消费端读到不存在的数据 |
| 状态用字符串硬编码 | 一处拼错就静默失效 |
| 循环里单条查库 | N+1，列表页一上线就慢 |
| 定时任务全表扫无索引 | 数据量上来后锁表 |
| catch 后只打日志不回滚 | 数据处于半完成状态 |
| 接口写完再补文档 | 文档永远落后，前端永远在等你 |
