> 版本：v1.0 ｜ 日期：2026-09-26 ｜ 状态：**已定稿**
> 架构：**单体应用**（Spring Boot + 模块化分包）

## 一、选型原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **业务驱动，不堆中间件** | 每个组件必须能指名道姓地说出它解决了哪个业务问题；说不出就不引入 |
| 2 | **熟悉度优先** | 基石栈取开发者最熟的组合，毕设的风险点在工期而非技术上限 |
| 3 | **单体优先** | 三端总用户量级是「一所学校的在校生」，单体足够；不引入微服务与注册中心 |
| 4 | **可演进而非一步到位** | 搜索引擎、对象存储这类能力用**接口隔离**，一期用轻实现，二期可替换 |
| 5 | **权限与状态在服务端** | 前端隐藏不是安全边界；状态机以 `business/03` 为准，后端是唯一权威 |

### 2.1 关于虚拟线程（JDK 21 的必答题）

JDK 21 的虚拟线程对本项目**暂不启用**，`spring.threads.virtual.enabled` 保持 `false`（Tomcat 继续用平台线程池）。理由：

- HikariCP、Lettuce/Jedis 连接池内部大量使用 `synchronized`，JDK 21 下 `synchronized` 会 **pin** 住载体线程（JEP 491 到 JDK 24 才修），开启后吞吐可能不升反降
- Sa-Token 的 `StpLogic` 依赖 `ThreadLocal`，虚拟线程下语义仍成立，但一旦引入线程复用型缓存（如池化的 `MessageDigest`、`SimpleDateFormat`）就会串号
- 本项目是校园单机场景，并发量远未到平台线程池的瓶颈；虚拟线程的收益点（海量长连接）只在 IM 上有意义，风险大于收益

论文写法建议：单独写一小节「虚拟线程适用性评估」，列出 pin 问题与实测对比——**评估后不采用**也是工程判断，比"用了最新特性"更有说服力。

## 四、基础设施的业务职责

### 4.1 MySQL

- 全部主数据；字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci`，事务隔离级别默认 RR
- 金额一律 `decimal(10,2)`，**禁止 float/double**
- 主键：雪花 ID（Long，序列化转 String，见第五章）
- 每张业务表：逻辑删除 `deleted`、创建/更新时间、创建/更新人（`MetaObjectHandler` 自动填充）
- 索引设计重点（决定筛选性能，比上 ES 更关键）：
  - 商品列表：`(status, category_id, campus, created_at)`、`(seller_id, status)`、`price`
  - 检索：`fulltext(title, description) WITH PARSER ngram`，`ngram_token_size = 2`
  - 审核队列：`(review_status, weight_score DESC, created_at)`（权重排序靠这里，不靠缓存）

### 4.2 Redis

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 会话 | Sa-Token 托管 | 用户端与管理端两套 key 前缀，互不干扰 |
| 图形验证码 / 短信码 | String + TTL | 管理端登录码、学号认证邮箱码 |
| 商品详情缓存 | String | 更新即删，不做双写 |
| 未读消息计数 | Hash | IM 与三分区通知 |
| 防重复提交 | String（一次性 token） | 发布、下单、支付 |
| 字典缓存 | String | A7 改动后发布，主动失效 |
| 敏感词库版本号 | String | 词库热更新触发 |

**明确不用 Redis 做的事**：审核队列的权重排序。ZSet 天然贴合「按分数取 TopN」，但一旦缓存与库不一致，审核员会看到两个队列——这个代价远大于性能收益。**排序走 MySQL 索引，权重分定时重算 + 变更时即时重算。**

### 4.3 RocketMQ

| Topic | 生产者 | 消费者动作 |
|---|---|---|
| `ITEM_SUBMIT` | 商品提交 | 计算权重分、敏感词扫描、进审核队列 |
| `ORDER_TIMEOUT` | 下单（**延迟消息 30 分钟**） | 未付款则取消订单并通知买家 |
| `ORDER_PAID`（事务消息） | 支付成功 | 商品转已售出、其余待付款订单取消 |
| `REVIEW_RESULT` | 审核/举报/申诉处置 | 投递站内「系统通知」分区、更新信用分 |
| `OP_LOG` | 各类写操作 | 操作日志异步落库（`@OpLog` AOP） |
| `MSG_NOTIFY` | 各类事件 | 站内消息三分区投递、未读计数累加 |

> 30 分钟超时用 RocketMQ 延迟消息，不要写定时轮询扫表——后者在数据量大时是灾难，且答辩容易被追问。

### 4.4 MinIO

- Bucket：`item-image`（商品图）、`verify-file`（认证凭证）、`avatar`
- 上传校验：**文件魔数**而非扩展名；限制大小（商品图 ≤5MB，凭证 ≤10MB）与尺寸
- 对外只暴露后端签名 URL，不外泄 AK/SK；凭证类文件**禁止公开读**
- 抽象 `StorageService { upload, getUrl, delete }`，实现类 `MinioStorage`；换 OSS 只改实现类与配置

## 五、横切能力

### 5.1 参数校验

- `spring-boot-starter-validation`，Controller 用 `@Validated`，DTO 上用 `@NotNull/@NotBlank/@Size/@DecimalMin`
- **分组校验**：`Draft`（存草稿，只校验标题）与 `Submit`（提交送审，全量校验）
- **跨字段约束自定义注解**：成色 = D 时 `flawDesc` 必填 → `@ConditionalRequired`
- Service 层方法同样加 `@Validated`，防止内部调用绕过校验
- 统一由 `@RestControllerAdvice` 捕获 `MethodArgumentNotValidException`，返回 400 + 首个错误字段，不整包抛出

### 5.2 接口文档（Knife4j）

- 分组：`学生端`、`管理端`、`开放接口`（字典下发等）
- 内部接口（MQ 补偿、定时任务触发）用 `@Hidden` 隐藏，或放到内网 profile
- 所有写接口必须写 `@Operation(summary)` 与错误码说明；审核类接口必须注明权限点
- 生产环境通过 `knife4j.production=true` 关闭，避免接口泄露

### 5.3 序列化（Jackson 四条硬规则）

| # | 规则 | 原因 |
|---|---|---|
| 1 | **Long 全部序列化为 String** | 雪花 ID 超过 JS 安全整数（2^53−1），小程序与 Web 端会精度丢失，表现为 ID 尾数变成 00 |
| 2 | 金额 `BigDecimal`，统一保留 2 位 | 禁止 double 参与金额运算 |
| 3 | 时间统一 `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai` | 三端展示一致；相对时间（"3 小时前"）由前端换算 |
| 4 | 统一响应体 `{code, msg, data, traceId}`，`null` 字段不输出 | 前端少做判空；traceId 用于联调与日志追踪 |

- 枚举对外输出 `code` 而非 `name`（`@JsonValue`），避免前端硬编码中文
- 成色、状态等字典**由后端下发**（`/api/dict/**`），三端不得硬编码

### 5.4 日志

两类日志**分开做，不要混为一谈**：

| | 访问日志（控制台） | 操作日志（落库，A9 可查） |
|---|---|---|
| 实现 | **Filter / HandlerInterceptor**，不用注解 | **自定义 `@OpLog` 注解 + AOP** |
| 为什么 | 覆盖所有请求，与业务语义无关，无差别记录 | 只记**有业务语义**的动作，全量 HTTP 日志是噪音 |
| 输出 | 日志文件 | `sys_operation_log` 表 |

**访问日志**：Filter 生成 `traceId` 写入 MDC，响应头回传 `X-Trace-Id`；日志格式含 `traceId, userId, uri, cost`。要打印请求体时用 `ContentCachingRequestWrapper` 包装（注意限大小，且脱敏）。
**应用日志**：Logback 按天滚动，ERROR 单独文件，保留 30 天。

**操作日志（`@OpLog` + AOP）**

```java
@Target(METHOD) @Retention(RUNTIME)
public @interface OpLog {
    String module();                 // review / item / user / system
    String type();                   // APPROVE / REJECT / BAN / OFF_SHELF ...
    String bizId() default "";       // SpEL：#itemId
    String desc() default "";
    boolean saveDiff() default false;// 是否记录变更前后的值（审核、封禁、改价必须开）
}
```

落库字段：操作人 id/姓名/角色、module、type、业务对象 id、desc、变更前后值、结果（成功/失败及错误码）、IP、UA、traceId、耗时。只追加，不可删改。
**审核留痕、举报处置、申诉裁决复用同一张表**，用 `type` 区分，申诉复审时可完整复盘。

**五个必须注意的点**

1. **事务提交之后再写**。业务回滚了但日志已落，等于记录了从不存在的操作。用 `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit` 回调，或直接发 `OP_LOG` 消息异步消费落库（后者与已有 RocketMQ 一致，推荐）。
2. **异步写要用自定义线程池**（`opLogExecutor`），不要用默认线程池，且队列要有界、拒绝策略要能降级（写不进去就打 ERROR 日志，不能影响主流程）。
3. **失败也要记**。`afterThrowing` 分支同样落库，`result = FAIL`，否则"谁尝试越权、谁反复失败"这条线索就断了。
4. **敏感字段脱敏**。变更前后的值里可能有手机号、学号，入库前脱敏。
5. **依赖要显式加**：Spring Boot 3 的 `spring-boot-starter-web` 不含 AOP，需单独引入 `spring-boot-starter-aop`。

**约定**：管理端凡是挂了 `@SaCheckPermission` 的写接口，**必须同时挂 `@OpLog`**——写进 `tech/03` 的 CR 清单，靠人盯不如靠清单。

### 5.5 异常处理

- 业务异常 `BizException(code, msg)` + 全局错误码枚举（按模块分段：商品 10xx、订单 20xx、审核 30xx、用户 40xx、系统 50xx）
- 未知异常统一兜底为 5000，返回 traceId，详情页不暴露堆栈
- **写操作失败必须可重试**：关键路径（下单、支付回调）用唯一业务键做幂等

### 5.6 幂等

- 下单 / 支付 / 审核处置：请求带一次性 `idempotentKey`（Redis 删除式校验）
- MQ 消费：以业务唯一键（订单号 + 事件类型）做去重表或 Redis SETNX

## 六、敏感词过滤（已定：分级处置）

| 项 | 方案 |
|---|---|
| 算法 | DFA / Trie 树（自实现约 200 行，或用 `com.github.houbb:sensitive-word`） |
| 词库 | 存 MySQL `sys_sensitive_word(level, word)`，启动时加载进内存，Redis 发布订阅触发热更新 |
| 分级 | **高危**（违禁品、校外引流、诈骗、联系方式）→ **直接拒绝**并返回命中位置<br>**低危**（擦边、疑似广告）→ 替换为 `*` 并**打标**，商品照常进入审核队列由人判断 |
| 三个入口 | ①商品标题/描述（提交时 + 审核时二次校验）②聊天消息（发送时，命中记违规计数）③举报/申诉文本 |
| 聊天策略 | 命中高危：消息拒绝发送并提示；命中低危：替换后放行。累计命中计入信用分与审核权重 |

> 分级而不是一律拒绝的理由：一律拒绝会误杀「低价出」「加微信详聊」这类正常校园表述；一律送审则会稀释审核队列，与「按权重排序」的设计目标冲突。

## 七、搜索引擎（已定：MySQL 一期 + 接口预留）

### 7.1 一期方案

- **全文检索**：MySQL 8 `FULLTEXT(title, description) WITH PARSER ngram`，`ngram_token_size = 2`
- **结构化筛选**（真正的主体）：分类 / 成色 / 校区 / 价格区间 / 状态 → 走 B+ 树索引
- **排序**：`ORDER BY` 结构化字段（校区优先、成色、信用权重、时间），不与全文相关性混合
- **搜索词表**：`sys_search_hot` 记录热词，用于搜索框下拉（Redis 计数）

### 7.2 接口预留（关键）

```java
public interface ItemSearchService {
    Page<ItemVO> search(ItemSearchQuery query);   // 一期：MySQL 实现
}
```

- 一期实现 `MysqlItemSearchService`，**业务代码只依赖接口**
- 二期若引入 ES：新增 `EsItemSearchService`，通过 `@ConditionalOnProperty` 切换，Service 层零改动

### 7.3 什么时候才值得上 ES（触发条件，写进论文）

同时满足以下两条再演进，缺一不动：
1. 商品表 ≥ 50 万行，或搜索 QPS 出现 MySQL 慢查询
2. 出现 MySQL 做不了的需求：同义词/自定义校园词典、相关度与结构化字段混合打分、搜索结果高亮

> 选型结论写进论文的话术：本项目搜索需求中约八成是**结构化筛选与排序**，两成是关键词匹配；前者依赖索引设计而非检索引擎，因此一期采用 MySQL 全文索引，并以接口隔离保留向 Elasticsearch 演进的能力。

## 八、鉴权与权限（Sa-Token，与前端矩阵同名）

### 8.1 双账号体系

- 两套 StpLogic：`StpUserUtil`（学生端）、`StpAdminUtil`（管理端），独立 token 前缀与配置文件
- 小程序：`code2session` 换 openid → 绑定学号 → 签发用户 token
- Web 用户端：手机号/学号 + 验证码
- 管理端：账号 + 密码 + **图形验证码**（A1 需求），失败 5 次锁定 10 分钟

### 8.2 权限点必须与前端同名（关键对齐）

后端 `StpAdminUtil.hasPermission("review.judge")` 中的字符串，**必须与前端 `data-perm` 完全一致**（16 个权限点见 `business/03` F-A1）。

- 实现方式：`StpInterfaceImpl` 从库里按角色查权限点列表
- 关键互斥：`review.judge`（裁决商品）与 `user.ban`（封禁账号）分属审核员与超级管理员
- **前端隐藏只是体验层**，每个写接口必须做 `checkPermission`，两者缺一不可
- 只读角色：能看全部数据，不持有任何写权限点，用于答辩巡盘

### 8.3 WebSocket 鉴权

握手阶段携带 token（`Sec-WebSocket-Protocol` 或 query），握手拦截器中校验并绑定 userId；连接建立后不再重复鉴权，但敏感动作（发消息）校验会话归属。

### 8.4 会话存储：Redis Dao，**不引入 JWT**

Sa-Token **默认不是 JWT**：默认 token 是随机串（`tokenStyle=uuid`），会话存服务端；持久层默认是**内存 Map**（`SaTokenDaoDefaultImpl`，重启即掉登录），所以必须换成 Redis：

```xml
<dependency>cn.dev33:sa-token-redis-jackson</dependency>  <!-- Jackson 序列化，不用 JDK 序列化 -->
```

**不引入 JWT 的理由（业务决定，不是口味）**

| 业务动作 | Redis 会话 | JWT 无状态 |
|---|---|---|
| 封禁用户后立即踢下线（`user.ban`） | `kickout` / `disable` 即时生效 | 做不到，要等 token 过期 |
| 管理员权限/角色变更后立即生效 | 即时 | 要等过期 |
| 被封禁用户的 WebSocket 连接 | 握手时查会话，直接拒 | token 未过期仍可连上 |
| 在线会话管理（管理端可查） | 支持 | 不支持 |

四条全部指向同一件事：**本项目需要"即时失效"**，而即时失效只能由服务端会话提供。

**若论文确实想出现 JWT**：只能用 `sa-token-jwt` 的 **Simple 模式**（JWT 样式 + 仍然存 Redis），保留踢下线能力；**绝不能用 Stateless 模式**，它会让封禁功能失效，与 `business/03` 的角色权限设计直接冲突。

**配置建议**

| 项 | 用户端 `StpUserUtil` | 管理端 `StpAdminUtil` |
|---|---|---|
| timeout | 7 天 | 2 小时（安全优先） |
| active-timeout | 开启续期 | 开启续期 |
| is-concurrent | `true`（手机 + 电脑同时在线） | `true`，但管理端保留会话列表便于审计 |
| is-share | `false` | `false` |

## 九、关键业务的技术实现（必写进论文）

### 9.1 付款才占位（无预定机制，核心并发点）

**两级校验**：Redis Lua 前置拦截（快速失败 + 削峰）→ MySQL 条件更新兜底（唯一权威）。

```
支付确认/回调
   │
   ├─ ① Redis Lua 抢占状态标记 ──► 返回值
   │      1  抢到   → 继续 ②
   │      2  幂等   → 同一订单重复回调，直接返回成功
   │      0  冲突   → 已被他人锁定/已售出，立即失败（不打到 DB）
   │     -1  缓存缺失 → 放行，交给 DB 裁决（关键：不能拒绝）
   │
   ├─ ② MySQL 条件更新（权威判定，影响行数=1 才算抢到）
   │
   ├─ ② 成功 → 提交事务，Lua 回写 SOLD（终态）
   └─ ② 失败 → 反向 Lua 释放标记（必须校验 holder 是自己的 orderId）
```

**① Redis Lua 脚本**（状态机抢占，不是扣库存）

```lua
-- KEYS[1] = cm:item:state:{itemId}
-- ARGV[1]='ON_SALE'  ARGV[2]='LOCKED'  ARGV[3]=锁TTL(秒)  ARGV[4]=orderId
local cur = redis.call('GET', KEYS[1])
if cur == false then
  return -1                                          -- 缓存缺失：放行给 DB
end
if cur == ARGV[2] then
  if redis.call('HGET', 'cm:item:holder', KEYS[1]) == ARGV[4] then
    return 2                                         -- 幂等重入
  end
  return 0                                           -- 他人已锁定
end
if cur ~= ARGV[1] then
  return 0                                           -- 已售出 / 已下架
end
redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
redis.call('HSET', 'cm:item:holder', KEYS[1], ARGV[4])
return 1                                             -- 抢到
```

Redis 单线程执行 Lua，脚本内多步不可分割，**判定原子性由此保证**。建议用 `RedisScript` + `RedisTemplate.execute()` 加载，脚本不拼字符串、不传用户参数拼接。

**② MySQL 条件更新（真正的一致性来源）**

```sql
UPDATE item SET status = 'SOLD', version = version + 1
WHERE id = ? AND status = 'ON_SALE' AND version = ?;
```

以**影响行数 = 1** 判定抢到；为 0 说明已被买走 → 该待付款订单取消并通知买家（模拟支付需原路退回）。

**三个必须写对的细节**

- **TTL 只需 60 秒**，不是 30 分钟。它覆盖的是"抢标记 → DB 提交"这段窗口（毫秒到秒级）；DB 提交后立即改写为 `SOLD` 终态，DB 失败则主动回滚。设成 30 分钟会在异常路径下把商品白白锁死半小时。
- **返回 -1 必须放行**。缓存未预热 / 已过期 / 被 LRU 淘汰时 Lua 无从判定，若设计成"缺失即拒绝"，缓存一失效商品就永远卖不掉。放行是安全的，因为 DB 会拦住。
- **回滚必须校验 holder**。释放标记前比对 `holder == 自己的 orderId`，否则 DB 慢的那一个请求会把别人的锁误释放。

**为什么不能只用 Lua**（论文要能答上来）

1. Redis 不是持久化权威：Lua 判定成功但 DB 提交前宕机 → 商品被标记却没卖成，只能等 TTL 自愈，期间误杀其他买家的请求。
2. Lua 不能访问 DB，"抢标记"与"落库"必然是两步，中间态无法消除——正确性只能由 DB 的条件更新保证。
3. Lua 解决的是**原子判定**，解决不了**持久一致**。二者不是替代关系，是前置过滤与最终裁决的关系。

**为什么不用 Redisson 分布式锁**：悲观串行化，把一次毫秒级的条件更新放大成"加锁 → 走业务流程 → 解锁"的临界区，还要处理锁超时与业务时长的博弈。本项目要的是"并发下恰好一个赢家"，条件更新天然满足，无需额外加锁。

**一致性边界（写进论文）**：Redis 前置不参与正确性判定，任何时刻以 MySQL 的 `item.status` 为准。缓存与库不一致时的最坏结果是"多放行一次到 DB"（被 DB 拦住）或"多拒绝一个已无货请求"（TTL 后自愈），**不会出现超卖**。

**诚实说明必要性**：校园场景 QPS 下，单靠 ② 的 MySQL 条件更新完全够用（行锁 + 唯一状态条件，毫秒级）。Lua 前置的实际收益是削峰、提前失败避免走完支付流程才发现冲突，以及论文的技术章节素材——不是必需的，但不能因此省掉 ②。

**降级**：Redis 不可用时，Lua 前置整段 try-catch 降级为"全部放行"，功能不受影响，只是 DB 压力上升（见第十一章风险表）。

### 9.2 订单超时取消

- 下单成功发送 RocketMQ **延迟消息**（延迟等级对应 30 分钟）
- 消费者检查订单仍是「待付款」则取消；已付款则直接丢弃
- 补偿：`@Scheduled` 每 10 分钟扫一次超时未处理订单，防消息丢失

### 9.3 审核权重与 SLA 计时

- 商品提交 → 计算权重分落库：`举报次数×3 + 图片风险×2 + 信用扣减 + 价格异常 − 等待衰减（每满 12h +1）`
- 等待衰减部分由定时任务每 30 分钟重算一次（或查询时实时计算补偿项，推荐后者，避免写放大）
- SLA 计时字段：`enter_queue_at`（进队时间）、`first_handle_at`（首次处置）、`handler_id`
  - 首审时长 = `first_handle_at − enter_queue_at`，> 2h 记未达标，> 24h 记积压红牌
  - 单条处置时长 = 处置提交时间 − Drawer 打开时间（前端埋点上报，用于操作效率指标）

### 9.4 站内消息三分区

- 一张 `msg_message` 表，`zone` 字段区分 `PRIVATE / SYSTEM / TRADE`
- 分区是为了避开 Vinted 的坑（通知与私信混流写进论文）
- 投递统一走 MQ，未读数落 Redis Hash，前端红点取未读总数

### 9.5 字典下发

- 分类 / 成色 A–D / 面交点 / 学院 / 校区五张表，管理端 A7 维护
- 提供 `/api/dict/all` 一次性下发（带版本号），Redis 缓存，管理端发布后主动失效
- **三端不得硬编码**：这条是 `design/` 三份规范的硬约束

### 9.6 信用分

- 初始 100；完成 +1（上限 120）、单方取消 −5、举报成立 −10、强制下架 −15、封禁清零
- 变更走 MQ 异步，但**必须落变更明细表**，用户详情页与管理端可查（对应 A4 抽屉里的信用分变动时间轴）
- 对外只暴露等级（高/中/低），分数仅管理端可见（见 `business/02` 决策）

## 十、工程约定

| 项 | 约定 |
|---|---|
| 响应体 | `Result<T> { code, msg, data, traceId }` |
| 分层 | Controller 不做业务；Service 内聚事务；Manager 层可选，跨域调用走 Service |
| 事务 | `@Transactional` 只加在 Service；事务内**不发 MQ**（改为事务提交后发送，或用事务消息） |
| DTO | 请求 `XxxReq`、响应 `XxxVO`、持久 `XxxEntity`，禁止 Entity 直接出 Controller |
| 枚举 | 落库存 code，对外输出 code；文案由字典下发 |
| 命名 | 表 `t_item` 或 `item` 统一（**建议不加前缀**）；字段下划线；布尔 `is_xxx` |
| 配置 | `application-{dev|prod}.yml`，敏感配置走环境变量，禁止密钥入代码库 |
| 时间 | 一律 `LocalDateTime`，DB `datetime`，不用时间戳 |
| 分页 | MyBatis-Plus `Page`，最大 100 条/页，默认 20 |
| 编码 | UTF-8；Lombok 可用但 `@Data` 不用于 Entity（避免 equals/hashCode 误用） |
| 工序 | 从需求到交付的七道工序与编码风格见 **`tech/03-后端开发工序与编码规范.md`** |

## 十一、决策记录

### 已定（2026-09-26）

| 议题 | 决策 | 理由 |
|---|---|---|
| 架构 | 单体 + Maven 多模块 | 用户量是单校在校生；微服务带来的运维成本无收益 |
| ORM | MyBatis-Plus | 乐观锁（占位并发）、逻辑删除、自动填充、分页是四个刚需 |
| 搜索引擎 | **MySQL 8 ngram 全文 + 接口预留** | 八成需求是结构化筛选；ES 的收益小于部署与一致性成本，触发条件见 7.3 |
| IM | **Spring WebSocket 原生** | 单体足够；Netty 的编解码/心跳/重连成本过高 |
| 对象存储 | **MinIO** | S3 兼容，Docker 单容器，与 OSS 接口一致便于迁移 |
| 敏感词 | **分级处置**（高危拒绝 / 低危打标） | 避免误杀正常表述，同时不稀释审核队列 |
| 鉴权 | Sa-Token 双 StpLogic | 用户端与管理端权限模型差异大；权限点与前端同名 |
| 文档 | Knife4j 4.x | 中文 UI，答辩可直接演示 |
| 定时任务 | Spring `@Scheduled` + MQ 延迟消息 | 不引入 XXL-Job |
| 审核队列排序 | MySQL 索引，不用 Redis ZSet | 缓存与库双份排序会让审核员看到两个队列 |

### 风险与降级

| 风险 | 降级方案 |
|---|---|
| RocketMQ 单机宕机 | 超时取消走 `@Scheduled` 补偿；站内消息降级为站内轮询 |
| MinIO 不可用时上传失败 | 临时写本地目录并记录，恢复后回迁（`StorageService` 加 `LocalStorage` 实现） |

| Redis 不可用 | 9.1 的 Lua 前置降级为「全部放行」，改由 MySQL 条件更新裁决，功能不受影响 |
| Redis 中商品状态标记与 MySQL 不一致 | 以 MySQL 为准；标记 TTL 60s 自愈，且缺失即放行，不会锁死商品 |
