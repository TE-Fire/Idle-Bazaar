# 后端技术选型与工程约定

> 版本：v1.0 ｜ 日期：2026-09-26 ｜ 状态：**已定稿**
> 架构：**单体应用**（Spring Boot + 模块化分包）
> 依据：`business/01`、`business/02`、`business/03`（三端业务与流程）、`design/01`–`03`（三端视觉规范）
> 定位：写代码前的唯一技术依据。未定义的依赖版本先补本文档。
> 决策记录：见第十一章（含每项选型的业务理由与已决/待决清单）

## 一、选型原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **业务驱动，不堆中间件** | 每个组件必须能指名道姓地说出它解决了哪个业务问题；说不出就不引入 |
| 2 | **熟悉度优先** | 基石栈取开发者最熟的组合，毕设的风险点在工期而非技术上限 |
| 3 | **单体优先** | 三端总用户量级是「一所学校的在校生」，单体足够；不引入微服务与注册中心 |
| 4 | **可演进而非一步到位** | 搜索引擎、对象存储这类能力用**接口隔离**，一期用轻实现，二期可替换 |
| 5 | **权限与状态在服务端** | 前端隐藏不是安全边界；状态机以 `business/03` 为准，后端是唯一权威 |

### 2.1 关于虚拟线程（JDK 21 的必答题）

JDK 21 的虚拟线程对本项目**暂不启用**，`spring.threads.virtual.enabled` 保持 `false`（Tomcat 继续用平台线程池）。理由：

- HikariCP、Lettuce/Jedis 连接池内部大量使用 `synchronized`，JDK 21 下 `synchronized` 会 **pin** 住载体线程（JEP 491 到 JDK 24 才修），开启后吞吐可能不升反降
- Sa-Token 的 `StpLogic` 依赖 `ThreadLocal`，虚拟线程下语义仍成立，但一旦引入线程复用型缓存（如池化的 `MessageDigest`、`SimpleDateFormat`）就会串号
- 本项目是校园单机场景，并发量远未到平台线程池的瓶颈；虚拟线程的收益点（海量长连接）只在 IM 上有意义，风险大于收益

论文写法建议：单独写一小节「虚拟线程适用性评估」，列出 pin 问题与实测对比——**评估后不采用**也是工程判断，比"用了最新特性"更有说服力。

## 三、架构与模块划分

### 3.1 部署形态

```

三端              │ 微信小程序    │ 用户 Web 端   │ 管理后台 Web  │
                  └──────┬───────┴──────┬───────┴──────┬───────┘
                         │  HTTPS / WSS │
                  ┌──────▼──────────────▼──────────────▼───────┐
单体应用           │        Spring Boot（单进程）                │
                  │  Controller ─ Service ─ Mapper              │
                  └───┬────────┬────────┬────────┬─────────────┘
                      │        │        │        │
                  MySQL 8   Redis 7  RocketMQ  MinIO
```

### 3.2 Maven 多模块（单体进程，代码分模块）

```
campus-market/
├─ campus-common      通用：统一响应、异常、错误码、工具类、常量、字典枚举
├─ campus-core        Entity / Mapper / Service / MQ 生产者消费者（业务主体）
├─ campus-user-api    学生端接口（Web + 小程序共用），端口 8080
├─ campus-admin-api   管理端接口，端口 8081（同一进程或独立进程，见下）
└─ campus-support     敏感词、存储、搜索、IM 等可替换能力的实现
```

> 用户端与管理端可以打成**两个 jar 共用 campus-core**，也可以单 jar 用两套 Controller 前缀（`/api/**` 与 `/admin/**`）。
> **建议单 jar + 路径前缀**：部署简单，且与 `design/03` 中「同一前端工程按角色分流」的约定一致。若学院要求接口分离，再拆两个 jar，不改业务代码。

### 3.3 包结构（`campus-core`）

**实际落地的是「技术分层」，不是按业务域分包**（早期文档画的是业务域，与代码不符，已按代码改正）：

```
com.campus.core
├─ entity     所有表的实体（MP 生成，集中放，不按域拆）
├─ mapper     Mapper 接口
├─ service    业务服务（见下：具体类，不拆接口 + impl）
├─ dto
│  ├─ req     入参 DTO，命名 *Req
│  └─ resp    出参 DTO，命名 *VO
├─ config     配置类
├─ errcode    错误码枚举
├─ handler    全局异常处理、MP 元对象自动填充
├─ init       启动初始化（演示管理员账号）
└─ satoken    Sa-Token 多账号体系
```

**为什么不按业务域（`core.item` / `core.order`…）分包：**

| 业务域分包 | 本项目情况 |
|---|---|
| 收益：领域边界清晰、模块可独立演化 | 单体毕设规模，19 张表、十余个 service，边界收益有限 |
| 收益：便于按域做权限/模块隔离 | 无插件化、无独立部署需求 |
| 成本：每个域一套 entity/mapper/service，跳转层级变深 | 反而拖慢开发 |
| 成本：跨域查询（商品 × 用户 × 订单）要跨包引用 | 本项目统计类查询不少，跨包引用更啰嗦 |

保持技术分层；真到需要拆的那天（比如要拆微服务），按域迁移是机械操作。

**DTO 为什么不放在 `service` 下面**：`controller` 也要用这批 `Req` / `VO`，它们实际是**跨模块的 API 契约**，不是 service 的私有物，所以提到 `core.dto` 下按方向分 `req` / `resp`。

> 依赖边界（2026-10-02 核实并改正，此前写反了）：
> - **validation 可用**：`campus-common` 引了 `spring-boot-starter-validation`，core 依赖 common →
>   `jakarta.validation` 的 `@NotBlank` / `@Size` / `@Pattern` / `@NotNull` **可以**写在 core 的 `dto.req` 上。
> - **openapi 不可用**：knife4j 只在两个 api 模块里，`@Schema` 只能写在 controller 的 VO 上，core 的 DTO 别写。
>
> 两种校验的分工：**格式类**（非空、长度、正则）用声明式注解，
> **跨记录的业务规则**（父级必须是启用的一级分类、色值不能重复）一律走 service 内的 `BizAssert`——
> 注解挡不住要查库的约束。controller 参数记得加 `@Valid`，否则注解不生效。

## 四、基础设施的业务职责

### 4.1 MySQL

- 全部主数据；字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`（MySQL 8 默认值，与容器 server 一致），事务隔离级别默认 RR
- 金额一律 `decimal(10,2)`，**禁止 float/double**
- 主键：雪花 ID（Long，序列化转 String，见第五章）
- 每张业务表：逻辑删除 `deleted`、创建/更新时间、创建/更新人（`MetaObjectHandler` 自动填充）
- 索引设计重点（决定筛选性能，比上 ES 更关键）：
  - 商品列表：`(status, category_id, campus, created_at)`、`(seller_id, status)`、`price`
  - 检索：`fulltext(title, description) WITH PARSER ngram`，`ngram_token_size = 2`
  - 审核队列：`(review_status, weight_score DESC, created_at)`（权重排序靠这里，不靠缓存）

### 4.2 Redis

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 会话 | Sa-Token 托管 | 用户端与管理端两套 key 前缀，互不干扰 |
| 图形验证码 / 短信码 | String + TTL | 管理端登录码、学号认证邮箱码 |
| 商品详情缓存 | String | 更新即删，不做双写 |
| 未读消息计数 | Hash | IM 与三分区通知 |
| 防重复提交 | String（一次性 token） | 发布、下单、支付 |
| 字典缓存 | String | A7 改动后发布，主动失效 |
| 敏感词库版本号 | String | 词库热更新触发 |

**明确不用 Redis 做的事**：审核队列的权重排序。ZSet 天然贴合「按分数取 TopN」，但一旦缓存与库不一致，审核员会看到两个队列——这个代价远大于性能收益。**排序走 MySQL 索引，权重分定时重算 + 变更时即时重算。**

> **实况（2026-10-08 补）**：当前 `queue()` 不分页，三来源合并后在**内存里排序**
> （类型优先 → 权重降序 → 进队时间升序），SQL 层只有 `WHERE status=...` 的过滤，
> `idx_queue` 只用到 `status` 前缀。上文「走 MySQL 索引」是按可分页、排序可下沉到 SQL 层的形态设计的，
> 队列规模大到需要分页时按此落地；在此之前改索引不会带来收益。

**key 的拼装归属**：全部 `cm:*` 业务 key 由 `com.campus.core.redis` 下的常量类提供（`RedisKeys.PREFIX` 定义唯一前缀，各模块一个 `XxxRedisKeys`，方法名 `buildXxxKey(...)`）。业务代码不写 key 字面量——否则改前缀、改层级要全项目搜索替换。约定见 §10。

> **不在本约定内**：Sa-Token 托管的会话 key（`satoken-user:*` / `satoken-admin:*`）由框架按 `token-name`（`MultiAccountConfig.USER_TOKEN_NAME` / `ADMIN_TOKEN_NAME`）自行生成，我们既不拼也不该改——上表「两套 key 前缀」指的就是它。

### 4.3 RocketMQ

| Topic | 生产者 | 消费者动作 |
|---|---|---|
| `ITEM_SUBMIT` | 商品提交 | 计算权重分、敏感词扫描、进审核队列 |
| `ORDER_TIMEOUT` | 下单（**延迟消息 30 分钟**） | 未付款则取消订单并通知买家 |
| `ORDER_PAID`（事务消息） | 支付成功 | 商品转已售出、其余待付款订单取消 |
| `REVIEW_RESULT` | 审核/举报/申诉处置 | 投递站内「系统通知」分区、更新信用分 |
| `OP_LOG` | 各类写操作 | 操作日志异步落库（`@OpLog` AOP）——**当前未启用**：`@OpLog` 走本地线程池落库，见 §5.4 第 1 条 |
| `MSG_NOTIFY` | 各类事件 | 站内消息三分区投递、未读计数累加 |

> 30 分钟超时用 RocketMQ 延迟消息，不要写定时轮询扫表——后者在数据量大时是灾难，且答辩容易被追问。

### 4.4 MinIO

- Bucket：`item-image`（商品图）、`verify-file`（认证凭证）、`avatar`
- 上传校验：**文件魔数**而非扩展名；限制大小（商品图 ≤5MB，凭证 ≤10MB）与尺寸
- 对外只暴露后端签名 URL，不外泄 AK/SK；凭证类文件**禁止公开读**
- 抽象 `StorageService { upload, getUrl, delete }`，实现类 `MinioStorage`；换 OSS 只改实现类与配置

## 五、横切能力

### 5.1 参数校验

- `spring-boot-starter-validation`，Controller 入参用 `@Valid`，DTO 上用 `@NotNull/@NotBlank/@Size/@DecimalMin`
- **两套校验**：暂存草稿（`draft = true`）与提交送审（`draft` 为空/false）。必填字段（标题/分类/成色/价格/校区）两套都查——`item` 表这些列 NOT NULL，草稿同样要落库；草稿豁免图片与描述（business/02「稍后补齐」口径）。单端点 + `draft` 标志分流，不用 JSR-303 分组：一个入口无法静态选定分组，且分组只影响注解、管不了 Service 里的跨字段规则
- **跨字段约束**：成色 = D 时描述必填 → Service 断言（`ItemService#requireGradeFlawDescribed`），单字段注解表达不了；仅送审路径生效，纯草稿暂存豁免
- Service 不加方法级校验：写入口全部经 Controller，跨字段与业务规则统一走 `BizAssert` 契约链（见 5.5）
- 统一由 `@RestControllerAdvice` 捕获 `MethodArgumentNotValidException`，返回参数错误(1000) + 首个错误字段，不整包抛出

### 5.2 接口文档（Knife4j）

- 分组：`学生端`、`管理端`、`开放接口`（字典下发等）
- 内部接口（MQ 补偿、定时任务触发）用 `@Hidden` 隐藏，或放到内网 profile
- 所有写接口必须写 `@Operation(summary)` 与错误码说明；审核类接口必须注明权限点
- 生产环境通过 `knife4j.production=true` 关闭，避免接口泄露

### 5.3 序列化（Jackson 四条硬规则）

| # | 规则 | 原因 |
|---|---|---|
| 1 | **Long 全部序列化为 String** | 雪花 ID 超过 JS 安全整数（2^53−1），小程序与 Web 端会精度丢失，表现为 ID 尾数变成 00 |
| 2 | 金额 `BigDecimal`，统一保留 2 位 | 禁止 double 参与金额运算 |
| 3 | 时间统一 `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai` | 三端展示一致；相对时间（"3 小时前"）由前端换算 |
| 4 | 统一响应体 `{code, msg, data, traceId}`，`null` 字段不输出 | 前端少做判空；traceId 用于联调与日志追踪 |

- 枚举对外输出 `code` 而非 `name`（`@JsonValue`），避免前端硬编码中文
- 成色、状态等字典**由后端下发**（`/api/dict/**`），三端不得硬编码

### 5.4 日志

两类日志**分开做，不要混为一谈**：

| | 访问日志（控制台） | 操作日志（落库，A9 可查） |
|---|---|---|
| 实现 | **Filter / HandlerInterceptor**，不用注解 | **自定义 `@OpLog` 注解 + AOP** |
| 为什么 | 覆盖所有请求，与业务语义无关，无差别记录 | 只记**有业务语义**的动作，全量 HTTP 日志是噪音 |
| 输出 | 日志文件 | `sys_operation_log` 表 |

**访问日志**：`AccessLogFilter`（common 层，`OncePerRequestFilter`）生成 `traceId` 写入 MDC，响应头回传 `X-Trace-Id`，并在 `finally` 里输出 `method / uri+query / status / 耗时 / IP`（traceId 已由 logback 的 `%X{traceId}` 输出，不再重复打印）。异常与 5xx 走 warn（只在正常路径打日志＝丢掉最该排查的 500），超 1s 记为慢请求。Knife4j 文档与静态资源路径不打日志，否则本地刷文档会淹没业务日志。要打印请求体时用 `ContentCachingRequestWrapper` 包装（注意限大小，且脱敏）——**当前未做**，登录接口的密码与验证码就在 body 里，收益小于风险。

**请求上下文**：`RequestContext`（traceId/method/uri/query/clientIp/UA/起始时刻）挂在 `RequestContextHolder` 的 ThreadLocal 上，由同一个 Filter（AccessLogFilter）的 `finally` 单点 `remove()`。登录人**不在**其中放——Filter 早于 Sa-Token 解析，取不到；改由 `AdminContext#getAdminId()` 懒加载回退 `StpAdminUtil`，首次取到后写回上下文复用。异步线程（`@Async`/MQ）无上下文，约定不使用 `AdminContext`。
**应用日志**：Logback 按天滚动，ERROR 单独文件，保留 30 天。

**操作日志（`@OpLog` + AOP）**

```java
@Target(METHOD) @Retention(RUNTIME)
public @interface OpLog {
    String module();                 // item / review / content / system / order
    String type();                   // APPROVE / REJECT / OFF_SHELF ...
    String bizId() default "";       // SpEL：#itemId / #id
    String desc() default "";
    boolean saveDiff() default false;// 是否记录本次变更内容（入参脱敏快照）
}
```

落库字段：操作人 id/姓名/角色、module、type、业务对象 id、desc、变更前后值、结果（成功/失败及错误码）、IP、UA、traceId、耗时。只追加，不可删改。
**审核留痕、举报处置、申诉裁决复用同一张表**，用 `type` 区分，申诉复审时可完整复盘。

**实现（2026-10-06 落地）**：`com.campus.core.oplog` 下四个类各管一段——`OpLog`（注解）、
`OpLogAspect`（在**请求线程**上抓快照）、`OpLogRecord`（不可变快照）、`OpLogWriter`（事务边界 + 异步落库）；
线程池在 `config/OpLogExecutorConfig`，脱敏在 `OpLogMasker`。推导与实测见 `notes/11`。

**五个必须注意的点**

1. **事务提交之后再写**。业务回滚了但日志已落，等于记录了从不存在的操作。用 `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit` 回调，或直接发 `OP_LOG` 消息异步消费落库。
   - 实现走的是 afterCommit 那条路，但**只给成功记录挂**；失败记录走「立即提交」（理由见第 3 条）。**本项目 `@OpLog` 挂在 Controller 上，进入切面时 Service 的事务已经提交**，注册不到同步也直接提交——两种挂法都成立。
   - **没有采用 `OP_LOG` 消息**：RocketMQ 目前无任何业务代码引用、本机也没起 broker，为一个横切能力引入运行时依赖不划算。真要换，只改 `OpLogWriter.record` 一处。
2. **异步写要用自定义线程池**（`opLogExecutor`），不要用默认线程池，且队列要有界、拒绝策略要能降级（写不进去就打 ERROR 日志，不能影响主流程）。
   - ⚠ 这是本项目**第一个 `Executor` Bean**，会让 Boot 的 `applicationTaskExecutor` 退让（它的自动配置条件是「容器里没有 Executor」）。当前零影响（无 `@Async`、无异步 MVC）；将来真要用 `@Async`，必须显式指定执行器。
3. **失败也要记**。`afterThrowing` 分支同样落库，`result = FAIL`，否则"谁反复失败"这条线索就断了。
   - **落地细节**：失败记录**不挂 `afterCommit`、立即提交**。它常常正是回滚的起因，挂了会被回滚一并抹掉——正好把这条「失败尝试」的记录弄丢。2026-10-06 在压测事务挂法时发现并修正（`notes/11` §3.2 / §7.2）。
   - ⚠ **但「谁尝试越权」不在本表**：`@SaCheckPermission` 由 `SaInterceptor` 在 `preHandle` 里校验，早于任何方法级切面，权限拒绝根本走不到切面。这条线索要看访问日志与 `GlobalExceptionHandler` 记录的 1002。
4. **敏感字段脱敏**。变更前后的值里可能有手机号、学号，入库前脱敏。
   - 两道口径：敏感**键名**（password / captcha / mailCode / phone / email / idCard / studentNo / token …）整值替 `***`；**值形**再兜一层——字符串里的手机号 → `138****8000`、邮箱 → `a***@qq.com`，防自由文本（驳回原因）里夹号码。落库前按列宽截断。
5. **依赖要显式加**：Spring Boot 3 的 `spring-boot-starter-web` 不含 AOP，需单独引入 `spring-boot-starter-aop`（`campus-core/pom.xml` 自骨架提交起已声明，无需再加）。

**约定**：管理端凡是挂了 `@SaCheckPermission` 的写接口，**必须同时挂 `@OpLog`**——写进 `tech/03` 的 CR 清单，靠人盯不如靠清单。
`/admin/auth/**` 的登录/注册/找回不在此列：它们没有权限点，也排除在拦截器之外。

### 5.5 异常处理

- **错误码契约链**：`IErrorCode` 接口（`getCode/getMsg`）是全后端「错误描述」的唯一契约——`BizException`、`Result.fail`、`BizAssert` 的入参都只认它。各模块错误码枚举实现该接口即天然接入三处
- **错误码分段且分模块维护**：通用 10xx（`CommonErrorCode`，在 common）/ 商品 11xx / 订单 20xx / 审核 30xx / 用户 40xx（含管理员登录）/ 系统 50xx / 字典 60xx（`DictErrorCode`）；业务枚举放各模块 `errcode` 包自行维护，**common 不感知业务**。新模块扩段先在此登记
- 未知异常统一兜底为 5000，返回 traceId，详情页不暴露堆栈
- **写操作失败必须可重试**：关键路径（下单、支付回调）用唯一业务键做幂等

### 5.6 幂等

- 下单 / 支付 / 审核处置：请求带一次性 `idempotentKey`（Redis 删除式校验）
- MQ 消费：以业务唯一键（订单号 + 事件类型）做去重表或 Redis SETNX

### 5.7 验证码与邮件（2026-09-29 补：管理端注册 / 找回密码）

管理端在登录、注册、找回密码三处共用图形验证码，注册与找回密码各再叠一层邮箱验证码
（流程见 `business/03` 的 F-A0 / F-A10）。本节只写**技术选型与工程约束**。

| 能力 | 实现 | 存储 | 生命周期 |
|---|---|---|---|
| 图形验证码 | `CaptchaService`：**JDK AWT 自绘**（`BufferedImage` + `Graphics2D`），4 位字符、3 条干扰线、120×40 PNG → base64 | Redis `cm:captcha:{key}` | 5 分钟，**一次性**（校验通过即删） |
| 邮箱验证码 | `MailService`：`JavaMailSender` + `SimpleMailMessage`，6 位数字 | Redis `cm:mail:code:{email}` | 10 分钟，一次性；`cm:mail:throttle:{email}` 做 60 秒节流 |
| 邮件通道 | QQ 邮箱 SMTP `smtp.qq.com:465`（SSL） | — | 授权码只在 `application-dev.yml`（已 gitignore），**不入库** |

**为什么图形验证码自绘，不用 Kaptcha / easy-captcha / `hutool-captcha`**：

| 方案 | 问题 |
|---|---|
| `hutool-captcha` | 项目只引了 `hutool-core`，为 4 位验证码再拉一个带 AWT 依赖的包不划算（见 2.1「不用 `hutool-all`」的同一条原则） |
| Kaptcha / easy-captcha | 配置项与 Filter/Servlet 写法偏重，且默认字符集含 `0/O`、`1/I/l` 这类易混字符，用户反复输错；自绘约 40 行即可控制字符集与干扰强度 |
| 第三方行为验证（滑块 / 无感） | 需要外网回调与密钥，答辩机上不一定通；毕设场景的威胁模型只是「挡住脚本批量撞库」，图片验证码够用 |

**为什么邮件用 SMTP 直连，不用阿里云邮件 / 短信 SDK**：管理端只有四个演示账号、注册需超管审批，
发信量是「每天几封」量级，SMTP 直连零成本；短信与第三方邮件 SDK 都要实名、备案与企业资质，
且把验证码通道交出去会多一个外部依赖点——一期不做，接口位置固定在 `MailService`，将来替换不动调用方。

**三条工程约束（违反会出安全问题）**：

1. **验证码文本永不下发前端**。返回体只有 `captchaKey` + 图片 base64，比对在 Redis 里做；
   把答案塞进隐藏域或图片 URL，等于把题目答案一起发给刷题的人。
2. **先比对、后删除**。先删的话，用户输错一次就把正确的码作废了，还得等 60 秒节流过去才能重发。
   同理「新密码不能与旧密码相同」必须放在校验邮箱码**之前**判，否则白消耗一个码。
3. **发信失败不能让流程 500**。`MailService` 捕获异常降级为日志；`campus.mail.enabled=false`
   时根本不发信，验证码直接打进日志，本地联调不依赖 SMTP，也不消耗 QQ 邮箱的每日限额。

**开关**（`application-dev.yml`，默认值面向本地联调）：

```yaml
campus:
  captcha:
    enabled: false   # 关：登录/注册/找回不用输验证码（演示前改 true）
  mail:
    enabled: false   # 关：验证码只打日志，不真发信（演示前改 true 并填授权码）
    from:            # 需与 spring.mail.username 一致，否则 QQ 拒发
spring:
  mail:
    host: smtp.qq.com
    port: 465
    username:        # 例：3037749727@qq.com
    password:        # QQ「设置 → 账户 → SMTP 服务」生成的 16 位授权码，≠ 登录密码
```

> `JavaMailSender` 用 `@Autowired(required = false)` 注入：`spring-boot-starter-mail`
> 只在配了 `spring.mail.host` 时才创建该 Bean，硬注入会让没配 SMTP 的机器直接起不来。

## 八、鉴权与权限（Sa-Token，与前端矩阵同名）

### 8.1 双账号体系

- 两套 StpLogic：`StpUserUtil`（学生端）、`StpAdminUtil`（管理端），独立 token 前缀与配置文件
- 小程序：`code2session` 换 openid → 绑定学号 → 签发用户 token
- Web 用户端：手机号/学号 + 验证码
- 管理端：账号 + 密码 + **图形验证码**（A1 需求），失败 5 次锁定 10 分钟

### 8.2 权限点必须与前端同名（关键对齐）

后端 `StpAdminUtil.hasPermission("review.judge")` 中的字符串，**必须与前端 `data-perm` 完全一致**（18 个权限点见 `business/03` F-A1）。

- 实现方式：`StpInterfaceImpl` 从库里按角色查权限点列表
- 关键互斥：`review.judge`（裁决商品）与 `user.ban`（封禁账号）分属审核员与超级管理员
- **前端隐藏只是体验层**，每个写接口必须做 `checkPermission`，两者缺一不可
- 只读角色：能看全部数据，不持有任何写权限点，用于答辩巡盘

### 8.3 WebSocket 鉴权

握手阶段携带 token（`Sec-WebSocket-Protocol` 或 query），握手拦截器中校验并绑定 userId；连接建立后不再重复鉴权，但敏感动作（发消息）校验会话归属。

### 8.4 会话存储：Redis Dao，**不引入 JWT**

Sa-Token **默认不是 JWT**：默认 token 是随机串（`tokenStyle=uuid`），会话存服务端；持久层默认是**内存 Map**（`SaTokenDaoDefaultImpl`，重启即掉登录），所以必须换成 Redis：

```xml
<dependency>cn.dev33:sa-token-redis-jackson</dependency>  <!-- Jackson 序列化，不用 JDK 序列化 -->
```

**不引入 JWT 的理由（业务决定，不是口味）**

| 业务动作 | Redis 会话 | JWT 无状态 |
|---|---|---|
| 封禁用户后立即踢下线（`user.ban`） | `kickout` / `disable` 即时生效 | 做不到，要等 token 过期 |
| 管理员权限/角色变更后立即生效 | 即时 | 要等过期 |
| 被封禁用户的 WebSocket 连接 | 握手时查会话，直接拒 | token 未过期仍可连上 |
| 在线会话管理（管理端可查） | 支持 | 不支持 |

四条全部指向同一件事：**本项目需要"即时失效"**，而即时失效只能由服务端会话提供。

**若论文确实想出现 JWT**：只能用 `sa-token-jwt` 的 **Simple 模式**（JWT 样式 + 仍然存 Redis），保留踢下线能力；**绝不能用 Stateless 模式**，它会让封禁功能失效，与 `business/03` 的角色权限设计直接冲突。

**配置建议**

| 项 | 用户端 `StpUserUtil` | 管理端 `StpAdminUtil` |
|---|---|---|
| timeout | 7 天 | 2 小时（安全优先） |
| active-timeout | 开启续期 | 开启续期 |
| is-concurrent | `true`（手机 + 电脑同时在线） | `true`，但管理端保留会话列表便于审计 |
| is-share | `false` | `false` |

## 九、关键业务的技术实现（必写进论文）

### 9.1 付款才占位（无预定机制，核心并发点）

**两级校验**：Redis Lua 前置拦截（快速失败 + 削峰）→ MySQL 条件更新兜底（唯一权威）。

```
支付确认/回调
   │
   ├─ ① Redis Lua 抢占状态标记 ──► 返回值
   │      1  抢到   → 继续 ②
   │      2  幂等   → 同一订单重复回调，直接返回成功
   │      0  冲突   → 已被他人锁定/已售出，立即失败（不打到 DB）
   │     -1  缓存缺失 → 放行，交给 DB 裁决（关键：不能拒绝）
   │
   ├─ ② MySQL 条件更新（权威判定，影响行数=1 才算抢到）
   │
   ├─ ② 成功 → 提交事务，Lua 回写 SOLD（终态）
   └─ ② 失败 → 反向 Lua 释放标记（必须校验 holder 是自己的 orderId）
```

**① Redis Lua 脚本**（状态机抢占，不是扣库存）

```lua
-- 规范脚本：campus-core/src/main/resources/lua/occupy.lua（经 LuaScripts 读入）
-- KEYS[1] = cm:item:state:{itemId}   KEYS[2] = cm:item:holder
-- ARGV[1]='ON_SALE'  ARGV[2]='LOCKED'  ARGV[3]=锁TTL(秒)  ARGV[4]=orderId
local cur = redis.call('GET', KEYS[1])
if cur == false then
  return -1                                          -- 缓存缺失：放行给 DB
end
if cur == ARGV[2] then
  if redis.call('HGET', KEYS[2], KEYS[1]) == ARGV[4] then
    return 2                                         -- 幂等重入
  end
  return 0                                           -- 他人已锁定
end
if cur ~= ARGV[1] then
  return 0                                           -- 已售出 / 已下架
end
redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
redis.call('HSET', KEYS[2], KEYS[1], ARGV[4])
return 1                                             -- 抢到
```

Redis 单线程执行 Lua，脚本内多步不可分割，**判定原子性由此保证**。脚本统一放 core 模块 `resources/lua/`（当前仅 `occupy.lua`，新增脚本只加文件），由 `LuaScripts` 在类初始化时读入内存、`RedisTemplate.execute()` 执行；key 一律经 KEYS 传入，脚本内不出现字面量 key（Cluster 下会算错 slot），不拼字符串、不传用户参数拼接。

**② MySQL 条件更新（真正的一致性来源）**

```sql
UPDATE item SET status = 'SOLD', version = version + 1
WHERE id = ? AND status = 'ON_SALE' AND version = ?;
```

以**影响行数 = 1** 判定抢到；为 0 说明已被买走 → 该待付款订单取消并通知买家（模拟支付需原路退回）。

**三个必须写对的细节**

- **TTL 只需 60 秒**，不是 30 分钟。它覆盖的是"抢标记 → DB 提交"这段窗口（毫秒到秒级）；DB 提交后立即改写为 `SOLD` 终态，DB 失败则主动回滚。设成 30 分钟会在异常路径下把商品白白锁死半小时。
- **返回 -1 必须放行**。缓存未预热 / 已过期 / 被 LRU 淘汰时 Lua 无从判定，若设计成"缺失即拒绝"，缓存一失效商品就永远卖不掉。放行是安全的，因为 DB 会拦住。
- **回滚必须校验 holder**。释放标记前比对 `holder == 自己的 orderId`，否则 DB 慢的那一个请求会把别人的锁误释放。

**为什么不能只用 Lua**（论文要能答上来）

1. Redis 不是持久化权威：Lua 判定成功但 DB 提交前宕机 → 商品被标记却没卖成，只能等 TTL 自愈，期间误杀其他买家的请求。
2. Lua 不能访问 DB，"抢标记"与"落库"必然是两步，中间态无法消除——正确性只能由 DB 的条件更新保证。
3. Lua 解决的是**原子判定**，解决不了**持久一致**。二者不是替代关系，是前置过滤与最终裁决的关系。

**为什么不用 Redisson 分布式锁**：悲观串行化，把一次毫秒级的条件更新放大成"加锁 → 走业务流程 → 解锁"的临界区，还要处理锁超时与业务时长的博弈。本项目要的是"并发下恰好一个赢家"，条件更新天然满足，无需额外加锁。

**一致性边界（写进论文）**：Redis 前置不参与正确性判定，任何时刻以 MySQL 的 `item.status` 为准。缓存与库不一致时的最坏结果是"多放行一次到 DB"（被 DB 拦住）或"多拒绝一个已无货请求"（TTL 后自愈），**不会出现超卖**。

**诚实说明必要性**：校园场景 QPS 下，单靠 ② 的 MySQL 条件更新完全够用（行锁 + 唯一状态条件，毫秒级）。Lua 前置的实际收益是削峰、提前失败避免走完支付流程才发现冲突，以及论文的技术章节素材——不是必需的，但不能因此省掉 ②。

**降级**：Redis 不可用时，Lua 前置整段 try-catch 降级为"全部放行"，功能不受影响，只是 DB 压力上升（见第十一章风险表）。

### 9.2 订单超时取消

- 下单成功发送 RocketMQ **延迟消息**（延迟等级对应 30 分钟）
- 消费者检查订单仍是「待付款」则取消；已付款则直接丢弃
- 补偿：`@Scheduled` 每 10 分钟扫一次超时未处理订单，防消息丢失

### 9.3 审核权重与 SLA 计时

- 商品提交 → 计算权重分落库：`举报次数×3 + ROUND(图片风险÷10) + 信用扣减 + 价格异常×5`
  - 图片风险分是 0–100，÷10 归一到 0–10。原式写「×2」与「归一化为 0–10」自相矛盾
    （0–100 ÷10 再 ×2 是 0–20），`business/03` F-A2 已于 2026-10-06 勘误，此处同步
  - 入库的是**基础分**，不含等待项
- 等待项每满 12h **+1**，是补偿不是衰减，符号为加。它不入库，**查询时实时算**，避免写放大
- 队列排序键 = 基础分 + 实时等待补偿。代码读的是四个分量字段（`report_count` / `image_risk` /
  `credit_deduct` / `price_abnormal`），**不是**打包好的 `priority_score`：UI 要逐项展示权重构成，
  总分必须由明细相加而来。`priority_score` 是同公式的冗余快照，供 SQL 层排序与报表，当前无读取方
- SLA 计时字段：`enter_queue_at`（进队时间）、`first_handle_at`（首次处置）、`handler_id`
  - 首审时长 = `first_handle_at − enter_queue_at`，> 2h 记未达标，> 24h 记积压红牌
  - 单条处置时长：`handle_cost_ms` 当前记的是**服务端处理这次处置动作的耗时**，不是审核员阅读单据的时长。
    准确口径要前端在 Drawer 打开时上报时间戳（多一个接口 + 时钟对齐），本期未做；
    概览条上的「30 秒」是目标值常量，不是统计值

### 9.4 站内消息三分区

- 一张 `msg_message` 表，`zone` 字段区分 `PRIVATE / SYSTEM / TRADE`
- 分区是为了避开 Vinted 的坑（通知与私信混流写进论文）
- 投递统一走 MQ，未读数落 Redis Hash，前端红点取未读总数

### 9.5 字典下发

- 分类 / 成色 A–D / 面交点 / 学院 / 校区五张表，管理端 A7 维护
- 提供 `/api/dict/all` 一次性下发（带版本号），Redis 缓存，管理端发布后主动失效
- **三端不得硬编码**：这条是 `design/` 三份规范的硬约束

### 9.6 信用分

- 初始 100；完成 +1（上限 120）、单方取消 −5、举报成立 −10、强制下架 −15、封禁清零
- 变更走 MQ 异步，但**必须落变更明细表**，用户详情页与管理端可查（对应 A4 抽屉里的信用分变动时间轴）
- 对外只暴露等级（高/中/低），分数仅管理端可见（见 `business/02` 决策）

## 十、工程约定

| 项 | 约定 |
|---|---|
| 响应体 | `Result<T> { code, msg, data, traceId }` |
| 分层 | Controller 不做业务；Service 内聚事务；Manager 层可选，跨域调用走 Service |
| 事务 | `@Transactional` 只加在 Service；事务内**不发 MQ**（改为事务提交后发送，或用事务消息） |
| DTO | 请求 `XxxReq`、响应 `XxxVO`、持久 `XxxEntity`，禁止 Entity 直接出 Controller |
| 枚举 | 落库存 code，对外输出 code；文案由字典下发。**类名一律以 `Enum` 结尾**（`AdminStatusEnum`、`MailCodeSceneEnum`、`LoginTypeEnum`），常量名 `UPPER_SNAKE_CASE`；由客户端传入的枚举只提供 `fromCodeOrNull`（返回 null，调用方转 1000），库里读出来的才用抛异常的 `fromCode` |
| 命名 | 表 `t_item` 或 `item` 统一（**建议不加前缀**）；字段下划线；布尔 `is_xxx` |
| Redis key | 形状 `cm:{模块}:{业务}:{标识}`；**一律经 `com.campus.core.redis` 下的模块常量类拼装**，方法名 `buildXxxKey(...)`，业务代码里不出现 key 字面量；项目前缀只在 `RedisKeys.PREFIX` 定义一次（见 4.2） |
| 配置 | `application-{dev|prod}.yml`，敏感配置走环境变量，禁止密钥入代码库 |
| 时间 | 一律 `LocalDateTime`，DB `datetime`，不用时间戳 |
| 分页 | MyBatis-Plus `Page`，最大 100 条/页，默认 20 |
| 编码 | UTF-8；Lombok 可用但 `@Data` 不用于 Entity（避免 equals/hashCode 误用） |
| 工序 | 从需求到交付的七道工序与编码风格见 **`tech/03-后端开发工序与编码规范.md`** |

## 十一、决策记录

### 已定（2026-09-26）

| 议题 | 决策 | 理由 |
|---|---|---|
| 架构 | 单体 + Maven 多模块 | 用户量是单校在校生；微服务带来的运维成本无收益 |
| ORM | MyBatis-Plus | 乐观锁（占位并发）、逻辑删除、自动填充、分页是四个刚需 |
| 搜索引擎 | **MySQL 8 ngram 全文 + 接口预留** | 八成需求是结构化筛选；ES 的收益小于部署与一致性成本，触发条件见 7.3 |
| IM | **Spring WebSocket 原生** | 单体足够；Netty 的编解码/心跳/重连成本过高 |
| 对象存储 | **MinIO** | S3 兼容，Docker 单容器，与 OSS 接口一致便于迁移 |
| 敏感词 | **分级处置**（高危拒绝 / 低危打标） | 避免误杀正常表述，同时不稀释审核队列 |
| 鉴权 | Sa-Token 双 StpLogic | 用户端与管理端权限模型差异大；权限点与前端同名 |
| 文档 | Knife4j 4.x | 中文 UI，答辩可直接演示 |
| 定时任务 | Spring `@Scheduled` + MQ 延迟消息 | 不引入 XXL-Job |
| 审核队列排序 | MySQL 索引，不用 Redis ZSet | 缓存与库双份排序会让审核员看到两个队列 |
| 图形验证码 | **AWT 自绘**，不用 Kaptcha / easy-captcha / `hutool-captcha` | 只引了 `hutool-core`；第三方默认字符集含 `0/O`、`1/I/l` 易混字符；自绘约 40 行即可控字符集，见 5.7 |
| 邮件通道 | **QQ 邮箱 SMTP 直连**，不用第三方邮件 / 短信 SDK | 发信量是每天几封，SMTP 零成本；第三方要实名与企业资质，且多一个外部依赖点，见 5.7 |
| 注册后状态 | `status=2` 待分配角色，**登录被 4006 拦下** | 角色只能由超管分配，注册接口不接受 `roleId`，否则任何人都能给自己审核权 |

### 风险与降级

| 风险 | 降级方案 |
|---|---|
| RocketMQ 单机宕机 | 超时取消走 `@Scheduled` 补偿；站内消息降级为站内轮询 |
| MinIO 不可用时上传失败 | 临时写本地目录并记录，恢复后回迁（`StorageService` 加 `LocalStorage` 实现） |
| 敏感词库过大导致内存占用 | 分级加载，只常驻高危词，低危词走 DB 查询 + 缓存 |
| MySQL 全文在大数据下变慢 | 达触发条件后切 ES，接口已预留，Service 层不改 |
| Redis 不可用 | 9.1 的 Lua 前置降级为「全部放行」，改由 MySQL 条件更新裁决，功能不受影响 |
| SMTP 不可用 / 未配授权码 | `campus.mail.enabled=false` 时验证码落日志不发信；开启但发送抛错时降级为日志，**注册与找回流程照常走完**，不返回 500 |
| 验证码图片生成失败（`ImageIO` 异常） | 返回空图并在前端提示「点击刷新」，不阻断登录页渲染 |
| Redis 中商品状态标记与 MySQL 不一致 | 以 MySQL 为准；标记 TTL 60s 自愈，且缺失即放行，不会锁死商品 |

## 十二、运行环境建议

```
Docker Compose（开发机 / 答辩机）
├─ mysql:8.0        约 500MB
├─ redis:7          约 50MB
├─ rocketmq:5.x     namesrv + broker + dashboard（broker 建议堆 1G）
├─ minio            约 200MB
└─ app（jar）        JVM 堆 1G
```

内存建议 **≥8G**（4G 会相当紧张：RocketMQ broker 与 ES 都吃内存，这也是不上 ES 的直接原因之一）。
前端：Vue3 + Vite（用户 Web + 管理后台同一工程按角色分流），小程序 uni-app；后端只提供 REST + WebSocket。
