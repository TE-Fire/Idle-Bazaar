## 一、本端定位：手机是「逛 + 聊 + 交割」的端

学生 90% 的时间在手机上，且二手交易的关键动作——**逛到、问清楚、约见面、当面验货、扫码签收**——都发生在移动端。

**一句话**：Web 端负责"把东西挂出去、把参数比清楚"，小程序负责"把这笔交易真正走完"。

| 本端独占 / 主承担 | 说明 | 对应业务 |
|---|---|---|
| 逛（无限流） | 第 3 秒内至少看到 4 件商品，不做搜索前置 | M-B1 |
| 即时沟通 | Carousell 的核心结论：二手平台的本质是"聊聊"，不是"上架" | M-B4 |
| 线下交割 | 面交导航、当面验货、扫码签收 | M-B6 |
| 学号认证 | 校园信任机制的主入口 | M-B7 |
| 发布（轻量） | 手机上补发一件、临时拍照上架 | M-B5 |

**明确不做的事**
- ❌ 不做多对象对比（屏幕放不下，且手机上人不做横评）
- ❌ 不做批量发布（打字与选图在手机上成本高，引导到 Web 端）
- ❌ 通知与私信不混在一个收件匣（Vinted 的真实可用性坑，见下）

## 三、核心业务流程

### F-M1 · 逛（首屏即内容）

```
打开小程序 → 系统 TabBar 默认首页
 → 首屏直接是双列瀑布流（搜索框吸顶但不抢占首屏）
 → 上滑：金刚区（10 个分类）→ 兴趣频道 chips → 无限流
 → 上拉加载更多；下拉刷新
 → 点卡片进 M2 详情
```

**判据**
- 首屏第 3 秒内可见 ≥4 件商品——先看到搜索框和分类金刚区即违反（`design/02` 原则 1）
- 图片占卡片 ≥60%，文字只留标题 + 价格 + 成色（`design/02` 原则 2）
- 瀑布流两列不等高是允许的，但同列内必须对齐
- 超过 100 条必须分页/虚拟列表，否则长列表卡顿

### F-M2 · 聊（本平台的心脏）

```
M2 详情页点「聊一聊」→ 进入会话（无会话则从首条消息创建）
 → 文字留言：询价 / 约时间 / 约地点，**订单金额一律按标价成交**——议价不是独立业务，没有报价/还价状态
 → 约定面交：文字沟通确定面交点与时间，下单时再选面交点
 → 消息页 = 私信号会话列表；系统通知与交易通知合并为「通知」列表（本期不区分私信红点，见 M-B10）
```

> 2026-10-22 降级决策：原「即时沟通（IM）」改为**同步询单留言**——WebSocket、图片消息、快捷短语卡片、三分区消息匣均不做，保留文字询价与纠纷取证文本。表与接口为升级实时预留（发送端点后续加推送通道即可），详见 01 决策表。

**判据（Vinted 教训的直接应用）**
- **系统通知与私信号分两个列表**：通知（审核结果 / 订单状态 / 系统公告）与私信（询单会话）不混在一个收件匣——否则用户要在"您的商品已售出"里捞对话
- 未读角标：私信红点 + 数字；通知只显示数字，不红点（避免抢注意力）。同步模式下未读数 = 拉取时对方发来的消息数，进入会话即清零
- 会话按最近消息时间倒序，交易中的会话可置顶
- 议价只是口头沟通，**订单金额一律按标价**；不设报价/还价状态（2026-09-26 决策）

### F-M3 · 发布（轻量版）

```
TabBar「＋」→ 选图（相册 / 拍照，≤9 张）
 → 表单：标题 / 分类 / 成色 / 价格 / 校区 / 面交点 / 描述
 → 支持「稍后补齐」：图片先存草稿，描述可空提交后补（但标题/价格/成色必填）
 → 提交 → 待审核 → 结果页
```

**判据**
- 移动端发布的定位是"临时补一件"，不是"批量出 20 本书"——发布页底部要有「需要一次发布多件？用电脑打开 Web 端」的引导
- 表单一屏不超过 5 个字段，其余收进「更多选项」
- 主图必选，否则无法提交（无图商品曝光极差）

### F-M4 · 交易与交割 ★移动端主导

```
M2 点「我想要」
 → 确认订单（面交点默认取卖家常用点，时间默认 3 天内）
 → 模拟支付 → 订单「待面交」
 → 到约定时间前：消息页推送提醒（提前 1 小时）
 → 面交现场：
     - 卖家/买家出示订单二维码（本端独占能力）
     - 对方扫码 → 双方核销 → 当场验货
     - 验货通过 → 买家点「确认收货」
     - 验货不通过 → 当场「取消并退款」，不计违约（面交当场拒收是合理场景，不应惩罚）
 → 确认收货 → 触发互评
```

**判据**
- **扫码核销是移动端独占**：Web 端没有摄像头场景，这一动作天然属于手机
- 面交当场拒收不计违约——这是线下交易相对快递的根本差异，规则上要照顾
- 待付款超时 30 分钟自动取消（与 Web 端一致）
- 面交提醒推送：提前 1 小时 + 约定时间到点各一次，不要更多（通知疲劳）

### F-M5 · 学号认证（校园信任的地基）

```
M6 我的 → 学号认证
 → 填写：姓名 / 学号 / 学院 / 校园邮箱（或学信网/一卡通截图）
 → 提交 → 状态「审核中」
 → 通过 → 商品卡与详情页出现认证标识；未通过 → 显示原因 + 重新提交入口
```

**判据**
- 认证是**可选但强激励**：未认证可发布，但搜索权重降权 + 卡片无标识
- 认证信息只在平台内展示为「已认证」布尔值 + 学院维度，**不公开展示学号**
- 一个学号只能绑定一个账号，重复绑定走人工审核

### F-M6 · 售后与举报

```
M8 订单详情「申请退款」/ M2 详情「举报」
 → 选原因 + 上传凭证（图片 ≤3）
 → 提交 → 可在「我的 → 我的工单」看进度
 → 处置完成 → 系统通知回执；不服可申诉一次
```

## 四、本端可见的状态

### 商品（买家视角优先）

| 状态 | 买家看到 | 卖家看到 |
|---|---|---|
| 在售 | 正常可拍 | 在售中，可编辑/下架 |
| ~~已预定~~ | **该状态已取消**（无预定机制） | 拍下只生成待付款订单，商品不锁定，先付款先得 |
| 已售出 | 「已售出」置灰 | 交易完成 |
| 已下架 | 不可访问 | 可重新上架 |
| 待审核 | 不可见 | 审核中 |
| 审核未过 | 不可见 | 看原因 → 改后重提 |

### 订单（与 Web 端一致，多一步核销）

```
待付款 ─超时/取消─> 已取消
   └─付款─> 待面交 ─扫码核销─> 已验货 ─确认收货─> 已完成 ─> 互评
                    └当面拒收─> 已退款（不计违约）
                    └单方取消─> 纠纷中（冻结）
```

### 认证状态

```
未认证 ─提交─> 审核中 ─> 已认证 / 未通过（可重提）
```

## 五、移动端独占能力清单（论文可用）

1. 无限瀑布流 + 下拉刷新 + 上拉加载（逛的主场）
2. IM：快捷议价卡、面交约定卡直接生成订单
3. 面交现场：订单二维码 + 扫码核销 + 当面验货
4. LBS 面交导航（跳转地图）
5. 手机号验证码登录 + 学号认证入口 + 资料编辑（昵称 / 头像，notes/20 D3）
6. 消息页：私信号会话列表 + 通知列表（同步留言，无实时推送）

> 论文句式参考：*二手交易的关键动作发生在移动场景（即时沟通、当面验货、扫码交割），因此小程序端承担交易主链路，Web 端承担发布与比价，二者按场景分工而非简单响应式适配。*

### 已决策的三项未决问题（2026-09-26）

| 问题 | 决策 | 落地与可扩展性 |
|---|---|---|
| 微信订阅消息 | **不接入** | 改为站内消息中心，三分区（私信 / 系统通知 / 交易通知），红点角标站内模拟。后续若申请到模板，服务端下发后在「系统通知」区同源展示，**UI 不改版** |
| 面交导航 / 第三方地图 | **不调起** | 地图区为静态校园示意图（楼栋 + 路网 + pin），保持「地图容器 + 导航按钮」组件拆分；后续把按钮换成 `wx.openLocation` 即可，版式与字段不变 |
| 社交模块（关注/动态/评论/海报） | **做，纯用户端增量**（2026-10-27 决策） | 评论权限放宽至登录用户均可；动态/评论发布即公开不预审，靠敏感词+举报；feed 先全广场；海报纯前端 canvas 合成不含码；不新增管理端权限点。设计见 notes/22 |
| 信用分对外可见性 | **只显示等级** | 对外呈现「信用高 / 中 / 低」+ 三格进度条，**不暴露分数**；分数仅管理端可见，用于搜索权重与人工审核判定（<60 分强制人工审核） |
1. M1 首页（双列瀑布流）★ 本端门面
2. M2 商品详情（底部操作条）
3. M5 消息（会话列表 + 聊天页，三分区）
4. M8 订单详情（状态时间轴 + 二维码）
5. M3 发布 / M6 我的 / M10 认证

**未决问题**
- 是否接入真实微信订阅消息？毕设无商户资质，大概率用「站内消息 + 前端模拟推送」替代
- 面交导航是否调起第三方地图？小程序需配置 `wx.openLocation`，毕设可只做静态示意图
- 信用分是否对外可见？建议只在个人主页显示等级（高/中/低），不暴露具体分数，减少攀比与刷分
