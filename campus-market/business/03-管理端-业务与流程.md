## 一、本端定位：管理端是「查 + 判 + 配」的端

用户是**平台运营 / 管理员**（不是学生）。核心诉求不是好看，是「一眼看出发生了什么」+「快速处置」。

| 动词 | 含义 | 对应业务 |
|---|---|---|
| 查 | 看板巡盘、数据下钻 | A-B1 |
| 判 | 审核商品、处理举报、复审申诉、介入纠纷 | A-B2 / A-B3 |
| 配 | 维护分类、成色、面交点、学院、校区 | A-B6 |

**明确不做的事**
- ❌ 不做移动端适配（使用者坐在办公桌前，这是合理取舍，写进论文）
- ❌ 不做发布商品、下单购买等 C 端业务（角色隔离）
- ❌ 不做"替用户改价改描述"（只能强制下架，不能代编辑，避免责任不清）

## 三、核心业务流程

### F-A0 · 注册（2026-09-29 决策新增）

```
/register → 邮箱（仅 @qq.com / @foxmail.com）+ 邮箱验证码 + 密码 + 图形验证码
 → 写 admin_user：status=2 待分配角色、role_id=0（占位，无权限）
 → 提示「已提交，待超级管理员分配角色后可登录」
```

**判据**

- 邮箱验证码 6 位数字，**10 分钟有效、一次性**（校验通过即删）；60 秒内同一邮箱只能发一次
- 一个邮箱只能注册一次（`uk_email`）
- **超级管理员不开放注册**：SUPER 只能由开发者经种子数据创建（`AdminAccountInitializer`），
  注册接口**不接受 roleId 参数**——否则任何人都能给自己审核权
- 注册后是「待分配」态，**登录会被拦下**（见 F-A1），由超级管理员在 A9 分配角色后才可登录

### F-A1 · 登录与鉴权

```
/login → 账号 + 密码 + 图形验证码
 → 校验角色：超级管理员 / 审核员 / 运营 / 只读
 → 按角色过滤菜单与操作按钮（前端隐藏 + 后端校验）
 → 进入 /dashboard
```

**补两条（2026-09-29 决策）**

1. 图形验证码在**登录、注册、找回密码**三处都要（防机器人爆破/刷验证码），
   本地联调可用 `campus.captcha.enabled=false` 关掉。
2. `status=2`（待分配角色）的账号**允许查库但拒绝登录**，提示「账号待分配角色，请联系超级管理员」；
   与 `status=0`（停用）区分开——前者是还没分配，后者是被停用。

**权限点矩阵**（2026-09-26 决策：毕设中真实实现，非静态示意）

| 权限点 | 超级管理员 | 审核员 | 运营 | 只读 |
|---|---|---|---|---|
| `dashboard.view` / `report.view` | ✓ | ✓ | ✓ | ✓ |
| `item.view` | ✓ | ✓ | ✓ | ✓ |
| `item.offline` | ✓ | — | ✓ | — |
| `item.delete` | ✓ | — | — | — |
| `user.view` | ✓ | — | ✓ | ✓ |
| `user.verify` | ✓ | — | ✓ | — |
| `user.ban` | ✓ | — | — | — |
| `review.view`（进审核队列页，只读） | ✓ | ✓ | ✓ | ✓ |
| `review.judge` / `review.forceoff` / `review.appeal` | ✓ | ✓ | — | — |
| `order.refund` / `order.arbitrate` | ✓ | — | ✓ | — |
| `content.edit`（字典增删改查） | ✓ | — | — | — |
| `settings.edit` | ✓ | — | — | — |
| `log.view` | ✓ | — | ✓ | — |

**判据**：角色最小划分为 4 类；审核员**不能**碰用户封禁与系统设置（关键互斥：`review.judge` 与 `user.ban` 分属不同角色）；所有写操作必须记操作日志（流程见 F-A11）。
前端按矩阵渲染菜单与按钮只是体验层，**后端必须用同一张矩阵对每个写接口做校验**，两者缺一不可——前端隐藏不是安全边界。

### F-A10 · 找回密码（2026-09-29 决策新增）

```
/login → 「忘记密码」 → /forgot
 ① 邮箱（注册时用的）+ 图形验证码 → 下发 6 位数字到邮箱（10 分钟有效）
 ② 填验证码 + 新密码 → 重算 bcrypt 哈希，清零 fail_count / lock_until
 → 跳回 /login
```

**判据**

- 验证码一次性、10 分钟失效、**60 秒内同一邮箱只能发一次**（防刷短信/邮件轰炸）
- **不泄露账号是否存在**：邮箱未注册时也返回「已发送，请查收」——
  否则这个接口就变成「枚举管理员邮箱」的工具
- 重置成功后**强制下线该账号的所有会话**（Sa-Token kickout），防止旧会话继续操作
- 新密码不得与旧密码相同（bcrypt `matches` 校验），避免"重置"了个寂寞

### F-A2 · 商品审核（每日最大工作量）

```
A5 审核队列 → 按权重排序取最上面一条（见下方权重公式）
 → 判读四项：
    ① 图片（是否网图、是否含联系方式二维码、是否违规）
    ② 标题/描述（是否含校外引流、是否涉违禁品）
    ③ 价格（是否异常低价/高价，触发价格异常预警）
    ④ 分类与成色（是否错配）
 → 处置：
    ├─ 通过 → 商品「在售」，通知卖家
    ├─ 驳回 → 选预设原因（图片不实/违禁品/引流/分类错配/其他）+ 可补充文字 → 通知卖家可改后重提
    └─ 直接下架 + 记违规 → 商品「已强制下架」，卖家信用扣分
 → 支持连续审核：处置后自动跳下一条（键盘 J/K 或按钮），这是效率关键
```

**审核队列权重公式**（建议，可直接写进论文）

```
优先级分 = 举报次数 × 3
          + 图片风险分        // 违禁图识别给的是 0–100，ROUND(÷10) 归一化为 0–10
          + 卖家信用扣减分     // (100 − 信用分) / 10
          + 价格异常分         // 偏离同类目均价 3 倍以上 = 5 分
          + 等待时长补偿       // 等待每满 12 小时 +1，防止老单永远沉底
```

> **2026-10-06 勘误**：图片风险项原写「× 2」，与注释「归一化为 0–10」自相矛盾（0–100 ÷10 再 ×2 是 0–20）。
> 已落地的实现是前端 `calcWeight`（`packages/shared/src/admin.ts`）与后端 `ReviewAdminService`，
> 两边都取 **0–10**，以代码为准，这里去掉了那个多余的「× 2」。
> 另外最后一项是**加分补偿**不是减分衰减，原式写成「− 等待时长衰减补偿」也是笔误，已改为「+」。

**判据**
- 队列必须**按权重排序**，不能按时间——按时间等于让风险最高的单子排在后面
- 单人单条平均处置时间目标 ≤30 秒：所以详情用 Drawer 而非跳转新页
- 处置动作必须留痕（谁、何时、依据、结果），申诉时要能复盘

### F-A3 · 举报处理

```
收到举报（来自 C 端）→ 进入举报队列（并入 A5，按 F-A2 权重排序）
 → 受理：看举报原因 + 双方凭证（聊天记录片段 + 图片）
 → 裁决：
    ├─ 不成立 → 驳回举报，通知举报人（附一句理由）
    ├─ 成立-轻 → 警告卖家 + 商品下架整改
    └─ 成立-重 → 强制下架 + 扣分 + 情节严重封禁账号
 → 通知双方（举报人看结果，被举报人看理由）
 → 被处置方可申诉一次 → F-A4
```

### F-A4 · 申诉复审

```
卖家/买家提交申诉（附新凭证）→ 进入申诉队列（优先级高于普通审核）
 → 换人复审原则：原处置人不得复审自己的单（若有第二个管理员账号则强制；单人毕设演示可标注该规则）
 → 复审结果：维持 / 撤销（恢复商品 + 撤销扣分）
 → 通知双方，申诉结果终局
```

### F-A5 · 学号认证审核

```
A4 用户管理 → 认证审核页
 → 核对：姓名 / 学号 / 学院 与校园邮箱或一卡通截图是否一致
 → 通过 → 用户「已认证」；不通过 → 填原因，用户可重提
 → 一学号多账号 → 转人工，标记异常
```

**判据**：认证审核是**低频但高责任**的动作，误通过会破坏整个校园信任机制，因此不做批量通过。

### F-A6 · 纠纷介入

```
订单进入「纠纷中」→ A6 订单管理 → 纠纷 Tab
 → 看：订单信息 + 商品快照（下单时的价格/成色/描述）+ 双方凭证（买家退款理由 / 卖家拒绝备注）
 → 裁决：退款买家 / 放款卖家（二选一）
 → 执行：订单转终态（已退款 / 已完成），记 OpLog（module=order, type=DISPUTE_JUDGE）
```

**判据**：必须看**商品快照**而非当前商品——卖家可能事后改价改描述，这是取证的关键设计点。

**本期口径（2026-10-22 收窄）**：① 裁决只做「全额退买家 / 全额放卖家」二选一，**不做部分退**——库里订单终态只有已退款/已完成，没有部分退状态，学生端也无对应流程，写了无法落库；② 原设计的「聊天记录」取证本期以「双方凭证」替代：IM 未实现（见 01/02 同步询单决策），纠纷可见的是买家退款申请理由与卖家拒绝备注两条文本；③ 强制退款由管理端对「退款中(6)/纠纷中(8)」订单发起，退款后商品恢复在售并清除占位标记，与学生端同意退款同一套恢复逻辑；④ 信用分变动本期不落 `credit_log`（决策见 notes/13），OpLog 留痕即审计依据。

### A6 订单管理 · 流程与状态流转（A-B7 展开）

```
订单列表（筛选：状态 / 纠纷 Tab / 买卖双方 / 时间）
 → 详情：订单信息 + 商品快照 + 双方凭证 + 状态时间轴
 → 两个处置入口：
    ① 强制退款（仅退款中 / 纠纷中）→ 已退款(7)，商品恢复在售(3)
    ② 纠纷裁决（仅纠纷中）→ 已退款(7) / 已完成(4)
```

管理端可做的状态迁移（学生端接口之上的增量，不重复学生端已有的取消/退款路径）：

| 订单当前状态 | 强制退款 | 纠纷裁决 | 说明 |
|---|---|---|---|
| 待付款(1) | — | — | 超时由系统自动取消，不人工介入 |
| 待面交(2) | — | — | 交易进行中，无管理端介入点 |
| 已验货(3) | — | — | 面交扫码后的独立中间态 |
| 已完成(4) | — | — | 终态 |
| 退款中(6) | ✅ | — | 卖家超时未响应时管理端代为处置 |
| 纠纷中(8) | ✅ | ✅ | 强制退款与裁决等效（都转已退款） |
| 已取消(5)/已退款(7) | — | — | 终态 |

**判据**：管理端只碰「退款中 / 纠纷中」两个需要人工的悬置态，其余状态要么系统自动（待付款超时）、要么终态，不给管理员直接改订单状态的能力——状态机能被人工任意跳转是审计上的灾难。

### F-A7 · 内容配置

```
A7 内容管理 → 四个可维护字典：
 ① 分类树（两级：教材教辅 / 数码电子 / 生活用品 / 服饰鞋包 / 运动户外 / 图书笔记 / 乐器 / 其他）
 ② 成色等级 A–D（文案 + 颜色，全端共用，不允许前端写死）
 ③ 面交点（名称 + 所属校区 + 开放时段 + 是否启用）
 ④ 学院 / 校区列表
```

**判据**：这四张字典是**全端一致性的源头**，必须由后台下发，三端不得本地硬编码。

**权限（2026-09-30 决策）**：字典的增删改查**只开放给超级管理员**（`content.edit` 已从运营角色移除）。
理由是字典一动会同时影响三端的展示与筛选（改一个分类名，在售商品、报表、C 端筛选全跟着变），
属于"高风险、低频次"操作，不给运营；运营要查字典走商品/用户页的下拉即可，不需要进这一页。
成色等级的**颜色**由后台随字典下发（`dict_grade.color`），前端不写死色值。

### F-A9 · 审核时效 SLA（2026-09-26 决策：纳入实现）

```
指标分两级，不可混用：
  ① 响应时效（对卖家的承诺）
     首审响应 ≤ 2 小时 → 达标
     P95 首审时长 ≤ 6 小时
     整体达标率 ≥ 95%
     超 24 小时未处置 → 积压红牌，需当日清零
  ② 操作效率（对审核员的要求）
     单条平均处置 ≤ 30 秒（因此详情用 Drawer，不跳转新页）
 → 采集：进入队列时间戳、首次处置时间戳、处置人
 → 呈现：看板 SLA 卡 / 审核队列「等待时长」列（标临期与超时）/ 报表分审核员明细
 → 阈值可在「系统设置 · SLA 配置」调整
```

**判据**
- 响应时效与操作效率是两个层级：前者是平台对用户的承诺，后者是人机效率。论文中分开陈述，避免被质疑口径不清
- SLA 必须落到**操作层**才有意义——审核队列直接标出该先处理谁，否则只是好看的数字
- 申诉另行承诺 48 小时内给出复审结论（比商品审核宽松，因为涉及双方举证）

### F-A11 · 操作日志（2026-10-01：由判据升级为流程）

```
原则：管理端所有写操作必须留痕（见第二节判据），这里把它落成可执行的清单。

记什么（五类业务动作，复用同一张 sys_operation_log，用 type 区分）
 ① 商品审核：通过 / 驳回 / 强制下架        module=review  type=APPROVE/REJECT/FORCE_OFFLINE
 ② 举报处置、申诉裁决                       module=review  type=REPORT_* / APPEAL_*
 ③ 用户处置：封禁 / 解封 / 认证通过 / 驳回  module=user    type=BAN/UNBAN/VERIFY_PASS/VERIFY_REJECT
 ④ 订单介入：退款裁决、纠纷判定              module=order   type=REFUND_JUDGE/DISPUTE_JUDGE
 ⑤ 系统配置：字典变更、SLA 阈值、敏感词、管理员角色分配   module=system

不记什么（边界）
 - 读操作：全量 HTTP 日志是噪音，走访问日志（tech/01 §5.4 左列）
 - 登录 / 登出 / 改自己密码：属账号安全事件，归 F-A1
 - 落库失败不阻断主流程：异步写，降级为 ERROR 日志

字段口径
 - 操作人：admin_id 取 AdminContext#getAdminId()（core/context，懒加载回退 sa-token）
 - admin_name / role_code 冗余存：删号后仍查得到是谁做的（db/01 §5.4）
 - IP / UA / traceId 直接取 RequestContext（AccessLogFilter 已备好），不重复解析
 - 变更前后值：审核、封禁、改价必须开 saveDiff=true，入库前脱敏（手机号 / 学号）
 - 失败也要记：result=FAIL + error_code，"谁反复失败、谁尝试越权"这条线索不能断

实现（注解 / AOP / 事务提交后异步落库）见 tech/01 §5.4，此处不重复
```

**判据**

- 与访问日志是**分工而非替代**：访问日志由 Filter 无差别记录所有请求（排查用），操作日志由 `@OpLog` 只记有业务语义的动作（追责用）。少任何一个，另一个都补不上
- 只追加、不可删改：这是审计表，A9 页面只读；管理员被删号后靠冗余的姓名/角色仍能还原
- **先有业务动作，再挂注解**：`@OpLog` 是贴在已有方法上的，`type` 枚举应由实际业务动作归纳出来。业务方法没定型前先造枚举，等业务一变就得返工
- 审核留痕、举报处置、申诉裁决复用同一张表，申诉复审时可按 `biz_id` 拉出完整时间线

## 四、全平台状态机（本端为权威定义）

### 4.1 商品

```
草稿 ─提交─> 待审核 ─通过─> 在售 ─买家付款─> 已售出（终态）
                    │        │
                    │        └─卖家下架─> 已下架 ─重新上架─> 在售
                    └─驳回─> 审核未过 ─改后重提─> 待审核
任意在售态 ─平台处置─> 已强制下架 ─申诉成功─> 在售
```

> **无「已预定」状态**（2026-09-26 决策）：拍下只生成待付款订单，商品不锁定、先付款先得；付款成功才转「已售出」，其余待付款订单自动取消并通知。以付款为唯一占位判据。

终态：`已售出` / `已强制下架`（申诉期满）。

### 4.2 订单

```
待付款 ─30min超时─> 已取消
   └─付款─> 待面交 ─核销+验货通过─> 已完成 ─> 互评（终态）
                    ├当面拒收─> 已退款（不计违约）
                    ├双方协商取消─> 退款中 ─> 已退款
                    └任一方发起─> 纠纷中 ─裁决─> 已完成 / 已退款（终态）
```

### 4.3 审核 / 举报 / 申诉

```
待审核 ─> 已通过 / 已驳回 / 已强制下架
举报：待受理 ─> 处理中 ─> 已处理（成立/不成立）
申诉：待复审 ─> 维持 / 撤销（终态，不可再申诉）
```

### 4.4 用户认证与账号

```
认证：未认证 ─> 审核中 ─> 已认证 / 未通过（可重提）
账号：正常 ─> 警告 ─> 封禁（可解封）
```

**管理员账号（admin_user.status，2026-09-29 补）**

| status | 含义 | 能否登录 | 谁来改 |
|---|---|---|---|
| 0 | 停用 | ✗ | 超级管理员 |
| 1 | 启用 | ✓（锁定期内除外） | 超级管理员 |
| 2 | **待分配角色** | ✗（提示联系超管） | 注册产生；超级管理员分配角色后转 1 |

> 锁定期不占 status，用 `lock_until` 字段表达（连续失败 5 次锁 10 分钟，见 F-A1）。

### 4.5 信用分（建议口径）

初始 100 分。交易完成 +1（上限 120）；违约单方取消 −5；被举报成立 −10；强制下架 −15；封禁清零至 0。
信用分影响：**搜索权重**（不直接禁止发布），低于 60 分强制人工审核其每一件商品。

| 问题 | 决策 |
|---|---|
| 谁能成为超级管理员 | **只有开发者能造**。SUPER 由种子数据（`AdminAccountInitializer`）创建，注册接口不接受 roleId，杜绝"注册即超管" |

| 图形验证码覆盖范围 | 登录 / 注册 / 找回密码**三处都要**，共用同一套下发与校验接口（Redis 存 key，一次性） |

**已决（2026-09-26）**

| 问题 | 决策 |
|---|---|
| 权限隔离 | **真实实现**。以「权限点」为最小粒度（16 个），四种角色持不同子集；前端按 `data-perm` 渲染菜单与按钮（无权限菜单不渲染、按钮置灰加锁），后端用同一张矩阵做接口鉴权。前端隐藏仅为体验层，不是安全边界 |
| 审核时效 SLA | **要做**，且分两级：响应时效（首审 ≤ 2h 达标、P95 ≤ 6h、达标率 ≥ 95%、超 24h 记积压红牌）+ 操作效率（单条平均处置 ≤ 30s）。两者层级不同，不可混用。落地：看板 SLA 卡、审核队列「等待时长」列标临期/超时、报表分审核员明细、设置页可调阈值 |
| 减碳系数 | **明确标注为估算假设**，非实测。报表内嵌警告条 + 「系数与假设」弹窗（系数表 + 计算公式 + 三条已知局限 + 改进方向）。论文中须原样标注，不得作为精确结论 |

**权限矩阵要点**：`review.judge`（裁决商品）与 `user.ban`（封禁账号）互斥——能判商品的人不能封人；只读角色用于答辩巡盘，能看全部数据、不能做写操作。
