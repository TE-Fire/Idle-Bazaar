## 一、本端定位：桌面是「发布 + 比价」的端

学生在 Web 端做的事和手机上不是同一件。**Web 端不负责"逛"，负责"出"和"选"。**

| 桌面能、手机不能 | 说明 | 对应业务 |
|---|---|---|
| 批量发布 | 拖拽多图 + 排序 + 右侧实时预览 + 键盘提交 | W-B4 |
| 多对象对比 | 最多 4 件横评参数 | W-B3 |
| 常驻筛选 + 悬停预览 | 一次看到全部筛选条件与组合结果 | W-B1 |
| 双视图（网格/列表） | 看图选网格，比参数选列表 | W-B1 |

**明确不做的事（划清边界，别把 Web 做成万能端）**：

- ❌ 不做线下场景：面交导航、当面验货、扫码签收归移动端
- ❌ 不做即时沟通的主战场：Web 聊天是辅助（打字方便时），询单留言为同步模式，无实时推送（2026-10-22 决策）
- ❌ 不做真实支付：全端统一为「模拟支付 + 线下交付」（个人主体申请不到微信支付商户资质）

## 三、核心业务流程

### F-W1 · 找货（检索闭环）

```
进入首页
 ├─ 分类条选类目 ──────────┐
 ├─ 顶栏搜索关键词 ────────┤
 └─ 直接浏览推荐 ──────────┤
                          ▼
              左侧常驻筛选（可叠加）
              分类树 / 价格区间 / 成色 A-D（复选）/ 校区 / 仅看认证卖家 / 发布时间
                          ▼
              已选条件在顶部以 chip 回显（可单个删除 / 一键清空）
                          ▼
              工具条：共 N 件 · 排序（默认/价格/时间/热度）· 网格⇄列表
                          ▼
              浏览结果 → 悬停看第二张图 → 进详情（F-W2）
```

**判据**
- 桌面一屏至少 12 件，宁挤不空（`design/01` 原则 3）
- 筛选是"与"逻辑（AND），成色多选取"或"（OR）——这是例外，需在 UI 上写清「成色任选其一」
- 结果为空时给「放宽条件的建议」（去掉校区 / 扩大价格区间），不要只显示"暂无数据"

### F-W2 · 比价决策（对比闭环）★桌面独占

```
浏览中把商品加入对比（卡片 hover 浮出「＋对比」）
   → 选中 ≥1 件时底部对比条滑入（56px，4 槽位）
   → 已选 2–4 件时可点「开始对比」
   → 进入 P4 对比页：参数横评表
        对比维度：价格 / 原价 / 成色 / 校区 / 面交点 / 卖家信用等级 / 发布时间 / 商品标签
        （议价不是独立业务，不进入对比维度）
        （差异项高亮，相同项弱化）
   → 决策：下单 / 收藏 / 移除某件 / 继续加
```

**判据**
- 上限 4 件：超过 4 件人的短时记忆比较不过来
- **只允许同类目对比**：跨类目（教材 vs 相机）参数无可比性，点第 2 件时若类目不同，提示「对比需同一分类」而非静默失败
- 对比条可收起但不清空选择（用 checkbox 控制显隐），收起后角标显示已选数量
- 卖家本人不能对比自己的商品
- 已售出/已下架的商品在对比条中被标灰，不占用槽位计数

### F-W3 · 批量发布 ★本端最大价值

```
进入 /publish
 ① 图片区：拖拽 / 点击选择，≤9 张
      - 拖拽进入时整块区域高亮（dashed 黄边）
      - 首张默认为主图，可拖拽改序、可删
      - 上传中该图位显示占位；失败即移除该图位并提示原因，可重新选图（不做单张重试按钮，重选即重试）
 ② 智能填充：上传后可给「分类猜测 / 成色建议」，由用户确认，不自动写死
 ③ 表单区：标题 / 分类 / 成色 A-D / 价格 + 原价 / 校区 / 面交点 / 描述 / 是否可议价 / 是否包配送
 ④ 右侧实时预览：按 P1 卡片与 P2 详情页的真实版式渲染（所见即所得）
 ⑤ 提交：
      - Ctrl+Enter 或点「发布」
      - 前端校验：9 图以内、标题 5–50 字、价格 > 0、必填项齐全
      - 提交后 → 商品进入「待审核」→ 跳结果页（预计 X 小时内完成审核 + 「再发一件」）
 ⑥ 暂存草稿：离开页面时若已填内容，提示保存草稿（本地 + 云端）
```

**判据**
- 提交即送审，**不直接上架**（校园实名制下，先审后发是平台信任机制的一部分）
- **暂存草稿**（`draft = true`）：落「草稿」态、不进审核队列；图片与描述可后补（含 D 档豁免描述必填），但标题/分类/成色/价格/校区仍必填——`item` 表这些列 NOT NULL，草稿同样要落库。草稿在「我的商品」里继续编辑或送审（送审 = 编辑时 `draft` 为空/false）
- **学生端删除自己的商品**：仅「草稿 / 已下架 / 审核未过」可删（软删，图片一并软删）；「已强制下架」不可删——申诉撤销要把商品恢复在售，商品没了恢复就失去落点，只能等平台处置
- 重新编辑已发布商品：改图/改价/改描述 → 若改动价格或成色，回「待审核」；只改描述可免审
- **成色 D 描述必填**，A/B/C 不要求：前三档买家有稳定预期，D「明显使用痕迹」具体显现在哪只能由描述承载；「D + 空描述」是「成色描述不符」纠纷的标准形态，而纠纷介入时按下单时的成色与描述取证（`business/03` F-A6）。发布与编辑两个入口都校验——改描述免审、改成色虽回待审核但重审不查这条，只堵一个入口会留下绕过路径
- 发布页是 Web 端唯一"必须做"的页面——不做，本端就没有存在理由（`design/01` 第五章）

### F-W4 · 交易推进

```
P2 详情页点「我想要」
 → 确认订单：面交点（下拉，默认卖家常用点）+ 面交时间（默认 3 天内）+ 备注
 → 提交 → 订单「待付款」（**商品不锁定，先付款先得**）
 → 模拟支付（本平台不走真实资金流，点「确认付款」即完成）
 → 订单「待面交」，双方可见面交点与时间
 → 线下见面（这一步发生在手机端/线下，Web 只做状态展示与备注补充）
 → 买家确认收货 → 订单「已完成」→ 触发互评（F-W5 评价）
```

**判据**
- 待付款超时 **30 分钟**自动取消（校园交易节奏快，超时不宜过长）
- **无预定机制**：付款前商品仍在售、可被他人拍下；付款成功才转「已售出」，其余待付款订单自动取消并通知。以付款为唯一占位判据
- 议价**不是独立业务**：聊天里口头问价即可，订单金额一律按标价成交
- 订单一旦「待面交」，取消需双方确认；单方取消记一次违约（影响信用分）
- Web 端不做"面交导航/扫码签收"，页面只提示「请在移动端查看导航与扫码」

### F-W5 · 售后与纠纷

```
已完成前发现问题
 → 买家「申请退款」（待付款 / 待面交阶段均可）
     ├─ 卖家同意 → 直接取消/退款，无违规记录
     ├─ 卖家 24h 未响应 → 系统自动同意
     └─ 卖家拒绝 → 进入「纠纷中」→ 转管理端 E 流程介入
 → 交易后发现问题（货不对板）→ 举报商品/卖家（转管理端 F 流程）
 → 对处置结果不服 → 申诉（转管理端 F4 复审）
```

**判据**
- 纠纷一旦进入，订单冻结，双方均不能再操作，直到裁决
- Web 端只提供"发起 + 查看进度 + 补充凭证"，裁决权全在管理端

### F-W6 · 登录（验证码登录 / 密码登录）

```
访问需登录的写操作（发布 / 编辑 / 我的商品 / 下单）
 → 请求被 1001 拦下 → 跳登录页（带 redirect，登录后回原页）
 → 选「验证码登录」：填手机号或 QQ 邮箱 → 获取验证码（60 秒一条）→ 填 6 位 → 登录
   选「密码登录」：填手机号或 QQ 邮箱 → 填密码 → 登录
 → 建立会话（token satoken-user，7 天），顶栏显示昵称与「我的商品」入口
```

**判据**
- 账号一律「手机号或 QQ 邮箱」，渠道由账号形态决定（手机号走短信、邮箱走邮件），前端不做第二种判断
- 验证码登录与密码登录并存：老账号从没设过密码，走「找回密码」设一个即可，不给密码登录就没人能进
- 验证码统一口径：6 位、10 分钟有效、一次性、同场景 60 秒节流、连续错 5 次作废（详见 notes/26）
- 密码登录错误分三种提示：密码不对 4037、账号没设密码 4038（提示改用验证码或找回）、错 5 次锁 10 分钟 4039
- 演示期短信与邮件都不真发，验证码随发码响应回显；上线前关掉两个 echo 开关即为生产形态
- 账号未注册 → 明确提示「未注册」（学生端不防枚举）；账号封禁 → 4001
- 登录态持久化在本地（刷新不丢）；退出登录清本地会话并回首页

### F-W6a · 注册（QQ 邮箱验证码）

```
登录页「注册账号」→ 填手机号、QQ 邮箱 → 获取验证码（发到邮箱）
 → 填邮箱验证码、昵称、密码、确认密码 → 勾选协议 → 注册
 → 后端直接下发令牌，注册即登录，回首页
```

**判据**
- 只验邮箱验证码：短信是演示假码，验它没有安全增益；手机号只做格式（`1[3-9]` 开头 11 位）与唯一性校验
- 邮箱限 QQ 系（`@qq.com` / `@foxmail.com`），大小写与首尾空格归一后再判重
- 昵称 2–16 字、密码 8–32 位且不含空格；前端先拦一遍是为了让用户提交前就看到问题，后端仍全量重校验
- 唯一性判断在验码之前：填了已注册的手机号 / 邮箱立刻提示（4036 / 4008），不必先等一条验证码
- 注册成功即登录：刚验完邮箱再让用户输一次验证码没有意义

### F-W6b · 找回密码（手机号或 QQ 邮箱）

```
登录页「忘记密码」→ 填手机号或 QQ 邮箱 → 获取验证码（按账号形态走短信 / 邮件）
 → 填验证码 + 新密码 + 确认 → 提交
 → 该账号所有会话下线 → 回登录页（账号已预填）
```

**判据**
- 两种渠道都通：注册只验邮箱，但手机号通常是记得的那个，只留一条路会把人卡死
- 「新密码不能与旧密码相同」在校验验证码之前：否则用户输个重复密码就把码用掉了，还得再等 60 秒
- 改密后强制下线该账号所有会话——可能已被盗用的旧会话必须失效，所以前端不能「改完继续用」，只能回登录页重登
- 账号未注册按渠道分别提示：手机号 4015、邮箱 4035

### F-W7 · 资料编辑（昵称与头像）

```
顶栏头像 / 昵称区 → 编辑入口（弹层）→ 改昵称 / 换头像（先上传拿 URL 再提交）
 → 保存 → 顶栏与「我的」即时换新；商品列表 / 详情里的卖家昵称同步换新
```

**判据**
- 可改字段白名单只有昵称和头像：手机号是登录标识，实名 / 学号走认证流程，信用分与账号状态归系统与管理端（notes/20 §四）
- 局部更新：只传要改的字段，不传不动；昵称去空格后 1–64 字符，头像为上传通道返回的 URL（≤255 字符）
- 头像为空回退昵称首字占位，图片加载失败同样回退，不显示破图
- 改昵称必须立即可见于商品列表与详情的卖家回填——公开资料缓存随写失效，不等 TTL

### F-W8 · 社交（关注 / 动态 / 评论 / 海报）★新增

社交四块是交易核心之上的增量（notes/22 定稿，本期未实现）：

```
个人主页（P9 /user/:id）
 ├─ 关注按钮 ──────────────┐
 ├─ Tab：动态 / 关注 / 粉丝 ─┤
 │   动态：发状态、分享商品、点赞、评论
 │   关注/粉丝：列表互看，按钮态切换
商品详情（P2 /item/:id）
 └─ 底部评论区 ─────────────┘ 登录用户均可评，仅 status=3 在售可评
任意商品/动态页
 └─ 分享 → 前端 canvas 合成海报（主图+标题+价格+水印），调系统分享
```

**判据**
- 评论权限放宽至**登录用户均可**，不限买家（与购后星级互评 `user_review` 区分：后者一单一评、走订单闭环）
- 动态/评论**发布即公开**，不进预审；合规靠 `sys_sensitive_word` 过滤 + `report` 举报后人工
- 动态信息流先只做**全广场时间流**，关注流二期
- 海报**纯前端合成、不含二维码**，后端零改动

## 四、本端可见的状态

### 商品（卖家视角）

| 状态 | 含义 | 本端可做 |
|---|---|---|
| 草稿 | 未提交 | 继续编辑（续存 / 送审）/ 删除 |
| 待审核 | 已提交 | 只能看，不能改关键字段 |
| 在售 | 审核通过 | 编辑 / 下架 / 置顶（若开放） |
| ~~已预定~~ | **该状态已取消**（无预定机制） | 拍下不锁货，付款才占位 |
| 已售出 | 交易完成 | 查看订单 / 评价 |
| 已下架 | 卖家主动下架 | 重新上架 / 编辑 / 删除 |
| 审核未过 | 驳回 | 看驳回原因 → 修改后重提 / 删除 |
| 已强制下架 | 平台处置 | 申诉 |

### 订单

```
待付款 ──30min超时──> 已取消
   │
   └─付款─> 待面交 ──扫码核销─> 已验货 ──买家确认收货─> 已完成 ─> 互评
              │                                        
              ├─付款前取消────────────────────> 已取消
              ├─已付款后退款申请──────────────> 退款中 ─> 已退款
              └─任一方发起纠纷────────────────> 纠纷中（冻结，转管理端）
```

> 「已验货」是面交现场扫码核销的中间态（`trade_order.status = 3`），
> 扫码动作发生在移动端，Web 端只展示二维码与核销状态。完整口径见 `notes/13` 第二节。

订单终态：`已完成` / `已取消` / `已退款` / `纠纷已裁决`。

### 已决策的三项未决问题（2026-09-26）

| 问题 | 决策 | 落地方式 |
|---|---|---|
| 议价是否作为独立业务 | **不作为** | 「可议价」降级为商品展示标签（卖家勾选），口头议价发生在聊天里；不做报价/还价流程与状态，订单金额一律按标价成交；对比维度与筛选条件均不出现议价 |
| 是否需要预定机制 | **不需要** | 取消商品「已预定」状态。拍下生成待付款订单（30 分钟超时取消），付款前商品不锁定、先付款先得；付款成功才转「已售出」，其余待付款订单自动取消并通知 |
| 是否开放置顶 / 推广 | **不做** | 商品管理只保留编辑 / 下架 / 删除；排序靠校区、成色、时间、信用权重，不引入商业化曝光位 |
| IM 是否做实时推送 | **不做**（2026-10-22 决策） | 降级为同步询单留言：一张 `chat_message` 表 + REST 发送/拉取，进入会话拉取即已读，无 WebSocket、无图片消息、无快捷短语卡片；消息按商品挂会话（买家询价、卖家回复），约定面交以文本沟通。2026-10-26 补充：会话窗顶部**商品信息卡片**已做（数据随会话列表与跳转参数下发，用户级开关默认开），它展示商品现状而非消息类型，不改变「无图片消息」的口径。小程序端同样口径（见 02 M-B4）。理由：① 实时推送的基础设施（WS + 未读推送）与订单链路前端抢工期，交易闭环才是核心叙事；② 同步留言保住了「聊聊」的询价场景与纠纷取证的文本痕迹；③ 后续要升级实时，只需在发送端点加推送通道，表与接口不变 |
| 社交模块（关注/动态/评论/海报） | **做，纯用户端增量**（2026-10-27 决策） | 评论权限放宽至登录用户均可；动态/评论发布即公开不预审，靠敏感词+举报；feed 先全广场；海报纯前端不含码；不新增管理端权限点。设计见 notes/22 |
