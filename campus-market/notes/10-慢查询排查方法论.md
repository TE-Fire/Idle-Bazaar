# 慢查询排查方法论

> 对应代码：`ItemAdminService.list()` / `ItemMapper.avgPriceByCategory()`，结论见 `notes/08` 附录 A.2。
> 起因：管理端商品列表在数据量上来后单次约 1s，首次登录约 5s。下面是我实际走的那一套流程，
> 不是"看到慢就加索引"。换任何一条慢 SQL 都能照着走。

---

## 零、四条原则（先立规矩，再动手）

1. **不看估算，只看实测。** 优化器给的是 `cost`，那是它基于统计信息的猜测。本篇实测里它猜反过至少两次。
2. **小数据量下测不出问题。** 本项目真实表只有 60 行，那时全表扫是最优解，加什么索引都不会被选中。
   想验证索引收益，先把数据放大到有区分度的量级。
3. **一次只改一个变量。** 加索引、加缓存、改 SQL 不要混在一起做，否则不知道是谁起的作用。
4. **加索引是全局变量。** 它不只影响你关心的那条 SQL，会改变优化器对**所有**查询的选择。
   所以加完必须把之前测过的所有变体重跑一遍做回归。

---

## 一、定位：先把"慢在哪"量出来

### 1.1 从一个模糊症状到具体的 SQL

用户说的是"列表 1s，首次登录 5s"，这不是可执行的信息。要拆成两件事：

- **一次请求到底发了几条 SQL？**
- **每条各花多少？**

本项目一次列表请求固定 **6 条 SQL**（分页 count + 主表数据 + 用户 + 举报数 + 审核记录 + 分类均价，
见 `notes/08` 附录 A.2）。数 SQL 的办法按代价从低到高：

| 手段 | 做法 | 适用 |
|---|---|---|
| 读代码 | 顺着 Service 走一遍，数 `xxxMapper.` 调用 | 最快，且能顺手发现 N+1 |
| MyBatis 日志 | 改日志级别打 SQL | 要看实际参数时 |
| MySQL `general_log` | `SET GLOBAL general_log=ON` | 不确定 ORM 发了什么时，**测完记得关** |

**别只盯着主查询。** "首次 5s"往往不是某一条 SQL 慢 5 秒，而是「多条 SQL 串联 + 冷启动」叠出来的。

### 1.2 冷态 vs 热态：差价能到 30 倍

这是最容易得出错误结论的地方。

- **冷**：InnoDB buffer pool 里没有这些页（要读磁盘）、执行计划还没缓存、JIT 没预热。
- **热**：稳定态，数据页都在内存里。

实测对照（同一条 SQL，`item_perf` 10 万行）：

| 场景 | 只选状态（加索引前） | 只选状态（加索引后） |
|---|---|---|
| 第一遍 | **19.6ms** | — |
| 第二遍 | **0.33ms** | 0.33ms |

**规则：任何耗时数字必须标注冷/热；报热态数字前先空跑一遍丢弃。**

"首次登录 5s" 恰恰是冷态——你的优化目标如果是"登录后第一眼"，那冷态才是要测的那个数。

### 1.3 一条 SQL 的耗时花在哪

按开销从大到小排，排查时照着这条清单对：

1. **扫了多少行**（表扫 / 索引扫）—— 通常是大头
2. **排序**（filesort）—— 没有索引能提供顺序时，要把结果全部排一遍
3. **回表**（二级索引 → 聚簇索引取其余列）
4. **聚合 / 临时表**（`GROUP BY`、`DISTINCT`）
5. 解析与优化 —— 量级极小，但**每次请求都发生**，所以缓存的收益也在这里

## 二、看执行计划

### 2.1 三个 EXPLAIN 的用途不一样

| 语句 | 给什么 | 什么时候用 |
|---|---|---|
| `EXPLAIN` | 表格形式，估算 `type`/`key`/`rows` | 一眼看"用没用上索引" |
| `EXPLAIN FORMAT=TREE` | 树形结构，能看出 `Table scan` / `Sort` 的嵌套关系 | 定位**病因**（是扫描还是排序） |
| `EXPLAIN ANALYZE` | 真实执行一遍，带 `actual time` / `actual rows` / `loops` | **判断快慢的唯一可信来源** |

**本项目踩过的坑**：我一开始只用 `FORMAT=TREE`，能看出"有 filesort"，但**它给不出快慢**。
`cost` 和估算 `rows` 在两种格式里都有，两者都不能当耗时用。判快慢必须 `ANALYZE`。

代价：`EXPLAIN ANALYZE` **会真的执行查询**（`INSERT`/`UPDATE`/`DELETE` 也会真的执行），
在写语句上用要小心。

### 2.2 怎么读 TREE / ANALYZE 的输出

真实输出（就是本次实验中"加索引后"的无筛选变体）：

```
-> Limit: 10 row(s)  (cost=5615 rows=10) (actual time=1.82..1.88 rows=10 loops=1)
    -> Index lookup on item_perf using idx_admin_list (deleted=0) (reverse)
       (cost=5615 rows=49661) (actual time=1.81..1.88 rows=10 loops=1)
```

读法：

- **从缩进最深的往外读**，那是先执行的节点；箭头 `->` 表示"结果流向谁"。
- `actual time=A..B`
  - `A` = 返回**第一行**用了多久
  - `B` = 返回**全部行**用了多久
  - `LIMIT` 场景下 A 和 B 可能很接近——说明只取了几行就够，正是我们要的效果。
- `rows=N` 是**实际**返回行数；对比 `cost=... rows=M` 的估算值，能看出优化器猜得准不准。
- `loops=N` = 这个节点被执行了几次。**嵌套循环连接里这个数会被放大**
  （本项目那个失败实验里 `Filter ... loops=100320`，就是被驱动表被扫了 10 万次）。

**关键信号词对照表**：

| 计划里出现 | 含义 | 是不是坏消息 |
|---|---|---|
| `Table scan on item` | 全表扫描 | 通常是，除非表真的小 |
| `Sort: ... limit input to 10 row(s)` | filesort，没有索引提供顺序 | **是**，这是本项目的主犯 |
| `Index lookup on ... (reverse)` | 反向扫索引 | **好事**，正是 `ORDER BY x DESC` 想要的 |
| `Index range scan` | 范围扫描 | 中性，看范围大小 |
| `Covering index lookup` | 覆盖索引，不需要回表 | **好事** |
| `Filter: (...)` | 索引只覆盖了部分条件，剩下的逐行判断 | 中性，注意 Filter 后剩多少行 |
| `Nested loop inner join` + 巨大 `loops` | 连接驱动方向可能选错了 | 要具体看 |

### 2.3 `cost` 会骗你——统计信息失真

本项目最典型的一次。同一条 `WHERE deleted=0 AND status=7 ORDER BY create_time DESC LIMIT 10`：

| 走的索引 | 优化器估的 cost | actual time |
|---|---|---|
| `idx_admin_list`（优化器自选） | 3189 | 1.67ms |
| `idx_admin_status`（强制） | **3189** | **0.26ms** |

cost 一模一样，实测差 6 倍。更极端的是估算行数：`status=6` 实际只有 **20 行 / 100300**，
优化器估的是 **24919 行**——差了 1000 倍。原因是复合索引 `(deleted, status, ...)` 上
`status` 的基数估算很不准（它不知道 `status` 的取值分布）。

**结论：估算值只用来解释"优化器为什么这么选"，不用来判断"这样选好不好"。**

## 三、放大数据（最关键的一步）

小库上优化器一律选全表扫，而且那是**正确**的选择（60 行的表扫比走索引还快）。
所以你在小库上永远测不出索引的价值。放大数据是这套流程的核心步骤。

### 3.1 建实验表——绝不碰真实表

```sql
CREATE TABLE item_perf LIKE item;
ALTER TABLE item_perf DROP INDEX ft_search;   -- FULLTEXT 灌数极慢，实验用先去掉
```

- 命名一律 `xxx_perf`，一眼能看出是实验表。
- **用完必须 `DROP`**，否则会混进真实表里。

### 3.2 灌数：用 `WITH RECURSIVE`，不要写脚本

```sql
INSERT INTO item_perf (id, seller_id, title, category_id, grade, price, campus_id,
                       status, published_at, create_time, deleted)
WITH RECURSIVE s(n) AS (SELECT 1 UNION ALL SELECT n + 1 FROM s WHERE n < 100000)
SELECT n, 1 + (n % 12), CONCAT('测试商品', n), 1211 + (n % 10), 'A',
       10 + (n % 500), 1001 + (n % 2),
       ELT(1 + (n % 5), 1, 2, 3, 3, 3),        -- 让 status=3 占 1/3，避免均匀分布
       NOW() - INTERVAL (n % 20000) HOUR,
       NOW() - INTERVAL (n % 20000) HOUR, 0
FROM s;
ANALYZE TABLE item_perf;
```

三个要点：

- **分布要刻意造得不均匀**。真实世界里热门分类、在售状态都占大头，均匀分布会让优化器做
  出和线上不一样的选择。上面 `ELT(...)` 就是让 status=3 占多数。
- **一定要造稀有值**。稀有值是暴露估算失真、暴露"索引没被选中"的最佳探针。
  本次补了 300 行 `status=7`（0.3%）和 20 行 `status=6`（0.02%）。
- **`ANALYZE TABLE` 不能省**。它重算统计信息；不跑的话优化器还按旧基数决策，实验白做。

### 3.3 一条查询要测几个变体

按**用到的列**来挑，不是按"用户可能点哪些"。管理端筛选是自由组合，本次拆成 6 类：

| 变体 | 为什么必须测 |
|---|---|
| 无筛选（默认首屏） | 最常发生的请求，最左列无条件，最容易全表扫 |
| 只选状态 | 用得上老索引前缀，但排序对不上 |
| 状态 + 校区 | 多个过滤列，看优化器怎么权衡 |
| 状态 + 分类 IN | 范围条件 |
| 仅关键词 | 预期无解，用来确认边界 |
| **`COUNT(*)` 同条件** | **最容易被漏掉的一条** |

**为什么 COUNT 必须单独测**：MyBatis-Plus 的 `selectPage` 会额外发一条 `SELECT COUNT(*)`，
优化器对它的选择和取数查询**不一定相同**。只测取数就会低估整体耗时——本次 count 就是那条
降不下来的地板（100k 行 208ms）。

## 四、从计划读出病因

| 计划里的症状 | 病因 | 处方 |
|---|---|---|
| `Table scan` | 最左列上没有可用条件 | 建以该列打头的索引 |
| 走了索引但仍 `Sort` | 索引不能提供 `ORDER BY` 的顺序 | 把排序键接到等式列之后 |
| `Filter` 后行数比扫描行数小很多 | 索引选择性不够，过滤列没进索引 | 把过滤列提到索引里 |
| `actual rows` 远多于最终 `Limit` 的行数 | 排序键不在索引 / 需要回表 | 覆盖索引，或把排序键放进索引 |
| 巨大 `loops` 的嵌套循环 | JOIN 驱动方向选错 | 看数据量决定谁驱动，必要时 `STRAIGHT_JOIN` |

本项目对上的就是前两条：`item` 原有 5 条索引**全部以 `status` 打头、按 `published_at` 排序**，
而管理端查的是 `WHERE deleted=0 ORDER BY create_time DESC`——**没有一条条件能对上**，
所以每个变体都 filesort。

## 五、设计索引

### 5.1 列顺序的三条规则

1. **等式条件的列在前，范围/排序列在后。**
   B+ 树只有在等式前缀之后才有序；中间插一个范围列，后面的列就无序了。
2. **`ORDER BY a DESC, b DESC` 等价于索引 `(a, b)` 的反向扫描。**
   MySQL 8 能反向扫索引，所以**不需要**专门建 `DESC` 索引。
   计划里看到 `Index lookup ... (reverse)` 就是它在这么干。
3. **排序键要放完整。** `ORDER BY create_time DESC, id DESC` 就把 `id` 也放进索引。
   否则 `create_time` 相同的行顺序不确定，优化器还得再排一次。

### 5.2 落到本次需求上

需求（`ItemAdminService.list`）：

```sql
SELECT ... FROM item WHERE deleted = 0 [AND status = ?] ORDER BY create_time DESC, id DESC LIMIT 10
```

按规则推：

- `deleted = 0` 是等式 → 放最左。它几乎恒为 0，等于一个常量，几乎不牺牲选择性。
- 不筛状态时要按 `create_time` 排 → 索引必须是 `(deleted, create_time, id)`。
- 筛状态时要把 `status` 插进等式位置 → 索引是 `(deleted, status, create_time, id)`。

**两条索引不能合并**：`(deleted, status, create_time, id)` 里 `create_time` 只在
`status` 固定之后才有序，满足不了"不筛状态"时的全局排序。所以要两条，不是一条写宽点就够。

```sql
ALTER TABLE item
  ADD INDEX idx_admin_list (deleted, create_time, id),
  ADD INDEX idx_admin_status (deleted, status, create_time, id);
```

实测效果（10 万行热态）：

| 变体 | 加索引前 | 加索引后 |
|---|---|---|
| 默认首屏（无筛选） | 813ms | **0.46ms** |
| 只选状态 | 1035ms | **0.33ms** |
| 状态 + 校区 | 670ms | **0.58ms** |
| `COUNT(*)` 无筛选 | 366ms | 208ms |

### 5.3 加之前先问：这条索引会被选中吗

**加了但优化器不用 = 白加**，还多付一份写代价和内存。

本次的 `idx_admin_status` 就是这样：**取数时不选它**（优化器偏好 `idx_admin_list` 反向扫 + Filter），
**只有 `COUNT(*)` 时选它**（因为它是覆盖索引）。所以它的收益只能按 count 那条算
（727ms → 251ms），不能按取数算。

**检验手段**：用 `FORCE INDEX` / `STRAIGHT_JOIN` 强制一下，看"如果用它会不会更好"。

```sql
EXPLAIN ANALYZE SELECT ... FROM item_perf FORCE INDEX (idx_admin_status) WHERE ...;
```

**这两个提示只用于假设检验，不要进生产 SQL**：写死索引会让统计信息变化后无法重新选择。

### 5.4 有些慢，索引治不了

遇到下面四类，别在索引上耗时间：

| 类型 | 为什么索引无效 | 本次实例 |
|---|---|---|
| `LIKE '%x%'` 前导模糊 | B+ 树从左往右匹配，不知道前缀就无法定位 | 关键词搜索 586ms，加索引前后一样 |
| 跨表 OR | 两个分支要走不同索引，优化器只能退化成扫描 | 关键词还要 OR 卖家昵称 |
| **全表聚合**（`GROUP BY` 全量、不随分页变） | 要扫的就是全部数据；加索引反而可能改变驱动方向 | `avgPriceByCategory`（下一节详述） |
| 大表 `COUNT(*)` | 本质是 O(匹配行数)，索引只能把"回表"降到"覆盖索引"，降不掉扫描量 | count 208ms，是剩下的地板 |

## 六、加索引反而更慢：JOIN 驱动方向

`ItemMapper.avgPriceByCategory()` 是个很好的反例：

```sql
SELECT i.category_id, AVG(o.amount)
FROM trade_order o JOIN item i ON i.id = o.item_id
WHERE o.deleted = 0 AND o.status = 4 AND i.deleted = 0
GROUP BY i.category_id
```

我按直觉给 `trade_order` 加了候选索引 `(status, deleted, item_id, amount)`（覆盖上面所有列）。结果：

| 方案 | 结果 |
|---|---|
| 原计划（走 `idx_expire`，从订单侧驱动） | 冷态 **1006ms**；热态 **384ms** |
| 加索引后，优化器自选 | 换成从 `item` 侧驱动，做 10 万次循环，冷态 **1971ms** |
| 强制用新索引 + `STRAIGHT_JOIN` | 热态 **469ms**，比原计划还慢 |

（冷/热数字不要跨行直接比，同标记的两数才是可比的一对。）

三个教训：

1. **加索引改变了优化器对这条 SQL 的驱动方向判断**，把一个还行的计划换成了坏计划。
   这就是"加索引是全局变量"最直接的例证。
2. **强制用上这条覆盖索引也只是打平**——说明瓶颈不在这里。
   真正的瓶颈是**必须按 `item_id` 回表 5 万次去取 `category_id`**，索引帮不了。
3. 处方不是索引，是**缓存**（见下一节）。

> 想彻底治它还有一条路：把 `category_id` 冗余进 `trade_order` 的快照字段
> （它已经存了 `item_title` / `item_price` 快照）。但那是 schema 变更，
> 收益要跟缓存方案比过再定，本期不做。

## 七、索引和缓存的分工

不是所有慢都该用缓存，也不是所有慢都该用索引。判断表：

| 特征 | 用索引 | 用缓存 |
|---|---|---|
| 结果随参数变化（分页、筛选） | ✅ | ❌（key 空间爆炸） |
| 结果不随参数变化、全量聚合 | ❌ 可能反效果 | ✅ 单一 key |
| 需要强一致 | ✅ | ❌ |
| 需要毫秒级且能接受短暂旧值 | ✅ | ✅ |
| 首次请求（冷启动） | ✅ **第一次就有效** | ❌ 首次必然 miss |

**最后一行是本次决策的关键**：用户报的是"首次登录 5s"，而缓存对首次请求天然无效。
索引对第一次请求就有效。所以先做索引、不先做缓存。

### 7.1 缓存的四个必答问题

任何一个缓存方案都要先答完这四个，答不上就别加：

1. **key 怎么设计？**（维度越多越危险）
2. **TTL 多长？**
3. **谁来失效？**（写操作主动 DEL，还是纯靠 TTL）
4. **Redis 挂了怎么办？**（降级还是报错）

### 7.2 本项目的既有口径

照抄 `DictService`（`notes/07`）定下的四条，不要另发明一套：

- **读穿**：miss 才查库，查到就写回。
- **异常降级直查库**：字典是发布页的依赖项，Redis 抖动不该让页面 500。均价同理——
  它只是列表上的一个提示。
- **失效用 DEL 不用 SET**。`DictService#deleteCacheKey` 的注释写死了理由：
  "并发下两次写的先后顺序无法保证，重算有可能把旧快照写回缓存"。
  而且重算要重查重序列化，DEL 只要一次。
- **只有一个 key 才值得缓存**。`/api/dict/all` 只有一个 key，所以值得；
  管理端字典列表要看到停用项、还要即时，就直查库。

### 7.3 本次：只缓存 `avgPriceByCategory`

理由：它是全量 `GROUP BY`、**不随分页与筛选变化**、结果只有几十行、几乎不变，
却每个列表请求都要跑一次。典型的"算一次存起来"。

- key：`cm:item:catAvg`（单一 key；新建 `ItemRedisKeys`，按 `RedisKeys` 的约定
  一个模块一个常量类）
- TTL：5 分钟。**一期没有订单写侧，也就没有主动失效的触发点，TTL 是唯一刷新手段**，
  所以不能像字典那样把它当"del 失败时的兜底"。订单模块落地后要在订单完成时一并 DEL。
- 降级：读写异常都 `catch` 住，`log.warn` 后直查库 / 直接返回本次查库结果。

### 7.4 真实的坑：缓存「写进去了」不等于「生效了」

这是本次最值钱的一个发现，也是**只靠读代码绝对看不出来**的那种。

第一版实现写完，跑起来看 Redis：

```
EXISTS cm:item:catAvg  →  1
TTL    cm:item:catAvg  →  294
GET    cm:item:catAvg  →  [{"categoryId":1212,"avgPrice":38.285000}, ...]
```

key 在、TTL 对、内容也是对的。**看起来完全正常。**

但再发一次请求，TTL 从 **264 变回 297**——被重新写了一遍。也就是说：**每次请求都 miss，
每次都查库、每次都重新写缓存**。缓存只贡献了写入开销，一点收益都没有，而且不报任何错。

**根因**在序列化器。`RedisConfig` 里是这么构造的：

```java
ObjectMapper mapper = new ObjectMapper();
mapper.registerModule(new JavaTimeModule());
GenericJackson2JsonRedisSerializer valueSerializer =
        new GenericJackson2JsonRedisSerializer(mapper);   // ← 类型信息在这里丢了
```

`GenericJackson2JsonRedisSerializer(ObjectMapper)` 这个**构造器只把你传的 mapper 原样用上**，
**不会**像无参构造器那样自动 `activateDefaultTyping`。而 Redis 的读取侧声明的是 `Object`：

```java
Object cached = redisTemplate.opsForValue().get(key);
```

没有 `@class` 告诉 Jackson 该还原成什么类，它只能给出 `LinkedHashMap`。于是：

```java
if (cached instanceof List<?> list) {
    if (!(list.get(0) instanceof ItemMapper.CategoryAvgRow)) return null;   // ← 永远为 false
}
```

`List<实体>` 变成了 `List<LinkedHashMap>`，`instanceof` 恒为 false → 永远走查库分支。

**同一个 bug 也命中了 `DictService.all()`**（`cached instanceof DictAllVO` 恒为 false），
也就是字典缓存**自实现以来一直是空转**。已实测确认：

| 实例 | 连续两次调用 | 缓存原文 | 结论 |
|---|---|---|---|
| 修复前（旧构建） | TTL **59 → 59**（被重置） | 无 `@class` | 每次 miss，空转 |
| 修复后 | TTL **59 → 49**（递减） | `{"@class":"com.campus.core.dto.resp.DictAllVO",...}` | 真的命中 |

修复只改了一处（`RedisConfig`），两个消费方一起修好。

**修复**：把类型信息显式打开，并限定允许还原的类范围（开了 default typing 后
`@class` 会被当成真实类名去实例化，不能放开成任意类）：

```java
private static final PolymorphicTypeValidator TYPE_VALIDATOR = BasicPolymorphicTypeValidator.builder()
        .allowIfSubType("com.campus.")
        .allowIfSubType("java.")
        .build();

mapper.activateDefaultTyping(TYPE_VALIDATOR, ObjectMapper.DefaultTyping.EVERYTHING,
        JsonTypeInfo.As.PROPERTY);
```

修完后缓存里长这样（`@class` 出现了）：

```json
["java.util.ArrayList",[{"@class":"com.campus.core.mapper.ItemMapper$CategoryAvgRow",
  "categoryId":["java.lang.Long",1212],"avgPrice":["java.math.BigDecimal",38.285000]}]]
```

**怎么在 5 分钟内发现这类问题**（写进这次的检查清单）：

| 检查 | 健康的表现 | 出问题的表现 |
|---|---|---|
| **连续两次调用，看 TTL** | TTL **递减**（真命中） | TTL **被重置**（每次 miss） |
| 看缓存原文 | 有 `@class` / 能看出结构 | 缺 `@class` |
| 看有没有报错 | —— | **通常一个错都没有**，这才是最坑的 |

> **只验证"key 写进去了"是不够的**。`EXISTS=1` 只证明写成功，不证明读得到。
> 必须验证"第二次调用不再回源"。

### 7.5 附带一条：不要缓存非 String 键的 Map

即便类型信息修好了，也**不要缓存 `Map<Long, BigDecimal>`**。

JSON 的对象 key **只能是字符串**，类型信息记录不到泛型参数上。存进去取回来是
`Map<String, BigDecimal>`，调用方拿 `Long` 去 `get`：

```java
fill.avgPrices.get(row.getCategoryId())   // Long key 查 String key 的 Map
```

**不抛异常，静默返回 `null`**——表现是"均价一列全是 0"，和上面的问题一样难查。

**做法：缓存 `List<CategoryAvgRow>`，读回来在 Java 里转 Map。**
List 的元素是有类型的，没有 key 类型这个坑。

> 通用规则：**缓存里放 List / 简单对象，不要放非 String 键的 Map。**

### 7.6 降级路径也要实测

`catch` 住异常不等于真的降级成功。本次往缓存里塞了两种坏数据各测一遍：

| 塞进去的内容 | 预期 | 实测 |
|---|---|---|
| `not-json-at-all`（非 JSON） | 反序列化抛异常 → 降级查库 | `code=0`，均价正常，缓存被重建成合法 JSON |
| `{"foo":123}`（合法 JSON、形状不对） | `instanceof` 不通过 → 降级查库 | 同上 |

两条都返回了正确数据、没有 500。**"包了 try/catch" 和 "出错时真的能降级" 是两件事。**

## 八、落地与回归

索引定下来之后的完整收尾流程：

1. **改 `db/schema.sql`** 的建表语句（新库初始化就带上）。
2. **对已存在的实库执行同样的 `ALTER TABLE ... ADD INDEX`**。
   只改 schema 不影响已经建好的库——这两步缺一不可。
3. **在真实库上复验**：小库上优化器可能仍然选全表扫，**这是正确的，不算回归**。
   确认的是"没有变坏"，不是"在小库上也走索引"。
4. **同步文档**。索引清单这类信息最容易和 schema 漂移——本次就发现
   `db/01-数据库设计.md` §4.3 写的是 `idx_credit` / `ft_title_desc`，
   而实际是 `idx_published` / `ft_search`。顺手核对名字。
5. **`DROP` 实验表**。

### 判断清单

1. 症状拆到具体 SQL 了吗？一次请求发几条？
2. 冷态还是热态？（热态要跑第二遍再取数）
3. 计划里是 `Table scan` 还是 `Index lookup`？有没有 `Sort`？
4. `actual rows` 和最终返回行数差多少？差得多 = 白扫了。
5. `loops` 是不是被放大成了几万、几十万？
6. 目标索引的**列顺序**对不对？（等式在前、排序在后、排序键放完整）
7. **这条索引会被优化器选中吗？** 用 `FORCE INDEX` 试，但别写进生产 SQL。
8. 加完索引，**把之前所有变体重跑一遍**（含 `COUNT(*)`），确认没有回归。
9. 是不是落到"索引治不了"的四类里了？（前导模糊 / 跨表 OR / 全表聚合 / 大表 COUNT）
   —— 是的话改走缓存，并答完缓存的四个问题。
10. **缓存加完了吗？连续调两次看 TTL 递减**（只看到 `EXISTS=1` 不算数，见 §7.4）；
    再往缓存里塞坏数据，确认能降级不 500（§7.6）。
11. `schema.sql` + 实库 + 文档三处都改了吗？实验表 `DROP` 了吗？临时起的调试实例停了吗？
