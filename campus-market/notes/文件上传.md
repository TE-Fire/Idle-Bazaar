# 文件上传

> 技术笔记 · 以本项目（campus-market）的图片上传实现为主线讲解 HTTP 文件上传。接口契约与字段口径见 notes/16 C1，本文不重复，只讲机制与取舍。

文件上传解决的问题只有一个：把二进制文件从客户端送到服务端并长期保存。本项目为此搭了一条完整链路——签票据、按模式分流、双端上传、事务后清理——每个环节都对应上传领域的一个通用问题：请求体怎么装、传输路径怎么选、双方怎么分工、不可信输入怎么防、出了错怎么收。本文按这条链路展开，通用原理放到项目代码上讲。

## 上传就是一次普通的 HTTP 请求

**文件上传没有专用协议，它就是一次普通请求，特殊之处仅在请求体里装的是二进制字节流。** 与普通表单提交相比有三个差别，每一个都在本项目里有明确落点。

其一，**请求体的解析方式由 Content-Type 决定**。服务端按请求头选择解析器，头与数据格式不一致解析必败。本项目只涉及两种格式：multipart/form-data（PROXY 模式，Spring 按 boundary 自动切分，业务代码拿到 `MultipartFile`）和裸二进制流（DIRECT 模式，前端 PUT 直传 MinIO，应用不解析）。

其二，**体积大决定了必须流式处理**。几十兆文件整体读进内存，几个并发就能耗尽堆空间。本项目的 PROXY 链路是 `file.getInputStream()` 直接交给 `MinioStorage#upload`，后者 `stream(input, size, -1)` 原样入桶，全程不落本地临时文件，内存占用与文件大小无关。

其三，**传输时间长决定了失败重试是常态**。本项目用「单图 5MB 上限」把单次请求压在弱网可接受的规模内——不引入分片，代价可承受；重试策略见后文「一致性」一节，它并不是免费的。

## 传输形态：只做了 multipart 与 PUT 直传

主流形态有四种，本项目的取舍如下：

| 形态 | 本项目 | 理由 |
|---|---|---|
| multipart/form-data | **用**（PROXY） | 通用性最好，浏览器与 uni.uploadFile 都默认支持 |
| 裸二进制 PUT | **用**（DIRECT） | 配预签名 URL 直传桶，文件流不经应用，省带宽 |
| base64 内嵌 JSON | 不用 | 体积膨胀 33%，商品图 MB 级不划算 |
| 分片上传 | 不用 | 5MB 上限下单次失败的代价可接受，分片的状态管理成本换不来收益 |

两种在用的方式对应策略模式的两个实现：`ProxyUploadStrategy` 与 `DirectUploadStrategy`。**这不是为「将来可能换 OSS」提前抽象——两通道今天就有真实分工**：小程序端 `uni.uploadFile` 只能发 multipart、发不了 PUT，这是平台限制，所以小程序固定走 PROXY；Web 端两种都能走，由配置决定。

## 票据制：把「怎么传」收口到服务端

**票据不是第三种传输方式，而是两种方式之上的组织层**：前端不自行判断该用什么姿势传，先调 `POST /api/file/upload-ticket` 拿一张「许可单」，单上写明模式、上传地址、请求方法、附带字段和有效期，前端照单执行。

代码组件是一条短链：`TicketIssueReq`（描述将要传什么）→ `UploadStrategyRouter`（按配置或请求选策略）→ 具体策略签发 `UploadTicket`。策略 Map 由 Spring 注入全部 `UploadStrategy` Bean 装配，将来加一种方式（如 OSS 走 STS 临时凭证）只需加一个 Bean，Controller 与前端零改动。

票据字段在两种模式下的取值：

| 字段 | PROXY | DIRECT |
|---|---|---|
| uploadUrl | 服务端 `/api/file/upload`（相对路径） | MinIO PUT 签名地址（绝对 URL） |
| httpMethod | POST | PUT |
| formFields | `objectKey` | 空 |
| expiresIn | 0（不过期，服务端收口） | 600 秒 |
| accessUrl | `{endpoint}/{bucket}/{objectKey}` | 同左 |

有两个设计点值得展开。**一是 accessUrl 在签票时就能给全**：桶是公开读、对象 key 由服务端生成，URL 只取决于 endpoint/桶/key 三者，与怎么传无关——所以无论走哪条通道，前端最后拿到的都是同一个地址，提交商品时 `images` 里放的就是它，业务层完全不感知传输差异。**二是模式的裁决权在服务端**：默认值来自 `campus.upload.mode`（dev/demo 均为 proxy），请求可显式覆盖但仅用于降级；策略未装配时 `Router` 抛明确错误而非静默降级——`DirectUploadStrategy` 标了 `@ConditionalOnBean(StorageService)`，demo 关掉 MinIO 时选 DIRECT 会得到「上传方式不可用」，而不是运行时空指针。`ProxyUploadStrategy` 刻意不依赖存储 Bean，所以关存储时 PROXY 票据仍可签，真正传文件那一步才报「对象存储未启用」。

## 前端两条路径

Web 端（`packages/api/src/file.ts` 的 `uploadImage`）先跑 `checkImageFile` 预检——大小与扩展名，**口径必须与后端 `UploadChecks` 逐字一致**，改一处必须同步另一处，前端预检只为少一次往返，不是安全边界。然后按票据分流：PROXY 组 FormData 走 `request` 实例，享受拦截器统一解包 Result；DIRECT 用裸 `fetch` PUT 直传 MinIO——绝对 URL、响应无 Result 包装，刻意不经 http 实例，也不设 Content-Type（签名时未约束该头，带了反而可能与签名校验冲突）。

小程序端（`apps/mini/src/utils/upload.ts`）固定传 `mode: 'PROXY'`，用 `uni.uploadFile` 发 multipart，`formData` 带票据的 `formFields`，并且**上传请求也要带登录令牌**——对象名带用户前缀，服务端按当前用户校验归属，匿名上传直接被拦截。另一个端点细节：小程序选图的临时路径可能不带扩展名，前端兜底补 `.jpg`，真实白名单校验仍以后端收到为准。

两条路径殊途同归：调用方只管拿到 `accessUrl`。商品发布页（Web `PublishView` 与 mini publish）用它做商品图上传；头像编辑（mini profile-edit、Web MainLayout）复用同一套函数——**当前实现里头像与商品图共用 `item-image` 桶和 `item/` 前缀**，这是有意的一期简化，桶隔离留到做认证凭证（`verify-file`）时再拆。

## 服务端安全边界

**总原则一条：客户端提交的一切都不可信——文件名、声明的类型、声明的大小、票据本身，服务端必须独立复核。** 本项目的防线逐条对应：

**对象名由服务端生成。** `UploadChecks#buildObjectKey` 产出 `item/{userId}/{uuid}.{ext}`：扩展名取自客户端文件名但过白名单，其余全部服务端决定。客户端文件名可能含路径遍历序列（`../`）或超长名，直接拿来构造存储路径会造成目录逃逸；随机 UUID 命名同时天然防覆盖。

**multipart 端点二次校验。** `FileUploadController#upload` 收到文件后重新执行 `requireOwnObjectKey` / `requireImageExt` / `requireSizeOk`——**票据可以被伪造，端点也可以绕过签票直调**，所以 objectKey 前缀必须是 `item/{当前用户}/`，否则拿到别人的 key 就能覆盖他人商品图（桶内同 key 覆盖即替换）。

**大小限制分两层。** 业务层 5MB 在 `UploadChecks`（`PARAM_ERROR`，文案明确告诉用户「5MB 以内」）；框架层 `spring.servlet.multipart` 10MB / 请求 20MB 兜底。两层的报错体验不同：5MB–10MB 之间的文件被业务层拦下、错误可读；超过 10MB 触发框架的 `MaxUploadSizeExceededException`，本项目未专门映射，落到全局兜底（5000）。前端预检让正常用户碰不到这两层，但它们都必须在服务端。

**扩展名白名单，魔数校验未做。** 白名单 jpg/jpeg/png/webp，**tech/01 4.4 原计划按文件头魔数校验真实类型，一期只做了扩展名**——伪装成 .jpg 的文件能过校验。当前风险可控（文件只做静态直出、不被服务端解析），但这是已知缺口，补法是在 `UploadChecks` 里加魔数断言，两种模式共用。

**公开读桶的取舍。** 建桶时 `PUBLIC_READ_POLICY` 只放行 `s3:GetObject`，写与列桶不公开；读 URL 直拼不过期，省去列表页批量签名的开销。代价是 URL 可被枚举，私密内容（认证凭证）将来必须换私有桶加限时签名——收口点在 `MinioStorage`，业务代码只依赖 `StorageService` 接口，换取址实现不动调用方。

## 删除的一致性与失败处理

**删库与删对象必须同事务边界，且顺序不能反。** `ItemImageJanitor#cleanupAfterCommit` 在删除事务内先查出未软删的图片 URL，把真正的 `deleteByUrl` 注册到 `afterCommit`：提交后才删对象，回滚则一张不动。反过来先删对象再回滚，会留下「商品还在、图全没了」的坏数据，比孤儿对象更难处理。调用点两处：学生端删除（`ItemService`）与管理端删除（`ItemAdminService`）。

**存储缺失要降级不要阻断。** `StorageService` 用 `ObjectProvider` 注入，`minio.enabled=false` 时整体跳过清理，删除主流程照常——留孤儿对象是可接受的二期债务，因清理不可用而让商品删不掉不是。

**重试不幂等，这是当前实现的真实代价。** objectKey 是随机 UUID，同一次失败重传会落两个对象。所以前端只在请求明确失败时提示用户手动重试，不做自动重试；若将来按内容哈希命名对象，重传天然幂等，才谈得上传输层的自动退避重试。

**「传了图但没提交商品」是设计内的中间态。** 上传接口只返回文件标识、不动业务表，业务表单另行提交，两者失败互不影响：上传成功而用户放弃，结果是孤儿对象；业务提交失败，已传的图仍可追踪。孤儿对象目前没有巡检任务（notes/16 缺口表第 1 条），泄漏量靠 5MB 上限与使用规模兜着。

## 已知缺口

| 缺口 | 代价 | 状态 |
|---|---|---|
| 魔数校验未做，只有扩展名白名单 | 伪装扩展名的文件可通过 | 一期接受，补法已明确 |
| DIRECT 签名未限定 Content-Type 与大小 | 签出的 URL 在 10 分钟内可传任意内容 | 仅 Web 端可用且需登录签票，一期接受 |
| 孤儿对象无定时巡检 | 「传了图没提交」的对象永久留存 | 二期（notes/16 缺口表第 1 条） |
| DIRECT 模式小程序端需配 request 合法域名 | 小程序固定 PROXY，不受影响 | 联调时验证 |

回到开头：上传领域的复杂度来自四个词——二进制、大体积、慢传输、不可信输入。本项目把它们的落点分别放在了两种 Content-Type、双层大小限制、5MB 上限加票据有效期、以及服务端复核四件套上；票据制把「怎么传」的决定权收进服务端，前端无论 Web 还是小程序都只认 `accessUrl`，这是整条链路里复用度最高的一层抽象。
