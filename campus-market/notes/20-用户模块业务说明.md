# 20 - 用户模块业务说明

> 格式遵循 notes/14 业务笔记标准模板。登录流程以 business/01 F-W6 为准，本文只做引用不重复；本文的主体是 2026-10-25 新增的资料编辑（昵称、头像）。

## 一、模块定位

学生端用户模块回答两个问题：「谁在用」和「他对外长什么样」。前者是登录建会话——手机号加短信验证码，流程定义在 business/01 F-W6，Sa-Token 实现记录在 notes/05；后者由资料编辑与学号认证承担，本文是它们的业务依据。模块边界有三条：管理端账号是另一套表与令牌（business/03 与 notes 未覆盖），不在本文主体内，但本文 D6 要写清管理端对**学生**账号的处置动作；关注、粉丝、个人动态等社交能力已在 notes/22 统一设计，数据模型见 db/01 §5.7，本文只预留调用位置、不重复规则；收藏与搜索见 notes/24。

## 三、业务条目

### D1 · 登录建会话（既有，从简）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/auth/send-code` | 免登录 | 发短信验证码（60 秒一条） |
| POST | `/api/auth/login` | 免登录 | 手机号 + 验证码换令牌 |
| POST | `/api/auth/logout` | 登录 | 退出并清会话 |

**前置**：无。手机号未注册返回未注册(4015)，不做防枚举（演示期账号全部来自种子数据）。

**规则**：流程、节流、封禁口径一律以 business/01 F-W6 为准；登录成功更新 `last_login_at` 并建立会话（令牌 satoken-user，7 天）。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `app_user` | `last_login_at` 更新 |
| 会话 | 建立，有效期 7 天 |

### D3 · 编辑昵称与头像

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| PUT | `/api/auth/profile` | 登录 | 改昵称 / 换头像，局部更新 |
| GET | `/api/auth/info` | 登录 | 改后刷新会话视图 |
| POST | `/api/file/upload-ticket` | 登录 | 头像图片签票（票据制，设计决策见 notes/18 问题 3） |

**前置**

- 已登录，未登录返回 1001；
- 头像先经上传通道拿到 `accessUrl` 再随本接口提交——本接口只收 URL，不接收文件流。

**规则**

1. 请求体含 `nickname` 与 `avatarUrl` 两个可选字段，至少传一个；都不传 → 参数错误(1000)。
2. 局部更新语义：字段为 null 表示不修改；传空串按「传了非法值」处理而非「不修改」——前端用空串表达「清空」时若被当成不修改，会静默丢操作。
3. 昵称校验：去首尾空格后非空、且不超过 64 字符 → 否则 昵称不合法(4020)。
4. 头像校验：非空、不超过 255 字符 → 否则 头像地址不合法(4021)；不做归属校验，可填任意 URL，风险见 §五。
5. 通过 → 按 id 局部更新，只写提供的字段，`update_time` 由数据库自动维护。
6. 更新成功后必须 DEL `cm:user:pub:{userId}`：昵称与头像在公开缓存载荷内，不失效则商品列表、商品详情、关注与粉丝列表里的用户信息滞后一个 TTL（10 分钟）。这份缓存同时服务管理端商品列表与审核队列（2026-10-26 接入，此前管理端直查 `app_user`），所以一次 DEL 覆盖四处展示，不需要按端分别失效。
7. 响应返回最新用户信息，前端据此刷新会话视图；令牌不变，其他已登录端下次调 `info` 时自然刷新。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `app_user` | `nickname` / `avatar_url` 按提供字段更新 |
| `cm:user:pub:{userId}` | DEL（昵称写入后立即失效） |

### D4 · 头像展示

**接口**：无独立接口——头像随三类既有响应下发：登录、`info`、卖家公开信息回填（后者本期载荷不含头像，见规则 3）。

**前置**：无。

**规则**

1. 展示优先级：`avatar_url` 有值 → 显示图片；为空 → 回退昵称首字占位（既有行为，不因新增字段改变）；图片加载失败同样回退占位，不显示破图。
2. 展示位置：学生端「我的」页头像区、Web 端顶栏；两端编辑入口都在同一视区（小程序为独立编辑页，Web 为顶栏弹层）。
3. 商品列表与详情的卖家回填本期不含头像——`ApiItemVO` 无该字段，待社交功能（个人主页、动态、评论）一并设计，不单独加。

**状态与数据变化**：无。

### D5 · 学号认证申请

学号认证是校园二手平台与闲鱼这类开放平台最本质的差别：它把「买家」从匿名账号变成**可追溯的在校学生**，面交才敢去，纠纷才有真实身份可以追。所以这条例目的设计重心不在表单，而在「一个人只能对应一个通过认证的学号」。

**接口**

| 方法 | 路径 | 鉴权 | 作用 |
|---|---|---|---|
| POST | `/api/user/auth/apply` | 登录 | 提交认证申请 |
| GET | `/api/user/auth/latest` | 登录 | 我最近一次申请（用于回显驳回原因） |

**前置**

- 已登录；当前 `app_user.auth_status` ∈ { 未认证(0)、未通过(3) }。
- 学院必须存在且启用（走字典校验，不许前端传任意 id）。

**规则**

1. 申请字段：`realName`（必填，≤32）、`studentNo`（必填，≤32，字母数字）、`collegeId`（必填）、`credentialUrl`（可选，一卡通或校园邮箱截图，走既有票据上传）。
2. **被驳回可以重提，每次重提新增一行 `user_auth`**。这张表是 A 类软删（留墓碑），不做「复用最后一行」——审核历史本身有价值，管理端要能回答「这个人提交过几次、前几次为什么被驳回」。
3. 提交成功：`user_auth` 插一行 `status=1`，同时 `app_user.auth_status` 置 1（审核中）。两处状态必须同事务写，只写一处会让「我的」页显示「未认证」而申请已在队列里。
4. 已认证（`auth_status=2`）再提交 → 已完成认证(4028)；存在审核中申请 → 申请审核中(4029)。
5. **学号唯一性在通过时校验，不在提交时**。提交时只提示、不拦截：同一个人可能先提交错了学号再重提，提交阶段就卡死会让人无法自助纠正。真正拦截放在管理端点「通过」那一刻——`app_user` 里已有别的账号用了这个学号 → 该学号已被其他账号认证(4030)。
6. 通过后回写 `app_user` 的 `real_name` / `student_no` / `college_id` / `auth_status=2`。真实姓名与学号**不对外展示**，只在下单、举报取证、管理端详情里可见。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `user_auth` | 新增一行，`status=1` |
| `app_user` | `auth_status` 由 0/3 变为 1 |

### D6 · 学生账号管理（管理端）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/user/list?keyword=&authStatus=&status=&pageNum=&pageSize=` | `user.view` | 学生列表，按注册时间倒序 |
| GET | `/admin/user/{id}` | `user.view` | 详情：资料 + 认证记录 + 信用流水 + 商品/订单计数 |
| POST | `/admin/user/{id}/ban` | `user.ban` | 封禁，带原因与可选到期时间 |
| POST | `/admin/user/{id}/unban` | `user.ban` | 解封 |
| POST | `/admin/user/{id}/credit` | `user.ban` | 人工调整信用分 |
| GET | `/admin/user/auth/pending?pageNum=&pageSize=` | `user.verify` | 待审认证队列，先到先审 |
| POST | `/admin/user/auth/{authId}/judge` | `user.verify` | 通过 / 驳回（驳回必填原因） |

**规则**

1. 列表的 `keyword` 同时匹配昵称、手机号、学号；手机号在列表里脱敏成 `138****1234`，详情页给全量——列表会被截图、会投屏，详情不会。
2. 封禁写 `status=2` + `ban_reason` + `ban_until`（空表示永久），**不动信用分**。信用分记的是交易行为，封禁是账号处置，两者混在一起会让解封出来的用户带着 0 分寸步难行，而且 `credit_log` 里会出现一条「被扣完」的假账，事后无法判断是违约扣的还是封禁扣的。
3. 解封写 `status=0`、清空 `ban_until` 与 `ban_reason`。到期封禁不解封也能登录（登录时判 `ban_until` 是否已过），但状态位仍要在下一次登录时被纠正，否则管理端列表永远显示「封禁中」。
4. 人工调分：`delta` 取 −20 到 +20 的整数，理由必填；结果夹在 0–120 之间。每次调整写一行 `credit_log`（`reason_type=ADMIN_ADJUST`，`remark` 落原文），这是「信用分为什么变了」的唯一解释来源（db/01 §5.5）。
5. 认证审核的「通过」要按 D5 规则 5 校验学号占用；驳回必须带原因，原因直接展示在学生端认证页，所以文案要能给人看，不能写「不符合要求」。
6. **信用调整复用 `user.ban` 权限点**，不新增第 19 个权限点。理由是它和封禁同属「处置账号」的一类动作，拆开会让权限矩阵多一列，而实际使用中是同一个人在做这两件事。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `app_user` | `status` / `ban_reason` / `ban_until`，或 `credit_score` |
| `credit_log` | 人工调整时新增一行 |
| `user_auth` | 审核后 `status` / `handler_id` / `handle_time` / `reject_reason` |

## 四、通用业务规则

**可改字段白名单只有昵称和头像。** 手机号是登录标识不可改；真实姓名与学号由认证流程写入、不经本接口；信用分、认证态、账号状态只有系统与管理端能改。白名单之外的字段请求里带了也忽略——局部更新的写入集合由服务端定，不由请求体定。

昵称不做敏感词过滤，也不要求唯一：项目有 `sys_sensitive_word` 表但没有过滤服务，本期不建；重名在校园场景可接受，识别用户靠 id 与信用分。头像上传走票据制既有通道，与商品图片共用 `item-image` 桶——头像没有独立 bucket，公开读口径一致；二期如拆分只需替换 `getUrl` 一处。

## 五、验收口径与已知缺口

验收口径：未登录调 `PUT /api/auth/profile` 返回 1001；两个字段都不传返回 1000；昵称传空串或超长返回 4020；头像传空或超长返回 4021；只传一个字段时另一个不动、`update_time` 变化；改昵称后立即访问商品列表或详情，卖家昵称为新值（缓存失效生效，不等 TTL）；头像保存后「我的」页与顶栏即时换图。

认证与管理的验收口径：提交认证后「我的」页立刻显示「审核中」，管理端 A4 待审队列出现该条；驳回后学生端认证页显示管理员写的原因，且能再次提交（`user_auth` 多一行）；通过后 `app_user.auth_status=2`、学号写入，学生端「学号认证」入口变为已认证态；用另一个账号提交同一个学号并通过时被 4030 拦下。封禁一个账号后该用户任何登录态请求返回 4001，解封后恢复，且信用分字段全程未变。人工加 10 分后 `credit_log` 多一行、分数为原值加 10；加到上限停在 120 而不是溢出。

已知缺口五条：头像与认证凭证 URL 都无归属校验，可填任意地址（含他人商品图），二期按上传票据的对象名前缀校验；昵称无敏感词过滤；换头像未保存时已上传图片成为孤儿对象（孤儿巡检是既有遗留，见 notes/18 问题 3）；Web 端没有独立「我的」页，编辑入口是顶栏弹层，个人主页待社交功能统一做；封禁账号不会同时下架其在售商品——商品仍可被搜索到，点进去聊一聊才发现卖家被封，二期在封禁时联动下架。
