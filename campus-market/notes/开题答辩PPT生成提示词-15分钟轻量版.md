# 开题答辩 PPT 生成提示词（15 分钟轻量版）

> 用法：整段复制给 PPT 生成工具。方括号 `【】` 处替换为你自己的信息。
> 与原版的差别：**14 页而非 18 页**、**每页给了用时预算**、**每页元素有硬上限**、**形态讲透而内功只露一手**。
> 删掉的：功能清单（35 个功能点）、数据与缓存设计整页、交易机制的两页详述。理由见下一节。

---

## 本版核心取舍：开题讲形态，不讲内功

开题答辩老师判断三件事：题目值不值得做、**做出来长什么样**、剩下的时间做得完吗。内功——并发一致性、状态机实现、缓存策略——在开题阶段**没有代码可演示**，讲出来只是一段抽象描述，听众跟不上，还挤掉讲形态的时间。

所以本版这样处理：

- **形态讲透**：系统有哪些页面、交易怎么走一圈、三种交付在哪里分叉、谁怎么认证、管理端有哪些工作面。这些是老师真正能「看懂」的东西，也是他们判断工作量的依据。
- **内功只露一手**：把并发一致性、状态迁移、核销双角色压成**一页三行清单**（P10），只传递「我知道坑在哪、也知道怎么填」，**不解释机制**。这一页的作用是被追问时的落点，不是主动讲的内容。
- **机制细节全部写进讲稿**：原子脚本的四种返回值、版本条件更新怎么生效、快照为什么不可回写——被问到再答。答得出比写在页上更有分量，因为写在页上老师会逐条读，读不懂反而扣分。

一条贯穿全篇的判据：**页面上可以出现技术名词，但不展开它的原理。**

这条线顺带把「智能」也切开了：**导购 Agent 是形态**（用户看得见、能演示、一句话说清），**四环节自动决策是内功**（用户看不见，只有数据能证明）。所以 Agent 完整讲一页，四环节压成 P10 底下的一行。

真正需要展开内功的场合是毕业答辩——那时有代码、有实测、有优化记录，同一个「并发付款」可以讲十分钟。这个任务留给论文与终期答辩。

## 汇报性质：开题讲方案，不讲成果

- 全篇设计态表述：「系统将包含」「拟定采用」「设计中」。**禁止**「已完成」「已实现」「实测」「上线」。
- 不放成果截图、不列实测数字，凡指标一律写「设计目标」。
- 不出「文献综述」「理论意义」「研究空白」「预期成果」这类套话。
- 不要出现「难点一」「难点二」这样的抬头——开题说「我有两个难点」容易引出「那你做得出来吗」；改说「这里有必须满足的约束」是主动的。

## 核心叙事：一次供需错配的撮合

**这是全篇立论，P2 讲不透，后面全塌。**

- **供给侧**：学生手里堆着用不上的闲置，便宜到不值得挂网卖、扔了可惜、班级群问一圈没人要。
- **供给侧的致命特征是同质化**：同一栋楼的台灯、风扇、插排、教材，人人都有同款——想卖的那件，往往正是隔壁室友在卖的。
- **需求侧**：周边社区居民需要这些生活用品，又不愿付新品价。
- **断点**：只隔一条街，信息不通，也互不信任。

**校内是同质互换**（买卖双方是同一批人、同一批品类），所以卖不动；**跨出校门才是异质互补**，学生过剩的正是居民缺的。学生内部那条「毕业生卖给新生」的通道只在每年 6 月和 9 月成立，且靠线下摆摊，线上平台没有增量——**平台真正的增量只能来自跨群体**。

平台补的就是这个断点：**只做中间人，不做运力**。三条口径：

1. 履约半径＝步行或顺路可达，货值低到承担不起物流。
2. 三种交付：面交、自提、**顺路送达**（卖方本就要往社区方向去）。
3. 信任来自身份认证与学校背书，不来自平台自称。

**禁止出现**：全城配送、骑手调度、同城速递、快递履约、物流体系、「送货上门」（须写「顺路送达」）。

## 页面纪律（五条硬规则）

1. **每页只讲一个观点**，标题写成判断句。不写「关键技术」，写「一件商品从发布到完成走哪几步」。
2. **每页视觉元素不超过 5 个**（一条要点、表格一行、图上一个方块，各算一个）。超了就拆页或删，**不许缩字号**。
3. 每条不超过 22 字。
4. 能上图的不要上字。
5. 讲稿另附，页面只放要点与结论，**不放机制推导**。

## 智能的处理（严格照此）

**只完整讲 Agent 一页（P11），四个环节只在 P10 占一行。**

导购 Agent 的形态：用户一句自然语言（「给宿舍添点东西，200 以内，这周能取」）→ 解析成结构化条件 → 调用平台真实数据检索 → 返回商品卡片 → 点卡片进详情走既有下单流程。用大模型，但**只做意图理解与话术组织，不生成任何商品属性**，也不代替用户下单。

三条纪律：

- 每提一次「智能」，后面必须紧跟一个可指名的机制，不许当形容词用。
- 提到大模型必须说明「**只做推理调用，不做训练**」。
- **禁止**：深度学习、神经网络、模型训练、微调、准确率、AUC、召回率。

## 可用技术事实（挑着用，别全堆）

**这一节的用途是讲稿与 P10 那一页，不是让你把它们铺到每页上。**

- **sa-token 1.38 + RBAC**：token 存 Redis 可主动失效，用户审核驳回或封禁后登录态立刻作废——这是不用 JWT 的直接原因；Web 与小程序可分别登录。
- **Lua 脚本**：占位、释放、浏览刷写、关注等六处逻辑下沉为脚本，保证「读—判断—写」不被并发插入。占位脚本返回五种值：1 成功 / 2 同订单幂等 / 0 已售出 / -2 他人付款中可重试 / -1 缓存缺失放行。
- **防超卖**：Redis 原子占位前置拦截 + MySQL `version` 条件更新最终裁决。
- **订单 11 态**：待付款 / 待面交 / 待发货 / 已发货 / 待自提 / 已验货 / 已完成 / 已取消 / 退款中 / 已退款 / 纠纷中。
- **核销**：码由卖方持有、仅买方录入，接口层拒绝卖方调用，任一方都无法单独完成。
- **收货方式三态**：面交 / 自提 / 顺路送达；地址与商品信息在下单一刻**快照进订单**。
- **身份**：用户表以「身份类型 + 认证状态」两个字段描述，学生与居民走不同认证通道，交易与评价逻辑复用。
- **互助**：复用动态（帖子）结构，用类型字段区分，**不新建业务表、不涉及支付与验收**。

## 逐页要求

**P1 封面（15s）**
题目居中，学院·专业 / 学号·姓名 / 指导教师 / 日期成块排在下方。

**P2 供需错配：两边都有，中间断了（70s）**
主图「在校学生 — 交易平台 — 周边社区居民」三栏。学生端：闲置、便宜到不值得卖、毕业只能扔；**学生端内部画一个自环箭头，旁注「同款人人都有，校内卖不动」——这一笔是整页关键**；居民端：缺这些用品、不愿付新品价、看不到校内信息；断点：一条街，信息不通、互不信任。
收口：**两类资源都在，缺的是把它们连起来的那条通道。**
小字：**校内是同质互换，跨出校门才是异质互补。**

**P3 平台定位：只做中间人（40s）**
标题「不建运力，只承担撮合与信任」。三条：履约半径＝步行或顺路可达；三种交付（面交 / 自提 / 顺路送达）；平台给状态与凭证，不承诺时效、不承担运力。
小字：**复用既有人流路径，不新增运力成本。**

**P4 同类方案与空白（45s）**
三列对比表：闲鱼 / 转转 / 校园墙。四维度：覆盖低货值、能出校门、验证身份、有交易凭证。
闲鱼——跨区运费吃掉低货值商品全部利润，无法验证学生身份；转转——偏 3C，同样受制于物流；校园墙——只在校内流转，而校内供需同质，出不了校门，无凭证。
收口：**校内出不去、校外够不着的那一段，是现有方案留下的空白。**

**P5 两端形态：用户端一条主链，管理端四个工作面（60s，这是「系统长什么样」的第一页，必须让人一眼看懂）**
左栏用户端（小程序）画一条页面竖向流程，每格一个页面名：
首页推荐流 → 分类 / 搜索 → 商品详情（含卖家信用与收货方式）→ 下单（选面交点或收货地址）→ 订单详情（含核销入口）→ 消息 → 我的（信用 / 评价 / 发布 / 地址）
右栏管理端（Web）四个方块：用户审核 / 商品审核 / 订单与纠纷裁决 / 字典与角色权限。
底部一句：**两端共用一套后端与一份订单状态，页面按角色裁剪。**

**P6 交易主干：一件商品从发布到完成（65s，本页承担「工作量是否成立」的判断）**
横向流程图，七格：
发布（选成色、收货方式、自提须选提货地址）→ 被浏览 / 收藏 → 下单（生成订单快照）→ 付款 → **三种交付在这里分叉**：面交（约面交点）/ 自提（凭码提货）/ 顺路送达（卖家发货）→ 核销或确认收货 → 互评（回写信用分）
在流程下方标出每一格的**凭证**：订单快照 / 核销码 / 地址快照。三个词出现即可，**不做解释**。
收口：**一条链闭合，三种交付只是中间分叉，状态与凭证共用一套。**

**P7 信任机制：双侧不对称（50s）**
标题「两条认证通道，一套约束标准」。四条：注册即选身份；学生——学号绑定 + 学生证审核，学校背书，强锚点，主要作供给侧；居民——手机号与居住区域验证，靠交易与评价累积信用，主要作需求侧；信用分统一计算，两侧约束一致。
收口：**供给侧用身份锚定，需求侧用行为累积，认证强度不同但约束标准一致。**
（身份只是用户表两个字段，不影响交易与评价逻辑复用。）

**P8 总体架构（40s）**
五层：接入（Web / 小程序）→ 鉴权权限（sa-token + RBAC）→ 业务（用户 / 商品 / 交易 / 社交与互助 / 管理）→ **智能业务层**（导购 Agent / 推荐排序 / 定价基准 / 风险评分 / 状态调度）→ 数据（MySQL / Redis / MinIO）。
要求：智能必须作为一层**显式出现在图上**，不能只在文字里提。这一页只给结构，不讲每层怎么实现。

**P9 技术选型（50s）**
表格五行，只留需要解释的：

| 技术 | 理由 |
|---|---|
| Spring Boot 3.2.5 + MyBatis-Plus | 生态成熟，单体部署便于个人服务器落地 |
| MySQL 8 | 交易需要事务与行锁，强一致优先 |
| Redis + **Lua 脚本** | 并发敏感逻辑下沉为原子脚本，写入不被打断 |
| **sa-token 1.38** | token 存 Redis 可主动失效，封禁即时生效，优于 JWT |
| Vue 3 + Element Plus / uni-app | Web 与管理端共用组件体系，小程序一套代码覆盖 |

收尾一句：**不引入公司级中间件，资源有限，够用优先。**

**P10 技术底牌：三处硬约束（45s，本页只露一手，不讲机制）**
一张三行表，每行「问题一句 + 对策一句」：

| 问题 | 对策 |
|---|---|
| 并发付款可能一物两卖 | 原子占位前置拦截，数据库版本条件更新最终裁决 |
| 订单分支多、状态易乱 | 11 态状态机，非法迁移由条件更新直接拒绝 |
| 单方核销可伪造完成 | 卖方持码、仅买方录入，接口层拒绝卖方 |

下方加一行（智能底座，一行封口）：**此外，撮合、定价、风控、调度四个环节由数据与规则自动判断，只读既有表、不新增数据表。**
本页语气要克制：**只给结论，不画时序图、不列四种返回值、不解释什么是窗口期**——这些留在讲稿里等提问。

**P11 导购 Agent：一句话进，商品卡片出（90s，全篇最重的亮点页）**
主图一条受约束的链路：用户一句话 → 解析意图并选工具 → 调用平台真实数据（商品检索 / 分类均价 / 卖家信用）→ 结构化条件回显可改 → 商品卡片 → 点卡片进详情，走既有下单流程。
三条设计约束（**这三条是亮点所在**）：
- **模型不接触数据库**，只通过注册函数取数；商品属性全部来自工具返回，结构上不存在编造的可能
- **不代替用户下单**，只产出卡片，成交仍走既有占位、地址、核销
- **解析结果结构化回显**（类目 / 预算 / 校区），用户可改，避免误解无法纠偏
补两句：降级——模型失败或超时回落关键词检索；实现——Spring AI Function Calling 注册三个方法，全是既有 Service 调用，不引入新中台。

**P12 创新点（35s）**
四条，每条一行，**只做收口不展开**：
1. **场景**：从供需同质化的校内流转，转向跨群体异质互补
2. **信任**：双侧不对称认证，供给用身份锚定、需求用行为累积
3. **形态**：受约束的对话式导购，模型不生成属性、不碰交易动作
4. **交易安全**：占位与版本更新双层裁决；核销双角色分离

**P13 进度与风险（50s）**
甘特图，2026 年 9 月至 2027 年 5 月，八阶段：需求调研（9–10）→ 方案与数据库设计（10–11）→ 核心交易闭环（11–12）→ 收货方式与地址（12–1）→ 社交与互助（1–2）→ 智能模块（2–3）→ 系统测试（3–4）→ 论文与答辩准备（4–5）。
**在 2026 年 11 月处画竖虚线标「开题」**，已过阶段实心、未来浅色。
右侧风险块两条：推荐与 Agent 依赖行为数据，早期用热度排序兜底并做离线评测；Agent 依赖外部模型服务，须有超时降级避免演示中断。
底部一行：**互助仅做发布与应答，不涉支付与验收，刻意控制复杂度。**

**P14 参考文献 + 致谢（25s）**
8–10 篇，格式「作者. 题名. 出处, 年份.」。必含 Spring Boot 官方文档、MySQL 8 手册、Redis 文档、Sarwar 的 Item-CF 经典论文、Kleppmann《Designing Data-Intensive Applications》。**中文文献由作者自补 2–3 篇近三年（2023–2026）真实可查的，检索不到宁可不列，不许编造卷期页码。**
底部居中一行：**感谢各位老师，请批评指正。**
