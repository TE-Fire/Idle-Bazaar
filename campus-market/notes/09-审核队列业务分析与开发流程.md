## 零、一句话结论

本期做 **A-B2 商品审核 + A-B3 举报与申诉**，都落在 A5 `/review` 一页：
三种来源（商品审核 / 举报处理 / 申诉复审）压成**一条队列**，
排序 = 类型优先（申诉 > 举报 > 商品审核）+ 组内按**权重分降序**，
处置用 Drawer 不跳页、处置完自动跳下一条（J / K 切换）。

**强制下架复用 `ItemAdminService.forceOffline`**——商品页与审核页是同一个动作的两个入口（notes/08 §1.1 已定），

## 一、业务分析

### 1.1 范围：为什么 A-B2 与 A-B3 要一起做

| 编号 | 业务域 | 业务动作 | 承载页面 | 本期 |
|---|---|---|---|---|
| A-B2 | 商品审核 | 待审队列取件 / 判读 / 通过 / 驳回（带原因）/ 强制下架 | A5 审核队列 | ✅ |
| A-B3 | 举报与申诉 | 受理 / 取证 / 裁决 / 处置 / 回执 / 申诉复审 | A5 审核队列 | ✅ |

两者共用 `/review` 一个页面、一套「权重排序 + 连续审核」交互（business/03 六章：A3 商品管理只承载 F-A2 的**入口**，
真正的判读处置在 A5）。分开做会把队列页改两遍，VO 与排序逻辑也要重写一次，所以合成一期。

### 1.2 三种来源与状态机（business/03 §4.3）

```
审核：待审核 ─> 已通过 / 已驳回 / 已强制下架      （item_audit.status 1/2/3/4）
举报：待受理 ─> 处理中 ─> 已处理（成立/不成立）    （report.status 1/2/3）
申诉：待复审 ─> 维持 / 撤销（终态，不可再申诉）     （appeal.status 1/2/3）
```

**进队条件**（决定队列里出现什么）：

| 来源 | 进队条件 | 出队条件 |
|---|---|---|
| 商品审核 | `item_audit.status = 1` | 处置后转 2 / 3 / 4 |
| 举报 | `report.status IN (1, 2)` | 处置后转 3，`result` 记 1成立 / 2不成立 |
| 申诉 | `appeal.status = 1` | 裁决后转 2维持 / 3撤销 |

### 1.3 权重公式：库里存一半，查询时补一半

`business/03` F-A2：

```
优先级分 = 举报次数 × 3
          + 图片风险分            // 0–100，ROUND(÷10) 归一化为 0–10
          + 卖家信用扣减分        // (100 − 信用分) / 10
          + 价格异常分            // 偏离同类目均价 3 倍以上 = 5
          + 等待补偿              // 等待每满 12 小时 +1（是补偿，不是惩罚）
```

> 2026-10-06 勘误：business/03 原式写「× 2」与「− 等待衰减补偿」，与注释和代码都不符，
> 已按前端 `calcWeight` 的口径改正（0–10、加法），见 §9.1。

**关键口径**：`item_audit.priority_score` 的注释写的是「基础权重分（**不含等待衰减**，查询时实时补偿）」，
索引 `idx_queue(status, priority_score, enter_queue_at)` 也是按这个形状建的。
所以最终排序键是 `priority_score + FLOOR(TIMESTAMPDIFF(HOUR, enter_queue_at, NOW()) / 12)`，
**不能只用库里的 `priority_score`**——那样风险最高的老单会沉底，正是 F-A2 判据要避免的。

前端 `calcWeight`（`packages/shared/src/admin.ts`）算的是同一个公式，五项拆开存是为了在 UI 上解释「它为什么排第一」。

### 1.4 从表结构读出的业务规则

**`item_audit`**（商品审核单据）

| 字段 | 口径 | 本期怎么用 |
|---|---|---|
| `status` | 1待审核 2已通过 3已驳回 4已强制下架 | 进队/出队条件 |
| `priority_score` | 基础权重（不含等待补偿） | 排序键的前半段 |
| `report_count` / `image_risk` / `price_abnormal` / `credit_deduct` | **进队时的快照** | 权重公式的四个输入；处置后不再变 |
| `enter_queue_at` | 进队时间，SLA 响应时效起点 | 等待补偿 + 「等待时长」列 |
| `first_handle_at` | 首次处置时间 | 首审时长 = 该值 − 进队时间（A9 SLA） |
| `handler_id` | 处置人 | 换人复审要靠它（F-A4）；分审核员 SLA 明细 |
| `handle_cost_ms` | 单条处置耗时，前端埋点上报 | 操作效率指标，本期**由前端上报**还是后端自己算，见问题 7 |
| `reject_reason` / `remark` | 驳回原因 / 处置备注 | 申诉复盘依据 |

**`report`**（举报工单）

- `target_type`：1商品 / 2用户。**演示数据 6 条全是 1**，所以本期队列只处理商品举报，用户举报留待 A-B5。
- `status`：1待受理 / 2处理中 / 3已处理；`result`：1成立 / 2不成立。
- `evidence` 是 JSON（≤3 张凭证图），前端要能展示。

**`appeal`**（申诉工单）

- `biz_type`：1商品审核 / 2举报 / 3订单纠纷；`biz_id`：关联业务 ID。
- `status`：1待复审 / 2维持 / 3撤销。
- ⚠ `biz_id` 指什么没写死，演示数据里也有矛盾——见 §七 数据问题 1。

## 二、开工前必须先拍板的 9 个问题

### 问题 1：🚨 队列列表挂哪个权限点？（缺 `review.view`）

现状的 16 个权限点里，审核域只有三个**写**权限：`review.judge` / `review.forceoff` / `review.appeal`。
只读角色（F-A1 矩阵说它「能看全部数据」）一个都不持有 → 进不了 `/review`；
前端 router 现在只能借 `review.judge` 做门禁，语义不对。

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 新增 `review.view`，四个角色都给（与 `item.view` 一致）；菜单门禁用它，三个写接口仍各挂各的 | 改 `PermCodes` + `admin_role_perm` 授权数据（实库已有数据，要写 SQL）+ 前端 ROLES 表 + 技能脚本 |
| B | 列表接口挂 `review.judge` | 只读角色进不去，与 F-A1 矩阵冲突；论文里会被问 |

**推荐 A**。这是权限矩阵的补漏，不是新设计——`item.view` / `user.view` / `dashboard.view` 都是同一模式的先例。

> **2026-10-06 已落地**：`PermCodes.REVIEW_VIEW` + `perm-codes.ts` + `admin_role_perm` 四行授权 + `router` 门禁
> 四处同步；`prototypes/admin/admin.js` 与 `settings.html` 的菜单 `data-perm="review.view"` 本来就有，
> 说明当初是后端漏了而不是设计上不要。权限点从此 16 → 17，各处「16 个」的表述已一并改掉。

### 问题 2：权重由后端算还是前端算？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 后端算 `parts` 五项 + `weight` 一起返回，前端直接展示、不再本地算 |
| B | 后端只排序不返回权重组成，前端用 `calcWeight` 自己算 |

**推荐 A**：队列顺序是后端给的，权重组成却由前端算，两边公式一旦漂移就会出现「排第一的那条解释出来的分不是最高」。
前端 `calcWeight` 保留但不参与队列展示（它是论文里可引用的公式实现）。

### 问题 3：三种来源一个接口还是三个？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 一个 `GET /admin/review/queue` 返回合并后的队列（`kind` 字段区分来源），前端按 `kind` 过滤切 Tab |
| B | 三个接口，前端自己合并排序 |

**推荐 A**：排序是跨来源的（申诉整体优先于举报），分成三个接口前端就得再排一次，而排序口径正是最不能漂移的东西。

### 问题 4：举报要不要「受理」这一步？

F-A3 的流程是 `待受理 → 处理中 → 已处理`。演示数据里两种状态各有一批（3 条待受理、2 条处理中）。

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 不做独立的「受理」接口。点开处置即视为受理，裁决时一步到位写 `status=3` + `result` |
| B | 加一个 `POST /admin/review/report/{id}/accept`，先把 1 改成 2，再单独裁决 |

**推荐 A**：「处理中」这个状态在单人审核场景下没有意义（没人会把单子挂起来等别人接），
多一个接口就多一次点击，而 F-A9 的硬指标是「单条处置 ≤30 秒」。`status=2` 保留在状态机里，由演示数据体现。

### 问题 5：申诉 `biz_id` 指什么？

`biz_type` 是 1商品审核 / 2举报 / 3订单纠纷，`biz_id` 的注释只写「关联业务ID」。

| 选项 | 口径 |
|---|---|
| **A（推荐）** | `biz_type=1 → item.id`；`2 → report.id`；`3 → trade_order.id` |
| B | 一律指 `item.id`，`biz_type` 只说明申诉的事由 |

**推荐 A**：`biz_type=2` 若不指 `report.id`，就丢掉了「申诉的是哪一次举报处置」，
F-A4 的「原处置人不得复审自己的单」取不到原处置人。演示数据 9003 与这个口径冲突，要修（§七 数据问题 1）。

### 问题 6：队列要不要分页？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 不分页，一次返回全部（12 条） |
| B | 真分页 |

**推荐 A**：连续审核（J / K + 处置完自动跳下条）依赖「整个队列在前端手上」这个前提，
分页会把游标逻辑切碎；队列规模由「待处置单据」决定，真实场景也是几十到几百的量级。
SLA 的积压红牌本身就是「队列不能太长」的约束。

### 问题 7：`handle_cost_ms`（单条处置耗时）谁写？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 后端自己算：进 Drawer（或拉详情）时刻记为起点，提交处置时算差值 |
| B | 前端埋点上报 |

**推荐 A**：前端上报要多一个接口和一次时钟对齐，而后端在处置方法里 `System.currentTimeMillis()` 前后一减就够了。
代价是它记的是「服务端处理时长」而不是「人看的时间」——但打开 Drawer 到提交这段时间本来就在前端，
准确做法是后端存「首次打开详情时间」。**简化**：本期用「队列接口返回该条的时间戳」作起点，
或者干脆只记处置动作本身的耗时并在注释里说明口径（留给 A8 报表用）。

### 问题 8：处置要不要真的改信用分？

`business/03` §4.5：强制下架 −15、被举报成立 −10。

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 本期**只改商品状态不改信用分**，扣分留给 A-B5 用户管理（那里要展示扣分记录与信用分曲线） |
| B | 本期就改 `app_user.credit_score` |

**推荐 A**：信用分是用户域的字段，改它就要有「扣分流水」可查（否则用户问凭什么扣，拿不出依据）。
用户管理还没做，现在扣分等于埋下一处无记录的副作用。本期在 `item_audit.remark` 里记「应扣 15 分」作为待办标记。

### 问题 9：处置后商品状态怎么转？

| 动作 | 商品状态 | 审核单据 |
|---|---|---|
| 通过 | `PENDING(2) → ON_SALE(3)`，`published_at = now()` | `item_audit.status = 2`，写 `handler_id` / `first_handle_at` |
| 驳回 | `PENDING(2) → REJECTED(6)` | `item_audit.status = 3`，写 `reject_reason` |
| 强制下架 | → `FORCED_OFFLINE(7)` | `item_audit.status = 4`（**复用 `ItemAdminService.forceOffline`**） |
| 举报成立-轻 | 商品下架整改（→ `OFFLINE(4)`？） | `report.status=3, result=1` |
| 举报成立-重 | 强制下架（→ 7） | 同上 + 走 `forceOffline` |
| 举报不成立 | 商品不动 | `report.status=3, result=2` |
| 申诉撤销 | 商品恢复（`FORCED_OFFLINE(7) → ON_SALE(3)` 或 `REJECTED(6) → PENDING(2)`） | `appeal.status=3` |
| 申诉维持 | 商品不动 | `appeal.status=2` |

⚠ 举报「成立-轻」到底把商品改成 4（卖家自己下架的语义）还是 7（平台处置）需要定：
**推荐走 `forceOffline` → 7**，理由同 notes/08 §1.2——平台处置是终态，不能混进「卖家可自行重新上架」的 4。

### `ReviewTaskVO` ↔ 前端 `QueueTask` 对齐表

| 前端字段 | 后端来源 | 备注 |
|---|---|---|
| `id` | 各单据主键 | 跨来源不唯一，前端排序用它做 key 即可 |

### 数据问题 2：申诉指向了没有被处置过的商品

```
9001 → item 4041（status=5 已售出，从未被处置）
9002 → item 4049（status=3 在售，从未被处置）
9003 → item 4008（status=3 在售）
```

申诉的前提是「存在一次可申诉的处置」。库里真正被处置过的只有两条：
`item_audit.status=3`（驳回）1 条、`status=4`（强制下架）1 条。

### 数据问题 3：`priority_score` 与权重公式对不上口径

库里待审核 5 条的 `priority_score` 是 **65 / 66 / 72 / 74 / 77**，
而按 F-A2 公式算（`举报0×3 + 风险0.8~2.2 + 信用0.1~0.4 + 价格0`）应该只有 **1~3 分**。
库里的值像是「0–100 的风险分」而不是权重分。

另外 `enter_queue_at` 是 9 月初到 9 月底，到现在（10 月）已过去 7–33 天，
按「每满 12 小时 +1」算，等待补偿是 **14–66 分**，会完全压过其他因子——
队列看起来就只是「按等待时长排序」，演示不出「举报多的排前面」。

修法两条，**都要做**：
1. 按 F-A2 公式重算 `priority_score`（或干脆把演示数据里的值改成公式算出来的小数值）
2. 把 `enter_queue_at` 刷成最近 1–3 天，让等待补偿落在 0–6 分区间

> 不改的话，权重排序这条 F-A2 判据在演示时**看不出效果**，答辩现场会被问「为什么它排第一」。
