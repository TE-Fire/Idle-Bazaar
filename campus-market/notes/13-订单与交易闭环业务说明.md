## 一、模块定位

**订单是整个平台唯一产出交易事实的模块。** 在它之前，后端已经能管理商品、审核商品、处置违规、查操作日志，
但这些能力都离不开别人的输入：商品靠管理员录入或演示数据，举报和申诉也只有演示数据。
真正由用户行为驱动、会改变商品状态的数据流一条都还没有。

| 缺口 | 具体表现 |
|---|---|
| 「已售出(5)」无人写入 | 只出现在数据字典里，没有任何业务路径能产生它；申诉撤销的恢复规则（`已强制下架(7)→在售(3)`、`审核未过(6)→待审核(2)`）始终缺一个真实触发场景 |
| 审核队列只有演示数据 | 三个来源里，商品审核要等学生发布，举报与申诉要等学生提交，而学生端连发布接口都没有 |
| `appeal.biz_type = 订单纠纷(3)` 被丢弃 | 不是写漏，是当时根本没有订单可供引用 |

所以订单与学生端必须一起做：单独补订单，队列里依然不会有真实单据；单独做学生端发布而订单缺失，
发布出来的商品永远只能走到「通过 / 驳回」，走不到交易。

| 订单落地后 | 解锁的东西 |
|---|---|
| `trade_order` 产生交易记录 | 商品「已售出(5)」有了真实来源；申诉撤销的恢复场景可演示 |
| 完成 / 违约可改信用分 | `credit_log` 的 `TRADE_DONE`、`BREACH_CANCEL` 两个 `reason_type` 有了写入方 |
| 订单纠纷有了承载 | `appeal.biz_type = 订单纠纷(3)` 已接进审核队列（见 O11） |
| 学生端发布接口 | `item_audit` 队列有了真实来源，不再只靠演示数据 |

## 三、业务条目

### O1 · 商品发布

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/item/publish` | 登录 | 发布：存草稿或提交送审两种 |

**前置**

- 当前用户已登录（`UserContext.getUserId()`，**不接受客户端传用户 id**）。

**规则**

1. 提交 `ItemPublishReq`：标题、描述、分类、成色、价格、图片、校区、面交点；`draft` 标志区分意图。
2. 判断提交意图：
   1. **存草稿**（`draft = true`）→ `item.status = 草稿(1)`，**不插入** `item_audit`，不进审核队列。豁免图片与描述（含 D 档描述必填）；但标题/分类/成色/价格/校区仍必填——`item` 表这些列 NOT NULL，草稿同样要落库（business/02「稍后补齐」口径）。
   2. **提交送审**（`draft` 为空/false）→ `item.status = 待审核(2)`，并**同步插入一条 `item_audit`**，否则管理端审核队列里看不到这件商品。
3. 进队时一次性算好四个快照分量（与 `notes/09` §五同口径）：
   1. `report_count`：当前实时举报数（进队时实查 `report` 表；2026-10-21 前恒 0，已修正）
   2. `image_risk`：**恒 0 的预留分量**——本期没有图片检测源，一期占位（db/01 §5.6 同口径），二期接识别服务后填入
   3. `credit_deduct`：当时的信用扣减分
   4. `price_abnormal`：价格是否偏离同类目成交均价 3 倍以上
4. 字典项（分类、成色、面交点）必须存在且启用；否则拒绝。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `item` | 插入一行；送审时 `status = 待审核(2)`，草稿时 `status = 草稿(1)` |
| `item_audit` | 送审时插入一条 `status = 待审核(1)`，带四个快照分量与 `enter_queue_at` |

### O2 · 商品编辑

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/item/{id}/edit` | 登录 + ownership | 编辑商品 |

**前置**

- 当前用户是该商品卖家。

**规则**

1. 判断商品当前状态：
   1. **草稿(1)** → 可继续编辑：`draft = true` 继续暂存（仍不进队）；`draft` 为空/false 即送审 → `status = 待审核(2)` 并进队（不论字段是否变化——此前从没进过队）。
   2. **在售(3) / 已下架(4)** → `draft` 标志忽略，按普通编辑处理。
   3. **审核未过(6)** → 可修改后重提：保存即回 `待审核(2)` 并进队，不论字段是否变化（business/01 状态机「看驳回原因 → 修改后重提」）。
   4. 其余状态（待审核/已售出/已强制下架）→ 当前状态不能编辑(1109)。
2. 已发布商品（在售/已下架）判断改动范围：
   1. 只改描述 → 免审，直接更新。
   2. **改价格或改成色** → 商品**回待审核**：`item.status = 待审核(2)`，并重新进队（刷新 `item_audit` 快照）。
      1. 理由：价格与成色是交易的核心事实，改动后必须重新过一遍判读。
3. 纯草稿暂存豁免「成色 D 描述必填」（允许先存着回头再补）；送审与已发布编辑两个路径都查。
4. 非卖家调用 → 无权操作他人商品。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `item` | 更新字段；草稿送审、驳回重提或已发布商品涉价格 / 成色时 `status = 待审核(2)` |
| `item_audit` | 草稿送审、驳回重提、已发布商品涉价格 / 成色时进队（草稿续存不进队） |

### O4 · 商品浏览与详情

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/item/list` | 免登录 | 首页 / 筛选 / 关键词搜索（ngram 全文索引已在库）；支持 `sellerId` 精确筛某卖家的在售品（个人主页用，2026-10-28 补） |
| GET | `/api/item/{id}` | 免登录 | 详情；浏览量 +1（Redis 聚合，5 分钟落库） |

**前置**

- 无。

**规则**

1. 列表：按校区、分类、成色、关键词筛选；关键词走 `ngram` 全文索引。
2. 详情：返回商品字段 + 图片列表 + 卖家信息；每访问一次浏览量 +1。
3. 商品不存在、已软删、或非在售态 → 商品不存在(1101)（对买家不可见）。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `item.view_count` | 详情被访问时不再直接写库：Redis `cm:item:view`（Hash，field = itemId）累加，`@Scheduled` 每 5 分钟批量落库。**库值最多滞后 5 分钟**，但接口返回的是「库值 + Redis 增量」，详情页与列表看到的数都是准的。浏览量不去重（热度粗略信号，做 UV 精确需另建去重表，不划算） |

### O5 · 下单

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/order/create` | 登录 | 下单 → `待付款(1)`；面交带面交点与约定时间，送货上门带收货地址 `addressId`（自提由商品提货地址带入） |

**前置**

- 商品 `status = 在售(3)`。
- 买家不是卖家本人。

**规则**

1. 校验商品在售；不在售 → 商品不存在(1101) / 当前状态不允许(1105 段 C 端语义)。
2. 插入一条 `trade_order`：`status = 待付款(1)`，带面交点、约定时间。
3. **下单不锁定商品**（铁律：无「已预定」）——判断 ownership 的唯一时刻是付款成功的那一刻，先付款先得。
4. 写入商品快照字段（见 §四.3）：`item_title` / `item_price` / `item_grade` / `item_main_image` + `snapshot json`。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | 插入一条 `status = 待付款(1)`，`expire_time = now + 30min` |
| `item` | **不动** |

### O6 · 模拟支付（两级占位）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/order/{id}/pay` | 登录 + ownership | 模拟支付 → 两级占位校验 → 按收货方式置后态（面交→`待面交(2)`、自提→`待自提(11)`、送货上门→`待发货(9)`），并批量取消同商品其余待付款订单 |
| POST | `/api/order/{id}/ship` | 登录 + 仅卖家 | 送货上门专用：`待发货(9)` → `已发货(10)` |
| POST | `/api/order/{id}/receive` | 登录 + 仅买家 | `已验货(3)` / `已发货(10)` / `待自提(11)` → `已完成(4)`，统一写 `verify_time` |

**前置**

- 订单属于当前买家，且 `status = 待付款(1)`。

**规则**

1. 第一级 · Redis Lua 抢占状态标记（`cm:item:state:{itemId}`）：
   1. 返回 `1` 抢到 → 继续第二级
   2. 返回 `0` 冲突 → 立即失败（商品已被他人买走）
   3. 返回 `-1` 缓存缺失 → **放行**交给 DB 裁决（缓存未预热或被淘汰时 Lua 无从判定，「缺失即拒绝」会让缓存一失效商品就永远卖不掉；放行是安全的，因为 DB 会拦住）
   4. 返回 `2` 幂等重入（同一订单重复支付）→ 直接返回成功，不重复扣减
2. 第二级 · MySQL 条件更新兜底：

   ```sql
   UPDATE item SET status = 已售出(5), version = version + 1
    WHERE id = ? AND status = 在售(3) AND version = ?
   ```

   1. 影响行数 = 1 → 占位成功
   2. 影响行数 = 0 → 占位失败，**回滚 Lua 标记前必须校验 holder 是自己的 orderId**，否则走得慢的请求会把别人刚拿到的锁误释放
3. 两级不是替代关系：Lua 挡掉绝大多数并发，DB 做最终裁决。
4. 占位成功后收尾：**同一商品其余所有待付款订单批量取消并通知买家**。
   1. 这不是可选的清理动作：不做，那些订单会悬在待付款状态直到各自 30 分钟超时才消失，而这期间买家看到的是「已付款待面交」的假象。
5. 本订单按收货方式置后态并记录 `pay_time`：面交→`待面交(2)`、自提→`待自提(11)`、送货上门→`待发货(9)`。

**关键参数（写错每一个都有明确的故障模式）**

| 参数 | 值 | 理由 |
|---|---|---|
| Lua 锁 TTL | **60 秒** | 覆盖「抢到标记 → DB 提交」这段毫秒到秒级窗口；设成订单超时时长（30 分钟）会在异常路径下把商品白白锁死半小时 |
| 缓存缺失返回值 | **-1 放行** | 见第 1.3 步 |
| DB 失败回滚 | **校验 holder** | 见第 2.2 步 |

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | 本订单 → 待面交(2) / 待自提(11) / 待发货(9)（按 `delivery_type`）；同商品其余待付款订单 → `已取消(5)` |
| `item` | 占位成功 → `已售出(5)` |

### O7 · 超时取消（系统内部）

**接口**

- **无对外接口**。触发点：`OrderService#cancelExpired`，由 `@Scheduled` 每 10 分钟扫描一次（决策 A，不引入 MQ）。

**前置**

- 扫描条件：`status = 待付款(1)` 且 `expire_time < now`（走 `idx_expire(status, expire_time)`）。

**规则**

1. 定时任务每 10 分钟扫一遍过期未付款订单。
2. 对每个命中订单：
   1. 订单仍是 `待付款(1)` → 取消：`status = 已取消(5)`，`cancel_type = 超时未付款`。
   2. 订单已付款 → 丢弃，不动。
3. 取消是纯状态迁移，不涉及资金（本平台不走真实资金流）。
4. RocketMQ 延迟消息方案**本期未接入**（`campus-core` 无任何 MQ 类）；调度扫描既是现行方案，也是将来消息方案的兜底——补消息时不需要改这段代码。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | 过期未付款 → `已取消(5)` + `cancel_type` |

### O8 · 取消订单

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/order/{id}/cancel` | 登录 + ownership | 取消；付款前后语义不同 |

**前置**

- 订单属于当前用户（买家或卖家）。

**规则**

1. 按付款与否分叉（已付款之后的「取消」不再是作废，而是一次退款申请）：
   1. **待付款(1)** → 直接作废：`status = 已取消(5)`，`cancel_type = 买家主动取消`（或卖家取消，按操作方记）。
   2. **任一已付款未完成态（待面交(2) / 已验货(3) / 待发货(9) / 已发货(10) / 待自提(11)）** → 落到 `退款中(6)`，等卖家受理（走 O9 流程）。
      1. 理由：钱已经在这个流程里「付」过，直接把订单置为已取消会让卖家的货款无从交代。
2. 已取消 / 已完成 / 已退款 → 拒绝（终态不可再动）。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | 待付款 → `已取消(5)`；任一已付款未完成态 → `退款中(6)` |

### O9 · 退款

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/order/{id}/cancel` | 登录 + ownership | **买家**发起退款申请（付款后取消的落点，即 O8 的已付款分叉，无独立端点） |
| POST | `/api/order/{id}/refund` | 登录 + ownership（限卖家） | **卖家**受理：同意 → `已退款(7)`，拒绝 → `纠纷中(8)` |

**前置**

- 订单 `status ∈ { 待面交(2), 已验货(3), 待发货(9), 已发货(10), 待自提(11) }`（买家申请）或 `退款中(6)`（卖家受理）。

**规则**

1. 买家申请：入口是 O8 的 `POST /api/order/{id}/cancel`（已付款分叉），订单 → `退款中(6)`。
2. 卖家受理，分三路：
   1. **同意** → 订单推进到 `已退款(7)`，不计违规；商品恢复 `在售(3)`——含重置占位标记，否则 Lua 继续把恢复在售的商品当已售挡下，货回来了却永远不能再卖。
   2. **24 小时未响应** → 系统自动同意，转 `已退款(7)`（商品同样恢复在售）。
      1. 24 小时起算点**借用 `update_time`**：`trade_order` 没有「申请退款的时刻」这一列，而订单停留在退款中时不会有别的地方改写 `update_time`，所以借用是安全的。
      2. 这是借来的语义：一旦退款这条分支上再长出别的写操作，应当补一列 `refund_apply_time`，而不是继续借用。
   3. **拒绝** → 订单转入 `纠纷中(8)`，双方冻结，转管理端裁决（O12）。
3. **本平台不走真实资金流，退款是一次状态迁移而不是一次资金退回**——文案上避免出现「款项已退回原账户」这类暗示存在真实结算的表述。
4. 卖家以外的人调用 `refund` → 落到「无权操作他人订单」（`handleRefund` 按 `seller_id` 校验）。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | `退款中(6)` → `已退款(7)` 或 `纠纷中(8)` |
| `item` | 转 `已退款(7)` 时由 `已售出(5)` 恢复为 `在售(3)` |

### O12 · 订单纠纷（发起 / 裁决）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/order/{id}/dispute` | 登录 + ownership | 任一方发起纠纷 → `纠纷中(8)` |
| POST | `/admin/order/{id}/arbitrate` | `order.arbitrate` | 管理端裁决（A6 订单页入口；`result` = `REFUND_BUYER` / `PAY_SELLER`） |
| POST | `/admin/review/appeal/{appealId}/judge` | `review.appeal` | 同一个 Service 的另一入口（审核队列 R4，见 `notes/09`） |

**前置**

- 订单 `status ∈ { 待面交(2), 已验货(3), 待发货(9), 已发货(10), 待自提(11), 退款中(6) }`（发起）；`appeal.biz_type = 订单纠纷(3)`（裁决）。

**规则**

1. 发起：订单 → `纠纷中(8)`，双方都不能再操作（冻结态）。
   1. **同事务写一条 `appeal`**（`biz_type = 订单纠纷(3)`，申请人 = 发起方）：申诉单是管理端取件的唯一入口，只冻订单不写单，纠纷在审核队列里不存在，谁也裁不了。卖家拒绝退款时由系统代写，申请人取买家（退款诉求本由买家发起）。
   1. Web 端只提供「发起 + 查看进度 + 补充凭证」，裁决权在管理端（`business/01` F-W5）。
2. 管理端取件：纠纷以 `appeal` 表 `biz_type = 订单纠纷(3)` 的形态出现在审核员面前（`notes/09` R4）。
   1. `biz_id` 指向 `trade_order.id`，由 `order.item_id` 反查商品
   2. 裁决时 `ReviewAdminService#judgeAppeal` **先按 `biz_type` 分流**：订单纠纷走 `OrderService#settleDispute`，其余两类才走对商品的 reverse revoke
   3. 语义差异：订单纠纷的商品本身可能从未被处置过，所以撤销（申诉成立）时要纠正的是**订单状态**，而不是把商品恢复上架
   4. **两个入口、一套实现**（2026-10-26）：审核队列走 `review.appeal`，订单页走 `order.arbitrate`——权限分属两个角色，但都进 `judgeAppeal`。若让运营去调审核接口，等于把申诉裁决权一并给了他（business/03 A6）
3. 裁决结果只能映射到已有终态：
   1. 买家赢（申诉成立）→ `已退款(7)`（商品恢复在售，同 O9 口径）
   2. 卖家赢（维持）→ `已完成(4)`
   3. 「纠纷已裁决」在库里**没有对应状态码**，这也是它无法成为独立终态的直接原因
4. 订单纠纷**没有原处置人**：它是买卖双方谈不拢后由系统转入的，此前不存在任何管理员处置，
   `originHandlerOf` 返回 null 会让 F-A4 的换人复审校验自动放宽——这不是规则被绕过，而是它本来就不存在「自己复审自己」的对象。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `trade_order` | `纠纷中(8)` → `已退款(7)` 或 `已完成(4)` |
| `appeal` | `status = 撤销(3)` / `维持(2)` |

**错误码**：2010 仅已完成可评、2011 评价窗口已过、2012 标签不合法；重复提交不报错（幂等返回既有评价）。

**前置**

- 订单状态 = 已完成(4)。待付款、待面交、已验货、退款中、纠纷中一律不可评——交易没走完，评人没有依据。
- 操作人是该单买家和卖家之一；`target_id` 由服务端按「对方」推出，**不接受前端传被评价人 id**（否则可以把差评挂到任意人头上）。

**规则**

1. 一单一评：唯一键 `(order_id, reviewer_id, deleted)`。重复提交返回既有评价而不是覆盖——评价是公开内容，允许改会让「先给好评再改差评」变成报复手段。
2. 收货后 30 天内可评，超窗口返回「评价已过期(2011)」。**窗口从 `trade_order.verify_time`（面交核销那一刻）起算**——库里没有单独的「收货时间」列，`status=4` 也没有记录落库时刻的字段；拿 `update_time` 起算会被后续任何写入（比如这次评价本身）刷新，越评越久。从下单算更不对。
3. 买家评卖家、卖家评买家各一条，互不依赖。**不做「双方都评完才互见」的双盲**：那要额外的揭晓状态和超时揭晓任务，收益是防报复评价，代价是链路变长。代价（谁先评谁吃亏）记入已知缺口。
4. 标签来自服务端常量表（如「描述一致」「发货快」「沟通顺畅」/「描述不符」「拖延」），不进字典表——它跟交易场景绑死，不是运营可配的内容。一次最多选 3 个。
5. 评价内容过敏感词服务（与动态/评论同一套）：高危词直接拒绝(4024)，低危词替换后入库。
6. **不联动信用分**。信用分在 O11 确认收货时已 +1，互评再动一次就是同一件事扣两次；口径必须分开——信用分记行为，评分记主观感受。
7. 个人主页的评分汇总按 `target_id` 现算 `AVG(rating)` 与各星级 `COUNT`，不做冗余列；评价条数在百级，实时聚合没有压力。

| 对象 | 变化 |
|---|---|
| `user_review` | 新增一行；双方各最多一条 |
| 订单详情 | 显示「我已评价 / 待评价」与对方评价内容 |

## 四、通用业务规则

### 4.1 订单状态机：十一个状态与四个终态

`trade_order.status` 在库里定义十一个取值：待付款(1)、待面交(2)、已验货(3)、已完成(4)、已取消(5)、退款中(6)、已退款(7)、纠纷中(8)、待发货(9)、已发货(10)、待自提(11)。

付款之后的分化由**收货方式**（`delivery_type`：面交 / 自提 / 送货上门）决定，不再是一条「付款即待面交」的直线：

```
待付款(1) ──30min超时──> 已取消(5)
   │
   └─模拟支付─┬─面交────> 待面交(2) ──买家核销─> 已验货(3) ──买家确认──> 已完成(4) ─> 触发互评
              ├─送货上门─> 待发货(9) ──卖家发货─> 已发货(10) ──买家确认──> 已完成(4)
              └─自提────> 待自提(11) ──买家确认自提──────────────> 已完成(4)
   任一「已付款未完成」态 ─付款后退款申请─> 退款中(6) ─> 已退款(7)
   任一「已付款未完成」态 ─任一方发起纠纷─> 纠纷中(8)（冻结，转管理端裁决）
```

- **终态是四个：已完成(4)、已取消(5)、已退款(7)、纠纷已裁决**（后者映射到 已完成(4) / 已退款(7)，库里没有独立码）。
- **三个新态（待发货(9) / 已发货(10) / 待自提(11)）都非终态，且与待面交(2)/已验货(3) 共享同一套退款与冻结语义**：都能经「取消」落到退款中(6)，也都能发起纠纷落到纠纷中(8)。三者的差别只在履约动作——面交要买家核销、送货上门要卖家先发货、自提要买家到店自取。
- **收货方式决定地址交互**：自提商品的提货地址由卖家发布时从自己的自提地址簿（`user_address.kind=PICKUP`）选定存到 `item.pickup_address_id`；送货上门必须由买家下单时选自己的收货地址（`kind=SHIP`）；面交仍走面交点。订单的 `delivery_type` 在创建时从商品抄入并固化，地址同时快照进 `address_contact/phone/detail`，之后不随商品或地址簿改动——与商品快照同一条取证原则。
- `已验货(3)` 不是终态：它只表示双方已在线下碰面并完成核销，货品是否认可还未确定，必须还能继续推进到已完成或退到纠纷中。
- 口径澄清：`business/01` 的流程图写「买家确认收货 → 订单已完成」，中间没有停顿；但库里有完整的
  `verify_code` / `verify_time` / `verify_by` 三个字段和「已验货」这个独立状态。两者不是冲突，是粒度不同——
  3 已验货是面交现场的核销动作，4 已完成才是对货品本身的认可，必须先有前者。
- `cancel_type` 区分取消来路（超时未付款 / 买家主动 / 卖家主动 / 被占用），见 `CancelTypeEnum`。

### 4.2 付款才占位：并发下唯一的所有权判据

1. 本平台取消了一切预定机制，判断 ownership 的唯一时刻是**付款成功的那一刻**（`business/01` 已决策）。
2. 工程后果：下单只插入一条待付款订单，商品保持在售不动；付款才是真正的争抢点。
3. 实现是两级结构（Redis Lua 前置 + MySQL 条件更新兜底），细节见 O6。
4. 一处已知的口径漂移：`tech/01` 的示例 SQL 写 `status = 'ON_SALE'` 这类字符串，而 `schema.sql` 的
   `item.status` 是 `tinyint`（在售(3)、已售出(5)）。**以库为准**，设计文档里的 SQL 是示意，不是待抄的实现。

### 4.3 商品快照：订单为什么抄一份数据

`trade_order` 有五个显式快照字段（`item_title` / `item_price` / `item_grade` / `item_main_image`）外加一个
`snapshot json` 存完整商品信息。这套冗余不是为了查询方便——订单列表展示标题和价格确实可以 JOIN `item` 拿到——
而是为了**防止卖家事后改价改描述**。

1. 二手交易纠纷的典型形态是「下单时说九成新，收到后发现描述不符」。
2. 若订单只存 `item_id`，卖家在面交前把描述或价格改掉，管理者复盘时看到的永远是改后的版本，买家无从举证。
3. 把完整的商品状态在下单那一刻固化进订单，纠纷取证才有可信的数据源。
4. **这些字段在下单之后一律不允许同步更新**，哪怕卖家后续修改了商品，历史订单的快照也必须保持下单时的原样。

### 4.4 学生端鉴权

1. 学生端认证无需新设计：`MultiAccountConfig` 已注册与管理端完全独立的 `StpUserUtil`（token 名 `satoken-user`、7 天、多设备并发）。
2. 取当前用户统一走 `UserContext.getUserId()`——与管理端 `AdminContext` 同构，同样是懒加载 + 请求内缓存。
3. 所有写接口都拿它作为当事人，**不接受客户端传来的用户 id**（那种写法等于允许替他人下单）。
4. 学生端不新增权限点：`StpUserUtil.checkLogin()` + ownership 校验即可。
5. `app_user` 的封禁状态在网关层判断，与既有设计一致，不在本轮展开。

## 五、验收口径与已知缺口

### 5.1 验收口径（业务侧）

- [ ] 发布商品：送审 → `待审核(2)` + `item_audit` 进队，管理端队列可见
- [ ] 编辑商品：只改描述免审；改价格 / 成色 → 回 `待审核(2)` 重新进队
- [ ] 下单：`待付款(1)`，商品保持 `在售(3)` 不动
- [ ] 支付：两级占位生效；同商品其余待付款订单一并取消
- [ ] 超时取消：30 分钟未付款 → `已取消(5)`
- [ ] 付款后取消 / 退款：`退款中(6)` → `已退款(7)`（卖家同意或 24h 自动）/ `纠纷中(8)`（卖家拒绝）
- [ ] 核销：任一方扫码 → `已验货(3)`，`verify_by` 记录实际扫码人
- [ ] 确认收货：`已验货(3)` → `已完成(4)`
- [ ] 纠纷：`纠纷中(8)` → 裁决映射 已退款(7) / 已完成(4)，商品状态不被误改
- [ ] 举报 / 申诉提交：管理端队列即时出现真实单据

> ⚠️ O6 的并发两级占位**未做实弹实测**（两个请求同时 `pay` 同一商品）。这是本模块唯一的核心并发路径，建议单独压一次。
