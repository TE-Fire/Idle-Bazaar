> 范围：订单模块（`trade_order`）与学生端的发布 / 交易 / 举报申诉接口。
> 实现以本文为准；与 `business/01`、`tech/01` 口径不一致处以本文定义为准，并把差异同步回原文档。

## 一、订单为什么是现在缺的那块拼图

**订单是整个平台唯一产出交易事实的模块。** 在此之前，后端已经能管理商品、审核商品、处置违规、查操作日志，但所有这些能力都离不开别人的输入：商品靠管理员在管理端录入或演示数据，举报和申诉也只有演示数据。真正由用户行为驱动、会改变商品状态的数据流一条都还没有。

这个缺口造成三处具体的、已经能观察到的问题。第一，`item.status` 里的「已售出（5）」从来没人写入过——它只出现在数据字典里，没有任何业务路径能产生它，于是申诉撤销时的恢复规则（`7→3`、`6→2` 逆转判定）始终缺一个真实的触发场景。第二，审核队列只有演示数据可查：队列的三个来源里，商品审核要等学生在前端发布才会自然产生，举报与申诉要等学生提交，而现在学生端连发布的接口都没有。第三，`appeal.biz_type = 3`（订单纠纷）在 `ReviewAdminService` 里被刻意丢弃——不是写漏了，是当时根本没有订单可供引用。

所以订单与学生端必须一起做。单独补订单模块，队列里依然不会有真实单据；单独做学生端发布而订单缺失，则发布出来的商品永远只能走到「通过/驳回」，走不到交易。两者合起来补齐的才是从发布到评价的完整闭环。

| 订单落地后 | 解锁的东西 |
|---|---|
| `trade_order` 产生交易记录 | 商品「已售出（5）」有了真实来源；申诉撤销的恢复场景可演示 |
| 完成/违约可改信用分 | `credit_log` 的 `TRADE_DONE`、`BREACH_CANCEL` 两个 `reason_type` 有了写入方 |
| 订单纠纷有了承载 | `appeal.biz_type = 3` 已接进审核队列（见第五节） |
| 学生端发布接口 | `item_audit` 队列有了真实来源，不再只靠演示数据 |

## 二、订单状态机：八个状态与四个终态

`trade_order.status` 在库里定义了八个取值：1 待付款、2 待面交、3 已验货、4 已完成、5 已取消、6 退款中、7 已退款、8 纠纷中。这里面有一个需要先坐实的口径分歧：`business/01` 的流程图写的是「买家确认收货 → 订单已完成」，中间没有停顿；但库里有完整的 `verify_code` / `verify_time` / `verify_by` 三个字段和「已验货」这个独立状态。两者不是冲突，是粒度不同——3 已验货是面交现场的核销动作，4 已完成才是对货品本身的认可，必须先有前者。

```
待付款 ──30min超时──> 已取消
   │
   └─模拟支付─> 待面交 ──扫码核销─> 已验货 ──买家确认收货─> 已完成 ─> 触发互评
                  │                                        
                  ├─付款前取消──────────────────────> 已取消
                  ├─付款后退款申请──────────────────> 退款中 ─> 已退款
                  └─任一方发起纠纷──────────────────> 纠纷中（冻结，转管理端裁决）
```

**终态是四个：已完成、已取消、已退款、纠纷已裁决。** 已验货不是终态，它只表示双方已经在线下碰面并完成核销，此时货品是否已经认可还未确定，因此它必须还能继续推进到已完成或退到纠纷中。

两个容易被忽略的细节。一是核销码在整个订单生命周期里只有一张（`uk_verify_code` 唯一约束证明了这一点——如果买卖双方各有一码，这个唯一键就应该是两条），所以核销是**任一方扫码即成立**的单次动作，`verify_by` 记录的是实际扫码的人，用于复盘而不是授权。二是 Web 端不做核销：按 `business/01` 的端部分工，扫码签收发生在移动端，桌面端只在 /order/:id 上展示二维码与核销状态。

## 三、付款才占位：并发下唯一的所有权判据

**本平台取消了一切预定机制，判断 ownership 的唯一时刻是付款成功的那一刻。** 这是 `business/01` 已决策的结论，它的工程后果是：下单只插入一条待付款订单，商品保持在售不动；付款才是真正的争抢点。

`tech/01` §9.1 已经把这条路径设计完整，实现时应按其执行——两级结构，Redis Lua 前置 + MySQL 条件更新兜底，二者不是替代关系：

```
模拟支付触发
   ├─ ① Redis Lua 抢占状态标记（cm:item:state:{itemId}）
   │      1 抢到 → 继续 ②      2 幂等重入 → 直接返回成功
   │      0 冲突 → 立即失败       -1 缓存缺失 → 放行交给 DB
   └─ ② UPDATE item SET status = 5, version = version + 1
        WHERE id = ? AND status = 3 AND version = ?      -- 影响行数 1 才算赢
```

三个细节不能写错，写错每一个都有明确的故障模式。**Lua 锁的 TTL 是 60 秒而不是 30 分钟**，它覆盖的是「抢到标记 → DB 提交」这段毫秒到秒级的窗口，设成订单超时时长会在异常路径下把商品白白锁死半小时。**返回值 -1 必须放行**而不是拒绝——缓存未预热或已被淘汰时 Lua 无从判定，设计成「缺失即拒绝」会让缓存一失效商品就永远卖不掉；放行是安全的，因为 DB 会拦住。**DB 失败回滚 Lua 标记前必须校验 holder 是自己的 orderId**，否则那个走得慢的请求会把别人刚拿到的锁误释放。

赢家占位之后还有一步收尾：**同一商品其余所有待付款订单要批量取消并通知买家**。这不是可选的清理动作——如果不做，那些订单会悬在待付款状态，直到各自的 30 分钟超时才消失，而这期间买家看到的是「已付款待面交」的假象。

需要留意一处代码层的不一致：`tech/01` 的示例 SQL 里写的是 `status = 'ON_SALE'` 这类字符串，而 `schema.sql` 的 `item.status` 是 `tinyint`（3 在售、5 已售出）。实现时以库为准，这条 SQL 应当写成 `status = 3` 与 `status = 5`。此处的 SQL 是设计示意，不是待抄的实现。

## 四、超时取消与逆向退款

下单成功即刻发一条 RocketMQ 延迟消息，延迟等级对应 30 分钟；消费者收到后检查订单仍是待付款则取消，已付款则直接丢弃。**只靠消息不够，还要 `@Scheduled` 每 10 分钟扫一次 `idx_expire(status, expire_time)` 做补偿**，防止消息丢失让某些订单永久悬停。这两条是配套的，前者负责时效，后者负责兜底，缺任何一条都会泄漏待付款订单。

这里有一个必须先摆到台面上的现实约束：**README 的已知待办里 RocketMQ 生产者/消费者至今未接入**（当前 `campus-core` 里没有任何 MQ 相关类）。因此订单的超时取消有两种落地方式，需要你选择（推荐项见第九节）。

逆向流程发生在付款之后。买家申请退款时订单进入退款中（6），此后分三路：卖家同意则直接推进到已退款（7）且不计违规；卖家 24 小时未响应由系统自动同意；卖家拒绝则订单转入纠纷中（8）。必须强调的是，**本平台不走真实资金流，退款是一次状态迁移而不是一次资金退回**——文案上要避免出现「款项已退回原账户」这类暗示存在真实结算的表述。

这里有一处先天的约束：**"申请退款的时刻"在表里没有专门的列**。`trade_order` 只有 `update_time`，而订单停留在退款中时不会有别的地方改写它，所以自动同意的 24 小时起算点只能借用 `update_time`。这层借用是安全的，但它是借来的语义——一旦退款这条分支上再长出别的写操作，应当补一列 `refund_apply_time` 而不是继续借用它。

同理，已付款之后的「取消」不再是一次作废，而是一次退款申请：钱已经在这个流程里「付」过，直接把订单置为已取消会让卖家的货款无从交代。因此实现上 `OrderService#cancel` 按付款与否分叉——待付款直接作废，待面交与已验货则落到退款中等卖家处理。

## 五、纠纷该怎样接进管理端

订单进入纠纷中（8）之后是冻结态，双方都不能再操作，等待裁决——这一点 `business/01` F-W5 已经定了，Web 端只提供「发起 + 查看进度 + 补充凭证」，裁决权在管理端。

落地时的关键问题是：这次纠纷以什么形态出现在审核员面前。现有通道是 `appeal` 表的 `biz_type = 3`（订单纠纷），而 `ReviewAdminService` 原本对它是丢弃处理（`appealTask` 解析不出商品就返回 null，单据不进队列）。既然订单已经存在，`biz_id` 指向订单后由 `order.item_id` 取商品没有技术障碍，本期按 B 落地：`appealItemId` 增加由订单反查商品的分支，并仿照 `reportsById` 补一个 `ordersById` 的批量查询，避免每条申诉回库一次。

接进队列之后有一处语义差异要留意：订单纠纷的商品本身可能从未被处置过，所以审核员撤销（申诉成立）时要纠正的是订单状态，而不是把商品恢复上架。`ReviewAdminService#judgeAppeal` 因此先按 `biz_type` 分流，订单纠纷走 `OrderService#settleDispute`，其余两类才走对商品的 `revoke`。

裁决结果只能映射到已有终态——买家赢（申诉成立）转已退款（7），卖家赢（维持）转已完成（4）。前文第二节提到的「纠纷已裁决」在库里没有对应状态码，这也是它无法成为独立终态的直接原因。

还有一点：订单纠纷**没有原处置人**。它是买卖双方谈不拢后由系统转入的，此前不存在任何管理员处置，`originHandlerOf` 返回 null 会让 F-A4 的换人复审校验自动放宽。这不是规则被绕过，而是它本来就不存在「自己复审自己」的对象。

## 六、商品快照：为什么订单要抄一份数据

`trade_order` 里有五个显式的快照字段（`item_title` / `item_price` / `item_grade` / `item_main_image`）外加一个 `snapshot json` 存完整商品信息。这套冗余不是为了查询方便——订单列表展示标题和价格确实可以 JOIN `item` 拿到——而是为了**防止卖家事后改价改描述**。

二手交易纠纷的典型形态是「下单时说九成新，收到后发现描述不符」。若订单只存 `item_id`，卖家在面交前把描述或价格改掉，管理者复盘时看到的永远是改后的版本，买家无从举证。把完整的商品状态在下单那一刻固化进订单，纠纷取证才有可信的数据源。因此**这些字段在下单之后一律不允许同步更新**，哪怕卖家后续修改了商品，历史订单的快照也必须保持下单时的原样。

## 七、学生端接口清单

学生端认证的基础设施已经就位：`MultiAccountConfig` 里注册了与管理端完全独立的 `StpUserUtil`，token 名 `satoken-user`、有效期 7 天、允许多设备并发。所以新接口只需要在 Controller 上用 `StpUserUtil.checkLogin()` 取当前用户，不必再设计登录。

| 域 | 接口 | 说明 |
|---|---|---|
| 商品 | `POST /api/item/publish` | 发布；含草稿存草稿、提交送审两种，送审后 item → 2 待审核并插入 item_audit 进队 |
| | `GET /api/item/list` | 首页 / 筛选 / 关键词搜索（ngram 全文索引已在库） |
| | `GET /api/item/{id}` | 详情；浏览量 +1 |
| | `POST /api/item/{id}/edit` | 编辑。**改价格或改成色须回待审核**，只改描述可免审 |
| | `POST /api/item/{id}/offline` | 卖家主动下架 → 4 |
| 订单 | `POST /api/order/create` | 下单 → 待付款；携带面交点与约定时间，商品不锁定 |
| | `POST /api/order/{id}/pay` | 模拟支付 → 两级占位校验 → 待面交，并批量取消同商品其余待付款订单 |
| | `POST /api/order/{id}/cancel` | 取消（付款前后语义不同，见退款分支） |
| | `POST /api/order/{id}/verify` | 扫码核销 → 已验货 |
| | `POST /api/order/{id}/receive` | 买家确认收货 → 已完成 → 触发互评入口 |
| | `GET /api/order/list` / `GET /api/order/{id}` | 我买到的 / 我卖出的（走 `idx_buyer` / `idx_seller`） |
| 举报 | `POST /api/report` | 提交举报，写入 `status = 1`；`target_type` 1 商品 / 2 用户 |
| 申诉 | `POST /api/appeal` | 提交申诉，写入 `status = 1`；`biz_type` 1 商品审核 / 2 举报 / 3 订单纠纷 |

举报与申诉这两个接口值得单独说明：它们只是**写入 status = 1 的一行**，不需要任何业务判断。审核队列的取件条件本来就是 `report.status IN (1,2)` 与 `appeal.status = 1`，所以只要学生能把这行插进去，管理端队列立刻就能看到真实单据——这两个接口是让审核模块真正活起来的最短路径。

权限方面学生端不需要新增权限点，`StpUserUtil.checkLogin()` 加 ownership 校验即可；`app_user` 表的封禁状态需要在网关层判断，这部分与既有设计一致，不在本轮展开。

## 八、与既有模块的接缝

三处接缝需要在实现时对齐，否则会出现状态不自洽。

其一，**商品售出的判定必须复用 `item.status` 的既有取值**：占位成功即改写为 status 5（已售出），不另创新状态，也不引入任何「预留」语义。同时 `ItemAdminService.forceOffline` 对「已售出/不可下架」的判断（错误码 1106 那条路径）要仍然成立——订单落地后，这条分支第一次有了真实触发场景。

其二，**商品发布必须同时插入 `item_audit`**，否则学生在前端发布的商品不会出现在管理端审核队列里，进而在队列中被遗漏。按 `notes/09` 的口径，进队时要一次性算好四个快照分量，其中举报次数取当前实时值、图片风险与信用扣减取当时的计算结果。

其三，**信用分现在有条件启动了**，但仍然建议不在本轮做。此前审核模块刻意不改信用分，理由是没有可查的扣分流水；而这个理由现在其实已经不成立——`AdminUserController` 与 `credit_log` 表都已就绪，`TRADE_DONE`(+1)、`BREACH_CANCEL`(−5) 都可以写出带流水的实现。我仍建议把它留到下一轮，原因是订单模块本身已经足够大，混进来会让首版难以验证。见第九节。
