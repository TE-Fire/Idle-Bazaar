> 上游依据：`business/03` §二 A-B2 / A-B3 · §三 F-A2 / F-A3 / F-A4 / F-A9 · §4.3 状态机
> 承载页面：A5 审核队列 `/review`（原型 `prototypes/admin/review.html`）
> 权限点：`review.view`（看队列，四角色）/ `review.judge` / `review.forceoff` / `review.appeal`
> 关联模块：`notes/08-商品模块业务说明.md`（强制下架两处共用）
> 配套：`db/schema.sql` 的 `item_audit` / `report` / `appeal`

> 本文只讲**业务与流程**。接口清单、后端类、决策记录在文末附录。

## 一、模块定位

**审核队列是「判」的端：把三种不同来源的待处置单据压成一条队列，按风险和紧急度排好序，让审核员连续处置。**

三来源：

| 来源 | 业务域 | 是什么 |
|---|---|---|
| 商品审核 | A-B2 | 卖家提交的商品，等他判通过 / 驳回 |
| 举报处理 | A-B3 | C 端举报商品，等平台裁决成立 / 不成立 |
| 申诉复审 | A-B3 | 被处置方不服，要求**换人**重判 |

### 1.1 为什么三种来源要合成一条队列

| 理由 | 说明 |
|---|---|
| **排序必须跨来源** | 申诉整体优先于举报、举报优先于商品审核——如果分三个接口，前端还得再排一次，而排序口径正是最不能漂移的东西 |
| **共用一套交互** | 权重排序 + Drawer 处置 + 处置完自动跳下一条（J / K 切换） |
| **共用一张留痕表** | 审核 / 举报 / 申诉复用 `item_audit`，按 `biz_id` 能拉出完整时间线（F-A11 判据） |

### 1.2 与商品管理（A-B4）的关系

同一件商品的**「强制下架」在商品页和审核页都能做**，两边**共用同一个 Service 方法**，结果完全一致，
只有权限点不同（商品页 `item.offline` / 审核页 `review.forceoff`）。商品页只承载 F-A2 的**入口**，
真正的判读处置在 A5。

## 三、业务流程详述

### R1 · 队列取件

**业务目标**：把当前所有待处置单据合成一条队列，**按权重排好序**，让审核员从最该处理的那条开始。

**触发方与入口**：任何角色进 A5 `/review` 页面，页面顶部拉一次队列。

**前置条件**：无。队列为空是正常状态（显示「暂无待处置」）。

**主流程**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 三张表各按进队条件查 | `item_audit.status=1` / `report.status IN (1,2)` / `appeal.status=1` |
| 2 | 组装成统一形状 | 三来源字段差异很大，压成同一种任务行 |
| 3 | 批量回填 | 用这一批的 `sellerId` / 商品 id 批量查用户、商品、分类名 |
| 4 | 算权重 | 五项拆开 + 总分，**都在后端算** |
| 5 | 排序 | 类型优先（申诉 > 举报 > 商品审核）+ 组内**权重降序** |
| 6 | 返回队列 + SLA 概览 | 一次返回全部（**不分页**） |
| 7 | 前端按 `kind` 切 Tab | 全部 / 商品审核 / 举报 / 申诉 |

**异常与边界分支**

| 场景 | 处理 |
|---|---|
| 队列为空 | 显示「暂无待处置」，SLA 各项为 0 |
| 某单据引用的商品已被删 | 回填字段留空，不报错（任务本身仍可处置） |

**约束与规则**

- **不分页**：连续审核依赖"整个队列在前端手上"这个前提，分页会把游标逻辑切碎；
  且队列规模由待处置单据决定，本身受 SLA「积压红牌」的约束
- **排序由后端给**，前端不本地算——否则两边公式一漂移，就会出现"排第一的那条解释出来的分不是最高"
- **判决类单据优先取件**：申诉最急（涉及双方举证，SLA 承诺 48 小时），举报次之（有举报人在等回执），商品审核最后

**涉及**：页面 A5 队列区 ｜ 表 `item_audit` + `report` + `appeal` + `item` + `app_user` ｜ 权限 `review.view`

---

### R2 · 商品审核（通过 / 驳回 / 强制下架）

**业务目标**：对卖家提交的商品做出裁决——这是每日最大工作量。

**触发方与入口**：审核员 → 队列点一条商品审核任务 → Drawer。

**前置条件**：该单据 `item_audit.status = 1`（待审核），对应商品 `item.status = 2`。

**判读四项**（Drawer 里要一眼看全）

| # | 判什么 | 看什么 |
|---|---|---|
| ① | 图片 | 是否网图、是否含联系方式二维码、是否违规 |
| ② | 标题 / 描述 | 是否含校外引流、是否涉违禁品 |
| ③ | 价格 | 是否异常低价 / 高价（对比同类目成交均价） |
| ④ | 分类与成色 | 是否错配 |

**主流程**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 打开任务 | Drawer 展示图片、标题、描述、分类、成色、价格、同类目均价、卖家信用、举报次数、风险分 |
| 2 | 判读四项 | |
| 3 | 三选一裁决 | 见下表 |
| 4 | 处置完自动跳下一条 | 键盘 J / K 前后切换，这是效率关键 |

**三种裁决的数据与状态变化**

| 裁决 | 商品 | 审核单据 | 通知 |
|---|---|---|---|
| **通过** | `PENDING(2) → ON_SALE(3)`，`published_at = now()` | `status=2` + `handler_id` + `first_handle_at` | 通知卖家 |
| **驳回** | `PENDING(2) → REJECTED(6)`，`reject_reason` 落库 | `status=3` + `reject_reason` | 通知卖家，可改后重提 |
| **强制下架** | → `FORCED_OFFLINE(7)` | `status=4`（**复用商品模块的方法**） | 通知卖家，可申诉 |

**异常与边界分支**

| 场景 | 处理 |
|---|---|
| 单据不存在 / 已软删 | 3003「审核任务不存在」 |
| 单据已被别人处置（并发） | 3001「该单据已被其他管理员处置」——用**条件更新** `WHERE id=? AND status=待处置`，影响行数 0 就抛错，比"先查后改"可靠 |
| 驳回未选原因 | 参数错误（1000） |
| 强制下架时商品状态已不允许 | 1106（如商品已售出）——**整笔回滚，不留脏数据** |

**约束与规则**

- **详情用 Drawer 不跳页**：F-A9 的硬指标是「单条处置 ≤30 秒」
- **强制下架与商品页共用同一方法**，结果必须完全一致（状态 7 + 新增 `item_audit.status=4` + 记处置人）
- **驳回原因走预设选项**（图片不实 / 违禁品 / 校外引流 / 分类错配 / 其他），可补文字

**涉及**：页面 A5 Drawer ｜ 表 `item` + `item_audit` ｜ 权限 `review.judge` / `review.forceoff` ｜ 错误码 1000 / 1106 / 3001 / 3003

---

### R3 · 举报裁决

**业务目标**：裁决 C 端提交的商品举报，给举报人和被举报人各一个明确结果。

**触发方与入口**：审核员 → 队列点一条举报任务 → Drawer。

**前置条件**：`report.status IN (1, 2)`（待受理 / 处理中），`target_type = 1`（商品）。

**主流程**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 打开任务 | 看举报原因 + 举报人凭证（图片 ≤3 张） |
| 2 | 核对被举报商品 | 标题、描述、图片、价格 |
| 3 | 二选一裁决 | 成立 / 不成立 |
| 4 | 提交 | 一步到位写 `status=3` + `result` |

**两种裁决的数据与状态变化**

| 裁决 | `report` | 商品 |
|---|---|---|
| **不成立** | `status=3, result=2` | 不动 |
| **成立** | `status=3, result=1` | **一律走强制下架 → `FORCED_OFFLINE(7)`** |

> 「成立」**不区分轻重**：一律走 `forceOffline`。理由是平台处置是**终态**，
> 不能混进「卖家可自行重新上架」的 `OFFLINE(4)`——否则被举报的商品下架后卖家一点就复活了。

**异常与边界分支**

| 场景 | 处理 |
|---|---|
| 单据不存在 | 3003 |
| 举报已处理（`status=3`）再裁决 | 3001 |
| 成立，但商品已售出 / 状态不允许下架 | 1106——**整笔回滚**，举报单仍留在队列里 |
| 未选裁决结果 | 参数错误（1000） |

**约束与规则**

- **没有独立的「受理」步骤**：点开处置即视为受理，裁决时一步到位写 `status=3`。
  「处理中」在单人审核场景下没有意义（没人会把单子挂起来等别人接），多一个接口就多一次点击，
  而 F-A9 的硬指标是「单条处置 ≤30 秒」。`status=2` 保留在状态机里、由演示数据体现
- 举报人能看到结果，被举报人能看到理由
- 被处置方可**申诉一次** → 转 R4

**涉及**：页面 A5 Drawer ｜ 表 `report` + `item` + `item_audit` ｜ 权限 `review.judge` ｜ 错误码 1000 / 1106 / 3001 / 3003

---

### R4 · 申诉复审

**业务目标**：给被处置方一次救济机会，由**另一个管理员**复核原处置是否恰当。

**触发方与入口**：审核员 → 队列点一条申诉任务 → Drawer（显示**原处置人与原处置结果**）。

**前置条件**：`appeal.status = 1`（待复审）；**复审人 ≠ 原处置人**（F-A4 换人复审原则）。

**主流程**

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 打开任务 | 看申诉理由 + 新凭证 + **原处置人 / 原处置结果** |
| 2 | 核对原处置 | 按 `biz_type` / `biz_id` 找到被申诉的那条处置 |
| 3 | 二选一裁决 | 维持 / 撤销 |
| 4 | 提交 | 申诉结果**终局**，不可再申诉 |

**`biz_type` 决定 `biz_id` 指什么**

| `biz_type` | 含义 | `biz_id` 指向 |
|---|---|---|
| 1 | 商品审核 | `item.id` |
| 2 | 举报 | `report.id` |
| 3 | 订单纠纷 | `trade_order.id` |

**两种裁决的数据与状态变化**

| 裁决 | `appeal` | 商品（反向恢复） |
|---|---|---|
| **撤销** | `status=3` | `FORCED_OFFLINE(7) → ON_SALE(3)`；`REJECTED(6) → PENDING(2)`（回到待审核重走一遍） |
| **维持** | `status=2` | 不动 |

**异常与边界分支**

| 场景 | 处理 |
|---|---|
| 单据不存在 | 3003 |
| 复审人就是原处置人 | 3002「申诉复审不能由原处置人处理」（F-A4 硬规则） |
| 申诉已裁决（`status IN (2,3)`）再裁决 | 3001 |
| 未选裁决结果 | 参数错误（1000） |

**约束与规则**

- **换人复审是硬规则**，不是建议：演示数据里两条待复审的原处置人都是 `super`(2101)，
  所以 super 复审会被 3002 拦下，必须用 `reviewer`(2102) 才走得通
- **撤销是"反向恢复"**：强制下架的恢复成在售、驳回的退回待审核——不是新建一条单据
- 申诉结果**终局**，状态机里没有第二次申诉

**涉及**：页面 A5 Drawer ｜ 表 `appeal` + `item` + `item_audit` / `report` ｜ 权限 `review.appeal` ｜ 错误码 1000 / 3001 / 3002 / 3003

---

### R5 · SLA 时效监控

**业务目标**：把「该先处理谁」直接摆在审核员面前，而不是只给一堆好看的数字。

**触发方与入口**：A5 顶部概览条（随队列一起返回）。

**两级指标（不可混用）**

| 层级 | 指标 | 阈值 | 面向谁 |
|---|---|---|---|
| **响应时效** | 首审响应 | ≤ **2 小时** 达标 | 对卖家的承诺 |
| | P95 首审时长 | ≤ 6 小时 | |
| | 整体达标率 | ≥ 95% | |
| | 积压红牌 | 超 **24 小时**未处置 | 需当日清零 |
| **操作效率** | 单条平均处置 | ≤ **30 秒** | 对人机效率的要求 |

**概览条呈现**

| 项 | 含义 |
|---|---|
| 待处置 | 队列总条数 |
| 临期 | 距首审 2 小时不到一定比例的条数 |
| 积压 | 超 24 小时的条数（红牌） |
| 单条处置目标 | 30 秒 |

**约束与规则**

- 响应时效与操作效率是**两个层级**：前者是平台对用户的承诺，后者是人机效率，论文中分开陈述
- SLA 必须落到**操作层**才有意义——队列的「等待时长」列要标出临期与超时
- **申诉另行承诺 48 小时**内给出复审结论（比商品审核宽松，因为涉及双方举证）
- 阈值可在「系统设置 · SLA 配置」调整

**涉及**：页面 A5 概览条 ｜ 采集字段 `enter_queue_at` / `first_handle_at` / `handler_id` / `handle_cost_ms` ｜ 权限 `review.view`

## 四、三种来源的状态机与进出队条件

`business/03` §4.3：

```
审核：待审核 ─> 已通过 / 已驳回 / 已强制下架        （item_audit.status 1/2/3/4）
举报：待受理 ─> 处理中 ─> 已处理（成立/不成立）      （report.status 1/2/3）
申诉：待复审 ─> 维持 / 撤销（终态，不可再申诉）      （appeal.status 1/2/3）
```

| 来源 | 进队条件 | 出队条件 |
|---|---|---|
| 商品审核 | `item_audit.status = 1` | 处置后转 2 / 3 / 4 |
| 举报 | `report.status IN (1, 2)` | 处置后转 3，`result` 记 1 成立 / 2 不成立 |
| 申诉 | `appeal.status = 1` | 裁决后转 2 维持 / 3 撤销 |

> 队列里实际出现的条数 = 三张表按上表条件查出来的总和。演示数据里是 12 条（商品审核 5 + 举报 5 + 申诉 2）。

## 五、权重公式与排序

### 5.1 公式（F-A2）

```
优先级分 = 举报次数 × 3
          + 图片风险分        // 0–100，ROUND(÷10) 归一化为 0–10
          + 卖家信用扣减分     // (100 − 信用分) / 10
          + 价格异常分        // 偏离同类目均价 3 倍以上 = 5
          + 等待补偿          // 等待每满 12 小时 +1（是补偿，不是惩罚）
```

F-A2 判据原文：

> 队列必须**按权重排序**，不能按时间——按时间等于让风险最高的单子排在后面。

### 5.2 库里存一半、查询时补一半

| 部分 | 存在哪 | 为什么 |
|---|---|---|
| **基础分** | `item_audit.priority_score` | 进队时按当时的数据算一次，作为**快照** |
| **等待补偿** | 不存库，**查询时实时算** | 等待时长是时间的函数，存了就永远是旧值 |

**最终排序键** = `priority_score + FLOOR(TIMESTAMPDIFF(HOUR, enter_queue_at, NOW()) / 12)`

不能只用库里的 `priority_score`——那样风险最高的老单会沉底，正是 F-A2 要避免的。
索引 `idx_queue(status, priority_score, enter_queue_at)` 也是按这个形状建的。

### 5.3 为什么权重拆成五项返回

五项拆开是为了在 UI 上解释**「它为什么排第一」**（tooltip 逐项展示，五项之和 = 总分）。
如果只给一个总分，答辩现场会被问「凭什么它排第一」而答不上来。

> ⚠️ 勘误（2026-10-06）：`business/03` 原式写「图片风险分 × 2」与「− 等待衰减补偿」，与注释和代码都不符。
> 已按前端 `calcWeight` 的口径（**0–10、加法**）改正。见附录 C。

## 六、业务规则与口径

### 6.1 换人复审（F-A4）

**原处置人不得复审自己的单。** 演示数据里两条待复审的原处置人都是 `super`(2101)，所以：
super 复审 → 3002 拦下；`reviewer`(2102) 复审 → 通过。这条规则是**可演示的**，不是纸面条款。

### 6.2 举报不做独立「受理」

见 R3。`status=2`（处理中）保留在状态机里，由演示数据体现，但**没有对应接口**。

### 6.3 信用分本期不改

`business/03` §4.5 写着「强制下架 −15、被举报成立 −10」，但本期**只改商品状态不改信用分**。
理由：信用分是用户域的字段，改它就要有「扣分流水」可查（否则用户问凭什么扣，拿不出依据），
而用户管理还没做，现在扣分等于埋下一处无记录的副作用。
处置备注里记「应扣 15 分」作为待办标记，扣分留给用户管理模块。

### 6.4 处置后商品状态怎么转（总表）

| 动作 | 商品状态 | 审核单据 |
|---|---|---|
| 通过 | `2 → 3`，`published_at = now()` | `item_audit.status=2` + `handler_id` + `first_handle_at` |
| 驳回 | `2 → 6` | `status=3` + `reject_reason` |
| 强制下架 | `→ 7` | `status=4`（复用商品模块方法） |
| 举报成立 | `→ 7`（走 `forceOffline`） | `report.status=3, result=1` |
| 举报不成立 | 不动 | `report.status=3, result=2` |
| 申诉撤销 | `7 → 3` 或 `6 → 2`（反向恢复） | `appeal.status=3` |
| 申诉维持 | 不动 | `appeal.status=2` |

### 6.5 两个「举报数」的口径（与商品页一致）

| 数字 | 出处 | 口径 |
|---|---|---|
