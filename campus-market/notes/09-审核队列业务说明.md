## 一、模块定位

**审核队列是「判」的端：把三种不同来源的待处置单据压成一条队列，按风险和紧急度排好序，让审核员连续处置。**

| 来源 | 业务域 | 是什么 |
|---|---|---|
| 商品审核 | A-B2 | 卖家提交的商品，等他判通过 / 驳回 |
| 举报处理 | A-B3 | C 端举报商品，等平台裁决成立 / 不成立 |
| 申诉复审 | A-B3 | 被处置方不服，要求**换人**重判 |

### 1.1 为什么三种来源要合成一条队列

| 理由 | 说明 |
|---|---|
| **排序必须跨来源** | 申诉整体优先于举报、举报优先于商品审核——如果分三个接口，前端还得再排一次，而排序口径正是最不能漂移的东西 |
| **共用一套交互** | 权重排序 + Drawer 处置 + 处置完自动跳下一条（J / K 切换） |
| **共用一张留痕表** | 审核 / 举报 / 申诉复用 `item_audit`，按 `biz_id` 能拉出完整时间线（F-A11 判据） |

### 1.2 与商品管理（A-B4）的关系

同一件商品的**「强制下架」在商品页和审核页都能做**，两边**共用同一个 Service 方法**，结果完全一致，
只有权限点不同（商品页 `item.offline` / 审核页 `review.forceoff`）。商品页只承载 F-A2 的**入口**，
真正的判读处置在 A5。

## 三、业务条目

### R1 · 队列取件

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/review/queue` | `review.view` | 合并队列 + SLA 概览；可选 `kind` 过滤（`item` / `report` / `appeal`） |

**前置**

- 无。队列为空是正常状态（显示「暂无待处置」）。

**规则**

1. 三张表各按进队条件查：`item_audit.status = 待审核(1)`、`report.status IN (待受理(1), 处理中(2))`、`appeal.status = 待复审(1)`。
2. 组装成统一形状：三来源字段差异很大，压成同一种任务行（`kind` 由 `QueueKindEnum` 的 `@JsonValue` 输出小写 `item` / `report` / `appeal`，与前端同形）。
3. 批量回填：用这一批的 `sellerId` / 商品 id 批量查用户、商品、分类名。
   1. 某单据引用的商品已被删 → 回填字段留空，不报错（任务本身仍可处置）
4. 算权重：五项拆开 + 总分，**都在后端算**，前端不再本地算。
5. 排序：
   1. 一级键：类型优先（申诉 > 举报 > 商品审核）
   2. 二级键：组内权重降序
   3. 排序由后端给，前端不本地算——否则两边公式一漂移，就会出现「排第一的那条解释出来的分不是最高」
6. 返回队列 + SLA 概览：一次返回全部，**不分页**。
   1. 理由：连续审核依赖「整个队列在前端手上」这个前提，分页会把游标逻辑切碎；且队列规模由待处置单据决定，本身受 SLA「积压红牌」的约束
7. 前端按 `kind` 切 Tab：全部 / 商品审核 / 举报 / 申诉。

**状态与数据变化**：无。队列为空时 SLA 各项为 0。

### R2 · 商品审核（通过 / 驳回 / 强制下架）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/admin/review/item/{auditId}/pass` | `review.judge` | 审核通过 |
| POST | `/admin/review/item/{auditId}/reject` | `review.judge` | 驳回（`reason` 必填） |
| POST | `/admin/review/item/{auditId}/force-offline` | `review.forceoff` | 强制下架（复用商品模块方法） |

**前置**

- 该单据 `item_audit.status = 待审核(1)`，对应商品 `item.status = 待审核(2)`。

**规则**

1. 打开任务：Drawer 展示图片、标题、描述、分类、成色、价格、同类目均价、卖家信用、举报次数、风险分；详情用 Drawer 不跳页（F-A9 硬指标：单条处置 ≤ 30 秒）。
2. 判读四项：
   1. 图片：是否网图、是否含联系方式二维码、是否违规
   2. 标题 / 描述：是否含校外引流、是否涉违禁品
   3. 价格：是否异常低价 / 高价（对比同类目成交均价）
   4. 分类与成色：是否错配
3. 三选一裁决：
   1. **通过**：商品 `待审核(2) → 在售(3)`、`published_at = now()`；单据 `status = 已通过(2)` + `handler_id` + `first_handle_at`；通知卖家
   2. **驳回**：商品 `待审核(2) → 审核未过(6)`、`reject_reason` 落库；单据 `status = 已驳回(3)` + `reject_reason`；通知卖家，可改后重提
   3. **强制下架**：商品 → `已强制下架(7)`；单据 `status = 已强制下架(4)`（复用商品模块方法，结果必须完全一致）
4. 处置完自动跳下一条：键盘 J / K 前后切换，这是效率关键。
5. 异常分支：
   1. 单据不存在或已软删 → 审核任务不存在(3003)
   2. 单据已被别人处置（并发）→ 该单据已被其他管理员处置(3001)——用**条件更新** `WHERE id=? AND status=待审核(1)`，影响行数 0 就抛错，比「先查后改」可靠
   3. 驳回未选原因 → 参数错误(1000)
   4. 强制下架时商品状态已不允许 → 当前状态不能下架(1106)（如商品已售出）——**整笔回滚，不留脏数据**
6. 驳回原因走预设选项（图片不实 / 违禁品 / 校外引流 / 分类错配 / 其他），可补文字。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `item` | 通过 → 在售(3) + `published_at`；驳回 → 审核未过(6) + 原因；下架 → 已强制下架(7) |
| `item_audit` | 转 已通过(2) / 已驳回(3) / 新增一条 已强制下架(4)，带处置人与时间 |

### R3 · 举报裁决

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/admin/review/report/{reportId}/handle` | `review.judge` | 举报裁决（成立 / 不成立） |

**前置**

- `report.status ∈ { 待受理(1), 处理中(2) }`，且 `target_type = 1`（商品）。

**规则**

1. 打开任务：看举报原因 + 举报人凭证（图片 ≤ 3 张）。
2. 核对被举报商品：标题、描述、图片、价格。
3. 二选一裁决，提交时一步到位写 `status = 已处理(3)`：
   1. **不成立**：`report.status = 已处理(3), result = 不成立(2)`；商品**不动**
   2. **成立**：`report.status = 已处理(3), result = 成立(1)`；商品**一律走强制下架 → `已强制下架(7)`**
      1. 「成立」**不区分轻重**：一律走 `forceOffline`。理由是平台处置是**终态**，不能混进「卖家可自行重新上架」的 `已下架(4)`——否则被举报的商品下架后卖家一点就复活了
4. 异常分支：
   1. 单据不存在 → 审核任务不存在(3003)
   2. 举报已处理（`status = 已处理(3)`）再裁决 → 该单据已被其他管理员处置(3001)
   3. 成立，但商品已售出 / 状态不允许下架 → 当前状态不能下架(1106)——**整笔回滚**，举报单仍留在队列里
   4. 未选裁决结果 → 参数错误(1000)
5. **没有独立的「受理」步骤**：点开处置即视为受理，裁决时一步到位写 `status = 已处理(3)`。
   1. 「处理中」在单人审核场景下没有意义（没人会把单子挂起来等别人接），多一个接口就多一次点击，而 F-A9 的硬指标是「单条处置 ≤ 30 秒」
   2. `status = 处理中(2)` 保留在状态机里、由演示数据体现，**没有对应接口**
6. 举报人能看到结果，被举报人能看到理由；被处置方可**申诉一次** → 转 R4。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `report` | 转 已处理(3)，`result` 记 成立(1) / 不成立(2) |
| `item` | 成立 → 已强制下架(7)（走 `forceOffline`）；不成立 → 不动 |
| `item_audit` | 成立时新增一条 `status = 已强制下架(4)`（复用商品模块留痕） |

### R4 · 申诉复审

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/admin/review/appeal/{appealId}/judge` | `review.appeal` | 申诉裁决（维持 / 撤销） |

**前置**

- `appeal.status = 待复审(1)`；**复审人 ≠ 原处置人**（F-A4 换人复审原则）。

**规则**

1. 打开任务：看申诉理由 + 新凭证 + **原处置人 / 原处置结果**。
2. 核对原处置：按 `biz_type` / `biz_id` 找到被申诉的那条处置。
   1. `biz_type = 商品审核(1)` → `biz_id` 指向 `item.id`
   2. `biz_type = 举报(2)` → `biz_id` 指向 `report.id`
   3. `biz_type = 订单纠纷(3)` → `biz_id` 指向 `trade_order.id`（由订单反查商品）
3. 二选一裁决：
   1. **撤销**（申诉成立）：`appeal.status = 撤销(3)`；商品**反向恢复**——`已强制下架(7) → 在售(3)`、`审核未过(6) → 待审核(2)`（回到待审核重走一遍）；订单纠纷走 `OrderService#settleDispute`，纠正的是**订单状态**（买家赢 → 已退款(7)）
   2. **维持**：`appeal.status = 维持(2)`；商品不动
   3. 撤销是「反向恢复」：不是新建一条单据
4. 提交：申诉结果**终局**，不可再申诉。
5. 异常分支：
   1. 单据不存在 → 审核任务不存在(3003)
   2. 复审人就是原处置人 → 申诉复审不能由原处置人处理(3002)
   3. 申诉已裁决（`status ∈ { 维持(2), 撤销(3) }`）再裁决 → 该单据已被其他管理员处置(3001)
   4. 未选裁决结果 → 参数错误(1000)

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `appeal` | 转 维持(2) / 撤销(3) |
| `item` | 撤销 → `已强制下架(7) → 在售(3)` 或 `审核未过(6) → 待审核(2)`；维持 → 不动 |
| `trade_order` | 仅 `biz_type = 订单纠纷(3)`：买家赢 → 已退款(7)，卖家赢 → 已完成(4) |

**约束**

- **换人复审是硬规则**，不是建议：演示数据里两条待复审的原处置人都是 `super`(2101)，
  所以 super 复审会被 3002 拦下，必须用 `reviewer`(2102) 才走得通——这条规则**可演示**。
- 订单纠纷**没有原处置人**（买卖双方谈不拢后由系统转入，此前不存在任何管理员处置），
  `originHandlerOf` 返回 null 会让 F-A4 的换人复审校验自动放宽。这不是规则被绕过，而是它本来就不存在「自己复审自己」的对象。
- **订单纠纷还有第二个入口**（2026-10-26）：A6 订单页的 `POST /admin/order/{id}/arbitrate`，挂 `order.arbitrate`。
  两个入口共用 `judgeAppeal`，只是权限分属审核员与运营——不给运营开 `review.appeal`，
  否则他顺带拿到了商品申诉的裁决权。

### R5 · SLA 时效监控

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/review/queue` | `review.view` | SLA 概览**随队列一起返回**，无独立接口 |

**前置**

- 无。

**规则**

1. 概览条四项：
   1. **待处置**：队列总条数（三张表按进队条件的总和）
   2. **临期**：等待 ≥ 2 小时且 < 24 小时，即**已过首审期但尚未积压**的条数
   3. **积压**：等待 ≥ 24 小时的条数（红牌，需当日清零）
   4. **单条处置目标**：30 秒（**常量，非统计值**）
2. 「临期」这个名字容易读反：它统计的是**已经超时的那批**，不是快到期的那批。
   真要表达「临近 2 小时」，判据应是等待时长落在某个百分比区间内，那是另一条口径，本期没做。
3. 等待时长 = 当前时间 − `enter_queue_at`（举报 / 申诉各自的进队时间同理）。
4. SLA 必须落到**操作层**才有意义——队列的「等待时长」列要标出临期与超时。

**两级指标（不可混用）**

| 层级 | 指标 | 阈值 | 面向谁 |
|---|---|---|---|
| **响应时效** | 首审响应 | ≤ **2 小时** 达标 | 对卖家的承诺 |
| | P95 首审时长 | ≤ 6 小时 | |
| | 整体达标率 | ≥ 95% | |
| | 积压红牌 | 超 **24 小时**未处置 | 需当日清零 |
| **操作效率** | 单条平均处置 | ≤ **30 秒** | 对人机效率的要求 |

**约束**

- 响应时效与操作效率是**两个层级**：前者是平台对用户的承诺，后者是人机效率，论文中分开陈述。
- **申诉另行承诺 48 小时**内给出复审结论（比商品审核宽松，因为涉及双方举证）。
  本期**未落地**：后端只有 2 小时与 24 小时两个阈值，SLA 概览不区分单据类型，申诉也按 2 小时计入。
- 概览条上的「单条处置目标 30 秒」是**目标值常量**，不是 `handle_cost_ms` 的统计结果。
  后者只在商品审核单据上记，且记的是服务端处置耗时而非审核员阅读时长，拿它算平均会偏低；
  准确口径要由前端打开处置抽屉时上报，留给 A8 报表。
- 阈值可在「系统设置 · SLA 配置」调整。

## 四、三种来源的状态机与进出队条件

```
商品审核：待审核(1) ─> 已通过(2) / 已驳回(3) / 已强制下架(4)      （item_audit.status）
举报：    待受理(1) ─> 处理中(2) ─> 已处理(3)（成立(1)/不成立(2)）  （report.status）
申诉：    待复审(1) ─> 维持(2) / 撤销(3)（终态，不可再申诉）        （appeal.status）
```

| 来源 | 进队条件 | 出队条件 |
|---|---|---|
| 商品审核 | 本期卖家提交 / 改价不再进审核队列：信用分 < 60 直接拦截（USER_CREDIT_TOO_LOW），≥ 60 免审直接上架；`item_audit` 商品审核单据仅保留给管理端强制重审等路径 | 处置后转 已通过(2) / 已驳回(3) / 已强制下架(4) |
| 举报 | `report.status ∈ { 待受理(1), 处理中(2) }` | 处置后转 已处理(3)，`result` 记 成立(1) / 不成立(2) |
| 申诉 | `appeal.status = 待复审(1)` | 裁决后转 维持(2) / 撤销(3) |

> 队列里实际出现的条数 = 三张表按上表条件查出来的总和。演示数据里是 12 条（商品审核 5 + 举报 5 + 申诉 2）。

### 4.1 处置后商品状态怎么转（总表）

| 动作 | 商品状态 | 审核单据 |
|---|---|---|
| 通过 | `待审核(2) → 在售(3)`，`published_at = now()` | `item_audit.status = 已通过(2)` + `handler_id` + `first_handle_at` |
| 驳回 | `待审核(2) → 审核未过(6)` | `status = 已驳回(3)` + `reject_reason` |
| 强制下架 | `→ 已强制下架(7)` | `status = 已强制下架(4)`（复用商品模块方法） |
| 举报成立 | `→ 已强制下架(7)`（走 `forceOffline`） | `report.status = 已处理(3), result = 成立(1)` |
| 举报不成立 | 不动 | `report.status = 已处理(3), result = 不成立(2)` |
| 申诉撤销 | `已强制下架(7) → 在售(3)` 或 `审核未过(6) → 待审核(2)`（反向恢复） | `appeal.status = 撤销(3)` |
| 申诉维持 | 不动 | `appeal.status = 维持(2)` |

## 五、权重公式与排序

### 5.1 公式（F-A2）

```
优先级分 = 举报次数 × 3
          + 图片风险分        // 0–100，ROUND(÷10) 归一化为 0–10
          + 卖家信用扣减分     // (100 − 信用分) / 10
          + 价格异常分        // 偏离同类目均价 3 倍以上 = 5
          + 等待补偿          // 等待每满 12 小时 +1（是补偿，不是惩罚）
```

F-A2 判据原文：

> 队列必须**按权重排序**，不能按时间——按时间等于让风险最高的单子排在后面。

### 5.2 基础分存库、补偿现算，排序读的是分量而不是总分

1. 基础分由四个快照字段构成——`report_count`、`image_risk`、`credit_deduct`、`price_abnormal`——
   **进队时落库，之后不再变动**；这样一件商品正在被处置时又来一条新举报，它在队列里的位置不会当场跳变。
2. 等待补偿**不入库**，每次取队列时用 `enter_queue_at` 到当前时间实时算，因为等待时长是时间的函数，存下来就永远是旧值。
3. 两者相加才是排序键：只用基础分会让风险最高的老单沉底，正是 F-A2 要避免的。
4. `item_audit.priority_score` 存的正是这四个分量之和（`zz-demo-data.sql` 末尾那条 UPDATE 按同一公式
   重算了全部行），数值上与基础分相等，但**队列排序不读它**：`fillWeight()` 用四个分量实时算。
   1. 取舍根据：UI 要逐项解释权重构成，总分必须由明细相加而来；若改读打包好的 `priority_score`，总分就依赖一处可能与分量漂移的存储值，恒等关系会破
   2. 因此该字段定位为**冗余快照**，供将来 SQL 层排序、分页与 A8 报表使用，当前没有读取方
5. 同理，`idx_queue(status, priority_score, enter_queue_at)` 目前只用上了 `status` 前缀。
   队列不分页，三来源合并后的排序在内存里做，SQL 层没有 `ORDER BY` 需要它；索引按权重排序的形状建着，是给将来分页或下沉到 SQL 层排序留的。

### 5.3 为什么权重拆成五项返回

1. 五项拆开是为了在 UI 上解释**「它为什么排第一」**（tooltip 逐项展示，五项之和 = 总分）。
   如果只给一个总分，答辩现场会被问「凭什么它排第一」而答不上来。
2. 恒等关系是单向的：**总分由明细相加得出**，不是总分算出来再拆成明细。
   这也是 5.2 里排序读分量而不读 `priority_score` 的原因。

> ⚠️ 勘误（2026-10-06）：`business/03` 原式写「图片风险分 × 2」与「− 等待衰减补偿」，与注释和代码都不符。
> 已按前端 `calcWeight` 的口径（**0–10、加法**）改正。见附录 C。

## 六、通用业务规则

### 6.1 换人复审（F-A4）

**原处置人不得复审自己的单。** 演示数据里两条待复审的原处置人都是 `super`(2101)，所以：
super 复审 → 申诉复审不能由原处置人处理(3002) 拦下；`reviewer`(2102) 复审 → 通过。这条规则是**可演示的**，不是纸面条款。

### 6.2 举报不做独立「受理」

见 R3。`status = 处理中(2)` 保留在状态机里，由演示数据体现，但**没有对应接口**。

### 6.3 信用分本期不改

`business/03` §4.5 写着「强制下架 −15、被举报成立 −10」，但本期**只改商品状态不改信用分**。
理由：信用分是用户域的字段，改它就要有「扣分流水」可查（否则用户问凭什么扣，拿不出依据），
而用户管理还没做，现在扣分等于埋下一处无记录的副作用。
处置备注里记「应扣 15 分」作为待办标记，扣分留给用户管理模块。

### 6.4 两个「举报数」的口径（与商品页一致）

| 数字 | 出处 | 口径 |
|---|---|---|
| 权重用的 | `item_audit.report_count` | **进队快照**（当时的未结举报数），之后不变 |
| 页面展示的 | `report` 表实时 count | 当前**未结**举报数 |

队列与商品管理页展示的都是实时未结值，权重分量用快照——两条链路各取各的，页面上要能看出来。

**未结 = `status ∈ { 待受理(1), 处理中(2) }`，已处理(3)不计**（2026-10-24 修正，此前含已处理）：
查实不成立的举报若永久留在计数里，卖家改价重提时快照会把旧数带进新审核单，权重只涨不落；
查实成立的举报商品已被强制下架，本就不在队列里，无需靠历史计数撑权重。
唯一读取方是 `ReportMapper#countByItem`，三处调用（队列展示、商品列表展示、进队快照）同口径。
