# 笔记 · 软删除标记为什么用时间戳

这份笔记对应 `db/01-数据库设计.md` 全局约定的第 2、3 条：逻辑删除字段 `deleted` 用 `bigint`，0 表示未删除，删除时写入毫秒级时间戳；唯一索引必须带上 `deleted`。记录的是这两条约定背后的推导过程，以及我在理解它时走过的一段弯路——我最初的判断是「为了避免低基数导致索引失效」，这个说法不准确，下面会说明错在哪里。

## 一、冲突从哪来

以收藏表 `favorite` 为例，业务要求「同一用户对同一商品只能收藏一次」，因此需要唯一索引 `uk_user_item (user_id, item_id, deleted)`。把 `deleted` 放进唯一键，是为了让「已删除的行」与「新插入的行」不互相排斥：删除后该行的 `deleted` 变为非 0，再次收藏时插入的新行 `deleted` 为 0，两者在索引中是不同条目，不发生冲突。

到这里为止，用 0/1 与用时间戳的效果相同。差别出现在第二次删除：

| 时刻 | 操作 | deleted = 1 | deleted = 时间戳 |
|---|---|---|---|
| t1 | 收藏 | 插入 `(u1,i1,0)` | 插入 `(u1,i1,0)` |
| t2 | 取消收藏 | 改为 `(u1,i1,1)` | 改为 `(u1,i1,T2)` |
| t3 | 再次收藏 | 插入 `(u1,i1,0)` | 插入 `(u1,i1,0)` |
| t4 | 再次取消 | 改为 `(u1,i1,1)`，与 t2 留下的行**重复** | 改为 `(u1,i1,T4)`，不重复 |

常量 `1` 只有一种取值，于是同一个业务键在整张表的生命周期里只能被软删除一次，第二次就会抛出重复键错误。这在收藏、关注、购物车这类反复增删的场景里是必现故障。

## 二、把需求抽象出来

由此可以看出这个字段真正的约束：**每一次删除都必须取一个此前没有被用过的值**。只要满足这一点，同一业务键就能被反复删除。时间戳只是最自然的一种实现——它不需要额外维护计数器或序列，取值天然递增，同时还把删除发生的时刻记录了下来，等于免费获得一份审计信息。替代方案在逻辑上同样成立（删除序号、UUID），但都需要额外的状态或存储空间。

顺着这个约束，还能解释另外两个字段细节。

未删除为什么存 `0` 而不是 `NULL`。MySQL 的唯一索引把 `NULL` 视为互不相等的值，因此 `(u1,i1,NULL)` 可以存在多行，「同一用户同一商品只能收藏一次」的约束会直接失效。`0` 是一个确定的值，才能被唯一索引真正约束住。

类型为什么是 `bigint`。秒级时间戳到 2038 年会超出 32 位有符号 `int` 的上界，毫秒级更是如此，所以不能用 `int`。用 `datetime` 也能达到目的，但 `bigint` 与 Java 的 `long` 一一对应，比较和索引结构都比日期类型简单，因此选它。

`deleted` 在复合唯一键中置于最后一列，是为了保住左侧前缀的匹配能力：查询条件只给 `user_id` 时仍能使用这个索引，若把 `deleted` 放在最前，前缀匹配就失效了。

## 三、一处需要澄清的误解

我最初把这个设计理解成「常量 1 会导致取值分布过于集中，索引区分度不够，所以要换成时间戳」。这个说法不成立，需要纠正。

索引区分度（选择性）的问题确实存在，但它针对的是**给 `deleted` 单独建索引**这种做法：一个只有两个取值、且绝大多数行都是 0 的列，单独建索引几乎无法过滤任何行，优化器会直接选择全表扫描。本项目从不为 `deleted` 单独建索引。

而对于 `WHERE deleted = 0` 这类查询，两种方案的选择性**完全相同**——无论用 `1` 还是时间戳，未删除行的取值都是同一个常量 0，直方图一致，优化器的判断也一致。时间戳并不会让这类查询变快。

`deleted` 在项目中的实际作用是作为复合索引的尾列，让「过滤已删除行」这一步在索引内部完成，不需要回表再判断。这个收益 0/1 方案同样具备。

## 四、代价与由此产生的约束

这个方案的成本是明确的。每次删除都会留下一条墓碑行，索引条目只增不减，长期运行后索引体积会持续膨胀。InnoDB 更新二级索引并不是原地改写，而是把旧条目标记删除再插入新条目，会产生碎片并交给后台 purge 线程清理。此外，唯一索引的插入不能走 change buffer——必须先读出索引页校验唯一性，目标页不在缓冲池时就是一次随机读，这是唯一索引比普通二级索引写入更贵的根本原因。这几项成本与用 0/1 还是时间戳无关，是软删除加唯一索引这个组合本身的代价。

由此产生三条工程约束。第一，判断未删除只能写 `deleted = 0`，写成 `deleted = 1` 会漏掉全部已删除行之外的正常数据判断逻辑，写成 `IS NULL` 则永远匹配不到。第二，MyBatis-Plus 的 `@TableLogic` 只接受常量值，无法配合时间戳方案，所以项目配置里明确不启用逻辑删除，查询一律显式带 `deleted = 0`。第三，时间戳的单位必须全局统一，项目已定为毫秒（`System.currentTimeMillis()`）；秒级除 2038 上界问题外，还存在同一秒内「删除—重插—再删」重复的风险，毫秒级下这种概率可以忽略。

最后一个待办：墓碑行需要清理策略。数据积累到一定规模后，应按 `deleted` 的时间范围归档或物理清除历史墓碑，可以通过定时任务处理。当前数据量在十万级，还不构成压力，但这条要留在待办里。

## 五、一个此前被略过的前提

上面第一、四节的结论全部依赖一个隐含前提：**「取消之后再次建立关系」是插入一条新行**。这个前提在原始设计里没有被写清楚，而它决定了整个方案是否成立。

如果改成复用同一行——删除时 `UPDATE SET deleted = T`，重建时 `UPDATE SET deleted = 0` 把这一行改回来——那么同一业务键在表里永远只有一行，`deleted` 在 0 与时间戳之间来回切换。这种情况下：不会有第二条 `(u1,i1,T)` 与之重复，因此不撞索引；行不会增加，因此没有墓碑累积；时间戳也就不再是必需品，0/1 同样能工作。

也就是说，「用 0/1 会撞唯一索引」这个理由只在插入新行的实现下成立。理解到这一层，才能看出真正需要回答的问题是：这张表要不要保留历史。

据此，项目把删除分成两类，写进了 `db/01` 第 9 条：需要留痕的表（用户注销、字典、会话、商品、订单）走 A 类，删除后重建插入新行，时间戳是必需品；没有审计价值的关联关系（收藏、关注）走 B 类，删除后重建复用同一行，同一业务键恒为一行，时间戳降级为「上次删除时间」的记录。

这个分类也顺带解决了一个并发问题：A 类下用户快速点两次收藏，第二个 `INSERT` 会撞唯一键需要捕获处理；B 类的 `UPDATE` 天然幂等，重复点击没有副作用。

顺着这个结论再往下推一步：既然 B 类同一业务键恒为一行，那么 `deleted` 用常量 1 在技术上完全够用，时间戳在那里**没有技术必要性**。这一点需要说清楚，否则容易误以为收藏表也依赖时间戳的唯一性。

项目仍然让 B 类写时间戳，理由是语义统一而非技术必要：`deleted` 在全库保持一种含义（0 未删、非 0 为删除时刻），就不必记住哪张表是布尔、哪张表是时间；否则一旦有人把「按删除时间归档」的任务用在收藏表上，常量方案下这条语句不会报错，只会静默出错。代价是一行多 7 字节，可以忽略。

值得记住的是这个推导链本身：先看重建出来的是否同一个实体，决定是新插一行还是复用旧行；只有「新插一行」才产生多条墓碑，才要求每次删除取不同值，时间戳才成为必需品。时间戳是这条链末端的结果，不是起点。
