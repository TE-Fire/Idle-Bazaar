## 一、业务分析

### 1.1 五张字典表各自的用途

| 表 | 内容 | 谁在用 | 备注 |
|---|---|---|---|
| `dict_campus` | 校区 | 面交点归属、用户所属校区、报表 | 最顶层，无外键 |
| `dict_college` | 学院（12 个） | 用户认证、报表「学院×品类」矩阵的**行** | 带 `campus_id` |
| `dict_category` | 商品分类**两级树** | 发布、审核、搜索、报表 | `parent_id` 自关联，一级为 0 |
| `dict_grade` | 成色 A–D | 发布、商品详情、报表成色分布 | `code` 唯一（`uk_code`） |
| `dict_meet_point` | 校内面交点 | 下单选面交点、报表「面交所热力」 | 带 `campus_id` + `open_hours` |

### 1.2 为什么字典排第一个

F-A7 判据原话：**这四张字典是全端一致性的源头，必须由后台下发，三端不得本地硬编码。**

```
dict_campus ──┬─→ dict_college（所属校区）
              └─→ dict_meet_point（所属校区）
dict_category ──→ item.category_id ──→ 审核 / 报表 / 搜索
dict_grade   ──→ item.condition   ──→ 详情 / 报表成色分布
```

其余模块的 mock 都通过 id 引用字典（商品的 `categoryId`、用户的 `collegeId`）；
字典改名时引用处一起变——这正是"源头"的收益，也决定了它必须先做。

### 1.3 从表结构能读出的业务规则

| 规则 | 依据 | 落点 |
|---|---|---|
| **停用而非删除** | 五张表都有 `status`（1 启用 0 停用）+ `deleted`（删除时间戳） | 前端 ContentView 已按"停用不删除"实现，接口不要提供物理删除 |
| **成色 code 全局唯一** | `uk_code(code, deleted)` | 新增成色时校验 code 不重复；注意唯一键**带 deleted**，所以已删除的 code 可以再用 |
| **分类两级** | `parent_id` + 注释"商品分类树（两级）" | 新增二级分类时校验父级必须是一级（parent_id 非 0 且自身是一级）→ 禁止三级 |
| **成色文案与颜色不得前端写死** | 表注释"前端不得硬编码文案与颜色" | ⚠️ **表里没有 color 列**，见第二节问题 1 |
| **按 sort 排序** | 五张表都有 `sort`，索引是 `(status, sort)` | 查询统一 `ORDER BY sort, id` |

### 1.4 现状盘点

| 层 | 状态 |
|---|---|
| DB 表 | ✅ 五张已建 |
| 种子数据 | ❌ **`db/zz-demo-data.sql` 里 dict_* 零条** |
| Entity / Mapper | ✅ 5 + 5（`core.entity` / `core.mapper`，2026-10-02） |
| Service / Controller | ✅ `DictService` + `DictAdminController` + 学生端 `DictController`（2026-10-02） |
| 前端类型（`@campus/shared`） | ✅ 五个 `Dict*Item` |
| 前端页面 | ✅ `/content` 五张字典 + 分类树 + 停用切换 |
| 前端 mock | ✅ `mock/dict.ts`，形状已按"后台返回"写（带 id / sort / enabled） |

## 二、开工前必须先拍板的 3 个问题

### 问题 1：`dict_grade` 缺 `color` 列 ✅ 已拍板：选 A，2026-09-30 已落地

- 表注释说"前端不得硬编码文案与**颜色**"，`business/03` F-A7 写的是"成色等级 A–D（文案 + 颜色，全端共用）"
- 但 `dict_grade` **没有颜色字段**；前端 `DictGradeItem.color` 现在是从 design/01 抄的固定值
- 选项：
  - **A（选定）给表加 `color`**，随字典下发 → 完全符合判据，改颜色不用发版
  - B 前端按 `code` 映射颜色 → 违反"不得硬编码"，且论文里会被问"为什么颜色改不了"

`db/schema.sql` 里现在的样子：

```sql
color char(7) NOT NULL DEFAULT '#8E8E93' COMMENT '徽章色值，如 #34C759；后台下发，前端不硬编码'
```

- 取 `char(7)` 而不是 `varchar(16)`：色值定长 `#RRGGBB`，7 个字符刚好，定长本身就是一种校验
- 默认 `#8E8E93`（iOS 灰）：新增成色忘了填色也不会渲染出透明徽章
- 种子四条已按 design/01 §4.1 补色：A `#1D9E75` / B `#34C759` / C `#FF9F0A` / D `#8E8E93`
- ⚠️ 遗留不一致（**未处理**）：种子里 A 叫"几乎全新"，前端 mock 里 A 叫"全新未拆"，四条文案都对不上。
  W4 灌 `zz-demo-data.sql` 时**照 `mock/dict.ts` 抄**，抄完自然一致

### 问题 2：`DictCategoryItem.itemCount` 要不要返回

- 前端类型里有 `itemCount`（该分类下在售商品数），用途是**删除前提示**
- 但商品模块还没做，联查 `item` 表现在是空的
- 选项：
  - **A 先不返回**（类型里标可选），等商品模块做完再补
  - B 现在就联查（返回 0，等于做了但没数据）
  - C 冗余到 `dict_category` 加 `item_count` 字段（要维护一致性，毕设规模不划算）

**现状（2026-10-02）**：按 A 落地——`DictCategoryVO.itemCount` 保留但恒定返回 0，
Service 里注释写明"商品模块落地前不要把它当成真实库存"。等商品模块做完再回头决定换成真值还是删字段。

### 问题 4（2026-10-02 写 Entity 时发现）：`dict_college` 缺 `campus_id` ✅ 已落地

- 前端 `DictCollegeItem` 有 `campusId`，管理端「学院」Tab 也能改所属校区，报表「学院 × 品类」按校区拆行要用；
  但表里没有这一列（同类的 `dict_meet_point` 有）
- 落地方式（与 `dict_meet_point` 同构）：
  ```sql
  campus_id   bigint       NOT NULL DEFAULT 0 COMMENT '所属校区，0=未指定',
  KEY idx_campus (campus_id, status),
  ```
  种子 12 个学院已按主校区(1001)/东校区(1002) 分配完毕
- 口径：**0 = 未指定**（与 `dict_category` 一级存 0 同一套路），VO 里 0 → null 交给前端
- ⚠ 遗留：`db/zz-demo-data.sql` 里**还没有 dict_\* 演示数据**（schema.sql 里那条注释说的"完整版"尚未写）。
  W4 灌数据时照 `mock/dict.ts` 抄（4 个校区 + 12 个学院，含 campus_id 与 color），抄完这条注释才成立

### 问题 3：接口路径与权限

- 管理端维护：`/admin/dict/**`，权限 `content.edit`（**已存在**）
- ⚠️ 2026-09-30 决策：`content.edit` **已从运营角色移除，只有超管持有**（见 `business/03` F-A7 权限段）。
  后端写接口照常挂 `PermCodes.CONTENT_EDIT` 即可，不用新造权限码——改的是**角色授权**，不是权限点本身
- 只读下发（三端共用）：走 `/api/dict/all` 还是也放 `/admin/dict/all`？
  - 学生端以后要调 → 放 `/api/**` 更符合"三端共用"语义
  - 但学生端目前只有健康检查，`/api/**` 没做登录拦截（见 `AdminWebConfig` 注释）
- 建议：**`/admin/dict/**`（管理端维护 + 管理端读取）+ `/api/dict/all`（只读下发，学生端将来用，本次只建不联）**

## 三、开发流程（按 `tech/03` 的 W0–W6 流水线）

### W0 备料：确认上面 3 个问题

- 问题 1（color 列）：✅ 已拍板并落地，见上文
- 问题 2（itemCount）：⏳ 仍待拍板——后端**已按 A 落地**（VO 保留字段但恒为 0），商品模块做完再决定换成真值
- 问题 3（路径与权限）：✅ 路径已定；权限部分已拍板为"仅超管"，见上文

### W1 成型：领域建模 ✅ Entity / DTO / Mapper 已落地（2026-10-02）

```
campus-core/src/main/java/com/campus/core/
  entity/    DictCampus / DictCollege / DictCategory / DictGrade / DictMeetPoint   ✅
  mapper/    5 个 BaseMapper 接口                                                 ✅ 2026-10-02
  dto/req/   DictCategorySaveReq / DictGradeSaveReq / DictMeetPointSaveReq          ✅
             DictCollegeSaveReq / DictCampusSaveReq
             DictStatusReq（按 id）/ DictGradeStatusReq（成色按 code）
  dto/resp/  DictCategoryVO / DictGradeVO / DictMeetPointVO                         ✅
             DictCollegeVO / DictCampusVO / DictAllVO
```

已定的几个实现口径（改代码前先看，别推翻重来）：

- **Req 各写各的**，不搞一个 `DictSaveReq` 通吃：字段差异太大（父子 / code+color / 校区+时段），
  共用类会退化成"每个字段都靠注释说明哪张表不用它"。
- **`*SaveReq` 里没有 `id`**：新增走 `POST /admin/dict/xxx`、编辑走 `PUT /admin/dict/xxx/{id}`，
  **改哪一条由 URL 路径决定**。Service 对应拆成 `createXxx(req)` / `updateXxx(id, req)`——
  不在一个方法里靠 `id == null` 分叉（那个分支 100% 由 Controller 强灌决定，Service 自己没判断力）。
  唯一例外是成色的 `code`：它是**业务主键**（A–D 真数据），不是路由用的代理键，所以留在 body 里。
- **Entity 的 `parentId` 一级存 0**（`idx_parent` 才走得动），**VO 里转 null**（前端契约）。
- **`deleted` 不加 `@TableLogic`**：照抄 `AdminUser` / `AdminRole`——`deleted` 是删除时间戳，
  靠 `AuditMetaObjectHandler` 插入时填 0，查询条件自己带 `deleted = 0`（唯一索引都带 deleted）。
- **声明式校验（`@NotBlank`/`@Size`/`@Pattern`）只管格式**；跨记录规则（父级必须是启用的一级、
  code 不重复、campusId 存在且启用）走 Service 的 `BizAssert`。controller 参数要加 `@Valid`。
- **VO 字段名迁就前端**（`label` / `desc` 而不是 `name` / `description`），省掉两端映射。
- **id 一律 Long**：Jackson 已全局转 String，前端类型本来就是 string。
- `itemCount` 保留在 `DictCategoryVO` 里但商品模块落地前**恒为 0**（问题 2 未拍板前的过渡写法）。

### W2 开模：契约先行（接口清单见第四节）✅ 已定稿（2026-10-02）

Controller 已落地，第四节表格就是最终版（18 个管理端 + 1 个只读下发）。

## 五、校验规则清单（Service 层用 `BizAssert`）

| 场景 | 规则 |
|---|---|
| 新增分类 | 名称非空且 ≤32；二级分类的父级必须存在、启用、**且自身是一级**（禁止三级）；同级不重名 |
| 编辑分类 | 已有子分类的分类不能再挂到别人下面（否则变三级）→ 6005 |
| 编辑分类 | **上级不能是自己**（否则库里 parent_id = 自身 id，前端按 parentId 组装树会无限递归）→ 1000 + 明细 |
| 「一级」/「未指定」怎么表示 | 库里存 **0**；请求里**不传与传 `"0"` 同义**，Service 开头就归一成 0，之后方法内不再有 null / 0 两套判断 |
| 停用分类 | ✅ 已拍板：**停用一级连带停用它的子分类**（避免"父停用子可选"的半成品状态）；启用**不**连带 |
| 停用校区 | ✅ 已拍板：**连带停用**该校区下的面交点与学院（校区是引用链顶端）；启用不连带 |
| 新增 / 编辑成色 | `code` ∈ A/B/C/D；按 code **upsert**（空库也能直接改文案）；`color` 为空兜底 `#8E8E93` |
| 新增面交点 | `campusId` 必须存在且启用；同校区下不重名 |
| 新增学院 / 校区 | 名称非空、同层不重名；学院可挂"未指定校区"（落库 0） |
| 删除 | **一律不提供**（停用即可），符合前端现有实现 |

## 七、2026-09-30 前端已落地的三件事（后端开工前先看这里）

### 7.1 分类启停"点了又弹回去"的 bug

症状：点分类行的开关，提示"已停用"，开关下一帧又回到启用。

根因是 **`data-source` 传的是 computed 的副本**：

```ts
const categoryTree = computed(() => {
  const roots = categories.value.filter(...).map((c) => ({ ...c, children: [] }))  // ← 浅拷贝
  ...
})
```

`toggle(record)` 改的是这份拷贝：① 不是响应式写入，不触发渲染；② 下次 computed 重算会用
`categories` 里的旧值把拷贝重新生成一遍，把它覆盖回去。
其余四张表的 `data-source` 就是 ref 数组本身，`record` 是响应式代理，所以只有分类这一张中招。

**修法**：分类单独走 `toggleCategory(record)`，按 `record.id` 回 `categories.value` 改源行。
**后端无关，但写 W3 时要记住**：前端拿到的是"两级平铺 + parentId"，树是前端自己组的，
所以更新一条分类后要么整棵树重新下发，要么前端本地按 id 打补丁——别只更新父行。

### 7.2 二级分类的新增与编辑

- 一级行多了「新增子分类」按钮（带 `parentId` 打开弹窗）
- 「上级分类」只列一级，且排除自己（`parentOptions`），避免自指
- 已有二级的一级不允许再挂到别人下面——树只允许两级
- `submit()` 从"只弹 toast"改成真正写 `categories.value`（新增 / 改名 / 改排序 / 改父级）

### 7.3 字典写操作收敛为超管

`admin_role_perm` 里删掉 `(30209,2003,'content.edit')` 一行即可，**不用新造权限码**。
前端/后端注解都不用改（`v-perm` 与 `@SaCheckPermission` 写的都是 `content.edit`）。

## 八、缓存与事务的口径（2026-10-02 拍板，写 Service 前先看）

原始诉求是「TTL 60s + 变更时同步更新缓存 + 用编程式事务防止回滚留下脏缓存」。
**前两条保留、第三条改了实现方式**，理由如下。

### 8.1 同意的两条

- **只有超管能改** —— 不用新造权限码，`content.edit` 已从运营移除（§7.3），后端照常挂它。
- **TTL 60s** —— 字典改动极少，60s 是个合理的兜底窗口。

### 8.2 改掉的两条

| 原方案 | 改成 | 为什么 |
|---|---|---|
| 变更时**同步更新**缓存 | 变更时**删除**缓存 | ① 重算要把五张表全查一遍再组装序列化，DEL 一次就够，下次读自然重建（读多写少，重建成本摊得开）；② 并发下两次写会乱序——A、B 先后改完，若 B 先算出旧快照写进去、A 后写，缓存就是 A 的旧值，要脏满 TTL。DEL 是幂等的，没有这个顺序问题 |
| 用**编程式事务**（防止回滚留脏缓存） | 事务该用还是用，但防脏缓存靠的是**提交后再动缓存**，不是事务的形式 | 不管声明式还是编程式，只要在事务**内**改缓存都有两个洞：① 回滚了但 Redis 已写 ⇒ 脏 60s；② 提交了但 Redis 写失败 ⇒ 同样脏。「提交后再删」同时堵住——回滚时库没变，缓存里的旧值本来就正确，不需要任何补偿 |

### 8.3 落地的三条规则

1. **只有 `/api/dict/all` 走缓存**（`cm:dict:all`）。管理端 `/admin/dict/**` **直查库**：
   它要看到停用项、要「改完立刻看到新值」，而且只有超管在点，缓存没收益，
   只会造成「改完列表没变」的假象。两边语义不同，**不能共用一个 key**。
2. **失效统一走 `DictService#evictCache()`**：事务外立即删；事务内注册 `afterCommit`，提交成功才删。
3. **单条 INSERT / UPDATE 不加事务**（本身原子，参照 `AdminAuthService` 那条注释里的教训）；
   只有「停用父分类连带子分类」「停用校区连带面交点与学院」这种**多条 UPDATE** 才用
   编程式 `TransactionTemplate` —— 边界就是那个 lambda，不会把整个方法拖成长事务。

### 8.4 Redis 挂了怎么办

读缓存失败 → 降级直查库；写 / 删缓存失败 → 只记 warn 日志。
字典是发布页的依赖项，Redis 抖一下就让整个发布页 500 不划算
（与 `AdminAuthService#isLocked` 同一个取舍）。
