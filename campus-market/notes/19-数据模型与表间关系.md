## 一、总貌：二十九张表，五种连法，零外键

全库 29 张表，按职责分十组。建库时约定了**不用外键约束**（db/01 约定 1：单体高并发下外键拖写入，且阻碍将来分库分表），所有「表 A 的字段指向表 B」都是**应用层承诺**，数据库只提供索引。所以读这个库的第一步不是找 FK，是认「引用字段」——而引用方式实际有五种混用，认不全就会漏掉连接（最典型的是 `item.grade` 存的是字符码不是 id）。

| 组 | 表 | 实库行数 | 一句话作用 |
|---|---|---|---|
| 字典 | `dict_campus` / `dict_college` / `dict_category` / `dict_grade` / `dict_meet_point` | 3 / 12 / 23 / 4 / 7 | 全端一致性的唯一下发源（`/api/dict/all`），三端不得硬编码 |
| 系数 | `carbon_factor` | 5 | 减碳估算系数，按一级分类，论文须标注为假设值 |
| 用户 | `app_user` / `user_auth` | 12 / 0 | 学生主记录；学号认证申请（**未接通**，见 §5.6） |
| 商品 | `item` / `item_image` / `favorite` | 97 / 157 / 0 | 商品核心表；图（≤9 张，sort=0 主图）；收藏（**未接通**） |
| 订单 | `trade_order` | 48 | 交易主单，含下单时商品快照 |
| 消息 | `chat_session` / `msg_message` | 9 / 36 | 会话（商品+双方唯一）；消息（私信/系统/交易三分区合一） |
| 审核 | `item_audit` / `report` / `appeal` | 78 / 9 / 5 | 三张案卷表汇成管理端同一条审核队列 |
| 信用评价 | `credit_log` / `user_review` | 0 / 0 | 信用流水；交易互评（**均未接通**） |
| 管理端 | `admin_user` / `admin_role` / `admin_role_perm` / `sys_operation_log` / `sys_sensitive_word` | 6 / 4 / 40 / 3 / 9 | 账号—角色—行式权限点；只追加操作日志；敏感词库 |
| 社交 | `user_follow` / `user_moment` / `moment_like` / `moment_comment` / `item_comment` | 0 / 0 / 0 / 0 / 0 | 关注关系、用户动态、动态点赞与两类评论（**设计中，未实现**，见 notes/22） |

## 二、五种引用方式

**id 引用是主流**，二十多处，按索引 JOIN 即可，没有需要特别提醒的。需要认得的是另外四种。

### 2.1 字符码引用（全库唯一一处）

`item.grade char(1)` 直接存 `dict_grade.code`（A/B/C/D），**不存字典 id**。理由是成色按 `code` upsert（notes/07 D2）、固定四档不存在「新增一档」，JOIN 条件写成 `g.code = i.grade`，与 id 引用相比只差在连接列的类型。实库校验 0 条商品引用了不存在的 code；`trade_order.item_grade` 是快照，同样存 code。

### 2.2 多态引用（四处，(类型, id) 二元组）

| 表 | 类型字段 | 值域 | id 字段 | 指向 |
|---|---|---|---|---|
| `report` | `target_type` | 商品(1) / 用户(2) | `target_id` | `item.id` 或 `app_user.id` |
| `appeal` | `biz_type` | 商品审核(1) / 举报(2) / 订单纠纷(3) | `biz_id` | `item_audit.id` / `report.id` / `trade_order.id` |
| `credit_log` | `reason_type` | varchar，见行内 | `biz_id` | 订单/举报/商品（**无写入方**） |
| `sys_operation_log` | `module` | item/order/user/review/… | `biz_id` | 各模块业务表 |

枚举值在 Java 侧已有单一事实来源（`AppealBizTypeEnum` / `ReportTargetTypeEnum`），但**数据库不校验 `biz_id` 真的存在**——脏指向只能靠应用层挡。实库现状：`report` 9 条中 8 条指向商品、1 条指向用户(2)；`appeal` 5 条为 商品审核(1)×3 + 举报(2)×2，订单纠纷(3)×0。

### 2.3 反范式快照（`trade_order` 快照组）

`item_title / item_price / item_grade / item_main_image / snapshot(json)` 五个字段在下单时定格。business/03 F-A6 的要求：纠纷取证看的是**下单时**的价格与描述，卖家事后改价改描述不能让历史订单跟着变。这也是订单对商品弱引用的底气（§5.2）。

### 2.4 自关联（`dict_category.parent_id`）

两级分类树，一级 `parent_id = 0`。注意**库里存 0、接口契约为 null**（`toCategoryVO` 刻意置 null，Jackson non_null 后键消失），前端判一级必须写「无 parentId」（`!c.parentId`），写 `=== 0` 全线踩空。

## 三、九组关系的字段级清单

每组只列**连接逻辑相关的字段**；主键一律雪花 `id`，全表共有字段（`create_time / update_time / deleted`）不重复列。基数是实库当前形态，不是理论最大值。

### 3.1 字典组与系数

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `dict_category.parent_id` | `dict_category.id` | 1:N 自关联 | 一级为 0；二级才是 `item.category_id` 的合法值 |
| `dict_college.campus_id` | `dict_campus.id` | N:1 | 0=未指定；停用校区连带其下学院、面交点不可用 |
| `dict_meet_point.campus_id` | `dict_campus.id` | N:1 | 面交所热力报表的地理维度 |
| `carbon_factor.category_id` | `dict_category.id` | 1:1 | **只挂一级分类**（实库 0 条挂二级）；二级品类算减碳要上卷 |
| `dict_grade` | 无出向引用 | — | 被 `item.grade` / `trade_order.item_grade` 按 **code 字符**引用（§2.1） |

### 3.2 用户组

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `app_user.college_id` | `dict_college.id` | N:1 | 报表「学院×品类矩阵」的行来源 |
| `app_user.campus_id` | `dict_campus.id` | N:1 | 与 `college_id` **不强制同校区**——学院自带 campus_id，用户资料是两次独立选择 |
| `user_auth.user_id` | `app_user.id` | **1:N** | 认证可重提，一人多条申请；idx_user(user_id, status) |
| `user_auth.college_id` | `dict_college.id` | N:1 | 申请时填写，可通过后覆盖 `app_user` 上的冗余 |
| `user_auth.handler_id` | `admin_user.id` | N:1 | 审核管理员；`status` 走到 通过(2) 时回写 `app_user.auth_status`（设计意图，功能未接通见 §5.6） |

`app_user.auth_status`（未认证(0)/审核中(1)/已认证(2)/未通过(3)）是**认证流程的落点**，商品卡「已认证」标识读它（`ApiItemVO.sellerAuthStatus`）。

`app_user.nickname` 与 `app_user.avatar_url` 由资料编辑接口（`PUT /api/auth/profile`，notes/20 D3）局部更新，是学生端唯二的自改字段。昵称同时落在公开资料缓存 `cm:user:pub:{userId}` 的载荷里，写后必须 DEL，否则商品列表与详情展示旧值——这也是该缓存本期唯一的主动失效点。

### 3.3 商品组

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `item.seller_id` | `app_user.id` | N:1 | idx_seller(seller_id, status) 服务「我发布的」 |
| `item.category_id` | `dict_category.id`（二级） | N:1 | NOT NULL；草稿态也必须落合法二级分类 |
| `item.campus_id` / `item.meet_point_id` | `dict_campus.id` / `dict_meet_point.id` | N:1 | 「校园四项字段」之二；meet_point 选填 |
| `item_image.item_id` | `item.id` | 1:N（≤9） | sort=0 为主图；`item.main_image` 是冗余，列表页免查图表 |
| `favorite.user_id + item_id` | `app_user.id` + `item.id` | 多对多落地表 | **B 类删除**：取消写时间戳，重收藏复用同一行置 0（db/01 §删除的两类实现） |

### 3.4 订单组

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `trade_order.item_id` | `item.id` | N:1 **弱引用** | 商品可软删而订单必须活着；靠快照组展示（§5.2） |
| `trade_order.buyer_id` / `seller_id` | `app_user.id` ×2 | N:1 ×2 | 下单时定死；`item.seller_id` 事后变化不影响在途订单 |
| `trade_order.meet_point_id` | `dict_meet_point.id` | N:1 | 热力报表维度；idx_meet(meet_point_id, meet_time) |
| `trade_order.verify_by` | `app_user.id` | N:1 | 扫码核销方，买卖任一——核销码一单一张（uk_verify_code） |
| `trade_order` 快照组 5 字段 | 反范式，无指向 | — | 纠纷取证依据（§2.3） |
| `user_review.order_id` | `trade_order.id` | N:1 | uk_order_reviewer(order_id, reviewer_id, deleted) 保一单一评 |
| `user_review.reviewer_id` / `target_id` | `app_user.id` ×2 | N:1 ×2 | 互评双方；idx_target(target_id, rating) 服务卖家信誉 |

### 3.5 消息组

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `chat_session.item_id` | `item.id` | N:1 | 0=无商品会话（平台介入的通道预留） |
| `chat_session.user_a` / `user_b` | `app_user.id` ×2 | 多对多落地 | **写入时按大小序归一**；uk_pair(item_id, user_a, user_b, deleted) 依赖它防重复会话 |
| `chat_session.last_msg_id` | `msg_message.id` | N:1 反向引用 | 会话列表免查消息表；last_msg_at 供排序 |
| `msg_message.session_id` | `chat_session.id` | N:1 | 私信(zone=1)非空；系统(2)/交易(3)通知为空 |
| `msg_message.sender_id` / `receiver_id` | `app_user.id` | N:1 | **系统通知 sender_id=0**——0 不是合法用户 id，查未读不能直接 JOIN app_user |

`zone` 必须建进索引（idx_receiver(receiver_id, zone, read_flag)），否则分区未读查询退化（db/01 §4.6，规避 Vinted 坑的关键设计）。实库 36 条消息全部是 私信(1)，系统/交易分区是二期预留。

### 3.6 审核组（三表一队列）

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `item_audit.item_id` | `item.id` | **1:N** | 一件商品多条审核记录：发布进队、改价重提、强制下架（最新一条非待审核时插新行）；实库 4015、4031、4050 一件多条 |
| `item_audit.handler_id` | `admin_user.id` | N:1 | SLA 分人统计；idx_handler(handler_id, first_handle_at) |
| `report.reporter_id` | `app_user.id` | N:1 | idx_reporter(reporter_id, status) 同时服务去重（notes/13 O13） |
| `report.target_type + target_id` | `item.id` 或 `app_user.id` | 多态 | 队列的举报任务**只收能解析出商品的**（target_type=商品(1)） |
| `report.handler_id` | `admin_user.id` | N:1 | 处理人 |
| `appeal.applicant_id` | `app_user.id` | N:1 | 申诉人必须是单据承受方（卖家/买家/被举报方） |
| `appeal.biz_type + biz_id` | `item_audit.id` / `report.id` / `trade_order.id` | 多态三指 | 全库最长的引用链入口；裁决时按 biz_type 分流（revoke / settleDispute） |
| `appeal.handler_id` | `admin_user.id` | N:1 | **换人复审**：不得为原处置人，写入时校验（F-A4） |

`item_audit` 的四个权重分量（`report_count / image_risk / credit_deduct / price_abnormal`）是进队快照，队列排序实时重算不读 `priority_score`（notes/09 §6）。

### 3.7 管理端组

| 引用方 | 指向 | 基数 | 语义与注意 |
|---|---|---|---|
| `admin_user.role_id` | `admin_role.id` | N:1 | 一个账号一个角色；待分配角色(2)状态不可登录 |
| `admin_role_perm.role_id` | `admin_role.id` | 1:N | 权限点**行式存储**不存 JSON——管理端 A9 按矩阵渲染；18 个权限点与前端 data-perm、后端注解三方同名 |

| `sys_operation_log.module + biz_id` | 各业务表 | 多态 | 无库级保证；idx_biz(module, biz_id) |

### 3.8 无关联的表

`sys_sensitive_word`（敏感词库，启动载内存 + Redis 发布订阅热更新）不引用任何表，也不被任何业务表引用——它是横切工具数据。

## 四、五条长链路：数据沿哪条路流

### 4.1 发布 → 审核 → 驳回 → 申诉 → 撤销

1. `ItemService.enqueueAudit`：`item` 落 待审核(2)，同事务写 `item_audit`（待审核(1)，四个权重分量快照）。
2. 管理端驳回：`item_audit` → 已驳回(3)，`item` → 审核未过(6)，`reject_reason` 落两边。
3. 卖家申诉：`POST /api/appeal`，`biz_type=商品审核(1)`，`biz_id = item_audit.id`；Service 校验申诉人是该商品的卖家。
4. 裁决撤销：`revoke()` 按商品当前状态反向恢复——强制下架(7)→在售(3) 并补 `published_at`；审核未过(6)→待审核(2) 并清空驳回原因，但**不新写审核单**，商品要等卖家再次编辑保存（价格/成色变化）才重新进队；维持则商品不动。

### 4.2 举报 → 处置 → 申诉（实库真实链）

`appeal 9003`（biz_type=举报(2)，biz_id=8006，维持(2)，handle_note「原判定证据充分，维持」）→ `report 8006`（reporter→target_type=商品(1)，target_id=4022，已处理(3)，result=成立(1)）→ `item 4022`。

这条链跨三张表、四个状态迁移，是**全库最长的纯外键链**：appeal → report → item，中间没有任何一张表同时持有三边，每次理解系统都要人工对齐一遍——这也是把 bizType 收敛成 `AppealBizTypeEnum` 的直接动因。注意链的中段（举报成立 → 商品强制下架）落在 `ItemAdminService.forceOffline`，它会同步落一条 `item_audit`（已强制下架(4)）供申诉方看原处置：**最新一条审核仍是 待审核(1) 时就地更新它**（保留原进队时间），否则**插入新行**且四个权重分量全 0、进队与首处时间都取当下——所以库里看到的强制下架审核单权重恒为 0，这不是数据缺漏。

### 4.3 下单 → 付款 → 核销 → 完成

1. 下单：`trade_order` 落 待付款(1)，同时定格快照五字段、生成 `order_no`（对外/幂等键）与 `verify_code`（uk，一单一张）。
2. 付款：Redis Lua 前置占位（TTL 60 秒，返回 -1 放行给 DB）+ MySQL 条件更新兜底；成功则 `item` → 已售出(5)，订单 → 待面交(2)。**全程无「已预定」状态**，付款才是唯一占位判据。
3. 核销：面交扫码，`verify_code` 匹配 → 已验货(3)，`verify_time / verify_by` 落库。
4. 确认收货：→ 已完成(4)。此后的互评（`user_review`）与信用流水（`credit_log`）在设计上挂在这一步，但两张表当前无写入方（§5.6）。

### 4.4 纠纷（订单侧的申诉）

`OrderService.openDispute` 同事务做两件事：`trade_order` → 纠纷中(8)，写 `appeal`（biz_type=订单纠纷(3)，biz_id=order.id）。复用的目的只是让它进同一条审核队列（notes/13 决策 2）。裁决 `judgeAppeal` 按 `isOrderAppeal` 分流到 `settleDispute`：买家赢 → 已退款(7) 且商品回 在售(3)、占位标记重置；卖家赢 → 已完成(4)。实库当前 0 条 订单纠纷(3) 申诉，链路未被种子数据触发过。

### 4.5 询单聊天

`chat_session` 以 uk_pair（item_id + 归一化后的双方）保证「同一商品同一对手只有一个会话」；`msg_message` 按 session_id 游标分页读，已读状态独立标。未读数 Redis 为准、库里 `a_unread / b_unread` 兜底。zone 分区（私信/系统/交易）目前只用了 私信(1)。

### 4.6 社交发布与互动（设计中）

社交四块能力（关注、动态、评论、海报）是交易核心之上的增量，已在 notes/22 定稿，本期未实现。与既有长链路的区别：动态/评论**发布即公开**，无预审队列——合规靠 `sys_sensitive_word` 过滤 + `report`(target_type 扩 3 动态/4 评论)举报后人工；被赞/评/关注的通知批次 3 经 `msg_message`（zone=2/3）推送。因此社交不构成如 §4.1–§4.4 那样的多状态迁移长链路，数据沿「写 `user_moment`/`*_comment` → 读广场流/详情」单向流动。

## 五、六个容易读错的点

**5.1 `item` ↔ `item_audit` 是 1:N，不是 1:1。** db/01 §二的 E-R 概览画成了 1:1，实库有 4015、4031、4050 三个商品各持多条审核记录。多记录的三个来源：发布进队一条；改价/改成色重提再进队一条；强制下架时若最新一条已不是 待审核(1)，`forceOffline` 会再插一条（§4.2）。notes/09 借「商品最新一条 item_audit」算基础分的写法本身就预设了多条。按 1:1 读会漏掉历史审核单，也会看不懂强制下架单权重恒 0。

**5.2 订单对商品是弱引用，快照是故意的。** 商品软删、改价、改描述都不影响在途与历史订单的展示与取证——订单侧有五字段快照。实库当前 0 条订单引用已软删商品（快照尚未被实战触发，但 schema 与代码路径都就位）。弱引用是单向的：订单拦不住商品被删，所以删商品的入口必须自查（`ItemStatusEnum.canDelete` 不放行已售出态，`deleteItem` 连带软删 `item_image` 不留孤儿图）。

**5.3 多态引用没有库级保证。** `appeal.biz_id` 指向哪张表全靠 `biz_type`，DB 不校验存在性，脏数据只能应用层挡。两个已知边界：举报用户(target_type=用户(2)) 解析不出商品，**进不了审核队列**（实库有 1 条，notes/09 已记）；`credit_log.biz_id` 无任何写入方，指向语义实际不可验证。

**5.4 `sender_id = 0` 是系统通知，不是用户。** 雪花 id 不会为 0，所以 0 是安全 sentinel；但查询/展示时不能 JOIN `app_user` 反查发送者，要按 zone 或 sender_id=0 分流。

**5.5 `chat_session.user_a < user_b` 是写入契约。** uk_pair 防重复会话完全依赖写入时把双方按 id 大小排序；哪条路径绕过归一化直接写，同一对用户就会出现两条会话。实库 0 违例。

**5.6 四张 0 行表是「未接通」，不是「没数据」。** `favorite`、`user_review`、`credit_log`、`user_auth` 四张表**没有 Mapper、没有 Service、没有 Controller**——收藏、互评、信用流水、学号认证四条功能整体未实现（管理端 `user.verify` 等权限点已预留）。读代码时不要以为「表建了就是通了」；`app_user.auth_status` 的已认证(2)目前只来自种子数据。

**5.7 社交五表是「设计中」，不是「已建好」。** `user_follow` / `user_moment` / `moment_like` / `moment_comment` / `item_comment` 五张表的设计见 notes/22，schema.sql 尚未落建表语句、无 Mapper/Service/Controller。它们与 `favorite` 等同属「表结构已规划、实现待排期」——读代码时不要以为文档列了就是通了。

## 六、报表四图的取数链路

| 图 | 主表 | JOIN 路径 | 分组维度 |
|---|---|---|---|
| 学期时间轴 | `item` + `trade_order` | 无 JOIN，两条时间线分别取 `item.published_at` 与 `trade_order.pay_time` | 按周，发布量/成交量双线 |
| 学院×品类矩阵 | `app_user` + `item` + `trade_order` | `trade_order.buyer_id/seller_id → app_user.college_id`，`item.category_id` 取二级上卷到一级 | 学院（行）× 一级品类（列）；可经 `dict_college.campus_id` 切校区 |
| 面交所热力 | `trade_order` + `dict_meet_point` | `trade_order.meet_point_id → dict_meet_point.id` | 面交点 × 时段（`meet_time`） |
| 循环率减碳 | `item` + `carbon_factor` | `item.category_id` 上卷一级 → `carbon_factor.category_id` | 循环率=已售出(5)/发布；减碳=Σ(售出件数×`factor_kg`) |

矩阵图是唯一需要三表联查的；热力与减碳都是两表。全部实时聚合不建中间表（db/01 C 档决策），万级数据量 MySQL 够用。
