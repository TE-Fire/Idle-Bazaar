## 汇报性质：这是开题，讲方案不讲成果

这是全篇最重要的语气约束。开题答辩汇报的是**打算做什么、怎么做、为什么这么做**，不是阶段性成果展示。听众是学院答辩组老师，他们只判断三件事：题目值不值得做、技术难在哪、剩下的时间做得完吗。

因此：

- 全篇使用设计态表述——「系统将包含」「拟定采用」「设计中」「预期达到」。
- **禁止**出现「已完成」「已实现」「目前系统」「实测」「上线」等成果汇报口吻。
- 不放已完成成果截图、不列实测性能数字。凡涉及指标，一律写成「设计目标」。
- 不出「文献综述」「理论意义」「研究空白」「预期成果」这类学术套话。

## 核心叙事：这是一次供需错配的撮合

**这是全篇的立论基础，所有页面都要为它服务。**

- 供给侧：在校学生手里有大量闲置物品，价格低廉、贴近生活，但对学生本人无用。这类东西便宜到不值得挂上网卖、扔了可惜、班级群里问一圈也没人要。
- **供给侧的关键特征是同质化**：同一栋宿舍楼里的台灯、小风扇、插排、教材、床帘，几乎人人都有同款——想卖的那件，往往正是隔壁室友正在卖的。
- 需求侧：学校周边社区的居民需要这些生活用品，又不愿为「用得上但非必需」的东西付新品价。
- 断点：两个群体地理上只隔一条街，信息不通，也互不信任。

**「同质化」这一条推翻了「校园二手」这个默认假设，必须讲透。** 校内买卖的本质是同质互换：买方和卖方是同一群人、卖的是同一批品类，「我有的你也有」，成交自然停滞。学生群体内部确实有一条「毕业生卖给新生」的通道，但它只集中在每年 6 月和 9 月两个窗口，而且靠线下摆摊完成，线上平台在其中没有增量。**所以平台真正的增量只能来自跨群体——学生手里过剩的生活用品，正是社区居民缺的耐用品，两边不在同一个同质圈里，这叫异质互补。**

这是把定位从「校园」拉到「同城」的唯一站得住的理由，也是答辩时最容易被追问的一处，必须准备到能脱稿讲。

平台补的就是这个断点——**只做中间人，不做运力**。因为货值低、距离短，交易根本承担不起物流成本；反过来正因为不做物流，平台才只需要承担撮合与信任两件事。

必须贯彻的三条口径：

1. **履约半径＝步行或顺路可达**。这是「同城」在本项目里的确切含义，不是行政意义上的同城，也不是面向全城配送。
2. **不承诺物流时效，不新增运力**。三种交付方式是：面交、自提、**顺路送达**（卖方本就要往社区方向去，顺带交付）。平台只提供状态与凭证，双方自愿协商。
3. **信任来自身份认证与学校背书，不来自平台自称**。这是大平台验证不了、而本项目天然具备的东西。

禁止出现的表述：全城配送、骑手调度、同城速递、快递履约、物流体系。

1. **每页只讲一个观点**。标题写成判断句——不写「关键技术」，写「并发付款时如何保证不超卖」。

## 「智能」的定位（关键，严格照此执行）

本系统的「智能」分两层，这一区分是全篇的关键，必须讲清：

**交互层——受约束的导购 Agent。** 用户用一句自然语言说出需求（「给宿舍添点东西，200 以内，这周能取」），Agent 解析成结构化条件，调用平台真实数据检索，返回商品卡片。这里用大模型，但**只用它做意图理解和话术组织，绝不让它生成任何商品属性**——商品信息全部来自工具返回的结构化数据，模型没有编造的入口。Agent 也不代替用户下单，成交仍走既有流程。

**业务层——四个环节自动决策。** 平台用数据和规则完成原本需要人工判断的事：

| 环节 | 具体机制 |
|---|---|
| 撮合 | 热度排序（浏览 / 收藏 / 成交加权 + 时间衰减）；基于物品的协同过滤推荐；面交点推荐（双方校区与社区距离 + 历史成交频次） |
| 定价 | 分类 × 成色二维均价基准；价格偏离阈值触发人工复核；发布页给出同分类近 30 天成交价参考区间 |
| 风控 | 用户信用分（成交率 / 好评率 / 响应时长 / 纠纷率加权）；付款占位防超卖；核销码双角色分离 |
| 调度 | 11 态订单状态机自动流转；超时自动取消、退款超时自动同意；纠纷自动升级至管理端裁决 |

必须遵守：

- 每提到一次「智能」，后面必须紧跟一个可指名的具体机制，不许单独把「智能」当形容词用。
- **禁止出现**：深度学习、神经网络、模型训练、微调、推荐准确率、AUC、召回率。提大模型时必须说明「只做推理调用，不做训练」，避免被引向无法交付的方向。
- 智能**不单设章节**，用两页承载：P12 讲 Agent 的链路与边界，P13 讲业务底座四环节。语气克制，讲「自动做判断」与「受约束的设计」而非「算法先进」。

## 可用技术事实清单（挑用得上的，不要全部堆砌）

**技术栈**：Java 21 + Spring Boot 3.2.5 + MyBatis-Plus 3.5.7 + MySQL 8 + Redis + MinIO；鉴权用 sa-token 1.38（token 落 Redis）；Redis 的原子操作全部下沉为 Lua 脚本；前端 Vue 3 + Element Plus + Vite；小程序 uni-app。

**架构**：前后端分离；后端按技术分层的多模块 Maven 工程（common / core / user-api / admin-api）；接口统一 `Result` 包装，错误码按模块分段。

**权限**：sa-token 1.38 + RBAC。token 存于 Redis（`sa-token-redis-jackson`），因此支持主动踢人下线——用户审核驳回或封禁后，登录态可立刻失效，这是选择 sa-token 而非 JWT 的直接原因。Web 端与小程序端可分别登录、互不影响。角色 + 权限点，约 18 个权限点。

**Redis 原子操作**：商品占位、占位释放、浏览量刷写、关注与取关等六处逻辑均写成 Lua 脚本（`occupy` / `release` / `view_flush` / `follow` / `unfollow` / `follow_flush`），由 `LuaScripts.load` 统一载入，脚本内 key 一律通过 KEYS 传入。占位脚本返回五类结果：1 抢占成功、2 同一订单幂等重入、0 已售出（终态）、-2 他人付款中可重试、-1 缓存缺失放行交数据库裁决。

**用户身份**：用户表以「身份类型 + 认证状态」两个维度描述。注册时选择学生或社区居民，各自走不同认证通道。

**交易**：订单 11 态状态机（待付款 / 待面交 / 待发货 / 已发货 / 待自提 / 已验货 / 已完成 / 已取消 / 退款中 / 已退款 / 纠纷中）。防超卖采用「Redis Lua 两级占位（商品状态 key + 持有者标识）+ MySQL `version` 乐观锁」两层兜底。核销码由卖方持有、仅买方录入，接口层拒绝卖方调用。

**收货方式**：面交 / 自提 / 顺路送达三态。下单时按类型分流，收货地址或提货地址在下单一刻**快照进订单**。

**社交与互助**：会话与消息，未读数按会话批量查询；议价在会话内完成，不进入订单。互助需求复用动态（帖子）结构，以类型字段区分普通动态与求助，**不新建业务表、不涉及支付与订单验收**。

**缓存**：字典双 key（学生端 / 管理端分离）；分类均价 Hash，TTL 5 分钟；浏览量先聚合到 Redis，定时任务落库。

**P8 信任机制：双侧不对称的信用设计**
标题：「两条认证通道，一套约束标准」

- 居民：手机号与居住区域验证，靠交易记录与评价累积信用，主要作为需求侧

**P9 技术选型与依据**
表格：技术 / 用途 / 理由。
- Java 21 + Spring Boot 3.2.5：生态成熟、与 MyBatis-Plus 契合、单体部署便于个人服务器落地
- MySQL 8：交易数据需要事务与行锁，强一致优先
- Redis：热点缓存与原子判重
- **Lua 脚本**：占位、释放、浏览刷写、关注等六处逻辑下沉为脚本，保证「读状态—判断—写状态」不被并发插入
- **sa-token 1.38**：token 存 Redis、可主动失效；相比 JWT 能实现封禁与审核驳回后的登录态立即作废，且支持 Web 与小程序分别登录
- MinIO：图片本地可控，不依赖第三方
- Vue 3 + Element Plus：管理端与 Web 端共用组件体系
- uni-app：一套代码覆盖小程序，降低多端成本
收尾：不引入公司级中间件，资源有限，够用优先。

**P10 难点一：并发付款如何不超卖**
先摆问题：多个买家同时点付款，如何保证一件商品只成交一次。
核心要点（本页是全篇技术含量最高的一页，必须讲透）：
- 判重不能写成「先 GET 看状态、再 SET 改成锁定」——中间存在窗口期，两个请求会同时读到在售，都以为自己抢到
- 因此把「读状态 → 判断 → 写状态 → 记录持有者」合并成一个 Lua 脚本，由 Redis 单线程原子执行，中间插不进其他命令
- 脚本返回五类结果，覆盖全部边界：**1 抢占成功 / 2 同一订单幂等重入 / 0 已售出（终态） / -2 他人付款中（可重试） / -1 缓存缺失放行交数据库裁决**
- Redis 只做前置拦截，**最终以 MySQL `version` 条件更新为裁决依据**，缓存失守时由数据库兜底
流程图：买家付款 → Lua 原子占位 → 数据库 `version` 条件更新 → 成功才置为已付款（失败则释放占位）。
结论：**脚本保证原子性，数据库保证正确性，两层各管一段，任一层失守仍有下一层兜底。**

**P11 难点二：交易状态不能乱**
11 态状态机图，标出三条分支（面交 / 自提 / 顺路送达）在付款后走向不同状态。
两条要点：
- 状态只能沿合法边迁移，非法迁移由条件更新直接拒绝，不依赖代码自觉
- 核销码由卖方持有、只能买方录入，接口层拒绝卖方调用，**任一方都无法单独完成核销**

**P12 导购 Agent：自然语言进，商品卡片出**
主图为一条受约束的链路：
用户一句话（如「给宿舍添点东西，200 以内，这周能取」）→ Agent 解析意图并选择工具 → 调用平台真实数据（商品检索 / 分类均价 / 卖家信用）→ 结构化条件回显给用户修改 → 商品卡片 → 用户点卡片进详情，走既有下单流程。
本页必须讲清三条设计约束（这是技术含量所在，不是限制而是设计）：
- **模型不接触数据库**，只通过注册的函数取数；商品属性一律来自工具返回，模型只负责筛选与表达，**结构上不存在编造商品属性的可能**
- **Agent 不代替用户下单**，只产出推荐卡片；成交仍走既有占位、地址、核销流程，模型不触碰交易动作
- **解析结果结构化回显**（类目 / 预算 / 校区），用户可以改，避免模型误解后无法纠偏
降级设计一句话：模型调用失败或超时，回落到关键词检索与分类筛选，保证演示与线上可用。
技术实现一句话：Spring AI 的 Function Calling，注册三个方法（商品检索、分类均价、卖家信用），后端全是既有 Service 调用，不引入新中台。

**P13 业务底座：四个环节的自动决策**
四行结构图，每行一个环节加一行机制：
- 撮合：热度排序（浏览 / 收藏 / 成交加权 + 时间衰减）、相似物品推荐（共现矩阵 + 余弦相似度，离线算好存 Redis）、面交点推荐
- 定价：分类 × 成色二维均价基准、价格偏离阈值转人工复核、发布页给出成交价区间
- 风控：信用分（成交率 / 好评率 / 响应时长 / 纠纷率加权）、付款占位、核销码双角色分离
- 调度：订单状态机流转、超时自动取消、退款超时自动同意
底部必须写这一句：**智能层不新增数据表，只读既有表、写缓存与计算字段。**
收口一句：**Agent 是交互层的智能（解决用户怎么表达需求），四环节是业务层的智能（解决平台怎么决策）；前者调用后者，不是两套体系。**

**P14 数据与缓存设计**
左：核心表六宫格（user / item / trade_order / user_address / msg_message / favorite）。
右：四条缓存策略——字典双 key 分离读写端 / 分类均价 Hash 缓存 5 分钟 / 浏览量先聚合再定时落库 / 未读数 Hash 批量点查。
原则：**按读取方式选数据结构，写入路径挂在事务提交之后。**

**P15 本设计的不同之处**
四条，每行一句标题加一句说明：
1. **场景**：从供需同质化的校内流转，转向跨群体的异质互补；用步行半径解掉「低货值承担不起物流成本」的悖论
2. **信任**：双侧不对称认证——供给侧用学校背书锚定，需求侧用行为累积，约束标准统一
3. **智能**：受约束的对话式导购与规则化底座并行——模型只做意图与表达，不生成商品属性、不触碰交易动作
4. **交易安全**：缓存占位 + 乐观锁双层兜底以数据库条件更新裁决；核销码双角色分离，卖方持码但无权核销
