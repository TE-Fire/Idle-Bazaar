# notes/16 · 图片上传、字典校验与询单留言实现笔记

2026-10-22 一轮落了三块功能：图片上传打通（策略模式双通道）、商品字典引用分级校验、询单留言（原 IM 的同步降级版）。三块的共同背景是毕设主线「交易闭环」已经跑通到订单，缺的是链条两头的素材——发布时能真的传图、发布内容能真的被校验、成交前能真的找到人。本文按实现顺序说三件事：为什么这样设计、边界条件放在哪、哪些是刻意留到二期的。

## 图片上传：票据制加策略模式

上传通道的选型争议在「文件流不经应用」和「改动小、双端兼容负担小」之间。最终两边都要：`StorageService` 之上加了一层票据制——前端不直接猜后端允许哪种传法，先调 `/api/file/upload-ticket` 换一张票据，票据里带 `mode` 与对应的上传参数（PROXY 给服务端接口地址，DIRECT 给 MinIO 的 PUT 签名 URL），前端拿到票据后按 mode 分流，但**整个交互流程只有一种**：选图 → 换票 → 上传 → 拿 objectKey 提交。模式切换是后端一个配置项（`campus.upload.mode`）的事，前端零改动，这也是票据制相对于「前端自己判断传法」的核心收益。

策略模式落在 `ProxyUploadStrategy` 与 `DirectUploadStrategy` 两个实现上，由 `UploadStrategyRouter` 按配置挑选，共同前置 `UploadChecks`：扩展名与 MIME 双重白名单（只收 jpg/jpeg/png/webp）、大小上限、bucket 固定为 `item-image`。两层策略都不信任客户端声明的类型——PROXY 分支拿到 `MultipartFile` 后仍然过一遍 `UploadChecks`，DIRECT 分支的签名 URL 里也带上 `Content-Type` 限制，签名只对约定类型生效。

读路径做了简化：bucket 设为公开读，图片 URL 由 endpoint 直接拼 objectKey，不过期、不签 GET。对毕设的数据敏感度这是划算的——省掉每次列表查询批量签名的开销，也避免前端缓存失效问题；代价是 URL 可猜测，二期若上私密 bucket 只需替换 `getUrl` 一处实现。

删除商品时的对象清理挂在事务边界上：`ItemImageJanitor.cleanupAfterCommit` 在删除事务内先查出未软删的图片 URL，把真正的 `deleteByUrl` 注册到 `afterCommit`。顺序不能反——先删对象再回滚，商品还在而图没了，这是比孤儿对象更坏的故障。`StorageService` 用 `ObjectProvider` 注入：demo 环境 `minio.enabled=false` 时不装配存储 Bean，清理整体跳过（留孤儿对象），删除主流程不受影响。

## 字典引用校验：为什么必须分两级

补上 business/01 O1 规则 4 时真正的坑不在「校验」而在「校验多严」。历史商品本就可能引用已停用的字典项——这正是字典缓存必须分「启用项」（`cm:dict:all`，学生端）与「全量」（`cm:dict:admin:full`，管理端）两套 key 的原因。如果编辑时也要求「必须启用」，那么任何一个被停用分类下的历史商品都将永远无法编辑，保存任何字段都被拒。所以 `DictService.validateItemRefs` 收了两个口径：

| 路径 | 口径 | 数据来源 |
|---|---|---|
| 发布（含草稿） | 存在且启用 | 启用缓存 `all()`，零额外 IO |
| 编辑 | 只查存在 | 四条 `selectCount`，编辑是低频操作 |

`meetPointId` 是选填项，传了才查；成色按 `code` 匹配且统一转大写后比对（成色表 code 唯一，与 `requireGradeFlawDescribed` 的 `equalsIgnoreCase` 口径一致）。草稿同样落库，所以草稿发布也走启用口径——引用无效的草稿存进去，送审时快照解析会是空的。

## 询单留言：复用原 IM 表，砍掉实时

business/02 曾把 IM 定为小程序 P0 主导能力，2026-10-22 决策降级为同步询单留言。降级的关键便利是 schema 里本来就有 `chat_session` 与 `msg_message` 两张表（原 IM 设计），结构正好覆盖同步需求——**不新建表、不改表**，且 `zone`（分区）与 `type`（消息类型）两列给二期升级留了位置：私信恒 zone=1、系统/交易通知、图片消息、面交卡片都在二期，升级实时 IM 不需要动 DDL。

会话以「商品 + 双方」为唯一键（`uk_pair`），`user_a`/`user_b` 按 id 大小序归一，买家询价与卖家回复天然落进同一行。并发首聊用 `DuplicateKeyException` 兜底：撞唯一键时取回对方刚建的那一行，不报错、不建重。发送权限收了一道：买家发起时对方必须是该商品卖家，防止借询单通道给任意用户发消息；卖家回复不限——能在会话里回复的，对方必然是在该商品下询过单的人，由会话存在性天然约束。

同步模式的心智模型是「进会话轮询、拉取即已读」：`messages` 只做分页读（`beforeId` 游标向上翻），已读标记独立成 `markRead`，进会话时调一次。未读数是一次 `select session_id` 的批量查（只取一列，Java 侧计数），不逐会话 count；商品摘要、对方昵称批量查后组装——一个用户的会话数是商品级，全量取不翻页。纠纷介入的取证按收窄后的 business/03 执行：看订单快照与双方凭证，聊天记录留待二期。

## 配置与遗留

`campus.upload.mode`（proxy/direct）与 `minio.enabled` 是两个独立开关：dev 环境 `minio.enabled=true` 走真实 MinIO，demo 环境关存储、上传接口返回明确错误而非启动失败。遗留三项：MinIO 孤儿对象无定时巡检（二期补）、DIRECT 模式小程序端需配 request 合法域名（联调时验证）、图片消息未做（二期 IM 一并）。
