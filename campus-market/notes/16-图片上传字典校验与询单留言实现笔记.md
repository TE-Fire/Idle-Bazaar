# notes/16 · 图片上传、字典校验与询单留言业务说明

2026-10-22 落地的三块功能：图片上传（票据制 + 策略模式双通道）、商品字典引用分级校验、询单留言（原 IM 的同步降级版）。三块共同补上交易闭环的链条两头——发布时能真的传图、发布内容能真的被校验、成交前能真的找到人。本文按 notes/13 的体例写：每个业务条目先列接口，再给规则与数据变化，设计取舍收进附录 C。涉及的对外接口共 7 个（另有一个内部校验方法挂在商品发布 / 编辑链路上）。

## 一、模块定位

三块功能分别落在三个位置，互不依赖，可单独审查：

| 模块 | 解决什么 | 落点 |
|---|---|---|
| 图片上传 | 商品图片从「提交 URL 字符串」变成「服务端签发、双通道上传」 | `campus-support` 存储包 + `/api/file` 两个端点 |
| 字典引用校验 | 商品引用的分类 / 成色 / 校区 / 面交点必须真实有效 | `DictService#validateItemRefs`，挂在 `ItemService` 发布与编辑 |
| 询单留言 | 买卖双方成交前的沟通通道（原 IM 降级为同步留言） | `/api/chat` 四个端点，复用 `chat_session` / `msg_message` |

## 三、业务条目

### U1 · 上传票据签发

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/file/upload-ticket` | 登录 | 按服务端配置或显式 `mode` 选策略，返回「怎么传」指令 |

**请求（`TicketIssueReq`）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `filename` | string | 是 | 原始文件名，服务端取扩展名做白名单校验 |
| `size` | long | 是 | 字节数，≤ 5MB（5242880）；前端先拦，服务端必须再查 |
| `contentType` | string | 否 | 客户端声明类型，服务端不信任（见规则 3） |
| `mode` | string | 否 | `proxy` / `direct`；不传按 `campus.upload.mode` 配置。小程序端固定传 `proxy` |

**响应（`UploadTicket`）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `mode` | enum | `PROXY` / `DIRECT`，前端按它选择上传动作 |
| `objectKey` | string | `item/{userId}/{uuid}.{ext}`，proxy 端点按它落桶 |
| `uploadUrl` | string | 实际发起上传的地址：proxy 是服务端相对路径，direct 是 MinIO 绝对地址 |
| `httpMethod` | string | `POST`（multipart）/ `PUT`（直传） |
| `formFields` | map | proxy 附带表单字段（objectKey）；direct 为空 |
| `headers` | map | direct 的 PUT 头（含 `Content-Type` 限制）；proxy 为空 |
| `accessUrl` | string | 公开读 URL，提交商品时进 `images` 的就是它；两种模式一致 |
| `expireSeconds` | number | 签名有效期；proxy 为 0（不过期，服务端收口） |

**规则**

1. 票据只描述「将要传什么」，文件本体不随票据走；真实上传按 mode 分流到 U2。
2. `accessUrl` 在上传前就能给出——对象 key 签票时已定，桶公开读，故前端换到票即可预渲染。
3. 两层策略都不信任客户端声明的类型：PROXY 分支拿到 `MultipartFile` 后仍过 `UploadChecks`，DIRECT 分支的签名 URL 带 `Content-Type` 限制，签名只对约定类型生效。
4. 白名单：jpg / jpeg / png / webp；大小 1B–5MB。非法返回 1000（`PARAM_ERROR` 带 detail，不占独立错误码段）。
5. objectKey 前缀固定 `item/{当前用户}/`——上传与清理都按这个前缀找归属。

### U2 · 图片上传（PROXY 模式第二步）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/file/upload` | 登录 | multipart 转发上传；仅 PROXY 模式的第二步 |

**请求**：`multipart/form-data`，`file`（文件本体）+ `objectKey`（票据的 `formFields`）。

**响应（`FileUploadVO`）**：`objectKey` + `url`。与票据里的 `accessUrl` 一致（同 key 同桶），单独返回是让前端上传完成后能就地校验，不必信票据。

**规则**

1. DIRECT 模式不走本接口——前端拿票据里的 `uploadUrl` 直接 PUT 到 MinIO，文件流不经应用。
2. `objectKey` 前缀必须是 `item/{当前用户}/`，否则拒绝（防止替别人对象覆写）。
3. 完整交互流程只有一种：**选图 → 换票 → 上传 → 拿 accessUrl 提交业务**。模式切换是后端 `campus.upload.mode` 一个配置项的事，前端零改动——这是票据制相对于「前端自己判断传法」的核心收益。
4. 删除商品时的对象清理挂事务边界：`ItemImageJanitor.cleanupAfterCommit` 在删除事务内先查出未软删的图片 URL，把真正的 `deleteByUrl` 注册到 `afterCommit`。顺序不能反——先删对象再回滚，商品还在而图没了，这是比孤儿对象更坏的故障。
5. `StorageService` 用 `ObjectProvider` 注入：`minio.enabled=false` 时不装配存储 Bean，清理整体跳过（留孤儿对象），删除主流程不受影响。

### D1 · 字典启用项下发

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/dict/all` | 免登录 | 五张字典（分类 / 成色 / 校区 / 面交点）的启用项一次下发 |

**规则**

1. 走启用缓存 `cm:dict:all`，读穿 + 异常降级；写操作两个 key（`cm:dict:all` 与管理端 `cm:dict:admin:full`）一起 DEL。
2. 两套 key 不能合并：商品可引用已停用 / 改过名的字典项，只缓存启用项会让历史商品名称解析成 null（详见 notes/07）。
3. 本接口是 D2 发布口径的数据源：发布校验走同一份启用缓存，零额外 IO。

### D2 · 商品字典引用校验（内部，挂发布 / 编辑）

**接口**：无独立对外接口。调用点两处：

| 调用点 | 位置 | 口径 |
|---|---|---|
| 商品发布（含草稿送审） | `ItemService` 发布链路 | `requireEnabled = true`：存在且启用 |
| 商品编辑 | `ItemService` 编辑链路 | `requireEnabled = false`：只查存在 |

**请求参数**（`DictService#validateItemRefs`）：`categoryId`、`grade`（成色 code）、`campusId`、`meetPointId`、`requireEnabled`。

**规则**

1. **两级口径的原因**：历史商品本就可能引用已停用的字典项。如果编辑时也要求「必须启用」，任何一个被停用分类下的历史商品都将永远无法编辑，保存任何字段都被拒。
2. 发布口径走启用缓存 `all()`，零额外 IO；编辑口径是四条 `selectCount`——编辑是低频操作，不值得为它预热第二份缓存。
3. `meetPointId` 是选填项，传了才查。
4. 成色按 `code` 匹配，统一转大写后比对（成色表 code 唯一）。
5. 草稿同样落库，所以草稿送审也走启用口径——引用无效的草稿存进去，送审时快照解析会是空的。
6. 校验失败抛 `DICT_REF_INVALID`(6006)。

**状态与数据变化**：无独立落库；校验通过则发布 / 编辑主流程继续，失败则整个写事务回滚。

### C1 · 发送留言

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/chat/send` | 登录 | 发送询单留言，返回消息 id |

**请求（`ChatSendReq`）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `itemId` | long | 是 | 商品 id，会话按「商品 + 双方」定位 |
| `toUserId` | long | 是 | 对方 id；不需要传 sessionId（前端拿不到，会话由服务端 upsert） |
| `content` | string | 是 | 文本 1–500 字；图片消息（type=2）与面交约定卡片（type=3）本期不做 |

**规则**

1. 会话以「商品 + 双方」为唯一键（`uk_pair`），`user_a` / `user_b` 按 id 大小序归一——买家询价与卖家回复天然落进同一行，双方看到的是同一份数据。
2. 并发首聊用 `DuplicateKeyException` 兜底：撞唯一键时取回对方刚建的那一行，不报错、不建重。
3. 发送权限收一道：买家发起时对方必须是该商品卖家（`CHAT_PEER_INVALID` 4019，商品不存在 4018）；卖家回复不限——能在会话里回复的，对方必然是在该商品下询过单的人，由会话存在性天然约束。
4. 消息落 `msg_message`：`zone = 1`（私信分区）、`type = 1`（文本）。两列是二期升级 IM 的预留位——`type` 的预定义为 1 文本 / 2 图片 / 3 卡片（面交约定）/ 4 系统通知，其中**面交卡片指双方约定面交时间地点时发送的结构化消息**（`extra` JSON 列存面交点 / 时间 / 商品引用，可被程序解析，支持导航、日历、一键确认），不是商品详情卡片；`zone` 则预留给系统 / 交易通知分区。升级实时 IM 不需要动 DDL。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `chat_session` | 首聊插入一行（uk_pair 归一）；已存在则更新 `last_message_id` / 更新时间 |
| `msg_message` | 插入一条，`sender_id` = 当前用户，初始未读态由接收方视角决定 |

### C2 · 会话列表

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/chat/conversations` | 登录 | 我参与的会话，按最近消息倒序 |

**响应（`ChatConversationVO`）**：`itemId`、`itemTitle`、`itemMainImage`、`price`、`status`、`peerUserId`、`peerNick`、`lastContent`、`lastAt`、`unread`（对方发来且未读的条数，拉取消息后清零）。

**规则**

1. 按「商品 + 对方」一行：买家看到「在哪件商品下和谁聊过」，卖家看到「谁在哪件商品下问过我」——双方同一行数据，不用两套逻辑。
2. 未读数是一次 `select session_id` 的批量查（只取一列，Java 侧计数），不逐会话 count；商品摘要、对方昵称批量查后组装。一个用户的会话数是商品级，全量取不翻页。
3. `price` / `status` 是**会话窗顶部商品卡片**的数据源（2026-10-26 新增）：卡片展示商品图、标题、价格，`status` 非 `ON_SALE`（已售出 / 已下架等）时价格置灰并挂状态标签——面交前双方能直接看到商品现状，避免对一件已售商品继续谈。组装时 `itemMap` 本就查的是完整 `Item` 实体，两个字段不增加 IO。
4. 卡片显隐是**用户级偏好**：前端本地存储（mini `uni storage` / web `localStorage`，key `chat:item-card:hidden`），默认展示，关闭后本机所有会话不再显示；点击卡片回商品详情。数据经跳转参数带入会话页，不新增接口。

### C3 · 会话消息（分页读）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/chat/messages` | 登录 | 倒序分页，`beforeId` 游标向上翻 |

**请求参数**：`itemId`（必填）、`withUserId`（必填）、`beforeId`（选填，游标）、`size`（选填，默认 30，上限 50）。

**响应（`ChatMessageVO`）**：`id`、`senderId`、`content`、`createdAt`、`mine`。

**规则**

1. `mine` 由服务端按发送人与当前登录用户比较给出，前端不自己判断左右气泡——判断逻辑放一端，双端不会再各写错一遍。
2. 无会话返回空列表（不报 404：会话可能还没建，空列表与「未聊过」语义一致）。
3. 同步模式的心智模型是「进会话轮询、拉取即已读」：已读标记独立成 C4，进会话时调一次；轮询间隔由前端定，后端无推送。

### C4 · 标记已读

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/chat/read` | 登录 | 把对方发来的未读消息标已读 |

**请求参数**：`itemId`、`withUserId`（均必填）。

**规则**：只标「对方发给我」的未读消息；自己发的消息无已读态。已读是单边动作，不回推给对方——本期不做「已读回执」。

## 四、通用业务规则

1. **鉴权口径**：`/api/chat/**` 与 `/api/file/**` 全部要求登录；`/api/dict/all` 免登录。用户身份一律 `UserContext.getUserId()` 服务端取，**不接受客户端传用户 id**（与 notes/13 §4.4 同一约定）。
2. **无实时通道**：本期是同步 REST 轮询，无 WebSocket。消息分页读 + 独立已读标记 + 未读批量查三件套就是为轮询设计的；接实时 IM 时 DDL 不动，前端把轮询换成订阅即可。
3. **表结构零新增**：三块功能没有新建任何表。图片走 MinIO 对象（URL 存 `item_image`），留言复用原 IM 设计遗留的 `chat_session` / `msg_message`。
4. **错误码落点**：图片与票据复用通用段 1000（带 detail）；字典引用 6006（`DictErrorCode`）；留言 4018 / 4019（`UserErrorCode` 用户段）。

| 1 | 上传通道选型 | A. 前端直接 PUT MinIO（文件流不经应用）<br>B. 文件流经服务端转发<br>C. 票据制 + 策略模式（双通道） | **C**：`StorageService` 之上加票据层，前端流程唯一（选图 → 换票 → 上传 → 提交），模式切换是后端一个配置项的事，前端零改动；小程序端固定 PROXY（`uni.uploadFile` 发不了 PUT） |
| 2 | 读路径是否签名 | A. 私密 bucket + 每次列表批量签 GET<br>B. 公开读 bucket、URL 直拼不过期 | **B**：省掉批量签名开销与前端缓存失效问题；代价是 URL 可猜测，二期上私密 bucket 只需替换 `getUrl` 一处实现 |
| 3 | 字典引用校验口径 | A. 一律要求「存在且启用」<br>B. 发布查启用、编辑只查存在 | **B**：一刀切查启用会把停用分类下的历史商品永久锁死，任何字段都保存不了 |
| 4 | IM 实时能力是否本期做 | A. 上 WebSocket 全量 IM<br>B. 降级为同步询单留言，复用既有两表 | **B**：schema 里本来就有 `chat_session` / `msg_message`，不新建表不改表；`zone` / `type` 两列给二期留位，升级实时不动 DDL |

### 实现顺序（已按此执行）

**票据与上传通道 → 字典两级校验 → 询单留言（会话 upsert → 发送 → 列表 → 分页 → 已读）。**
前两步是发布链路的前置，留言独立成链；三者除共用登录态外无横向依赖。
