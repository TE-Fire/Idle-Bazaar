## 问题 1 · 事务边界圈错范围：超时扫描的大事务

**结论：根因不是「在循环里做更新」，而是事务的原子性范围与业务的原子性范围不匹配——把一批彼此独立的取消圈成了一个原子单位。修复方向不是缩小事务，而是把事务下沉到单笔。**

### 场景

平台不预定库存：下单只写一条待付款订单，商品保持在售，所有权在付款成功那一刻才判定。待付款订单 30 分钟不付即超时，由 `OrderService#cancelExpired` 每 10 分钟扫描一轮兜底取消（`tech/01` §9.2，本期不引 MQ，定时扫描即超时取消的实现载体）。单笔取消走条件更新：WHERE 带 `status = 待付款`，影响行数 0 表示状态已被并发改走，本次作废——这个设计本身是正确的，问题出在包裹它的外层事务。

### 代码（修复前，`OrderService.java`，提交 e607bde 时状态）

```java
@Scheduled(fixedDelay = 10 * 60 * 1000L)
@Transactional(rollbackFor = Exception.class)
public void cancelExpired() {
    List<TradeOrder> expired = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.WAIT_PAY.getCode())
            .le(TradeOrder::getExpireTime, LocalDateTime.now()));
    int count = 0;
    for (TradeOrder order : expired) {
        count += cancelOne(order, CancelTypeEnum.SYSTEM_TIMEOUT, "30 分钟未付款，系统自动取消");
    }
    if (count > 0) {
        log.info("[order] 超时取消待付款订单 {} 笔", count);
    }
}

private int cancelOne(TradeOrder order, CancelTypeEnum type, String reason) {
    return orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
            .eq(TradeOrder::getId, order.getId())
            .eq(TradeOrder::getStatus, order.getStatus())
            .set(TradeOrder::getStatus, OrderStatusEnum.CANCELED.getCode())
            .set(TradeOrder::getCancelBy, type.getCode())
            .set(TradeOrder::getCancelReason, reason));
}
```

### 分析

触发「前 99 笔成功、最后 1 笔失败」的不是业务冲突，而是基础设施故障——死锁、连接抖动、undo 段满。业务冲突走的是条件更新落空（影响行数 0），不抛异常，循环照常继续。也就是说，这个代码在正常并发下一直工作正常，故障面前才暴露代价：

1. **全批回滚**。第 100 笔抛出异常，外层事务 ROLLBACK，前 99 笔的执行全部作废。这批订单只能等 10 分钟后的下一轮扫描，期间一直挂在「待付款」。
2. **行锁窗口贯穿整批**。外层事务从第一笔更新起就握着这些订单的行锁，直到最后一笔提交才释放。而这批订单恰好是「买家可能正在付款」的那批——`pay` 的 `claimItem` 要抢同一商品行、同表的待付款行，超时扫描在阻塞真实付款。积压量决定这个窗口有多长。
3. **单轮耗时不可控**。`selectList` 一次捞全量过期订单，循环长度由积压量决定；`@Scheduled` 默认单线程调度器，一轮跑太久会挤占同一调度器上后续任务的时机。

往下追一层，`@Transactional` 加在这里的直觉是「循环里改多行，包个事务保证一致」。但这个一致性判断错了：每笔订单的取消是一个独立的业务事实，笔与笔之间不存在「要么全取消、要么全不取消」的业务约束。**事务的原子性应该匹配业务的原子性**——这是本例的根因，也是所有批处理任务加事务前该先回答的问题。

### 方案

按「原子性下沉到单笔」改造，三处联动：

1. **`cancelExpired` 去掉方法级事务**，循环内 try-catch：单笔失败只记 error 日志继续跑，不影响已提交的批次。失败的订单状态没变，下一轮扫描会再次捞到它——**重试不需要补偿机制，由条件更新的幂等性免费提供**。
2. **`cancelOne` 内用 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）自管事务**。没有另建一个带 `@Transactional(REQUIRES_NEW)` 的方法，是因为同类内 `this.xxx()` 调用不走 Spring 代理，注解会静默失效——这是 Java 事务最常踩的坑，编程式模板顺带绕开它。
3. **异常不在 `cancelOne` 里吞**。`cancelOne` 有两个调用方：超时扫描之外，用户主动取消（`cancel` 的 WAIT_PAY 分支）也复用它，且要求「影响行数必须为 1，否则抛业务异常让外层回滚」。若在方法内 catch 后返回 0，真实的 DB 故障会被掩盖成一句「订单状态无效」。失败语义因入口而异，只能由调用方处理。
4. **查询侧限量**：`ORDER BY expire_time + LIMIT 200`。一次捞全量是同一问题的另一面（大结果集、长内存驻留）；限量后积压分多轮消化，`fixedDelay` 保证轮次不重叠。

修复后代码（提交 89bab40）：

```java
@Scheduled(fixedDelay = 10 * 60 * 1000L)
public void cancelExpired() {
    List<TradeOrder> expired = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.WAIT_PAY.getCode())
            .le(TradeOrder::getExpireTime, LocalDateTime.now())
            .orderByAsc(TradeOrder::getExpireTime)
            .last("LIMIT " + EXPIRE_SCAN_BATCH));
    int count = 0;
    for (TradeOrder order : expired) {
        try {
            count += cancelOne(order, CancelTypeEnum.SYSTEM_TIMEOUT, "30 分钟未付款，系统自动取消");
        } catch (Exception e) {
            // 单笔失败只丢这一笔：状态未变，下轮扫描自动重试，不能让它拖垮已成功的
            log.error("[order] 单笔超时取消失败，留待下次扫描重试：orderId={}", order.getId(), e);
        }
    }
    if (count > 0) {
        log.info("[order] 超时取消待付款订单 {} 笔", count);
    }
}

private int cancelOne(TradeOrder order, CancelTypeEnum type, String reason) {
    TransactionTemplate template = new TransactionTemplate(txManager);
    template.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    return template.execute(status -> orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
            .eq(TradeOrder::getId, order.getId())
            .eq(TradeOrder::getStatus, order.getStatus())
            .set(TradeOrder::getStatus, OrderStatusEnum.CANCELED.getCode())
            .set(TradeOrder::getCancelBy, type.getCode())
            .set(TradeOrder::getCancelReason, reason)));
}
```

### 否掉的方案

| 方案 | 否掉的原因 |
|---|---|
| 保留外层事务，每 N 笔 `REQUIRES_NEW` 提交一次 | 只把回滚半径从整批缩到一个分批，没消除问题；且同类自调用下 `REQUIRES_NEW` 注解静默失效，改完可能根本不生效 |
| 合成一条 `UPDATE ... WHERE status=待付款 AND expire_time<=now()` | 单语句最彻底，且本场景取消原因固定、适用；但丢逐笔失败可见性，单笔异常只能靠数据库侧日志排查。超时取消的取消理由唯一时可选它 |

逐笔独立事务的代价是失败的那笔要等下一轮（最长 10 分钟延迟）。对超时取消这个场景可接受——它本身就是个兜底机制，不是实时承诺。

### 遗留观察点

改动未联调。验证时重点看两处：单笔失败的 error 日志是否带 orderId（没有的话下轮重试时无法定位）；取消过程中同商品的真实付款是否还会被阻塞（行锁窗口缩短后的直接可观测效果）。

## 问题 2 · 同一病灶的第二实例：退款自动同意扫描漏改

**结论：`autoRefund` 不是「没做」，而是「做了但停在问题 1 的旧模式」——文档审查时被误判为缺失功能，核查后确认功能已在，遗漏的是与 `cancelExpired` 同源的事务重构。修复直接套用问题 1 的方案，无新决策。**

### 场景

买家对已付款订单发起取消（O8 的 WAIT_MEET/VERIFIED 分支），订单转退款中(6)；卖家 24 小时未处理，由 `OrderService#autoRefund` 每 30 分钟扫描一轮，自动同意并转已退款(7)，商品同步恢复在售（notes/13 第四节）。

功能的发现过程本身就是教训：TE 审 notes/13 时提出「24 小时系统自动同意未做」，核查后确认代码已在（`@Scheduled` + `@EnableScheduling` 均生效），但这份实现停留在问题 1 修复之前的模式。**同一病灶修一处不够——重构类改动完成后，应当按模式（`@Transactional` + for 循环 + 无 LIMIT 的全量 `selectList`）全局扫一遍同文件乃至同项目，而不是只修被点名的那一个方法。**

### 代码（修复前，`OrderService.java`）

```java
@Scheduled(fixedDelay = 30 * 60 * 1000L)
@Transactional(rollbackFor = Exception.class)
public void autoRefund() {
    LocalDateTime deadline = LocalDateTime.now().minusHours(AUTO_REFUND_HOURS);
    List<TradeOrder> pending = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.REFUNDING.getCode())
            .le(TradeOrder::getUpdateTime, deadline));
    int count = 0;
    for (TradeOrder order : pending) {
        int rows = orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
                .eq(TradeOrder::getId, order.getId())
                .eq(TradeOrder::getStatus, OrderStatusEnum.REFUNDING.getCode())
                .set(TradeOrder::getStatus, OrderStatusEnum.REFUNDED.getCode())
                .set(TradeOrder::getCancelReason, AUTO_REFUND_REASON));
        if (rows == 1) {
            count++;
            restoreItemOnRefund(order);
        }
    }
    // ...
}
```

### 分析

根因与问题 1 完全相同：笔与笔之间没有「要么全退、要么全不退」的业务约束，却被圈进了一个原子单位。前 99 笔同意、第 100 笔遇死锁或连接抖动，整批回滚，这批退款申请要再等 30 分钟。三处具体表现与问题 1 一一对应（全批回滚、行锁窗口贯穿整批、单轮耗时不可控），不再重复论证。

两处场景差异只影响参数选择，不改变方案：

1. **排序键要另选**。退款中订单没有 `expire_time` 可排，但 `update_time` 就是进入退款中的时刻（借用语义见方法注释），按它升序即「先被冷处理的更早解决」，比无序更符合公平性，也顺带把每轮处理范围收敛到最老的一批。
2. **积压概率更高**。超时取消的积压源于买家不付款（个人行为），退款积压则可源于卖家集体不处理（比如期末集中挂售后无人打理），因此这里的 LIMIT 不是可选项。单笔事务里除了订单更新还挂着 `restoreItemOnRefund`（商品状态 + Redis 占位标记重置），链路更长，回滚半径大的代价也更高。

### 方案

套用问题 1 的三处联动，无新决策：`autoRefund` 去掉方法级事务、循环内 try-catch；抽出 `autoRefundOne` 用 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）包住「条件更新 + 恢复商品」；查询侧 `ORDER BY update_time + LIMIT 200`，复用 `EXPIRE_SCAN_BATCH`（「超时扫描每轮处理上限」的语义覆盖本场景，不新增常量）。与 `cancelOne` 的差别仅在于异常语义：`cancelOne` 有两个调用方、拒绝入口要求异常照实传播，`autoRefundOne` 只服务扫描一个入口，行数 0（卖家刚好自己点了同意）属正常并发结果，直接返回即可。

改动位于 `campus-core/.../service/OrderService.java`（`autoRefund` / `autoRefundOne`），编译验证通过，尚未提交，提交后回填锚点。

## 问题 3 · notes/16 替换时的设计决策摘存：图片上传、字典校验、询单留言

**结论：2026-10-25 按 TE 要求将 notes/16 重写为其他示例业务笔记，原三功能的设计决策在此摘存。代码未动、仅文档搬家；这三条结论是后续改动的约束前提——头像上传复用票据通道、昵称写入触发公开缓存失效，都踩在其中划定的边界上。**

### 图片上传：票据制加策略模式

上传通道选型的争议在「文件流不经应用」与「改动小、双端兼容负担小」之间，最终两边都要：`StorageService` 之上加票据层，前端先调 `/api/file/upload-ticket` 换票据（带 `mode` 与上传参数），再按 mode 分流 PROXY（服务端 multipart）或 DIRECT（MinIO PUT 签名），但**交互流程只有一种**——选图 → 换票 → 上传 → 拿 objectKey 提交；模式切换是后端 `campus.upload.mode` 一个配置项的事，前端零改动。

两条硬约束：① 两层策略都不信任客户端声明的类型——PROXY 分支拿到 `MultipartFile` 后仍过 `UploadChecks`（扩展名与 MIME 双白名单、大小上限），DIRECT 分支的签名 URL 带 `Content-Type` 限制；② 删除时的对象清理挂 `afterCommit`——先删对象再回滚等于「商品还在而图没了」，比孤儿对象更坏；demo 环境 `minio.enabled=false` 时存储 Bean 不装配，清理整体跳过，删除主流程不受影响。读路径取公开读 bucket、URL 直拼不过期，省掉批量签名开销；代价是 URL 可猜测，二期上私密 bucket 只需替换 `getUrl` 一处。

### 字典引用校验：为什么必须分两级

历史商品本就可能引用已停用字典项，所以校验分两个口径：**发布（含草稿）查「存在且启用」**，走启用缓存 `cm:dict:all` 零额外 IO；**编辑只查「存在」**（四条 `selectCount`）。一刀切要求启用，会把停用分类下的历史商品永久锁死——任何字段都保存不了，这正是字典缓存必须分「启用项」（学生端）与「全量」（管理端）两套 key 的同一理由。`meetPointId` 选填、传了才查；成色按 `code` 匹配且统一转大写。

### 询单留言：复用原 IM 表，砍掉实时

business/02 的 IM 降级为同步询单留言，关键是 schema 本就有 `chat_session` 与 `msg_message`——**不新建表、不改表**，`zone` 与 `type` 两列给二期升级留位。会话以「商品 + 双方」为唯一键（`uk_pair`），`user_a`/`user_b` 按 id 大小序归一；并发首聊用 `DuplicateKeyException` 兜底撞键，不报错、不建重。发送权限收一道：买家发起时对方必须是该商品卖家；卖家回复不限——能在会话里回复的，对方必然是在该商品下询过单的人，由会话存在性天然约束。同步心智模型是「进会话轮询、拉取即已读」，未读数一次批量查只取 `session_id` 列。
