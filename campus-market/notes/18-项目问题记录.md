## 问题 1 · 事务边界圈错范围：超时扫描的大事务

**结论：根因不是「在循环里做更新」，而是事务的原子性范围与业务的原子性范围不匹配——把一批彼此独立的取消圈成了一个原子单位。修复方向不是缩小事务，而是把事务下沉到单笔。**

### 场景

平台不预定库存：下单只写一条待付款订单，商品保持在售，所有权在付款成功那一刻才判定。待付款订单 30 分钟不付即超时，由 `OrderService#cancelExpired` 每 10 分钟扫描一轮兜底取消（`tech/01` §9.2，本期不引 MQ，定时扫描即超时取消的实现载体）。单笔取消走条件更新：WHERE 带 `status = 待付款`，影响行数 0 表示状态已被并发改走，本次作废——这个设计本身是正确的，问题出在包裹它的外层事务。

### 代码（修复前，`OrderService.java`，提交 e607bde 时状态）

```java
@Scheduled(fixedDelay = 10 * 60 * 1000L)
@Transactional(rollbackFor = Exception.class)
public void cancelExpired() {
    List<TradeOrder> expired = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.WAIT_PAY.getCode())
            .le(TradeOrder::getExpireTime, LocalDateTime.now()));
    int count = 0;
    for (TradeOrder order : expired) {
        count += cancelOne(order, CancelTypeEnum.SYSTEM_TIMEOUT, "30 分钟未付款，系统自动取消");
    }
    if (count > 0) {
        log.info("[order] 超时取消待付款订单 {} 笔", count);
    }
}

private int cancelOne(TradeOrder order, CancelTypeEnum type, String reason) {
    return orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
            .eq(TradeOrder::getId, order.getId())
            .eq(TradeOrder::getStatus, order.getStatus())
            .set(TradeOrder::getStatus, OrderStatusEnum.CANCELED.getCode())
            .set(TradeOrder::getCancelBy, type.getCode())
            .set(TradeOrder::getCancelReason, reason));
}
```

### 分析

触发「前 99 笔成功、最后 1 笔失败」的不是业务冲突，而是基础设施故障——死锁、连接抖动、undo 段满。业务冲突走的是条件更新落空（影响行数 0），不抛异常，循环照常继续。也就是说，这个代码在正常并发下一直工作正常，故障面前才暴露代价：

1. **全批回滚**。第 100 笔抛出异常，外层事务 ROLLBACK，前 99 笔的执行全部作废。这批订单只能等 10 分钟后的下一轮扫描，期间一直挂在「待付款」。
2. **行锁窗口贯穿整批**。外层事务从第一笔更新起就握着这些订单的行锁，直到最后一笔提交才释放。而这批订单恰好是「买家可能正在付款」的那批——`pay` 的 `claimItem` 要抢同一商品行、同表的待付款行，超时扫描在阻塞真实付款。积压量决定这个窗口有多长。
3. **单轮耗时不可控**。`selectList` 一次捞全量过期订单，循环长度由积压量决定；`@Scheduled` 默认单线程调度器，一轮跑太久会挤占同一调度器上后续任务的时机。

往下追一层，`@Transactional` 加在这里的直觉是「循环里改多行，包个事务保证一致」。但这个一致性判断错了：每笔订单的取消是一个独立的业务事实，笔与笔之间不存在「要么全取消、要么全不取消」的业务约束。**事务的原子性应该匹配业务的原子性**——这是本例的根因，也是所有批处理任务加事务前该先回答的问题。

### 方案

按「原子性下沉到单笔」改造，三处联动：

1. **`cancelExpired` 去掉方法级事务**，循环内 try-catch：单笔失败只记 error 日志继续跑，不影响已提交的批次。失败的订单状态没变，下一轮扫描会再次捞到它——**重试不需要补偿机制，由条件更新的幂等性免费提供**。
2. **`cancelOne` 内用 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）自管事务**。没有另建一个带 `@Transactional(REQUIRES_NEW)` 的方法，是因为同类内 `this.xxx()` 调用不走 Spring 代理，注解会静默失效——这是 Java 事务最常踩的坑，编程式模板顺带绕开它。
3. **异常不在 `cancelOne` 里吞**。`cancelOne` 有两个调用方：超时扫描之外，用户主动取消（`cancel` 的 WAIT_PAY 分支）也复用它，且要求「影响行数必须为 1，否则抛业务异常让外层回滚」。若在方法内 catch 后返回 0，真实的 DB 故障会被掩盖成一句「订单状态无效」。失败语义因入口而异，只能由调用方处理。
4. **查询侧限量**：`ORDER BY expire_time + LIMIT 200`。一次捞全量是同一问题的另一面（大结果集、长内存驻留）；限量后积压分多轮消化，`fixedDelay` 保证轮次不重叠。

修复后代码（提交 89bab40）：

```java
@Scheduled(fixedDelay = 10 * 60 * 1000L)
public void cancelExpired() {
    List<TradeOrder> expired = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.WAIT_PAY.getCode())
            .le(TradeOrder::getExpireTime, LocalDateTime.now())
            .orderByAsc(TradeOrder::getExpireTime)
            .last("LIMIT " + EXPIRE_SCAN_BATCH));
    int count = 0;
    for (TradeOrder order : expired) {
        try {
            count += cancelOne(order, CancelTypeEnum.SYSTEM_TIMEOUT, "30 分钟未付款，系统自动取消");
        } catch (Exception e) {
            // 单笔失败只丢这一笔：状态未变，下轮扫描自动重试，不能让它拖垮已成功的
            log.error("[order] 单笔超时取消失败，留待下次扫描重试：orderId={}", order.getId(), e);
        }
    }
    if (count > 0) {
        log.info("[order] 超时取消待付款订单 {} 笔", count);
    }
}

private int cancelOne(TradeOrder order, CancelTypeEnum type, String reason) {
    TransactionTemplate template = new TransactionTemplate(txManager);
    template.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    return template.execute(status -> orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
            .eq(TradeOrder::getId, order.getId())
            .eq(TradeOrder::getStatus, order.getStatus())
            .set(TradeOrder::getStatus, OrderStatusEnum.CANCELED.getCode())
            .set(TradeOrder::getCancelBy, type.getCode())
            .set(TradeOrder::getCancelReason, reason)));
}
```

### 否掉的方案

| 方案 | 否掉的原因 |
|---|---|
| 保留外层事务，每 N 笔 `REQUIRES_NEW` 提交一次 | 只把回滚半径从整批缩到一个分批，没消除问题；且同类自调用下 `REQUIRES_NEW` 注解静默失效，改完可能根本不生效 |
| 合成一条 `UPDATE ... WHERE status=待付款 AND expire_time<=now()` | 单语句最彻底，且本场景取消原因固定、适用；但丢逐笔失败可见性，单笔异常只能靠数据库侧日志排查。超时取消的取消理由唯一时可选它 |

逐笔独立事务的代价是失败的那笔要等下一轮（最长 10 分钟延迟）。对超时取消这个场景可接受——它本身就是个兜底机制，不是实时承诺。

### 遗留观察点

改动未联调。验证时重点看两处：单笔失败的 error 日志是否带 orderId（没有的话下轮重试时无法定位）；取消过程中同商品的真实付款是否还会被阻塞（行锁窗口缩短后的直接可观测效果）。

## 问题 2 · 同一病灶的第二实例：退款自动同意扫描漏改

**结论：`autoRefund` 不是「没做」，而是「做了但停在问题 1 的旧模式」——文档审查时被误判为缺失功能，核查后确认功能已在，遗漏的是与 `cancelExpired` 同源的事务重构。修复直接套用问题 1 的方案，无新决策。**

### 场景

买家对已付款订单发起取消（O8 的 WAIT_MEET/VERIFIED 分支），订单转退款中(6)；卖家 24 小时未处理，由 `OrderService#autoRefund` 每 30 分钟扫描一轮，自动同意并转已退款(7)，商品同步恢复在售（notes/13 第四节）。

功能的发现过程本身就是教训：TE 审 notes/13 时提出「24 小时系统自动同意未做」，核查后确认代码已在（`@Scheduled` + `@EnableScheduling` 均生效），但这份实现停留在问题 1 修复之前的模式。**同一病灶修一处不够——重构类改动完成后，应当按模式（`@Transactional` + for 循环 + 无 LIMIT 的全量 `selectList`）全局扫一遍同文件乃至同项目，而不是只修被点名的那一个方法。**

### 代码（修复前，`OrderService.java`）

```java
@Scheduled(fixedDelay = 30 * 60 * 1000L)
@Transactional(rollbackFor = Exception.class)
public void autoRefund() {
    LocalDateTime deadline = LocalDateTime.now().minusHours(AUTO_REFUND_HOURS);
    List<TradeOrder> pending = orderMapper.selectList(new LambdaQueryWrapper<TradeOrder>()
            .eq(TradeOrder::getStatus, OrderStatusEnum.REFUNDING.getCode())
            .le(TradeOrder::getUpdateTime, deadline));
    int count = 0;
    for (TradeOrder order : pending) {
        int rows = orderMapper.update(null, new LambdaUpdateWrapper<TradeOrder>()
                .eq(TradeOrder::getId, order.getId())
                .eq(TradeOrder::getStatus, OrderStatusEnum.REFUNDING.getCode())
                .set(TradeOrder::getStatus, OrderStatusEnum.REFUNDED.getCode())
                .set(TradeOrder::getCancelReason, AUTO_REFUND_REASON));
        if (rows == 1) {
            count++;
            restoreItemOnRefund(order);
        }
    }
    // ...
}
```

### 分析

根因与问题 1 完全相同：笔与笔之间没有「要么全退、要么全不退」的业务约束，却被圈进了一个原子单位。前 99 笔同意、第 100 笔遇死锁或连接抖动，整批回滚，这批退款申请要再等 30 分钟。三处具体表现与问题 1 一一对应（全批回滚、行锁窗口贯穿整批、单轮耗时不可控），不再重复论证。

两处场景差异只影响参数选择，不改变方案：

1. **排序键要另选**。退款中订单没有 `expire_time` 可排，但 `update_time` 就是进入退款中的时刻（借用语义见方法注释），按它升序即「先被冷处理的更早解决」，比无序更符合公平性，也顺带把每轮处理范围收敛到最老的一批。
2. **积压概率更高**。超时取消的积压源于买家不付款（个人行为），退款积压则可源于卖家集体不处理（比如期末集中挂售后无人打理），因此这里的 LIMIT 不是可选项。单笔事务里除了订单更新还挂着 `restoreItemOnRefund`（商品状态 + Redis 占位标记重置），链路更长，回滚半径大的代价也更高。

### 方案

套用问题 1 的三处联动，无新决策：`autoRefund` 去掉方法级事务、循环内 try-catch；抽出 `autoRefundOne` 用 `TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）包住「条件更新 + 恢复商品」；查询侧 `ORDER BY update_time + LIMIT 200`，复用 `EXPIRE_SCAN_BATCH`（「超时扫描每轮处理上限」的语义覆盖本场景，不新增常量）。与 `cancelOne` 的差别仅在于异常语义：`cancelOne` 有两个调用方、拒绝入口要求异常照实传播，`autoRefundOne` 只服务扫描一个入口，行数 0（卖家刚好自己点了同意）属正常并发结果，直接返回即可。

改动位于 `campus-core/.../service/OrderService.java`（`autoRefund` / `autoRefundOne`），编译验证通过，尚未提交，提交后回填锚点。

## 问题 3 · 冷启动重建的并发控制：为什么锁的不是 userId，分段锁在换什么

**结论：`synchronized` 锁的是「对象身份」而非「数值」，而 id 是数值——装箱后同一数值不保证是同一个对象，锁可能在完全没人抢的情况下失效，且失效是静默的。安全的做法是锁一把身份确定、只归这段代码使用的专用对象；专用锁的数量又直接等于并发度，于是用「固定 64 把锁 + 取模映射」把内存从 O(用户数) 压到 O(1)，代价是无关用户偶尔共享一把锁。这不是本项目的特殊技巧，而是 Guava `Striped` 的同一思路手写版。**

### 场景

`FollowService#ensureLoaded` 是关注模块所有读路径的前置：ZSET 是 MySQL 的缓存，而缓存为空有两种含义——用户真没关注任何人，或服务刚重启还没加载过。二者靠 ZSET 内容区分不了，只能另设 `loaded:*` 标记 key，标记置上才认为该集合可信。所以冷启动后的第一批请求会集中打到同一条重建逻辑上，是典型的 cache breakdown：热点 key 失效瞬间，并发线程一起回源。

重建的动作不是幂等追加，而是「先 `DEL` 再按库 `ZADD`」，`DEL` 会清掉别人刚写进去的关系——这让并发控制从「省一次查库」的性能问题，升级成「丢数据」的正确性问题。论证见下文「为什么必须互斥」。

### 代码

```java
/** 重建串行化：按 userId 取模分 64 段，避免为每个用户常驻一把锁 */
private final Object[] loadLocks = initLocks();

private void ensureLoaded(long userId, boolean fans) {
    String marker = fans ? FollowRedisKeys.loadedFollowers(userId) : FollowRedisKeys.loadedFollowing(userId);
    // 快路径：标记在即已重建过，直接信任 ZSET
    if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(marker))) {
        return;
    }
    // 同一用户同一集合只允许一个线程重建，否则并发 DEL 会抹掉别的事务刚写入的关系
    synchronized (loadLocks[(int) (userId & 63)]) {
        // 二次确认：等锁期间可能已被前一个线程建好
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(marker))) {
            return;
        }
        String key = fans ? FollowRedisKeys.followers(userId) : FollowRedisKeys.following(userId);
        // 先清空：上次重建半途失败会留下残缺成员
        stringRedisTemplate.delete(key);
        // …按 deleted = 0 查出该用户的全部活跃关系，逐条 ZADD（score = 关注时间）
        // 标记最后写：中途失败则标记不落，下个请求重新完整重建
        stringRedisTemplate.opsForValue().set(marker, "1");
    }
}
```

### 为什么锁的不是 userId

第一层原因是语言层面根本锁不了。`synchronized` 的括号里必须是引用类型，`long` 无法直接作为 monitor，写成 `synchronized (userId)` 编译不过；想锁就得先装箱成 `Long`，而这一步恰恰是雷区：

**装箱不保证同一数值对应同一对象。** `Long.valueOf(long)` 只在 -128～127 区间返回缓存实例（区间可用 `-XX:AutoBoxCacheMax` 调整，默认如此），超出范围每次 `new` 一个。于是 `synchronized (someLongId)` 在雪花 id 上几乎百分百失效——两个线程锁的是两个不同对象，互斥完全不成立。更糟的是它的失效形态：在 1～127 的小 id 上（测试数据、种子数据常常就是小 id）它工作得好好的，换成真实雪花 id 就静默失灵，本地测不出、线上偶发，属于最难排查的一类。**锁的正确性不能依赖一个「多数情况下成立」的隐式假设。**

第二层原因在语义上：monitor 认的是引用地址，不是 `equals`。只要对象身份可能变化，`equals` 相等毫无意义。第三层原因在作用域上：即便强制统一实例（比如把 id 缓存进 `Map<Long, Long>`），锁的也是 JDK 的公共对象类型，任何别的代码锁同一个 `Long` 实例都会与本段逻辑互相阻塞——`String.intern()` 更是把冲突面扩大到整个 JVM 的字符串常量池。用业务数值当锁，等于把自己的临界区挂在公共设施上。

可行的替代路线是 `Map<Long, Object> lockMap`，`computeIfAbsent(userId, k -> new Object())` 取每用户专属锁，语义完全正确，代价是锁对象随用户数无界增长、且需要清理策略（用户不再访问后没人负责移除）。这正好引出分段锁要解决的事。

### 分段锁在换什么

锁的数量与并发度是一对硬约束：每用户一把 → 内存 O(用户数)，理论并发最高；全局一把 → 内存 O(1)，全部串行。分段锁取中间态：**预建固定 N 把锁，用 id 的哈希位选一把。** 内存是常数，并发度约为 N，代价是映射到同一段的用户会互相等待（伪冲突）。

本项目的实现是 `Object[64]`、索引 `userId & 63`：

- **为什么用 `&` 而不是 `%`**：64 是 2 的幂，`& 63` 等价于 `% 64` 但更快；更关键的是负数——Java 里 `-1 & 63` 得 63，而 `-1 % 64` 得 -1，直接数组越界。雪花 id 目前恒正，但取位写法天然对负数免疫。
- **为什么是 64**：经验值是「预期并发重建线程数 × 2～4」。重建本身要查一次全量关系 + N 次 `ZADD`，是几十到几百毫秒级的重操作，实际并发只有冷启动那一瞬；64 把 `Object` 约 1KB 内存，够用且无感。
- **分布靠不靠得住**：`& 63` 只用 id 的低 6 位，等价于假设低位均匀。雪花 id 低 12 位是同一毫秒内的序列号，跳动充分；自增主键低位也均匀。但若 id 形如 `x * 64`（低 6 位恒 0），所有用户会退化成共享同一把锁——这是分段锁的隐性陷阱，所以选掩码前必须知道 id 的生成方式，不确定时应改用 `hashCode` 混淆或 `Math.floorMod`。Guava 的 `Striped` 内部做的正是这类二次散列。
- **前提是锁容器为所有线程共享**：`FollowService` 是 Spring 单例，`loadLocks` 是它的 `final` 字段，所有请求线程拿到的是同一批锁对象，互斥才成立；若哪天把该类改成 prototype，锁立刻形同虚设。`final` 在这里还附带安全发布语义——构造完成后其他线程看到的必然是初始化好的数组。

### 为什么必须互斥（不是省一次查库）

写路径 `follow()` 的顺序是「先 `ensureLoaded` 再执行 Lua」，也就是说作者认为进入 Lua 时该集合已可信。去掉锁之后，重建与写入会交错出这样一个序列：

1. A 检查标记不存在，准备重建；
2. B 同样检查标记不存在，紧接着完成 `DEL` + `ZADD` + 置标记，再执行 Lua 把「A 关注 B」写进两个 ZSET 与 pending；
3. A 这时才执行它的 `DEL`——**把 B 刚写入的关系连同整个集合一起清空**；
4. A 按自己查库的结果重建，而 B 的新关系还在 pending 里、尚未落库，查不到，于是不会被补回；A 随后置上标记，让这个残缺集合变成「可信」。

结果是一条真实发生过的关注在 Redis 里永久缺失：标记已置，不会再触发重建；DB 五秒后倒是落库了，但没有任何路径把它推回 ZSET。**互斥在这里守的是这条数据链，省掉重复回源只是顺带的收益。**这也解释了为什么重建必须先 `DEL`、标记必须最后写：`DEL` 保证不会新旧混杂，标记最后写保证中途崩溃时下个请求会重新走完整流程，两者合起来构成自愈。

另外要分清：这里的「双重检查」不是 JMM 意义上的 double-checked locking。经典 DCL 要防的是指令重排与字段可见性（所以单例字段必须 `volatile`）；而这里的标记存在 Redis 里，可见性由 Redis 服务端命令的先后顺序保证，第二次检查纯粹是逻辑上的「等锁期间状态可能已变」，与内存模型无关——所以 `marker` 不需要也没有资格谈 `volatile`。

### 否掉的方案

| 方案 | 否掉的原因 |
|---|---|
| `synchronized (userId)` / 锁装箱后的 `Long` | 装箱缓存只覆盖 -128～127，雪花 id 上锁对象身份不成立，互斥静默失效；且锁公共类型会与无关代码互相阻塞 |
| `synchronized (this)` / 锁 `FollowService` 或 Mapper 实例 | 退化成全局锁，任何两个用户的冷启动都串行，热点时段一个重建拖住所有人 |
| `Map<Long, Object>` 每用户一把锁 | 语义正确，但锁对象随用户数无界增长，且没有自然的回收时机（用户不再访问后仍需清理） |
| `("follow:load:" + userId).intern()` | intern 池是 JVM 全局共享设施，冲突面最大，且字符串常量池的驻留对象不可控收缩 |
| 不加锁，靠「重建内容一致，重复做也无所谓」 | 忽略 `DEL` 与并发写入的交错，会真的丢关系，见上一节 |

### 遗留与改进点

1. **持锁时间包含一次全量查库**。粉丝量大的用户重建时，同段请求要排队几百毫秒。若将来出现大 V，可把「抢重建权」从 JVM 锁换成 Redis 的 `SET loading:{uid} NX EX 5`：抢不到的不排队，直接走 `listFromDb` 兜底返回，体验更好，也顺带解决多实例问题。
2. **多实例下 JVM 锁失效**。两个进程会各自重建同一 key，上面那个 `DEL` 交错窗口在跨进程时重新出现，需换 Redis 分布式锁（带 token + 续期）或改为启动预热。当前单 jar 部署，用 JVM 段锁是最省的选择，这一点已写进类注释作为约束。
3. **`DEL` + N 次 `ZADD` 非原子**。可以用 pipeline 把 N 次往返压成一次；即便中途失败也不需要额外补偿，靠「标记最后写 + 下次重建先清空」自愈。

## 问题 4 · 动态区加缓存：先按「共享范围」筛，再谈 key 与 TTL

**结论：缓存设计的第一决策不是「缓存什么数据」，而是「这份数据被多少人共享」。共享范围同时决定三件事——命中率的上限、key 的粒度、以及哪些字段必须从缓存里剔除。按这个顺序筛完，可缓存的范围比直觉小得多：广场流与个人主页值得缓存，关注流与动态详情不值得；`liked` 和「作者本人视角」这类随 viewer 变化的字段必须留在缓存之外，否则命中率从「全站」塌成「单人」，或者把第一个访问者的状态发给所有人。**

### 场景

动态区此前完全没有缓存，四条读路径每次直接打库。业务上动态对实时性要求不高——新内容晚一两分钟出现可以接受——是典型的「适合缓存」对象。目标是在不引新中间件、不改接口的前提下把列表页的数据库压力压下去，同时为每个 key 设置「保底时间 + 随机偏移」的过期时间，避免同批写入的 key 在同一刻集中失效。

### 第一步：先量成本，再决定要不要缓存

`MomentService#square` 一页 10 条实际打 5 次 SQL：

| 查询 | 用途 |
|---|---|
| `selectPage` 的 count | 分页总数 |
| `selectPage` 的主表 | 当页动态 |
| `itemMapper.selectBatchIds` | 分享型动态的商品摘要 |
| `likeMapper.selectList` | 点赞数，顺带算出「我是否赞过」 |
| `commentMapper.selectList` | 评论数 |

作者信息已经走 `UserPubCache`，不在本次范围内。5 次查询里，前 2 次是分页框架的固定开销，后 3 次是「批量回填关联」，正是缓存能整段省掉的部分——缓存命中最多少掉 4 次查询，剩 1 次补点赞态（见后文）。

**先数清楚成本，才知道缓存该省哪几次查询。**如果一页只有 1 次查询，加缓存的复杂度就不值得。

### 第二步：两个「失效」不是一回事，对应两种手段

「大量缓存键在同一时刻集中失效」是**缓存雪崩**，「单个热点键失效瞬间并发回源」是**缓存击穿**。这两个问题在这一场景里同时存在，所以两种手段都要上：

1. **雪崩**：列表页是按页写入的，同一批 key 天然在同一刻过期。对策是 TTL 加随机偏移，把过期时刻打散。
2. **击穿**：广场第一页是全站最热的 key，过期瞬间所有并发请求一起回源。随机 TTL 对它无效——单个 key 的 TTL 再随机，过期那一刻依然是所有请求同时发现 miss。对策是互斥重建：只放一个实例回源，其余短暂重读。

只做随机 TTL 不做互斥，第一页每次过期都会在数据库上打出一个尖峰；只做互斥不做随机 TTL，同一批 key 仍会集体过期，只是把并发回源串行化。**两者解决的是不同的问题，不能互相替代。**

### 第三步：用「共享范围」筛出该缓存的对象

判断标准只有一句：这份数据有多少人看到的是同一份？

| 读路径 | 共享范围 | 结论 |
|---|---|---|
| 广场流 | 全站用户共享同一页 | 缓存，收益最高 |
| 个人主页动态 | 按作者共享，粉丝与访客复用 | 缓存前 3 页 |
| 关注流 | per-viewer，几乎不交叉 | **不缓存** |
| 动态详情 | 名义上按动态共享，实际不成立（见下） | **不缓存** |
| 列表第 4 页往后 | 共享，但访问稀疏 | 不缓存 |

关注流被筛掉的直接理由是命中率：key 里必须带 `viewerId`，两个人几乎不会命中同一份，命中率上限就是「同一个人重复刷新」的概率；而 key 的数量随用户数线性增长，等于把 Redis 当成一个更慢、更贵的数据库。它现在已经很快——关注关系读 Redis ZSET，剩下 1 次 `IN` 查询——没有缓存的必要。

**动态详情被筛掉的理由更值得记：它看起来最该缓存，实际上不行。**详情首屏必须按 viewer 判断可见性——作者本人要能看到自己被「敏感词屏蔽(1)」的动态，别人看不到。这个判断依赖 `userId`，意味着每次请求都得先查一次主表拿到 `audit_status` 和作者，这一次主键查询无论如何省不掉。省不掉主键查询，剩下的评论列表就只是「一次 `IN` 查询」，为它再维护一份缓存并处理评论新增失效，收益不足以覆盖复杂度。

这一条是设计阶段没想到的：最初把详情排进了缓存清单，连 TTL 都定好了（300 + [0,180]），写代码时才发现「缓存只装公共视图」这条约束先于 TTL 生效——详情根本没有一个与 viewer 无关的视图可存。

### 第四步：缓存里不能放什么

这一层是「按共享范围筛」的延伸，也是本次最容易埋雷的地方。两个字段必须剔除：

**其一，`liked`。**`MomentVO.liked` 是 per-viewer 的。如果整页 VO 连它一起缓存，这份列表就只能给一个人用——要么按 viewer 分 key（命中率归零），要么把第一个访问者的点赞态发给所有人（假阳性）。做法是缓存里 `liked` 恒为 `false`，命中后按当前用户批量补一次：

```java
private MomentPageVO patchLiked(MomentPageVO vo, long viewerId) {
    if (vo == null || vo.getList() == null || vo.getList().isEmpty() || viewerId <= 0) {
        return vo;
    }
    List<Long> ids = vo.getList().stream().map(MomentVO::getId).toList();
    Set<Long> mine = new HashSet<>();
    for (MomentLike l : likeMapper.selectList(new LambdaQueryWrapper<MomentLike>()
            .in(MomentLike::getMomentId, ids)
            .eq(MomentLike::getUserId, viewerId)
            .eq(MomentLike::getDeleted, 0L))) {
        mine.add(l.getMomentId());
    }
    for (MomentVO m : vo.getList()) {
        m.setLiked(mine.contains(m.getId()));
    }
    return vo;
}
```

一次 `IN` 走覆盖索引，代价远小于省掉的 4 次查询；而如果把它烤进缓存，等于用一次查询的节省换来命中率的崩塌。

**其二，作者本人的视角。**个人主页对「自己」和「别人」返回的内容集合不同：自己要多返回 `audit_status=1` 的屏蔽内容。这个差异同样依赖 viewer。处理方式不是补丁，而是**让本人视角直接绕过缓存**：

```java
public MomentPageVO userMoments(long viewerId, long targetUserId, int pageNum, int pageSize) {
    boolean self = viewerId == targetUserId;
    if (self || !cacheablePage(pageNum)) {
        return loadUserMoments(viewerId, targetUserId, pageNum, pageSize);
    }
    // …命中缓存后 patchLiked
}
```

绕过而不是补丁，是因为「补」需要额外查询出被屏蔽的那几条再插回列表、还得处理分页与总数的偏移，逻辑会变得比重写一份查询更绕；而自己看自己主页是低频操作，直查库的代价可以忽略。

这两个结论合起来给出一条约束：**加载公共视图时必须用一个不存在的 viewer**。若图省事直接传真实 `viewerId` 去加载，第一个访问者的点赞态会被写进共享缓存，之后所有人看到的都是他的状态——而且这种错误不会报错，只在「为什么别人说我赞过」这类反馈里浮现。

```java
/** 加载公共视图时用的假 viewer：liked 恒 false，命中后按当前用户补 */
private static final long ANON_VIEWER = 0L;
```

### 第五步：TTL 取「保底 + 随机偏移」

```java
public static Duration ttl(long baseSeconds, long jitterSeconds) {
    return Duration.ofSeconds(baseSeconds + ThreadLocalRandom.current().nextLong(jitterSeconds + 1));
}
```

用 `ThreadLocalRandom` 而不是 `Math.random()`：后者多线程争同一个 seed，且无法避免在热点线程上产生额外开销。

| 缓存 | 保底 base | 随机 jitter | 实际寿命 |
|---|---|---|---|
| 广场流第 1 页 | 90s | 0–60s | 90–150s |
| 广场流第 2–3 页 | 180s | 0–120s | 180–300s |
| 个人主页第 1 页 | 180s | 0–120s | 180–300s |
| 个人主页第 2–3 页 | 300s | 0–180s | 300–480s |

三条取值原则比数字本身更重要：

- **jitter 不超过 base。**实际寿命最坏是 base 的 2 倍。若 base 90、jitter 给到 600，名义上「1 分半过期」实际可能 11 分钟，一旦有内容需要撤回，残留时间不可控。
- **jitter 不能太小。**只给 5 秒，同批写入的 key 仍挤在 5 秒窗口内过期，等于没打散。经验值是 base 的 50%–100%。
- **不做定时预热。**随机 TTL 只能打散「不同时刻写入」的 key；若有个任务每早把热页全量重刷一遍，它们又被对齐到同一刻过期，等于人为制造雪崩。懒加载（miss 才回源）天然没有这个问题。

### 第六步：把「正确性」和「新鲜度」分开处理

这两件事混在一起，方案会迅速变复杂。分开之后各自只有一句话：

- **正确性（不该出现的内容必须立刻消失）——版本戳主动失效。**举报下架时 `INCR cm:moment:feed:ver`，列表 key 里带这个版本号，全部列表同时逻辑失效。旧 key 不 `SCAN` 删除，交给 TTL 回收。
- **新鲜度（新发的动态多久出现）——靠 TTL。**发布动态**不** INCR：版本戳会让所有列表一起失效，而发布是高频低价值事件，为它制造一次全量回源不划算；「自己发的动态最多 2 分钟后出现在广场」在容忍范围内。作者看自己主页走直查，不受影响，所以本人不会产生「我发了但看不到」的困惑。

```java
/** 广场流某一页，全站共享；ver 变化即整体失效 */
public static String squarePage(long ver, int pageNum, int pageSize) {
    return MODULE + "feed:square:v" + ver + ":p" + pageNum + ":s" + pageSize;
}
```

### 实现：读穿 + 互斥重建

```java
public <T> T getOrLoad(String key, Class<T> type, Duration ttl, Supplier<T> loader) {
    T cached = get(key, type);
    if (cached != null) {
        return cached;
    }
    Boolean locked = tryLock(key);
    if (locked == null) {          // Redis 不可用：直接回源，不在缓存上耗时间
        return loader.get();
    }
    if (locked) {
        try {
            T loaded = loader.get();
            if (loaded != null) {
                put(key, loaded, ttl);
            }
            return loaded;
        } finally {
            unlock(key);
        }
    }
    for (int i = 0; i < WAIT_ROUNDS; i++) {   // 3 次 × 30ms，最长 90ms
        sleepQuietly();
        T retry = get(key, type);
        if (retry != null) {
            return retry;
        }
    }
    return loader.get();           // 仍为空就自己查库，不死等
}
```

三个细节：

1. **锁 TTL 3 秒，不是 30 秒。**它只覆盖一次回源，宁可提前释放导致多一次回源，也不能让锁挂死后所有请求排在数据库上。
2. **没抢到锁不排队死等。**3 次 × 30ms 上限 90ms，超时就直查库。让少量请求穿透，好过让全部请求卡在等锁上——这跟「必须互斥」的取舍相反，因为这里锁保护的是性能而非数据正确性（对比问题 3 的重建 `DEL` 交错）。
3. **`tryLock` 返回三态而不是布尔。**`true` 抢到、`false` 被占、`null` Redis 不可用。用布尔会把「Redis 挂了」和「有人正在重建」混成同一条路径，前者还要白等 90ms 才回源。

```java
/** true 抢到 / false 被别人占着 / null Redis 不可用（三态，null 时调用方直接回源） */
private Boolean tryLock(String key) {
    try {
        return Boolean.TRUE.equals(stringRedisTemplate.opsForValue()
                .setIfAbsent(MomentRedisKeys.rebuildLock(key), "1", LOCK_TTL));
    } catch (Exception e) {
        log.warn("[moment] 重建锁不可用，直查库", e);
        return null;
    }
}
```

版本戳走 `StringRedisTemplate`，对象缓存走 `RedisTemplate<String, Object>`。这不是风格问题：后者的 value 序列化器带 `@class`，`increment` 会把计数器写成 JSON 往返，之后再自增直接报错。

### 否掉的方案

| 方案 | 否掉的原因 |
|---|---|
| 整页 VO 连 `liked` 一起缓存，key 里带 viewerId | 命中率从「全站」塌成「单人」，key 数量 = 用户数 × 页数，Redis 变成更慢的数据库 |
| 关注流也缓存 | per-viewer 不交叉，同样的命中率问题；它本身只剩 1 次 `IN` 查询，收益本就有限 |
| 详情整体缓存 | 首屏必须查主表判断可见性（作者可看屏蔽态），这次主键查询省不掉；剩下的评论列表高频变化，还要额外处理写失效 |
| 列表 key 不带版本戳，只靠 TTL | 下架内容会残留一整个 TTL（最长 8 分钟）。「已下架还能看到」是正确性问题，不能拿新鲜度的容忍度去换 |
| 下架时 `SCAN` 删除所有列表 key | 要把整个 keyspace 走一遍、每批一次往返，为一个低频事件做全库遍历不值；而且遍历期间新旧写入并存，删不干净 |
| 缓存空页做 null 哨兵防穿透 | 列表空页是 `count=0` 的廉价查询，没有穿透面；真正会被随机 id 打的是详情，而它对不存在的 id 直接抛 4022，不产生缓存，也就没有穿透面 |
| 定时任务批量预热热页 | 会把随机 TTL 打散的 key 重新对齐到同一刻过期，抵消雪崩防护，属于帮倒忙 |
| 缓存更新的方式是「写过之后回写缓存」 | 并发写时后到的旧值可能覆盖先到的新值；本项目一律用失效（`INCR`），不用回写 |

### 验证

验证用的是「改数据看返回」而不是数 SQL 条数：项目日志开了 DEBUG，但 appender 异步刷盘，按行号切区间统计会把上一次请求的 SQL 算到下一次里（第一次统计就撞上了，得出「第 4 页也没查库」的假结论）。行为验证没有这个误差。

| 场景 | 结果 |
|---|---|
| 发布新动态后立即看广场第一页 | 仍 6 条、不含新动态——缓存未失效，符合「发布不主动失效」 |
| 同一时刻作者看自己主页 | 新动态立刻可见——本人视角直查，不受缓存影响 |
| `INCR cm:moment:feed:ver` 后再看广场 | 7 条、含新动态——版本戳整体失效生效 |
| 3001 点赞后，3001 与 3002 分别看广场 | `liked=true` / `liked=false`——点赞态没被烤进共享缓存 |
| 连续 3 次删 key 触发重建 | TTL 分别是 149 / 139 / 92 秒，都落在 90–150 且互不相同 |
| 个人主页（非本人） | key 生成，TTL 246 秒，落在 180–300 |
| 本人访问自己主页 | 缓存 TTL 从 245 自然递减到 242——没被重写，确认走的是直查 |
| 举报成立 → 下架 | 版本戳 1→2，广场立刻 6 条不含目标，详情返回 4022 |

### 一个实现时才暴露的问题：`likeCount` 也在滞后

第一轮验证点赞时就看到了：3001 点完赞，`liked` 正确变成 `true`，但 `likeCount` 还是 1（缓存里的旧值）。`patchLiked` 只补了「我是否赞过」，没有也不该去重算计数——重算就要把整页的点赞数重新聚合一遍，等于把缓存省下的那次 `IN` 查询又加回来。

判断它可以接受，依据在前端：`toggleLike` 是乐观更新，本地先把 `liked` 和 `likeCount` 一起改掉，失败再回滚（`MomentsView.vue`、`MomentDetailView.vue`、小程序 `moments/index.vue` 三处一致）。也就是说**操作者本人看不到这个滞后**，只有别人在 TTL 内刷新时会看到旧计数——点赞数晚一两分钟更新，属于可接受范围。

这条也说明了缓存设计的一个前提：**写后立刻要反馈的地方，要靠前端乐观更新兜住，而不是指望缓存实时。**如果前端是「点完重新拉列表」，这个滞后就会变成显眼的 bug。

### 遗留与改进点

1. **详情与评论区仍直查库。**若将来详情页成为热点（比如分享出去的动态被大量访问），可单独缓存评论第一页（TTL 60+[0,30]），写评论与下架时精确 `DELETE`。
2. **发布后最长 90–150 秒才进广场。**这是「不为高频低价值事件全量回源」的主动取舍，已写进 `MomentService` 类注释。要更快，只能在发布时删第一页——但 key 里有 `pageSize` 维度和版本戳，删不干净，收益不抵麻烦。
3. **版本戳是全局的。**一次下架会让**所有**作者主页的列表缓存一起失效，而不是只失效相关作者。下架是低频事件（举报成立才触发），这样换来的实现简单度是划算的；若将来下架变频繁，要按作者维度拆分版本戳。
4. **Redis 需要 `maxmemory` + `allkeys-lru` 兜底。**个人主页 key 随「被访问过的作者数」增长，单页 VO 约 6–10KB，日均 2000 个主页约 20–60MB。没有上限策略时，动态缓存可能把字典、分布式锁这类必须命中的 key 挤出去。
5. **锁没有持有者校验。**极端情况下 A 的锁过期后 B 抢到、A 再 `delete` 会误删 B 的锁，后果是多一次回源，不会写错数据，因此没有引入 token + Lua 的释放脚本。
