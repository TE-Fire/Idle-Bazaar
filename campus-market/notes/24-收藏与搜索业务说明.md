# 收藏与搜索业务说明（学生端商品域）

> 两个功能都不改动商品主流程，但都直接落在 `item` 表和商品列表接口上：收藏要给详情页一个「已收藏」状态、要给列表一个收藏入口；搜索要给首页一个落点页面。它们的共同约束是**不新增商品状态**——收藏不改 `item.status`，搜索只读不写。

## 一、收藏

收藏是「用户—商品」的一段关系，不是商品的一种状态。这与「我想要 / 下单」有本质区别：收藏不动 `item.status`，也不影响任何人的可买性，所以它可以发生在商品生命周期的任何阶段——在售能收，已售出也能收（用户会去收藏一件已经卖掉的东西，等着卖家再出同款）。已售出的商品在收藏列表里置灰并提示「已售出」，但记录保留。

**接口**

| 方法 | 路径 | 鉴权 | 作用 |
|---|---|---|---|
| POST | `/api/item/{id}/favorite` | 登录 | 收藏，幂等 |
| DELETE | `/api/item/{id}/favorite` | 登录 | 取消，幂等 |
| GET | `/api/item/favorites` | 登录 | 我的收藏，分页 |

**规则**

1. **同一用户对同一商品恒为一行**。`favorite` 走 B 类软删：取消时把 `deleted` 写成时间戳，重新收藏时把**同一行**的 `deleted` 置回 0，`create_time` 不更新。这张表的唯一索引是 `(user_id, item_id, deleted)`，如果取消时写常量 1，重新收藏就会和那条「已删除」的行撞唯一索引而插不进去——这是 B 类必须写时间戳的直接原因（db/01 第一节）。
2. **`item.fav_count` 与收藏行同事务增减**。计数用 SQL 自减而不是「先查再写」：`UPDATE item SET fav_count = GREATEST(fav_count - 1, 0) WHERE id = ?`。`GREATEST` 是给历史脏数据兜底，计数只用于展示，真值永远以 `favorite` 表的行数为准，对不上时以行数重算、不回写。
3. **重复收藏、重复取消都返回成功**。按唯一键先查：已收藏还点收藏，直接返回成功且不再加计数；未收藏点取消同理。前端连点两次不该弹错误。
4. **详情页的「已收藏」不额外发请求**。`/api/item/{id}` 在登录态下顺带查一次是否存在有效收藏行，把 `favorited` 放进返回体；未登录固定 `false`。这样详情页首屏只有一次请求。
5. **收藏列表按收藏时间倒序**，返回商品卡片需要的字段（标题、价格、成色、主图、状态）+ 收藏时间。已软删的商品不返回（不是置灰，是列表里不出现——商品没了，收藏指向不存在的东西）。

**边界**

- 不限制「收藏自己的商品」。技术上无成本，产品上也没有害处（闲鱼允许），加一条判断反而要多解释一句。
- 不做「收藏数超过 N 提醒卖家」「收藏降价通知」这类衍生能力，收藏在本期就是纯收藏。
- 收藏列表不返回商品描述与图集，只返回主图——列表页不需要，避免为了几张图多查一次。

## 二、关键词搜索

搜索复用现有的商品列表接口，没有独立接口。`/api/item/list` 的 `keyword` 参数同时匹配标题与描述，与其他筛选条件（分类、成色、校区、价格区间）叠加，排序仍按发布时间倒序。**实现是 `LIKE '%keyword%'`，不是 `MATCH ... AGAINST`**：`item` 上虽然有 `ft_search(title, description) WITH PARSER ngram` 全文索引，但 ngram 对两字短词（「教材」「耳机」）的相关性打分很弱，反而不如 LIKE 的结果稳定；万级数据量下 LIKE 的全表扫描也在毫秒级，所以索引留着没有启用，判断写在 `ItemService` 的注释里。

搜索页缺的只是前端落点：移动端 M7 和 Web 端 P5 一直没建，首页搜索框点了之后要么没反应、要么只按分类跳转。

**页面规格**

移动端 `pages/search/index`：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 搜索栏 | 自动聚焦，右侧「取消」返回上一页 | — |
| 历史 | 最近 10 条，点词即搜；单条可删、可整体清空 | `uni.getStorageSync('searchHistory')`，纯本地 |
| 热门 | 8 个一级分类名，点即跳分类页并选中该分类 | `/api/dict/all` 的 `categories` |
| 结果 | 双列商品卡，下拉刷新 + 上拉加载 | `/api/item/list?keyword=` |

热门区点一下是**按分类进分类页浏览**（`pendingCategoryId` 意图 + `reLaunch`），不是把这个分类名当关键词再搜一遍：分类名（「教材教辅」）几乎不会出现在标题里，当关键词用只会搜出空列表。

Web 端 `/search?q=`：与 `/list` 共用结果卡与筛选条，搜索框保留关键词可二次修改，输入为空时把焦点留在搜索框而不跳页。关键词同样交服务端 LIKE——早期版本是「服务端拉 50 条再前端 `includes` 过滤」，第 51 件之后的命中会被漏掉，两端口径也不一致，已改掉。

**规则**

1. 关键词去首尾空格，长度上限 50，超长截断而不报错（用户粘贴长句是常态）。前端截断后服务端 `ItemService#cut` 再兜一刀，防止绕过前端发超长 LIKE。
2. 空词不进入结果态，留在搜索页。
3. 历史词重复出现时提到最前，不产生第二条。
4. 命中 0 条给空态 + 「看看其他在售」按钮，回首页而不是留在死页面。
5. **不做「热搜」接口**。真实热搜要么建 `search_history` 表统计词频、要么对标题分词，两条路都要额外写数据管道；本期热门区直接展示分类，页面文案写「热门分类」而不是「热搜」——不许把分类伪装成热搜词。

## 三、接口一览

| 模块 | 方法与路径 | 鉴权 | 说明 |
|---|---|---|---|
| 收藏 | `POST /api/item/{id}/favorite` | 登录 | 收藏，重复调用幂等 |
| 收藏 | `DELETE /api/item/{id}/favorite` | 登录 | 取消，重复调用幂等 |
| 收藏 | `GET /api/item/favorites?pageNum=&pageSize=` | 登录 | 我的收藏，时间倒序 |
| 搜索 | `GET /api/item/list?keyword=&...` | 免登录 | 复用既有列表接口 |

## 四、错误码

| 码 | 常量 | 文案 | 触发 |
|---|---|---|---|
| 1111 | `FAVORITE_ITEM_NOT_FOUND` | 商品不存在或已下架 | 收藏时商品已软删 |

只新增这一个码。不单独给「不允许收藏自己的商品」留码，因为这条限制本身不做。

## 五、验收口径

- 商品详情页点收藏 → 图标变实心，`favorite` 表多一行，`item.fav_count` +1；再点一次 → 变空心，行 `deleted` 有值，`fav_count` −1。
- 收藏处于取消状态时再次收藏 → `favorite` 表**行数不变**（仍是那一行，`deleted` 回到 0），`create_time` 未变。
- 收藏列表里已售出的商品带「已售出」标记，点击进详情能看到商品（不是 404）。
- 移动端搜索页输入「教材」→ 结果与 Web 端 `/list?keyword=教材` 一致；清空关键词 → 回到搜索页而不是空列表。
- 搜索历史杀掉小程序重进仍在（本地存储），清空后不再出现。
