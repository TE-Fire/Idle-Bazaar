# 22 - 社交模块（关注·动态·评论·海报）业务说明

> 格式遵循 notes/14 业务笔记标准模板。状态机、权限、接口口径如有冲突，以 business/03 与管理端为权威。数据模型字段以 db/01 §5.8 为唯一来源（DDL 已落库，见 schema.sql 十）。

## 一、模块定位

社交模块在「交易 + 审核」核心之上叠加**用户关系与内容互动层**，把一次性交易沉淀为持续互动，提升复购与留存。模块边界有三条：只新增四类能力——关注/粉丝、用户动态、商品评论、一键分享海报；不改变商品、订单、审核的既有逻辑；动态与评论的合规靠「敏感词过滤 + 举报后人工」而非预审队列，把审核资源留给商品；海报是纯前端合成，后端零改动。

与谁共用动作：作者昵称展示走 `UserPubCache`（与商品列表/详情共用，昵称改后已随写失效）；敏感词复用 `sys_sensitive_word`（与商品描述同一条过滤路径）；举报复用 `report`（`target_type` 已扩到 1 商品 / 2 用户 / 3 动态 / 4 商品评论 / 5 动态评论，社交三类走独立处置通道）；通知复用 `msg_message`（批次 3）；管理端审核复用 `review.*` 四个既有权限点。

## 三、业务条目

### S1 · 关注 / 取关

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/social/follow` | 登录 | 关注（body: followeeId） |
| POST | `/api/social/unfollow` | 登录 | 取关（body: followeeId） |
| GET | `/api/social/follow/check?followeeId=` | 登录 | 是否已关注（按钮态） |

**前置**

- 已登录，未登录返回 未登录(1001)；
- `followeeId` 必填且指向存在的用户，且不等于自己 → 否则 参数错误(1000)；
- 关注目标不能是自己（前端无入口，接口兜底）。

**规则**

1. 关注：
   1. 若 `user_follow` 已存在 `(follower, followee, deleted=0)` 的活跃行 → 已是关注中，幂等返回成功，不改数据；
   2. 否则按 B 类重建：先 `UPDATE ... SET deleted=0 WHERE follower_id=? AND followee_id=? AND deleted>0`，影响行数 0 → `INSERT` 新行（雪花 id，`deleted=0`）；
   3. 并发首关两请求同时走 INSERT → 后到者撞 `uk(follower_id, followee_id, deleted)` → 捕获重复键，视为成功（同一关系恒一行）。
2. 取关：
   1. 存在活跃行 → `UPDATE ... SET deleted=<毫秒时间戳> WHERE follower_id=? AND followee_id=? AND deleted=0`；
   2. 无活跃行 → 幂等返回成功（已取关）。
3. 关注/取关不写通知（通知在批次 3 接通 `msg_message`）。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `user_follow` | 关注：`deleted=0` 或新建；取关：`deleted` 置毫秒时间戳 |

### S2 · 关注列表 / 粉丝列表

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/social/profile?userId=` | 登录 | 用户公开主页聚合：资料 + 关注/粉丝/在售数 + 查看者关注态（`userId` 空 = 看自己） |
| GET | `/api/social/follow/list?type=following\|fans&userId=&pageNum=&pageSize=` | 登录 | 关注 / 粉丝分页列表 |

**前置**

- `profile`：`userId` 指向的用户须存在，否则 参数错误(1000)；资料取 `app_user` 公开四字段（昵称 / 头像 / 信用分 / 认证态），计数复用 FollowService 的 ZSET 读路径；在售数实时 `COUNT`；
- 看自己需登录；看他人主页粉丝/关注为公开（本期入口均在登录态内）；
- `type` 仅允许 `following` / `fans`，其他值 → 参数错误(1000)；
- `userId` 可空（空 = 看自己），传值时该用户须存在，否则 参数错误(1000)；`pageSize` 上限 50。

**规则**

1. `type=following`：查 `follower_id=目标用户 AND deleted=0`，按 `create_time` 倒序分页（走 `idx_follower`）；
2. `type=fans`：查 `followee_id=目标用户 AND deleted=0`，按 `create_time` 倒序分页（走 `idx_followee`）；
3. 读优先走 Redis 两个 ZSET（`cm:follow:following/followers:{uid}`），集合未加载时先按库重建；Redis 不可用退回查库，结果一致；
4. 每条带目标用户公开信息（昵称 / 头像 / 信用分 / 认证态，走 `UserPubCache`）与「当前查看者是否已关注」（粉丝列表的「回关」按钮态）；
5. 响应除 `list` 外回带 `followingCount` / `fansCount`（目标用户的两项计数），个人主页顶部直接取用，不再单发统计请求；计数取 `ZCARD`，与列表同源。

**状态与数据变化**：无。

### S3 · 发布动态

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/moment/publish` | 登录 | 发动态（type 1 状态 / 2 分享商品） |

**前置**

- 已登录；
- `type` 必填且 ∈ {状态(1), 分享商品(2)}，否则 参数错误(1000)；
- `type=分享商品(2)` 必须带合法 `itemId`，否则 参数错误(1000)。

**规则**

1. 内容过滤：入参 `content` 经 `sys_sensitive_word` 过滤——
   1. 命中高危词（level=1）→ 直接拒绝，不入库；
   2. 命中低危词（level=2）→ 替换并打标后继续（打标不落库，仅服务层标记）；
   3. `type=状态(1)` 且 `content` 为空、无图 → 参数错误(1000)（动态不能全空）。
2. `type=分享商品(2)`：校验 `itemId` 对应 `item` 存在且在售(3)；不存在或非在售 → 参数错误(1000)。
3. `images` 为 URL 数组，长度 ≤ 9，超出 → 参数错误(1000)；空数组允许。
4. 通过 → `INSERT` `user_moment`：`audit_status=正常(0)`（发布即公开），`type` 按请求，`item_id` 仅分享态填充。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `user_moment` | 新增一行，`audit_status=正常(0)` |

### S4 · 动态列表（广场 / 个人主页）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/api/moment/square?page=` | 免登录 | 全广场时间流（未登录 `liked` 恒 false） |
| GET | `/api/moment/following?page=` | 登录 | 关注流（只看已关注作者） |
| GET | `/api/moment/user/:userId?page=` | 登录 | 个人主页动态 |
| GET | `/api/moment/:id` | 登录 | 动态详情（含点赞数 + 评论列表） |

**前置**：广场 `square` 免登录（未登录传匿名视角 `ANON_VIEWER=0`，只影响 `liked` 恒 false，其余字段一致）；关注流、个人主页、详情需登录。

**规则**

1. 广场流 `square`：查 `deleted=0 AND audit_status=正常(0)`，按 `create_time` 倒序分页（走 `idx_square`）；`audit_status≠正常(0)` 的内容不出现在广场（敏感词屏蔽/举报下架均不可见）。**未登录可看**——广场是引流页，拦登录等于把人挡在门外；点赞/发布/评论再引导登录（`liked` 由 `patchLiked` 按当前用户回填，匿名视角整段跳过）。
2. 关注流 `following`：取我关注的人（最近关注的优先，最多 300 个）再按 `user_id IN (...)` 查正常动态。**关注关系读 Redis 而不是查库**——关注/取关先在 Redis 生效、每 5 秒才批量落库，读库会让刚关注的人在流里消失一个刷库周期。关注为空直接返回空页，不回落广场（回落会让「关注」这个 tab 名不副实）。
3. 个人主页 `user/:userId`：查 `user_id=:userId AND deleted=0`，按 `create_time` 倒序；**看自己时纳入 `敏感词屏蔽(1)`**（自己发的内容自己看不见会以为发布失败），看别人只出 `正常(0)`；`举报下架(2)` 对任何人都不出，包括作者——下架是平台结论，不是待处理的草稿。
4. 详情 `:id`：返回动态正文 + 作者公开信息 + 点赞数（实时 COUNT）+ 评论列表（走 S6 列表口径，`deleted=0` 且 `audit_status=正常(0)`）；作者本人可打开自己被 `敏感词屏蔽(1)` 的动态，其他人 4022。
5. 前端默认落在广场流：新用户没有关注关系，先落关注流会是一片空白；关注流空态给「去广场」的引导。**未登录也能翻广场**，只有点「关注」、点赞、发动态才跳登录页（带 `redirect=/pages/moments/index`，登录后回落广场；未登录时 `onShow` 强制把 scope 退回广场）。

**状态与数据变化**：无。

|---|---|---|---|

3. 点赞数展示实时 `COUNT(*)`（走 `idx_moment`）。

**状态与数据变化**

### S8 · 一键分享海报

**接口**：无对外接口——纯前端 `canvas` 合成，后端零改动。

**前置**：已登录（入口在登录态内）。

**规则**

1. 取商品主图 + 标题 + 价格（来自商品详情响应）+ 平台水印，前端 `canvas` 绘制为图片；
2. 底栏带**二维码回链**，扫开即落到该商品详情：Web 端指向 `/item/:id`（history 路由），H5 端指向 `/#/pages/item/detail?id=`；码是纯前端点阵绘制（`@campus/shared` 的 `encodeQr` / `drawQr`，纠错级别 M），不需要后端签小程序码；
3. 画布被跨域主图污染导致导出失败时，去掉主图重画一次，**二维码照旧**——否则海报既没图又没入口；
4. 生成后调系统分享 / `onShareAppMessage`，保存到相册由系统能力完成。

**状态与数据变化**：无。

**版面口径**（踩过）：底栏高度、二维码边长写死为常量（Web `BAR_H=240 / QR_BOX=168`、小程序 `BAR_H=115 / QR_BOX=84`），正文自底栏**反推**基线（元信息 → 价格 → 标题），不再从上往下累加——累加写法在底栏位置上移后会让分隔线穿过价格、品牌文案压住元信息。画布比例相应改为 750×1100（小程序 375×560，导出 750×1120）。

### S9 · 举报

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| POST | `/api/report` | 登录 | 提交举报（body：`targetType` / `targetId` / `reason` / `evidence`） |

**前置**

- 已登录；
- `targetType` ∈ {商品(1), 用户(2), 动态(3), 商品评论(4), 动态评论(5)}，其他值 → 参数错误(1000)；
- `targetId` 指向的对象须存在且未被删除：商品 → 商品不存在(1003)、动态 → 动态不存在(4022)、两类评论 → 资源不存在(1003)、用户 → 资源不存在(1003)；
- 不得举报自己：商品的卖家、动态/评论的作者等于举报人 → 不能举报自己(3006)；
- `reason` 非空且 ≤255 字；`evidence` 是已上传的凭证地址，最多 3 张。

**规则**

1. 目标校验按 `targetType` 分派到各自的表，社交三类额外要求 `deleted=0`——已删除的内容没有处置对象；
2. 去重的口径是「同一人对同一对象的**未结案**单据」：`reporter_id + target_type + target_id` 且 `status ∈ {待受理(1), 处理中(2)}` 已存在 → 重复举报(3005)。已结案的可以再举报一次，不必为「上次判不成立、这次又犯」另开口子；
3. 通过 → `INSERT report`：`status=待受理(1)`、`result` 留空；`evidence` 存 JSON 数组，后端不做结构解析（审核员只需要看图）；
4. 社交三类**不生成审核队列任务**。队列的权重按商品举报次数累加、SLA 按审核单统计，混入动态与评论会把排序规则弄脏，改由 S10 的社交举报通道单独处置。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `report` | 新增一行，`status=待受理(1)`、`result` 空 |

### S10 · 管理端处置

两条通道：商品侧的审核队列（notes/09 有过完整口径，这里只列与本模块相关的端点）和社交举报的独立通道。

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/review/queue?kind=` | `review.view` | 审核队列：商品审核 / 举报 / 申诉三来源合并，不分页；`kind` 可过滤 item / report / appeal |
| POST | `/admin/review/item/{auditId}/pass` | `review.judge` | 商品审核通过 → 在售 |
| POST | `/admin/review/item/{auditId}/reject` | `review.judge` | 商品审核驳回（body：`reason` / `note`） |
| POST | `/admin/review/item/{auditId}/force-offline` | `review.forceoff` | 商品强制下架（body：`reason` / `note`），终态 |
| POST | `/admin/review/report/{reportId}/handle` | `review.judge` | 商品举报裁决（body：`result` / `reason` / `note`） |
| POST | `/admin/review/appeal/{appealId}/judge` | `review.appeal` | 申诉复审（`result`：2 维持 / 3 撤销） |
| GET | `/admin/social/report/list?status=&targetType=&pageNum=&pageSize=` | `review.view` | 社交举报列表，只出动态与两类评论 |
| POST | `/admin/social/report/{reportId}/handle` | `review.judge` | 社交举报裁决（body 同商品举报） |

**前置**

- 管理员已登录且持有对应权限点：只读角色只有 `review.view`，进得来、动不了；越权由拦截器在进入方法前拒（1002），不落操作日志；
- 社交举报列表：`targetType` 传值时必须 ∈ {3,4,5}，否则 1000「只能查社交三类」；`status` 可选；`pageSize` 封顶 50；
- 裁决类接口：`result` 必填且 ∈ {成立(1), 不成立(2)}，其他值 → 1000。

**规则**

1. 社交举报列表查 `deleted=0` 的单据，按提交时间倒序；举报人、被举报内容摘要（≤60 字）、内容作者三样**一次批量组装**，不逐条打库——列表页一屏 20 条，逐条打库就是 60 次往返；
2. 裁决 `result=成立(1)` 的连锁动作：内容 `audit_status` 置 `举报下架(2)` → 广场流、关注流、评论列表立刻不再返回；推一条 `msg_message`（`zone=2`、`sender_id=0`、`type=4`）告知作者；作者信用分 `REPORTED(-10)` 并写 `credit_log` 流水；
3. `result=不成立(2)`：内容不动，只把单据结掉；
4. 成立时 `reason`（处置依据）必填，不成立可不填；`note` 会拼进通知文案，空则回落到 `reason`；
5. 结单据用**条件更新**（`status IN (待受理, 处理中)` 才允许改成已处理），并发双击只有一个能成功，另一个拿 3001——先查后改挡不住同时点两下；
6. 已结案的单据再裁决 → 已处理(3001)；单据不是社交类型 → 1000「请到审核队列处置」，避免从错误入口改了商品举报的状态却不动商品；
7. 内容在裁决前已被作者删除 → 单据照常结案，只是没有下架对象、不推通知、不扣分。举报人提交时内容还在，处置时没了，不能因此把单据卡住。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `report` | `status → 已处理(3)`、`result`、`handler_id`、`handle_time`、`handle_note`；仅当原状态 ∈ {1,2} |
| `user_moment` / `item_comment` / `moment_comment` | 成立时 `audit_status=举报下架(2)` |
| `app_user` + `credit_log` | 成立时信用分 −10，留 `REPORTED` 流水 |
| `msg_message` | 成立时给作者一条 `type=4` 系统处置通知 |

### S11 · 敏感词库维护

给词库开增删改，是因为它是发帖与两处评论的唯一内容闸门，而此前只能改库——运维绕不开 SQL，改完还得记得手工 `INCR` 版本号，漏一步就得多等 5 分钟。

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/sensitive/list?level=&status=&pageNum=&pageSize=` | `settings.edit` | 词库分页，按创建时间倒序；`pageSize` 封顶 100 |
| POST | `/admin/sensitive` | `settings.edit` | 新增（body：`word` / `level`），同词重复 4026 |
| PUT | `/admin/sensitive/{id}` | `settings.edit` | 改词面与级别，同词重复 4026 |
| POST | `/admin/sensitive/{id}/status` | `settings.edit` | 启停（body：`enabled`） |
| DELETE | `/admin/sensitive/{id}` | `settings.edit` | 软删，同词可再建 |

**前置**

- 整组只挂 `settings.edit`：一个词同时影响商品描述、动态与两类评论，与字典维护同一收口理由——改的是「什么内容能发出去」，写权限必须收口；
- `level` 只能是 1 高危 / 2 低危，其他值 1000；不传按 2 低危（误设高危会直接拦掉发布，代价比漏拦一句重）；
- 目标行不存在或已删 → 4027；新增或改名撞上**未删行** → 4026，停用词也算重名。

**规则**

1. 写操作成功后统一调 `SensitiveWordService#refresh()` 自增 `cm:sensitive:ver`，各实例 3 秒内惰性重载。管理端不直接改内存或缓存——一致性只走版本戳这一条路，多开一条就多一种失效顺序要守；
2. **写方法不包事务**：单表一行写完即提交，再自增版本戳。若包进事务，版本戳会在数据可见之前自增，其它实例按新版本重载却读到旧词库，而版本号不再变化，这份旧数据会一直用到本地 TTL 过期（5 分钟）；
3. 删除是 B 类软删，`deleted` 置当前毫秒而非 0/1——唯一索引 `(word, deleted)` 靠它允许同词重建，置 0 会让该词再也建不回来，置时间戳则历史行留在表里可追溯；
4. 停用词不进内存快照，等于立刻从过滤中摘掉；把停用词重新启用比再建一条干净，所以重名判断把停用词也算进去；
5. 五个写接口全挂 `@OpLog`（`module=system`）：词库改动直接决定「什么内容能发出去」，事后要能回答「这条高危词是谁、什么时候加的」。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `sys_sensitive_word` | 增行 / 改 `word`·`level` / 改 `status` / `deleted` 置时间戳 |
| `cm:sensitive:ver` | 每次写后 `INCR`，驱动各实例重载 |
| `sys_operation_log` | 五类动作各留一条，`module=system` |

### S12 · 平台公告发布 / 撤回

学生端的通知页一直能看，但**没有任何端点能写进去**：`msg_message` 里 `zone=2`、`sender_id=0` 的行只能靠手工插库造出来。举报处置与互动通知确实会写这张表，但那是"某个事件的副产品"，不是"平台要对外说一句话"。这一条补的是后者。

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/notice/list?pageNum=&pageSize=` | `content.edit` | 已发布公告（按批次聚合，一条公告一行） |
| POST | `/admin/notice` | `content.edit` | 发布，`title` / `content` / `campusId`（空=全员） |
| DELETE | `/admin/notice/{batchId}` | `content.edit` | 撤回，按批次软删 |

**规则**

1. **按接收人逐行写**。`msg_message` 的读模型是「按 `receiver_id` 取我的消息」，不是「取所有广播再判断我看不看」，所以一条公告发 N 个人就写 N 行，共享一个 `batch_id`。代价是写放大：全校 5000 人就是 5000 行。这一取舍在万级用户下撑不住，届时应改成「公告表 + 已读表」的拉模型，但那是重构读接口的事，不在本期。
2. **`batch_id` 是撤回的依据**。没有它，"撤回这条公告"就退化成按 `content` 模糊删，删错是必然的。`batch_id` 用雪花 id，一条公告一个。
3. **`type=6`，与处置通知（4）、互动通知（5）分开**。类型混在一起的后果是通知页没法用标签区分「平台公告」和「你的动态被下架了」，而这两类文案语气完全不同。
4. 接收人范围：`campusId` 为空表示全员；填了则只发给该校区用户。封禁账号（`status=2`）不发——发了也读不到，只是徒增未读数。
5. 发布前过敏感词服务，高危词直接拒（4024）。公告是平台自己说的话，更不能带违规内容。
6. 写入分批，每批 500 行，避免一次 `INSERT` 拼出超长 SQL。单次发送人数上限 5000，超了直接拒——这是防止误触"全员公告"的闸门，不是性能优化。
7. 撤回只是软删收件行，不改发件记录：管理端的公告列表读的是这批行的聚合（`GROUP BY batch_id`），软删后仍能看到「已撤回」状态，而不是从列表里凭空消失。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `msg_message` | 每个接收人一行：`zone=2`、`sender_id=0`、`type=6`、`batch_id` 同批、`extra={"title":...,"campusId":...}` |
| `sys_operation_log` | 发布 / 撤回各留一条，`module=system` |

## 四、通用业务规则

**审核三态**（`user_moment.audit_status` / `moment_comment.audit_status` / `item_comment.audit_status`）：`正常(0)` / `敏感词屏蔽(1)` / `举报下架(2)`。发布即 `正常(0)`，不做预审；命中高危敏感词在发布接口直接拒绝（不入库），低危词替换后入库并标 `正常(0)`（打标不落库）；`举报下架(2)` 由批次 3 接入 `report` 后人工置位。广场流、关注流、评论列表只取 `正常(0)`。

`敏感词屏蔽(1)` 目前**没有自动写入口**：低危词在入库前已替换成等长 `*`，内容本身不再命中，于是没有「需要屏蔽」的中间态。这一态留给后续的高危词复审或人工置位，可见性规则（仅作者可见、详情对作者放行）已按最终口径实现，不随写入方式变化。

**三态由枚举统一持有**：三张表的 `audit_status` 归 `ContentAuditStatusEnum`（`正常(0)` / `屏蔽(1)` / `下架(2)`），Service 里不再各写一份 `private static final int AUDIT_*`。此前三个类各声明自己用得到的值——`MomentService` 只有 0 和 1、`ItemCommentService` 只有 0、`SocialReportAdminService` 只有 2——没有任何一处持有完整的三态，改值时只能靠注释对齐。**不要和 `AuditStatusEnum` 混用**：那是商品审核**单据**状态（`1 待审 / 2 已通过 / 3 驳回 / 4 强制下架`），两边都有「2」但含义相反，借用一次就是「被举报的动态变成正常可见」，编译器不会拦。

**敏感词库热更新**：词库整表载入内存（过滤在发布/评论热路径上，逐次查库不划算），多实例各持一份副本。改词后调用 `SensitiveWordService#refresh()` 自增 `cm:sensitive:ver`，各实例最多 3 秒后重载，本实例立即重载；Redis 不可用时退回本地 5 分钟 TTL，过滤本身不中断——缓存刷新失败不该让发布接口报错。核对间隔取 3 秒而不是每个请求都读一次 Redis：写路径 QPS 低，但 Redis 抖动时不能把它放大成每次请求一次超时等待。

**管理端改词入口**：`/admin/sensitive/*` 五个端点（S11）。改词、启停、删除都在写成功后调 `refresh()`，改完 3 秒内全端生效，不必重启、也不必再手工 `INCR`。管理端只改库、不碰内存快照——一致性由版本戳统一负责。

**删除两类**：`user_follow` / `moment_like` 为 B 类软删（复用行，`deleted` 时间戳，唯一键带 `deleted` 置尾）；`user_moment` / `moment_comment` / `item_comment` 为 A 类留墓碑（`INSERT` 新行）。重建语义遵循 db/01「删除的两类实现」。

**计数口径**：关注数、粉丝数、点赞数、评论数均实时 `COUNT(*)` 走索引；量级小不冗余列，压力大再给 `app_user` 加 `follow_count` / `fans_count`。

**评论开放条件**：仅 `item.status=在售(3)` 可发商品评论；商品评论不限买家（登录用户均可），与购后 `user_review`（一单一评）并存不冲突。`reply_to` 存目标用户 id（扁平列表，只 @人、不定位父楼）。

**权限**：四功能均为纯用户端能力，**不新增管理端权限点**；社交内容审核复用 `review.view` + `report`（`target_type` 扩 3 动态 / 4 评论，批次 3）。

**通知**：复用 `msg_message` 的 `zone=2` 分区，`sender_id=0` 表示平台发出，靠 `type` 分两类——`4` 系统处置（下架/裁决结果）、`5` 互动（被赞 / 被评 / 被关注）。同一事件去重走 Redis（点赞 24 小时、评论 30 分钟、关注 7 天），去重失败按首次处理：重复通知只是打扰，漏通知是信息丢失。推送内部吞异常，处置成功不因一条消息回滚。

**信用分**：`credit_log` 流水 + `app_user.credit_score`，初始 100 / 上限 120 / 下限 0，分值集中写死在 `CreditReasonEnum`。读分用行锁（`SELECT ... FOR UPDATE`）而非先读后写——管理端会有多人同时处置同一作者。当前接线：商品举报成立 `REPORTED(-10)`、社交举报成立 `REPORTED(-10)`、商品举报被申诉撤销 `REPORT_REVOKED(+10)`；`TRADE_DONE` / `BREACH_CANCEL` / `FORCE_OFF` / `BAN` 只登记了口径，未接业务（举报成立内部已强制下架，再接 `FORCE_OFF` 会双计）。写后失效 `cm:user:pub:{id}`，公开主页与商品卡上的分即时更新。

**feed 与海报**：动态信息流有广场（全站）与关注（仅关注作者）两条；海报纯前端合成、底栏带扫码回链。

## 五、验收口径与已知缺口

验收：关注后对方粉丝 +1、按钮态切换；取关后粉丝 −1；商品在售可评论、下架后接口拒；动态发布后广场即时可见（全广场流）；关注流取关后立刻为空、重新关注立刻出现；敏感词高危词发布被拒、低危词被替换；管理端改词/启停/删除后 3 秒内全端生效（不重启，也不必再手工 `INCR`）；点赞/取消幂等、计数实时；海报生成为本地图片可保存、扫码落到商品详情；被赞/被评/被关注各推一条通知且同一事件不重复；举报成立后作者信用分 −10 并留流水，重复裁决不二次扣分；自己被 `敏感词屏蔽(1)` 的动态只有自己看得到；社交举报与商品举报分别落在两条处置通道，只读角色能进列表但调不动裁决（1002）。

已知缺口（二期已清零，剩余为口径保留项，不影响主链路）：

- **`敏感词屏蔽(1)` 无自动写入口**：低危词入库前已替换，内容不会命中，该态留给后续人工置位/复审，可见性规则已按终态实现。
- **`credit_log` 另外四种原因未接业务**：`TRADE_DONE` / `BREACH_CANCEL` / `FORCE_OFF` / `BAN` 只在枚举里登记了口径，等交易闭环与封禁能力落地再接。
- **关注流上限 300 个关注对象**：`IN` 列表不设口子会打爆 SQL；超出部分只影响「最近 300 个关注」之外的老关注，校园场景达不到。
- **海报二维码指向当前部署域名**：Web 用 `location.origin`，H5 用当前 `origin`，小程序里回落到 `VITE_SHARE_BASE`（未配置则不画码）。真要投放到微信生态仍需小程序码，那需要后端签名与 `wxacode` 接口。
