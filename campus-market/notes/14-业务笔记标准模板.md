# 14 - 业务笔记标准模板

> 本文是所有业务相关笔记（`NN-<模块>业务说明.md`）的**强制格式规范**。
> 新写业务笔记、改造既有笔记，一律照此结构；要改格式先改本文。
> 技术笔记（实现原理、API 语法、排查方法）不适用本文，仍按原风格写。

---

## 一、格式总纲

一篇业务笔记固定五段，顺序不可调换：

| 段 | 标题 | 内容 |
|---|---|---|
| 一 | 模块定位 | 模块做什么、边界在哪、与谁共用动作 |
| 二 | 业务清单 | 一张索引表：编号 / 业务 / 数据对象 / 触发方 / 入口 / 权限点 |
| 三 | 业务条目 | **正文**。一条业务一个 `###`，条目内固定三块 |
| 四 | 通用业务规则 | 横切规则：状态机、排序、权限矩阵、口径 |
| 五 | 验收口径与已知缺口 | 业务侧验收清单、遗留问题 |

附录（代码落点、错误码表、决策记录）接在五段之后，格式沿用原有约定。

「业务条目」小节内固定三块，顺序固定：

1. **接口**——这条业务涉及的全部接口表（规则 3）；
2. **前置**——前置条件，无则写「无」；
3. **规则**——「控制程序式」结构化表达（规则 2）；
4. **状态与数据变化**——有状态迁移时列，无则可省。

---

## 二、三条硬规则

### 规则 1 · 状态码一律写成「中文(原值)」

正文、表格、流程图中出现的状态码，一律中文名在前、括号内附原值。**禁止裸数字，禁止裸英文枚举。**

| 禁止 | 必须 |
|---|---|
| `item.status=2` | `待审核(2)` |
| 从 `PENDING` 到 `ON_SALE` | 从 `待审核(2)` 到 `在售(3)` |
| `appeal.status=1` 待复审 | `待复审(1)` |

原值是库里的数字码或代码里的枚举名，两者都要能一眼对照回代码。状态机图同样遵守：

```
待付款(1) ──超时 30min──> 已取消(5)
     │
     └─模拟支付─> 待面交(2) ──扫码核销─> 已验货(3) ──确认收货─> 已完成(4)
```

错误码不在此列，保留数字 + 中文含义（如 `参数错误(1000)`），因为它本身就是带文案的码。

### 规则 2 · 规则用「控制程序式」表达

规则部分不写大段散文，按程序的三种基本结构组织——**顺序步骤、条件分支、终止结果**。

- 顺序步骤用有序列表，一步一个动作，动作用「主语 + 谓语 + 宾语」写实；
- 条件分支写「条件 → 结果」，左侧是能被机器判断的谓词，右侧是业务结果或错误码；
- 每个分支必须落到一个可执行结果：状态变化、错误码、或明确的「不动」；
- 嵌套用缩进表示，两层为限；
- 语义模糊的词（「挂一下」「顺手处理」）不入正文，接口位置一律写「标注在」。

### 规则 3 · 接口信息先于规则

每个业务条目的第一块是接口表，列全这条业务涉及的接口：

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/dict/grades` | `content.edit` | 查成色列表（含停用项） |

- 路径、方法、权限点与 `Controller` 实际注解一致，写错等于教错后来人；
- 系统内部触发（定时任务、消息消费）没有对外开放接口时，写「无对外接口」，并说明触发点；
- 同一条业务读接口与写接口都要列，读接口是规则的上下文。

## 三、条目模板（照抄后填内容）

```markdown
### D# · 业务名

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
|     |      |         |      |

**前置**

- 条件 1
- 条件 2（无则写「无」）

**规则**

1. 步骤一
2. 步骤二
   1. 若满足条件 A → 结果 A（含错误码）
   2. 若不满足 → 结果 B
3. 步骤三

**状态与数据变化**

| 对象 | 变化 |
|---|---|
|      |      |
```

## 四、填写样例（取自 `notes/07` D2）

### D2 · 成色等级维护（A–D 四档）

**接口**

| 方法 | 路径 | 权限点 | 作用 |
|---|---|---|---|
| GET | `/admin/dict/grades` | `content.edit` | 查成色列表（A–D，含停用项） |
| PUT | `/admin/dict/grade/{code}` | `content.edit` | 新增 / 编辑成色（按 code upsert） |
| POST | `/admin/dict/grade/{code}/status` | `content.edit` | 启停成色 |

**前置**：无。成色按 `code` upsert，空库直接调也能补出四条。

**规则**

1. 查看：四档 A / B / C / D，显示文案与色块。
2. 保存成色：
   1. `code` 不在 A/B/C/D → 拒绝（成色是固定四档，没有「新增一档」）
   2. `code` 缺失 → 参数错误(1000)
   3. 色值格式不是 `#RRGGBB` → 参数错误(1000)；表单「没填」必须发 `null` 而不是空串（正则只跳过 null）
   4. 色值留空 → 取默认 `#8E8E93`
   5. 通过 → 按 `code` upsert：有则更新，无则插入
3. 启停成色：转 停用(0) 后不再随字典下发，发布页不可选；转 启用(1) 后恢复下发。

**状态与数据变化**

| 对象 | 变化 |
|---|---|
| `dict_grade` | 按 `code` upsert；停用时 `status = 停用(0)` |

## 五、附录与维护

- 附录 A（代码落点）、附录 B（错误码表）、附录 C（决策记录）沿用原有内容；错误码表若涉及状态含义，同样遵守规则 1。
- 改造既有笔记时，业务规则一条都不许丢——只改表达，不改口径；确需删的内容先在决策记录里留一句。
- 样例引用了 `notes/07` 的内容，改 `notes/07` 的 D2 时同步回本文。
- **已按本文改造的笔记**：`07-字典模块业务说明.md`、`08-商品模块业务说明.md`、`09-审核队列业务说明.md`、`13-订单与交易闭环业务说明.md`（2026-10-11）。
  这四篇即格式的事实样例；新写业务笔记（message、stats 等）直接照本文结构写，不必再改造一次。
