# 注册与找回密码业务说明

## 一、三条链路为什么长成现在这样

学生端原来只有「手机号 + 短信验证码」一种入口，`app_user` 表里既没有邮箱也没有密码。这带来一个直接后果：**没注册过的人无处注册，忘了的人无处找回**——短信码进不来，账号就彻底锁死。这次补的三条链路（注册、找回密码、密码登录）都是围着这个缺口长的。

分工是这么定的：**注册只验邮箱验证码，登录两种方式并存，找回两种渠道都通**。

注册只验邮箱，是因为短信在演示期是假码，验它没有任何安全增益；而学生基本都有 QQ 邮箱，收一封信没有门槛。手机号只做格式与唯一性校验，它在这里的身份是「联系方式 + 将来的登录名」，不是凭证。

登录保留两种方式，是因为老账号从来没设过密码。如果只给密码登录，这批人一个都进不来；如果只给验证码登录，那新注册用户设的密码就成了摆设。两条路由 `type` 区分（1 验证码 / 2 密码），账号一律「手机号或 QQ 邮箱」，**渠道由账号形态决定，不由前端选择**——前端多一种判断就多一套口径。

找回密码支持两种渠道，因为用户记得的往往是手机号，注册时用的却可能是随手注册的小号邮箱。只留一条路，就会有人卡在「邮箱还在但密码忘了」的中间。

## 二、验证码的四条约束与它们的存储结构

四个渠道 × 三个场景，共用同一套约束：**6 位、10 分钟有效、一次性、同账号 60 秒一条、连续错 5 次作废**。

一次性与 5 次作废都落在同一个实现点上：校验通过即删 key，校验失败则给失败计数加一，计数到 5 直接删掉验证码。这样做的理由是**验证码只有一份，留着的唯一价值是让人继续试**；试错次数一满，留着它反而变成一个可以被爆破的 6 位数字。

渠道与场景在 Redis key 上分离，不能合并。邮箱码带场景（注册码不能拿去改密码，改密码的码也不能拿去登录），短信码同理；两边的节流则按账号而非场景算——同一个邮箱在 60 秒内既发注册码又发找回码，本来就是异常行为。

| key | 形态 | TTL |
|---|---|---|
| 邮箱验证码 | `cm:user:mail:code:{SCENE}:{email}` | 10 分钟 |
| 邮箱节流 | `cm:user:mail:throttle:{email}` | 60 秒（`setIfAbsent` 抢占） |
| 短信验证码 | `cm:user:sms:code:{SCENE}:{phone}` | 10 分钟 |
| 短信节流 | `cm:user:sms:throttle:{phone}` | 60 秒 |
| 密码失败计数 | `cm:user:pwd:fail:{userId}` | 10 分钟 |

节流用 `setIfAbsent` 而不是「先查再写」：并发下两个请求同时通过检查各发一条，是典型的检查与执行分离漏洞。**抢到才允许发，抢不到直接返回 4010 / 4016。**

## 三、注册：校验顺序决定了用户等多久

注册的校验顺序是 **格式 → 唯一性 → 验证码 → 落库**，唯一性排在验码之前。

这不是随意排的。验证码只有一次机会，如果先验码再判重，用户填了一个已注册的手机号，会先被要求等一条短信、拿到码、输进去，然后才被告知「这个号已经注册了」——一次不必要的等待。把唯一性提前，填错的当场就能改。

代价是**注册场景可以枚举账号**：填一个邮箱就知道它有没有注册过。这和登录时报「未注册」是同一套取舍，学生端不做防枚举——它的安全收益远小于「让人知道自己该登录还是注册」的收益。

昵称这里有个容易被忽略的细节：**注册的昵称上限是 16 字，资料编辑的上限是 64 字，两个错误码（4043 / 4020）**。同一个字段两种上限，如果共用一个错误码，文案只能写一种，用户看到的提示必然和实际规则对不上。注册是唯一一次定名，短一点更像昵称；编辑时放宽是因为那时候已经有人在用这个名字了，卡太死会逼人改名。

注册成功直接下发令牌，**注册即登录**。刚验完邮箱再让人输一次验证码，纯属形式主义。

## 四、密码登录：三种失败要分开说

密码登录的失败分成三类，各有各的出口：

密码不对是 4037，账号存在但没设过密码是 4038，连续错 5 次锁 10 分钟是 4039。

**4038 必须单独存在。** 老账号的 `password_hash` 是空的，如果和其他失败混着报「密码不正确」，用户会一直以为是自己记错了，反复尝试直到被锁——而真正该做的是改用验证码登录，或者走找回密码设一个。文案里写了这两个出口。

锁定按 `userId` 计数而不是按账号字符串：同一账号换大小写、换渠道（手机号 / 邮箱都指向同一个人）都应该落在同一个计数器上。次数用完 10 分钟窗口自然过期，不做永久封禁——这是防爆破，不是惩罚。

## 五、找回密码：两处顺序是刻意的

第一处是**「新密码不能与旧密码相同」必须在校验验证码之前**。验证码一次性，如果先验码再判重，用户输了个和原来一样的密码，码就被消耗掉了，还得再等 60 秒重新发。判重提前，错误可以当场改，码还在。

判重本身要用 `passwordEncoder.matches` 比对新旧哈希，不能比字符串——`password_hash` 是 BCrypt，每次加密结果都不同。

第二处是**改密之后强制踢掉该账号所有会话**（`StpUserUtil.stpLogic.kickout`）。改密码的前提是「密码可能已经泄露」，而泄露意味着旧会话可能已经被人拿着用。改完还让旧会话活着，等于只换了门锁没换钥匙。

这也是前端在找回成功后不能「改完继续用」的原因：令牌已经失效了，页面只能回登录页重登，账号带在 query 里预填省一次输入。

## 六、前端三页共用基元的两个坑

Web 端三页（登录 / 注册 / 找回）的表单基元放在全局 `cm-auth-*`（`styles/index.scss §4`），小程序端标签改在上方、其余同源。共用而不是各写一份，是因为三页的输入框、发码按钮、主按钮必须长得一模一样，复制三份迟早各自漂移。

第一个坑是**字段名不能只靠 placeholder**。注册有六格、找回有两格密码，一旦填了值就分不清哪格是「密码」哪格是「确认密码」。所以 Web 端加了左内联 60px 字段名，小程序端用上方小字——375pt 宽度下左内联会把输入框挤到 260pt 以内，邮箱地址直接显示不全。这不是两套设计，是同一规则在两个宽度下的解法。

第二个坑是**账号参数的双重编码**。小程序找到回密码页跳到登录页时要带 `?account=`，如果发送端 `encodeURIComponent` 一次、`uni.reLaunch` 内部再编一次，`@` 会变成 `%2540`，页面虽然靠再解一次能显示对，URL 却是脏的。正确做法是发送端不编码（`@` 与 `.` 在 query 里合法），接收端也不二次解码——`onLoad` 拿到的 query 已经是解码后的值。这和之前登录 redirect 那个 `%252F` 是同一个坑，凡是「自己编一次 + 框架再编一次」的地方都会踩。

## 七、上线前要关的两个开关

短信与邮件在演示期都不真发：验证码照常生成、存 Redis、打日志，并**随发码响应回显**（`devCode`）。前端把回显值当成功提示弹出来，于是整个流程不用接任何第三方就能跑通验收。

上线前要做的事只有两件：关掉 `campus.user.sms.echo` 与邮件侧的 echo 开关，把短信发送一处换成真实服务商。其余逻辑（节流、TTL、一次性、作废、踢会话）都是生产形态，不需要改。
