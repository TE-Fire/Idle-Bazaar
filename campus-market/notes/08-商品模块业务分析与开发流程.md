## 一、业务分析

### 1.1 A-B4 在管理端的位置：与 A-B2 的分界

这是本期最容易做错的地方——商品页和审核队列页**都能下架同一个商品**，必须先说清谁负责什么。

| 动作 | 归属业务域 | 权限点 | 承载页面 | 本期 |
|---|---|---|---|---|
| 列表筛选 / 分页 | A-B4 | `item.view` | `/items` | ✅ |
| 查看详情（只读） | A-B4 | `item.view` | `/items` Drawer | ✅ |
| 强制下架 | A-B4 与 F-A2 **共用** | `item.offline`（商品页）/ `review.forceoff`（审核页） | `/items`、`/review` | ✅ |
| 删除 | A-B4 | `item.delete` | `/items` | ✅ |
| 审核通过 / 驳回 | A-B2 | `review.judge` | `/review` | ❌ 下期 |
| 举报处置 / 申诉复审 | A-B3 | `review.judge` / `review.appeal` | `/review` | ❌ |

**关键**：权限矩阵（`business/03` F-A1）里**审核员只有 `item.view`**——能在商品页看，不能处置。
所以商品页的「下架」按钮对审核员不渲染，处置必须去 `/review`。这不是功能缺失，是刻意设计的互斥：
`review.judge`（判商品）与 `user.ban`（封人）分属不同角色。

### 1.2 商品状态机（库值 ↔ 枚举 ↔ 前端）

`business/03` §4.1 原文：

```
草稿 ─提交─> 待审核 ─通过─> 在售 ─买家付款─> 已售出（终态）
                    │        │
                    │        └─卖家下架─> 已下架 ─重新上架─> 在售
                    └─驳回─> 审核未过 ─改后重提─> 待审核
任意在售态 ─平台处置─> 已强制下架 ─申诉成功─> 在售
```

| 库值 | Java 枚举 | 前端 `AdminItem.status` | 含义 | 平台可下架 | 平台可删 |
|---|---|---|---|---|---|
| 1 | `DRAFT` | `DRAFT` | 草稿（未提交） | — | ✅ |
| 2 | `PENDING` | `PENDING` | 待审核 | ✅ | — |
| 3 | `ON_SALE` | `ON_SALE` | 在售 | ✅ | — |
| 4 | `OFFLINE` | `OFFLINE` | 已下架（**卖家自己**下的） | — | ✅ |
| 5 | `SOLD` | `SOLD` | 已售出 | — | ❌ 有订单引用 |
| 6 | `REJECTED` | `REJECTED` | 审核未过 | — | ✅ |
| 7 | `FORCED_OFFLINE` | `FORCED_OFFLINE` | 已强制下架（**平台**处置） | — | ✅ |

> `OFFLINE`(4) 与 `FORCED_OFFLINE`(7) 必须分开：前者卖家可自行重新上架，后者要走申诉。
> 平台处置落到 7 而不是 4，就是这个区别——**处置是终态，不是"暂时藏起来"**。

两条补充判据：
- **无「已预定」**（2026-09-26 决策）：拍下只生成待付款订单，商品不锁定、先付款先得。列表不显示预定态。
- **删除只开放给非在售态**：在售 / 待审核的先下架再删，避免误删正在交易的货。

### 1.3 从表结构读出的业务规则

**`item`**

| 字段 | 规则 | 对本期的直接影响 |
|---|---|---|
| `main_image` | 主图，列表页免查图表 | 列表 VO 直接用它，**不联 `item_image`** |
| `status` | 1–7，见上表 | 下架 / 删除的前置校验 |
| `grade` | char(1) A–D | 直接当字符串返回，与前端 `condition` 对齐 |
| `version` | 乐观锁（付款占位并发用） | **本期不带**——管理端处置是单人操作，无并发场景；带了要前端回传，徒增复杂度 |
| `view_count` / `fav_count` | 浏览 / 收藏 | 列表「浏览 / 想要」两列直接读 |
| `published_at` | 审核通过（上架）时间 | = 前端 `auditAt`，SLA 首审响应要用；草稿 / 待审核为 NULL |
| `deleted` | 软删（bigint 时间戳，db/01 B 类） | 删除走**软删**，与全库一致 |
| `FULLTEXT ft_search` | ngram 关键词索引 | 见 §二 问题 5 |

**`item_image`**：≤9 张，`sort=0` 为主图 → **详情接口**返回 `images`（按 sort 升序），列表不返回。

**`item_audit`**

| 字段 | 口径 | 本期怎么用 |
|---|---|---|
| `status` | 1待审核 / 2已通过 / 3已驳回 / 4已强制下架 | 下架时**新增一条 status=4** |
| `image_risk` | 0–100 风险分 | 列表 `riskScore` 取最新一条 |
| `report_count` | **进队时的快照**，不是实时值 | 权重用它；列表的「举报次数」**另算**（见下） |
| `reject_reason` / `remark` | 驳回原因 / 处置备注 | 申诉复盘依据 |
| `first_handle_at` / `handler_id` / `handle_cost_ms` | SLA 计时 | 本期列表不用，留给 A-B2 / A-B8 |
| `idx_queue(status, priority_score, enter_queue_at)` | 队列排序 | 本期不用 |

**`report`**：`target_type=1` 表示举报商品 → 列表的 `reportCount` 取**实时** count
（`target_type=1 AND target_id=? AND deleted=0`）。

> ⚠️ 两个「举报数」口径不同，别混：`item_audit.report_count` 是**进队快照**（权重公式的输入，
> 随时间不变）；列表显示的 `reportCount` 是**当前实时值**（运营要看到"又被人举报了"）。
> 前者给审核权重用，后者给人看，两条链路各取各的。

**`trade_order`**：`status=4` 已完成、`amount` 成交金额 → `categoryAvgPrice` 的数据源（见问题 3）。

## 二、开工前必须先拍板的 8 个问题

> **2026-10-06 已按推荐项全部拍板**，并在本次落地。实施结果与偏差见 §九。

> 每个都给了推荐项，拍板后我把 ⬜ 改成 ✅ 再动代码。

### 问题 1：商品页的「下架」与审核队列的「强制下架」是不是同一个动作？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 同一个 Service 方法 `forceOffline(itemId, reason, note)`，商品页与审核页两个入口都调它；**权限点不同**（入口各自 `@SaCheckPermission`） |
| B | 两套方法各自实现 |

**推荐 A**：处置结果必须完全一致（status→7 + 写 `item_audit` + 记处置人），两套实现必然漂移，
到时候「为什么从商品页下架的记录和从审核页下的不一样」没法解释。权限点在 Controller 层区分即可。

### 问题 2：强制下架的留痕落在哪？（与 `@OpLog` 直接相关）

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 本期写 `item_audit`（新增一条 `status=4`，带 `handler_id` / `remark`）；`@OpLog` 等审核模块做完统一补 |
| B | 本期就把 `@OpLog` 做出来，下架 / 删除直接挂注解 |
| C | 什么都不写，等 `@OpLog` |

**推荐 A**，理由两条：
1. `business/03` F-A11 判据原文「**先有业务动作，再挂注解**」——现在业务动作只有下架 / 删除两个，
   提前造 `type` 枚举，等审核模块一进来就得返工。
2. 但**业务留痕不能等**：强制下架是可申诉的处置动作，申诉复审要能拉出「谁、何时、依据什么」，
   这条链就是 `item_audit`（F-A11：「审核留痕、举报处置、申诉裁决复用同一张表，按 `biz_id` 拉出完整时间线」）。
   `@OpLog` 记的是「谁点了哪个按钮」，是**审计层**；`item_audit` 记的是**业务层**，两者不是替代关系。

### 问题 3：`categoryAvgPrice`（同类目成交均价）怎么算？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 查 `trade_order`（`status=4` 已完成）× `item.category_id` 求 `AVG(amount)`；该分类无成交 → 返回 0 |
| B | 查 `item` 表在售商品均价（口径变成"在售价"，不是"成交价"） |
| C | 新建分类均价快照表，定时任务刷 |

**推荐 A**：`business/03` F-A2 权重公式原文就是「偏离**同类目均价** 3 倍」，成交价才是均价的正确口径。
降级回 0 是安全的——前端 `isPriceAbnormal` 里 `if (avg <= 0) return false`，不会误标红。
选项 C 是过度设计：分类只有几十个，实时查一次够用。

> 实现上不用每条商品查一次：一次查全部分类的均价放进 Map，内存回填（见 W3）。

### 问题 4：真分页还是一次返回全量？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 真分页，MyBatis-Plus `Page`，新增 `com.campus.common.result.PageResult<T>`（`list` / `total` / `pageNum` / `pageSize`） |
| B | 一次返回全量，前端本地分页（现状） |

**推荐 A**：商品是最大的表，毕设里「列表一次拉全表」会被问。分页插件已装好，成本只是新增一个 `PageResult`。
代价：`PageResult` 要放进 `campus-common`（订单 / 用户 / 日志列表都要用），属于公共层改动——**需要你点头**。

### 问题 5：关键词搜索用 `LIKE` 还是 `FULLTEXT`？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | `item.title LIKE '%kw%'` + `app_user.nickname LIKE '%kw%'` |
| B | `MATCH(title, description) AGAINST(? IN BOOLEAN MODE)` |

**推荐 A**：MySQL 8 的 ngram parser 默认 `ngram_token_size=2`，中文单字（如"书""笔"）**匹配不到**，
且改这个参数要写进配置并**重启 mysqld** 才生效——容器重建后还得记得带上。60 条数据 `LIKE` 完全够。
`ft_search` 索引**建了先留着**，论文里写「为数据量增长预留的检索方案」即可，不要为了用而用。

### 问题 6：批量操作本期做不做？

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 不做 |
| B | 做批量下架（多选 → 一次下架） |

**推荐 A**：`business/03` §二在 A-B4 的业务动作里列了"批量操作"，但它是业务域描述不是验收项。
批量下架的责任认定在毕设里说不清——一次下架 20 件，每一件的依据是什么？申诉时怎么复盘？
且当前前端没有多选列。本期砍掉，如果后面有需要再加（那时 `forceOffline` 已经是单条方法，批量只是包一层循环）。

### 问题 7：删除开放给哪些状态？软删还是硬删？

| 项 | 推荐 |
|---|---|
| 可删状态 | `DRAFT`(1) / `OFFLINE`(4) / `REJECTED`(6) / `FORCED_OFFLINE`(7) |
| 不可删 | `PENDING`(2) / `ON_SALE`(3)（先下架）/ `SOLD`(5)（**有订单引用，删了订单查不到商品**） |
| 删除方式 | **软删**（`deleted` 写时间戳，与全库 db/01 B 类一致）；`item_image` 一并软删，不留孤儿图 |

> 前端现在的 `canDelete` 是 `OFFLINE | REJECTED | FORCED_OFFLINE`，**比推荐少一个 `DRAFT`**。
> 草稿从未对外，留着只会占列表，建议放开——这是个一行改动，要不要加请你定。

### 问题 8：🚨 分类「按一级筛选」换了雪花 ID 后怎么做？

现状前端：`!i.categoryId.startsWith(filters.categoryId)`（依赖 mock 的 `ca101` ⊂ `ca1`）。
真 ID 是雪花，**这个判断恒不成立**。

| 选项 | 做法 |
|---|---|
| **A（推荐）** | 后端 `ItemListReq.categoryId` 收到的是**一级分类 id**，SQL 里 `category_id IN (SELECT id FROM dict_category WHERE parent_id = ?)` |
| B | 前端传二级 id 集合，后端 `IN (...)` |
| C | 只允许按二级筛选 |

**推荐 A**：前端下拉本来就是一级分类（`ROOT_CATEGORIES`），用户体验不变，改动全在后端一条子查询。
选项 B 要前端先拉全树再拼 id 列表，把后端该干的活推给前端。

### W3 加工：编码实现

`core/service/ItemAdminService.java`（具体类，不拆 interface + impl），四个方法：
`list(req)` / `detail(id)` / `forceOffline(id, req)` / `delete(id)`。

**四条实现要点**

1. **列表用「分页主表 + 批量回填」，不要写一条大联表 SQL**
   主表分页查 `item` → 拿到这一页（≤20 条）的 `sellerId` 集合与 `categoryId` 集合 →
   分别批量查 `app_user`（昵称 / 信用分）、`report` 计数、分类均价 Map → **Java 里回填**。
   理由：LEFT JOIN + GROUP BY 会跟 MP 分页的 count 查询打架（总数被放大）；两次查询在 20 条规模下
   没有性能问题，SQL 还更简单可读。**这个模式审核队列 / 订单管理 / 用户管理都会复用，先在商品模块定下来。**

2. **字典名称不查库，走 `DictService`**
   `categoryName` / `campusName` / `meetPointName` / 成色文案都从 `/api/dict/all` 那份缓存取（60s TTL）。
   字典是全端一致性的源头（`business/03` F-A7 判据），不要在这里另写一套查询。

3. **强制下架（问题 1 选 A）**

## 七、两个架构问题的答复

### 7.1 `@OpLog` 是「采集端」，不是日志业务模块

**结论**：`@OpLog` = 写日志的**采集端**（注解 + AOP 切面 + 异步落库），
日志业务模块 = **采集端 + 消费端**（`sys_operation_log` 表 + A9 页面 `/settings/logs` 的查询接口 + `log.view` 权限）。

拆开看：

| | 是什么 | 现状 |
|---|---|---|
| 采集端 | `@OpLog` 注解 + AOP 切面 + `opLogExecutor` 异步落库 | ❌ 没做（`backend/README.md` 待办清单里挂着） |
| 存储 | `sys_operation_log` 表 | ✅ `schema.sql` 已建好（16 个字段，含 `before_value`/`after_value`/`result`/`trace_id`） |
| 消费端 | A9 操作日志页 `/settings/logs` + 查询接口 | ❌ 没做（A-B9 P2） |

`DictAdminController` 类注释里那句「写接口的 `@OpLog` 待该注解落地后统一补」，补的就是**采集端**。

**为什么现在不做是对的**——`business/03` F-A11 判据原文：

> **先有业务动作，再挂注解**：`@OpLog` 是贴在已有方法上的，`type` 枚举应由实际业务动作归纳出来。
> 业务方法没定型前先造枚举，等业务一变就得返工。

现在只有字典（5 类写操作）和即将有的商品（2 类），`type` 枚举归纳不出来——
F-A11 列的五类动作（审核 / 举报申诉 / 用户处置 / 订单介入 / 系统配置）里，**用户、订单、审核三条线都还没开工**。

**建议时机**：**A-B2 审核队列做完之后**一次性做（采集端 + A9 页面一起）。那时五类业务动作齐了，
`type` 枚举一次定准。商品模块本期只有 2 个写接口（下架 / 删除），后补挂两个注解的成本可以忽略。

**风险与对冲**：每加一个写接口就多一处待补。对冲办法是 CR 清单第 11b 已经写了这条——
靠清单盯，不靠记性。另外本期把**业务层留痕**（`item_audit`）做掉（问题 2 选 A），
这样即使 `@OpLog` 晚到，可申诉的处置动作也不会断链。

> 两类日志不要混：访问日志（`AccessLogFilter`，无差别记所有请求，排查用）走控制台；
> 操作日志（`@OpLog`，只记有业务语义的动作，追责用）落库。「少任何一个，另一个都补不上」（F-A11 判据）。

### 7.2 `dto/req`、`dto/resp` 要不要按业务再分子目录

**结论：本期不分。等商品模块做完（届时不分包约 30 个类）再一次性分。**

现状盘点：

| 包 | 现有 | 商品模块新增 | 之后 |
|---|---|---|---|
| `dto/req` | 10（Admin×4 + Dict×6） | +2（`ItemListReq`、`ItemOfflineReq`） | 12 |
| `dto/resp` | 9（Admin×3 + Dict×6） | +3（`ItemListVO`、`ItemDetailVO`、`ItemImageVO`） | 12 |

全部模块做完（商品 / 订单 / 用户 / 审核 / 报表 / 日志）估算 50–70 个类——**到那时确实该分**。

| 选项 | 做法 | 成本 | 收益 |
|---|---|---|---|
| **A（推荐）现在不分，定个触发规则** | 保持平铺，靠命名前缀（`ItemXxx` / `OrderXxx` / `UserXxx`）；在 `tech/03` 写一条：**单包类数 > 25 或同前缀 > 5 个时，按业务域分包** | 0 | 到点再分，一次分准 |
| B 现在就分 | `dto/req/item/`、`dto/req/order/`… | 全量 import 路径改动（现有 19 个类 + 所有引用方），diff 全是路径噪声 | 早分早清爽 |
| C 永远不分 | 靠命名前缀 | 0 | 60+ 个类平铺在一个包里，找起来靠搜索 |

**推荐 A 的三条理由**

1. **现在分是纯 churn**：字典的 13 个类要挪位置、所有 import 要改，但业务上什么都没变。
2. **分包的正确边界要等业务域齐了才看得准**。举个眼前就会遇到的例子：
   `ItemListVO` 既要给商品管理列表用，又要给审核队列用——放 `dto/resp/item/` 还是 `dto/resp/review/`？
   现在拍这个板，等审核模块一进来大概率要再挪一次。
3. **命名前缀已经解决了 80% 的查找问题**：IDEA 里搜 `Item` 前缀和打开 `item` 包一样快，
   而 import 路径**完全不变**。真到了 60 个类平铺影响阅读时，分包是一次 IDE 重构的事。

**折中（如果你现在就想做点什么）**：把触发规则写进 `tech/03` 的编码规范，到点执行——
这条我可以现在就加，不动任何代码。
